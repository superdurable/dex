section: Changed
---
- Behavior change: **limits.maxConcurrentStepsPerFlow** is now enforced, with the default of 1000. It caps the active Step executions (WaitFor, waiting, or Execute) of one Flow run; the Flow timeout handler does not count. A Flow start or RPC that would raise the count above it fails with RESOURCE_EXHAUSTED, and a Step completion that would do so fails the Step attempt without retry, with the error type **ValueTooLarge**. Both messages name the key. A command that does not raise the count always runs. Flow runs that started earlier keep the limit they recorded: the configured value, or 10000 for a child Flow. Child Flows now record the configured limit. [Reference](/reference/server/configuration#step-and-channel-limits)
- Behavior change: **limits.maxChannelMessages** is now enforced, and its default drops from 10000 to 1000. It caps the pending messages of each Channel of a Flow run. A Client publish or RPC that would leave a Channel with more pending messages fails with RESOURCE_EXHAUSTED, and such a Step result fails the Step attempt without retry, with the error type **ValueTooLarge**. A request that publishes several messages fails as a whole. Messages that a canceled Step returns to its Channel never fail. Each Flow run records the limit at start, so runs that started before this release have no Channel message limit. [Reference](/reference/server/configuration#step-and-channel-limits)
- Upgrade the active process and the standby together, because the server applies commands differently. [Upgrades](/reference/server/upgrades)
