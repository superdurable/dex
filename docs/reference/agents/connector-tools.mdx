# Connector tools

An agent session can call [Connector](/concepts/connector) operations as
tools. [Connectors as tools](/agent-frameworks/connectors-as-tools#connectors-as-tools) explains the
rules: which operations an agent can use, which Step runs a call, approval,
outcomes, write order, and crashes. This page covers the packages and settings.

**ConnectorToolSource** offers the operations, the way **McpToolSource** offers
an MCP server's tools. The Python and TypeScript cores ship it. The built-in
agent loop and every Python and TypeScript framework adapter take it, through
**tool_sources** in Python and **toolSources** in TypeScript. The Go core has
function tools only.

## Install {#install}

Install the core with the Connector SDK, and each Connector package an agent
uses:

```bash
pip install 'dex-agents[connectors]' dex-connector-stripe
npm i @superdurable/dex-agents @superdurable/connectors-sdk @superdurable/connector-stripe
```

Some Python Connector packages are released on GitHub before PyPI. Install one
from its release tag. The release notes give the exact command:

```bash
pip install "dex-connector-<name> @ git+https://github.com/superdurable/dex-connectors-library@<tag>#subdirectory=connectors/<name>/python"
```

Pin the versions you tested. Connector tools need Connector packages whose
**dex-connector.json** carries agent metadata. To analyze a Flow that imports
them, use a Dex CLI that reads this metadata. The
[CLI change log](/reference/cli/changelog) names the release.

## Name the tools {#connector-tools-offered}

Name each operation an agent may use with **connector_tool** in Python or
**connectorTool** in TypeScript. The operation must be marked
**agent.exposed** in its **dex-connector.json**. Otherwise the agent definition
fails when it is built.

The tool name defaults to the Connector ID and the operation in snake case,
such as **stripe_create_refund**. The snake case matches the Connector library's
own Python names: an acronym stays one word, so **listStoryIDs** becomes
**list_story_ids**. The description and the argument schema come from the
manifest.

## Step options {#step-options}

A Connector tool's Step uses the operation's own Execute timeout and retry
policy, with at most three attempts. A `bounded_write` tool is the exception;
see [Bounded resends](#bounded-resends). A session's **tool_policies**
(**toolPolicies**) entry for a Connector tool changes only its approval and,
for a `bounded_write` tool, its send cap. The manifest decides the effect
class.

To override approval, pass **requires_approval** in Python or
**requiresApproval** in TypeScript to the tool. It takes a bool or a predicate
over the call's arguments.

Changed in 0.6.12: a `bounded_write` tool gets more than three attempts when
its send cap needs them, and a tool policy can set its send cap.

## Bounded resends {#bounded-resends}

Since 0.6.12.

A Connector Mutation can resend a write whose outcome is unknown, such as
after a timeout or a 5xx response, a bounded number of times. The manifest
declares it in two **agent** fields of **dex-connector.json**:

| Field | Values | Meaning |
| --- | --- | --- |
| **repeatOnUnknown** | `safe`, `limited`, or `unsafe` | What the Connector may do when a send's outcome is unknown |
| **maxSends** | An integer from 2 to 10, with `limited` only | The most sends of one call |

The core maps the tier to an effect class:

| Manifest | Effect class | Runs in |
| --- | --- | --- |
| **agent.retry: safe** | `idempotent_write` | `CallTool`, at most three attempts |
| **repeatOnUnknown: limited** with a valid **maxSends** | `bounded_write` | `CallTool`, with the attempts below |
| Anything else, including `unsafe` and a manifest without the fields | `non_idempotent_write` | `CallSingleAttemptTool`, once |

A `bounded_write` tool also needs the operation definition in the Connector
package to declare `limited` with the same cap. A Connector package built for
`@superdurable/connectors-sdk` 0.11.0 or `dex-connectors-sdk` 0.10.0 or later
does. An unknown **repeatOnUnknown** value, a **maxSends** outside 2 to 10, or a
definition that disagrees keeps the Mutation `non_idempotent_write`.

When a send's outcome is unknown, the Connector returns a retry. The next
attempt's single-dispatch fence lets the Connector read the write back first.
If read-back finds it, the call records **succeeded** without another send.
Otherwise the Connector sends again, while the call's sends stay below the cap.
At the cap, a write that read-back cannot find selects **uncertain**, and the
call records `outcome_unknown`. A definite failure, such as a branch marked
**rejected**, is never resent.

A `bounded_write` call gets the operation's own maximum attempts. When those
are unlimited, it gets three. Either way it gets at least **maxSends**. The
operation's retry window still applies, so a short window can end the call
before the cap. When the attempts run out, the call records `outcome_unknown`.

A `bounded_write` call waits for approval as any Connector tool does: when the
manifest recommends it or the application asks for it.

### Set the send cap per tool {#max-sends}

Set **max_sends** (**maxSends** in TypeScript) on the tool's `ToolPolicy` to
replace the manifest's cap, from 1 to 10. `1` turns resending off. A value
outside that range fails when the session Flow is built in TypeScript, and when
the `ToolPolicy` is created in Python. A tool that is not `bounded_write`
ignores it. The policy's **effect** does not change a Connector tool's effect
class.

The call keeps the cap it was deferred with on every attempt, so a deploy that
changes the policy affects only later calls. A raised cap adds its difference
from the manifest's cap to the call's attempts, so the Connector can reach it.
A lower cap keeps the attempts, which pre-send retries such as rate limits can
use.

The send cap reaches the Connector through the Connector SDK. TypeScript needs
`@superdurable/connectors-sdk` 0.11.0 or later; an earlier release ignores the
cap. Python needs `dex-connectors-sdk` 0.10.0 or later; with an earlier
release, the Connector never resends.

### Upgrade every Worker first {#bounded-write-upgrade}

A Worker older than 0.6.12 cannot read a session that recorded a
`bounded_write` call. Neither can an older **dexcli agents-tui**. Upgrade every
Worker of a session Flow type, and the Dex CLI that opens its sessions, before
a Worker offers a `limited` Connector tool.

## Result size {#connector-tools-result-size}

A result reaches the model as compact JSON with sorted keys. A result larger
than 64 KiB of text is cut, and the model reads the note "[Dex] truncated, N
bytes" after it. The record's **truncated_output_bytes** holds the full size.
Change the bound on the source or on one tool.

## Connections {#connector-tools-connection}

A Connector tool uses a Connector connection, as a Connector Step does. The
application opens it by its connection name from the project configuration,
once at Worker startup:

- **Local development.** Set **DEX_CONNECTOR_CONFIG_FILE** to the
  **connections.json** file of your local Connector configuration, by default
  **$HOME/.dex/connectors/connections.json**. It must hold an authorized
  connection with the name the application opens. To create it, run **dexcli
  dev**, open **Connectors** in Dex Web, add a connection with that name, and
  authorize it. See
  [Add a connection](/reference/web/local-connector-setup#add-a-connection).
- **Deployed.** The **DEX_PROJECT_\*** settings select the project
  configuration that the hosting platform or operator writes.

Setting **DEX_CONNECTOR_CONFIG_FILE** or any **DEX_PROJECT_\*** setting
requests a project configuration. An incomplete or invalid one fails at
startup. The Worker reads the configuration at startup, so restart it after a
change.

Keep the same configuration on every Worker while Connector calls wait for
approval. Any Worker may run an approved call, and it needs the same tool and
connection.

A Connector tool stores only the logical connection name with the call, as a
Connector Step does. The credentials stay with the Worker.

## Outcomes {#outcomes}

The operation ends in one of its branches, and the branch decides the tool call's record. In the manifest, a Connector author marks the branches where nothing took effect as **rejected**, and the branches where the write may have taken effect as **unknown**. Dex uses the first row that matches. Every row above the rejected row, except the success row, records `outcome_unknown`, so doubt never becomes a safe failure:

| Branch | Record | The model sees |
| --- | --- | --- |
| **uncertain** | `outcome_unknown` | That the outcome is unknown |
| A Mutation's **defect** | `outcome_unknown` | That the outcome is unknown |
| A success branch, such as **sent** or **refunded** | **succeeded** | The result value |
| Any other Mutation branch, when its single-dispatch fence cannot prove that nothing was sent | `outcome_unknown` | That the outcome is unknown |
| A branch marked **rejected**, such as `providerRejected` | **failed** | The branch and the provider's message |
| A branch marked **unknown**, or a Mutation branch that is not listed | `outcome_unknown` | That the outcome is unknown |
| A Query branch that is not listed, including **defect** | **failed** | The branch and the message |

A Mutation's **defect** can happen after the provider was called, so the write may have taken effect. A Mutation with a single-dispatch fence records whether its request may have left. If it may have, marking the branch **rejected** does not turn the failure into a rejection. For a `bounded_write` call, the fence also counts the sends of earlier attempts. When an earlier send may have taken effect, a later branch marked **rejected** still records `outcome_unknown`.

Changed in 0.6.12: the core reads the send count that a fence with a send cap records. Earlier releases did not count a claim that carries a send count as a possible send.

Reconcile `outcome_unknown` as for any tool; see [Reconcile outcome_unknown](/agent-frameworks/tool-calls#reconcile-outcome-unknown).

## Crashes {#crashes}

A Worker crash during a Connector write never sends the write twice. How a write recovers depends on how the Connector can tell whether the provider got it:

- **Deduplicated by the provider.** The Connector sends the call's idempotency key, and the provider drops a repeated key.
- **Looked up first.** The provider has no idempotency key. Before a retry sends anything, the Connector looks for the earlier write at the provider. The Connector also records, during the attempt, whether the request has left the Worker.

| What happened | Retry-safe write, deduplicated by the provider | Retry-safe write, looked up first | Single-attempt write |
| --- | --- | --- | --- |
| The Worker died before the request was sent | Dex retries with the same key. The write happens once, and the call records **succeeded**. | Dex retries. The lookup finds no write, but nothing proves that the request was never sent, so the retry sends nothing. The call records `outcome_unknown`. | The call records `outcome_unknown`. Nothing was sent. |
| The Worker died after the provider accepted the write | Dex retries with the same key. The provider drops the repeat, and the call records **succeeded**. One write. | Dex retries. If the lookup finds the write, the call records **succeeded**. If not, it records `outcome_unknown`. One write either way. | The call records `outcome_unknown`. One write. |
| The provider asked to retry later, such as for a rate limit | Dex retries. The write happens once. | Dex retries. The write happens once. | The call records **failed**, with "not sent; the provider asked to retry later", if the Connector recorded that the request never left the Worker or that the provider refused it without acting. Otherwise it records `outcome_unknown`. |

A single-attempt write records **failed** only when the Connector's record proves that nothing was sent, because a request to retry later alone proves nothing. The model can then call it again without anyone checking the provider. The later writes of that response are still skipped.

A `bounded_write` call recovers like a write that is looked up first, except that the retry may send again. A crash after a send counts as a send whose outcome is unknown. The retry reads back first and sends again only while the call's sends stay below its cap. So a crash can make a duplicate, at most up to the cap. See [Bounded resends](#bounded-resends).

## The Slack tool in the examples {#slack-example}

The agent examples open the Slack connection **support-slack**. Without a
project configuration, or without that connection in it, they log one line and
run without the Slack tool.

The Slack app needs the bot scope **chat:write**, and its bot must be a member
of the channel. After a Worker stops during a post, the Connector reads the
thread back to learn whether the reply was sent. That needs the user scopes
**channels:history** and **groups:history**. Without them, such a post records
**outcome_unknown**.
