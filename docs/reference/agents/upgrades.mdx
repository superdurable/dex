# Upgrade agent code while sessions wait {#upgrades}

A waiting session runs the code of the Worker that takes its next Step. Nothing
replays the agent loop, so a deploy takes effect at the next model call or tool
call, even in the middle of a turn. During a rolling deploy, two Steps of one
session can run on different versions.

- Keep each agent's Flow type stable. Running sessions resume by it.
- Keep a tool available while a running turn or a pending approval still
  refers to it.
- A recorded tool call keeps the effect and approval rule that applied when the
  model asked for it. Changed tool policies apply to later calls.
- A changed prompt or model takes effect at the next model call. A changed
  tool takes effect at its next call.
- Between the Steps of a turn, **FrameworkRunState**, the session Attribute
  that holds the framework's serialized run state, carries the turn from one
  Step to the next. The framework version on the new Worker must restore it. Stay within the framework range that the adapter pins, and upgrade the
  adapter and the framework together.
- Before a rolling deploy, read the [change log](/reference/agents/changelog)
  entries of every release after the one you run. They name the upgrade order
  that a release needs.
- **Some upgrades cannot run side by side.** When the change log says so, stop
  every Worker of the Flow type on the older release before any Worker on the
  newer release starts. [Release notes](#release-notes) lists these releases.

### What a stop does to in-flight calls {#in-flight-calls}

A release that needs every older Worker stopped, or a server upgrade that
stops every server process, interrupts the calls that are running:

- A Worker that you stop gracefully lets running handlers finish for the drain
  timeout, 30 seconds by default, and then cancels them. A cancelled model call
  or `CallTool` runs again later. A single-attempt tool that was cancelled
  records `outcome_unknown`. See [Graceful stop](/reference/agents/workers#graceful-stop).
- A server stop fails every attempt that a Worker had received. A
  single-attempt tool among them records `outcome_unknown`. See
  [Agent tools and server upgrades](/concepts/failover-and-deploys).
- While no Worker runs, session RPCs such as `send_user_message` fail; see
  [RPCs during a deploy](/agent-frameworks/production#rpcs-during-a-deploy).

To keep these to a minimum, stop the Workers gracefully before the upgrade,
with a drain timeout above your usual tool call time, and check the sessions
that record `outcome_unknown` afterwards; see
[Reconcile outcome_unknown](/agent-frameworks/tool-calls#reconcile-outcome-unknown).

See [Versioning Flow code](/concepts/change-flow-code#versioning-flow-code)
for the general rules.

## Release notes {#release-notes}

These notes apply to specific releases. The rules above apply to every deploy.

### Readers before writers of failed {#failed-status}

Upgrade every reader of a session before the Workers that write the status
**failed**. A Worker or client from a release without that status cannot
decode it, so its **get_agent_snapshot** of a failed session raises an error.
Only failed sessions are affected.

### Messages in AgentMessageChunks {#message-chunks}

The release that stores messages in **AgentMessageChunks** cannot run side by
side with older Workers. Older sessions keep every message in
**AgentMessages**. Once a newer Worker stores a message there, it moves the
older messages into **AgentMessageChunks**, a few chunks per Step. If an older
Worker then runs a Step of that session, the turn fails, because it cannot read
the moved messages. Stop every older Worker of the Flow type before a newer
one starts.

### Session settings during a rollout {#session-settings-rollout}

Start sessions with session settings, and call **update_session_settings**, only
after every Worker of the Flow type runs a release that has session settings.
An older Worker drops the settings of a session that it starts. It neither
writes nor reads the copy of the settings that a turn keeps. A turn that an
older Worker starts runs without settings, so some of its model calls can use
the Worker's default model.
