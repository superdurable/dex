# Troubleshoot a Flow run

When a Flow does not advance or fails, check Worker availability first. Then
follow the read-only debugging workflow.

## Worker API availability

When a Worker cannot receive or complete a Step call, the Flow cannot advance.
You may see a Step stay active, its retry count grow, or a terminal failure
once the retry policy runs out.

Check these items in order:

1. Collect the Flow ID, Run ID, Flow type, Worker version, and Dex Server
   address. Put them in the incident record before changing anything.
2. Check the Worker logs for handler exceptions, registration failures, and
   startup configuration. Include the Flow ID or Run ID in log searches.
3. Check the network route between Dex Server and the Worker: service discovery,
   address, TLS, authentication, and any load-balancer health checks. For a
   [pull Worker](/reference/server/workers), check that its outbound streams to
   the server are connected.
4. Confirm that the deployed Worker registered the Flow, Step, and RPC names
   used by the open Flow. A deployment can be healthy while an old Step type is
   missing from that Worker version.
5. Inspect the affected Step in Dex Web. The retry attempt, Worker error,
   gRPC status, and stack trace distinguish an unavailable Worker from an
   application failure.

After you fix availability, let an active retry continue if its retry policy
still allows more attempts. For a Flow in a terminal status, first verify the
fix with a new run. Then, if that is the recovery you want, use
[Time Travel](/reference/server/runtime-client#time-travel) from a safe Step
boundary. Do not restart or time travel a Flow only to test connectivity.

## Flow failure and timeout

A Flow can fail because a Worker handler returns a failure, Worker retries are
exhausted, or the Flow reaches its configured timeout.

You set a Flow timeout when the Flow starts, and Dex keeps it as a durable
timer. Zero turns it off. For the timeout policy, choose **FAIL**, **CANCEL**,
or a Flow timeout handler. The start event shows the configured duration and
the resolved policy. The deadline is an absolute time.

Every positive timeout has one internal **sys:timeout_handler** timer. You can
see it in active-Step diagnostics. **SkipTimer** can fire it early by its timer
index. Before you recover a Flow that failed on its timeout, fix the cause.

## Read-only debugging workflow

Start with Dex Web. It shows what the Flow recorded in application terms,
before you turn to raw JSON.

### 1. Select the relevant event

Open the Flow by Flow ID and Run ID, choose **Timeline**, then select the
Step event that is waiting, completed, or failed. On a wide screen, Timeline
runs left to right, oldest first. Each event's icon shows its kind, and only
waiting, failed, and canceled events are colored. The selected event panel
below the Timeline shows the event's title and its event number.

The event number is the event ID. It stays the same on every page and after
pruning. **Timeline** shows one page of events and opens on the newest page.
The **Events** bar above the Timeline pages through events. A page holds
1,000 events by default; its **Page size** setting switches it to 100.
Use **Older page** and **Newer page** to move between pages, and **Oldest
page** to open the oldest retained page. Use **Latest page** to return to the
page that **Live** keeps extending.

The selected event panel lists **Related events**: the event's WaitFor, its
source execution, and the executions it started. An entry on the current page
offers **Show #N**, which selects that event. An entry on another page offers
**Go to #N**, with a hint that it is on an older or newer page. **Go to #N**
loads a page around the event and highlights it. **Back** returns to the previous page. Dex Server
keeps only a
[recent history window](/reference/server/configuration#history-window). A
pruned related event reads **Outside the retention window** and offers no
action. **Not on this page** means Dex Web knows the related event exists but
cannot locate it, so it offers no jump. The oldest retained page states which
event numbers were removed.

### 2. Read inputs, Attributes, conditions, and outputs

Keep **Details** selected and read **Input** first. It shows the Step input and
the Attributes the method read. For a WaitFor event, **Output** shows the
WaitFor condition and its results. For a completed Step, **Output** shows the
Step decision, the next Step input, and resulting Attribute changes. On a wide
screen, **Input**, **Output**, and
**Context** sit side by side. Each Step decision target reads as one row, such
as the next Step type, its input, and its options; **Decision details** expands
the rest. Attribute rows preview their values, and **Show all** opens a long
one.

### 3. Expand a failed Step's stack trace

For a retrying or failed Step, select the failed event from **Timeline** or the
failed node from **Execution graph**. Under **Failure**, compare the attempt, Worker
error type, error detail, and gRPC status. Expand **Stack trace** before asking
the owning team to investigate.

### 4. Save auditable JSON with dexcli

Use the same Flow ID and Run ID in the CLI. These commands are read-only and
print JSON. Attach their output to the incident, or keep it in secure
diagnostic storage.

~~~bash
dexcli flow inspect FLOW_ID --run-id RUN_ID

dexcli flow history FLOW_ID --run-id RUN_ID --all

dexcli flow inspect FLOW_ID --run-id RUN_ID --all-history --no-hydrate

dexcli flow history FLOW_ID --run-id RUN_ID --all --no-hydrate
~~~

**dexcli flow inspect** returns the current Flow summary and state when it is
available. **dexcli flow history** returns semantic events. Use **--all** to
retrieve every history page. Dex Server keeps only a
[recent history window](/reference/server/configuration#history-window), so
**--all** returns the retained events. Use **--no-hydrate** when payloads may be large or
sensitive: the output then keeps blob references and does not fetch their
contents.

### 5. Ask the Dex SDK skill for an investigation

The [Dex SDK skill](/build-with-ai/dex-developer-skill/dex-sdk)
can guide a repository-aware investigation. Give it the identifiers and
require a read-only first pass. Use the invocation syntax for the selected
Plugin or standalone installation, followed by this request:

~~~text
Diagnose Dex Flow FLOW_ID, Run ID RUN_ID. The Worker version is
WORKER_VERSION and Dex Server is SERVER_ADDRESS. First perform read-only checks:
inspect Dex Web, application logs, dexcli flow inspect, and dexcli flow history
with --all. Do not stop, time travel, restart, or otherwise modify a Flow unless
I explicitly authorize that action. Report the suspected failing Step, evidence,
and the safest recovery option.
~~~
