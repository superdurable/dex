# Order Support Agent

An order support agent with two tools, built once for each agent framework. Pick your framework, and every section below follows that choice.

**SDKs:** Python · TypeScript

Every framework uses the same order support agent. It has two tools on an in-memory order desk:

| Tool | Policy | What Dex does |
| --- | --- | --- |
| `look_up_order` | read | Runs without approval and retries on failure. |
| `cancel_order` | non-idempotent write | Waits in `AwaitToolApproval`, then runs at most once. |

`cancel_order` cancels an order only while it is still processing.

The Python agents are under [examples/python/agent-harnesses](https://github.com/superdurable/dex/tree/main/examples/python/agent-harnesses). The TypeScript agents are under [examples/typescript/src/products/agent-harnesses](https://github.com/superdurable/dex/tree/main/examples/typescript/src/products/agent-harnesses).

```python
def build_claude_agent_sdk_order_support_flow(
    order_desk: OrderDesk, model: str, slack_connection: slack.Connection | None
) -> AgentSessionFlow:
    """Builds the session Flow; ``model`` is a Claude model name, such as "claude-opus-5-5"."""

    # The tools are closures, so they call the OrderDesk passed in here.
    @tool(
        "look_up_order",
        "Look up one order by its order ID and return its items and status.",
        {"order_id": str},
    )
    async def look_up_order(arguments: dict[str, Any]) -> dict[str, Any]:
        order = order_desk.describe_order(arguments["order_id"])
        return {"content": [{"type": "text", "text": order}]}

    @tool(
        "cancel_order",
        "Cancel one order that has not shipped yet.",
        {"order_id": str, "reason": str},
    )
    async def cancel_order(arguments: dict[str, Any]) -> dict[str, Any]:
        result = order_desk.cancel_order(arguments["order_id"], arguments["reason"])
        return {"content": [{"type": "text", "text": result}]}

    # Every session gets the same options, so the factory does not read its context.
    def build_options(context: ClaudeAgentOptionsContext) -> ClaudeAgentOptions:
        return ClaudeAgentOptions(
            model=model,
            env=build_claude_cli_environment(os.environ),
            system_prompt=ORDER_SUPPORT_INSTRUCTIONS,
            # No Claude Code built-in tools: the agent uses only the order tools.
            tools=[],
            # Settings files could approve a tool before Dex asks for approval.
            setting_sources=[],
        )

    return claude_agent_session_flow(
        build_options,
        [look_up_order, cancel_order],
        flow_type=CLAUDE_AGENT_SDK_ORDER_SUPPORT_FLOW_TYPE,
        tool_sources=build_slack_tool_sources(slack_connection),
        tool_policies={
            "look_up_order": ToolPolicy(ToolEffect.READ),
            "cancel_order": ToolPolicy(ToolEffect.NON_IDEMPOTENT_WRITE),
        },
    )
```

```typescript
export function createClaudeAgentSdkOrderSupportFlow(
  orderDesk: OrderDesk,
  model: string,
  cliEnvironment: Readonly<Record<string, string>>,
  slack: Connection | undefined,
) {
  const lookUpOrder = tool(
    "look_up_order",
    "Look up one order by its order ID and return its items and status.",
    { order_id: z.string() },
    async ({ order_id }) => ({ content: [{ type: "text", text: await orderDesk.describeOrder(order_id) }] }),
  );
  const cancelOrder = tool(
    "cancel_order",
    "Cancel one order that has not shipped yet.",
    { order_id: z.string(), reason: z.string() },
    async ({ order_id, reason }) => ({ content: [{ type: "text", text: await orderDesk.cancelOrder(order_id, reason) }] }),
  );
  return createClaudeAgentSessionFlow(
    {
      options: {
        model,
        systemPrompt: orderSupportInstructions,
        // No Claude Code built-in tools: the agent uses only the order tools.
        tools: [],
        // Settings files could approve a tool before Dex asks for approval.
        settingSources: [],
        // Only the variables in cliEnvironment reach the CLI, so no other Claude credential can take over.
        env: { ...cliEnvironment },
      },
      customTools: [lookUpOrder, cancelOrder],
      toolPolicies: {
        look_up_order: { effect: "read" },
        cancel_order: { effect: "non_idempotent_write" },
      },
      toolSources: createSlackConnectorToolSources(slack),
    },
    claudeAgentSdkOrderSupportFlowType,
  );
}
```

```typescript
export function createPiOrderSupportFlow(
  orderDesk: OrderDesk,
  model: Model<Api>,
  slack: Connection | undefined,
  apiKey?: string,
): OrderSupportSessionFlow {
  const lookUpOrder: AgentTool<typeof lookUpOrderArguments> = {
    name: "look_up_order",
    label: "Look up order",
    description: "Look up one order by its order ID and return its items and status.",
    parameters: lookUpOrderArguments,
    execute: async (_toolCallId, { order_id }) => textResult(await orderDesk.describeOrder(order_id)),
  };
  const cancelOrder: AgentTool<typeof cancelOrderArguments> = {
    name: "cancel_order",
    label: "Cancel order",
    description: "Cancel one order that has not shipped yet.",
    parameters: cancelOrderArguments,
    // Not safe to repeat, so Dex asks for approval first and runs it at most once.
    replay: "never",
    execute: async (_toolCallId, { order_id, reason }) => textResult(await orderDesk.cancelOrder(order_id, reason)),
  };
  return createBuiltinAgentSessionFlow(
    {
      name: "order-support",
      instructions: orderSupportInstructions,
      model: createPiAiModelClient(model, { apiKey }),
      tools: [piAgentFunctionTool(lookUpOrder, { effect: "read" }), piAgentFunctionTool(cancelOrder)],
      toolSources: createSlackConnectorToolSources(slack),
    },
    piOrderSupportFlowType,
  );
}
```

## Worker {#register-the-worker}

One Worker serves the session Flows of every harness in the example. In Python, agent session Steps are async, so the Registry allows async handlers. Build the same session Flow in every process that starts sessions or calls their RPCs. The Registry, Worker, and Client setup is the same for every framework; each tab shows only how that framework's session Flow is built and registered.

<SdkTabs
  examples={{
    python: 'examples/python/agent-harnesses/agent_harness_examples/app.py',
  }}>
<SdkSnippet lang="python">

```python
        # Agent session Steps are async, so the Registry allows async handlers.
        self.registry = Registry(
            tuple(example.session_flow for example in self.examples), allow_async_handlers=True
        )
        config.blob_cache_dir.mkdir(parents=True, exist_ok=True)
        self.blob_cache = open_blob_cache(BlobCacheConfig(str(config.blob_cache_dir), 1 << 30))
        self.worker = AsyncWorker(
            self.registry,
            self.blob_cache,
            WorkerOptions(
                server_address=config.server_address,
                pull=PullWorkerOptions(max_concurrent_tasks=MAX_CONCURRENT_TASKS),
            ),
        )
        self.client = AsyncClient(
            self.registry, self.blob_cache, ClientOptions(server_address=config.server_address)
        )
```

## Session routes {#session-routes}

Every harness serves the same HTTP routes, so you can try them side by side. Each route is one call on the session Flow: start a session, send a message, or resolve an approval.

The calls inside the routes are the Dex Agents API, and they are the same in your app:

| What the route does | Dex Agents call in Python | Dex Agents call in TypeScript |
| --- | --- | --- |
| Start a session | `AgentSessionClient.start_session` | `startAgentSession` |
| Send a user message | `AgentSessionClient.send_user_message` | the `sendUserMessage` RPC, or `sendAgentUserMessage` |
| Read the session | `read_agent_event_stream_snapshot` or `AgentSessionClient.get_agent_snapshot` | the `getAgentSnapshot` RPC, or `readAgentSnapshot` |
| Approve or reject a tool call | `AgentSessionClient.resolve_interrupt` | the `resolveInterrupt` RPC |

Everything else belongs to the example: the URL paths, the JSON shapes, the session token, and the error codes. The Python and TypeScript examples shape them a little differently. Design your own routes around the calls above.

Starting a session returns a session token: an HMAC of the session ID under `DEX_AGENT_SESSION_KEY`. Every other route checks the token in the **X-Agent-Session-Token** header and answers 403 without it. Without `DEX_AGENT_SESSION_KEY`, the example picks a random key, so a restart ends every token. A real application uses its own sign-in instead.
