# Customer Refund

A customer asks for a refund. The Flow checks the order and the refund policy, waits for a manager when the amount is large, issues the refund, and tells the customer. This page has three Flows for this process: one short Flow to read first, and two larger Go Flows.

**SDK:** Python, TypeScript, Java, and Rust (refund with manager approval), Go (deterministic policy and agentic review)

## Refund with manager approval {#refund-with-manager-approval}

Northstar Studio asks for a refund of a 1,249.00 USD subscription renewal after a service interruption. `CustomerRefundFlow` runs eight Steps, grouped as Intake, Evidence, Control, Resolution, and Close.

<DocsFlowDefinitionGraph graph={readableFlow} />

The graph comes from the Python example. The TypeScript example has the same Steps, groups, Attributes, Channel, and transitions. Its RPCs are named `approveRefund` and `rejectRefund`. Its **Check policy** has one denial branch instead of two.

**Check policy** applies the refund policy. It denies a charge older than 30 days or one with no recorded outage. It sends an amount over 1,000 USD to **Request manager approval**, and refunds a smaller amount at once. **Request manager approval** waits for one message on a Channel, then refunds or denies by the manager's decision.

    final class CheckPolicy implements Step<RefundCase> {
        @Override
        public Class<RefundCase> getInputType() {
            return RefundCase.class;
        }

        @Override
        public StepDecision execute(final Context context, final RefundCase input) {
            final Order order = input.order();
            final boolean outsideWindow = order.daysSinceCharge() > REFUND_WINDOW_DAYS;
            final boolean noOutage = order.outageHours() == 0;
            if (outsideWindow || noOutage) {
                CASE_STATUS.set(context, "denied");
                final String note;
                if (outsideWindow && noOutage) {
                    note = "The charge is outside the 30-day window and no outage was recorded.";
                } else if (outsideWindow) {
                    note = "The charge is outside the 30-day window.";
                } else {
                    note = "No outage was recorded for this order.";
                }
                return StepDecision.goTo(WriteCustomerMessage.class, input.withOutcome("denied", note));
            }
            if (order.amountUsd() > MANAGER_APPROVAL_LIMIT_USD) {
                CASE_STATUS.set(context, AWAITING_MANAGER);
                return StepDecision.goTo(RequestManagerApproval.class, input);
            }
            return StepDecision.goTo(IssueRefund.class, input);
        }
    }

    /** Wait for a manager to approve or reject the refund. */
    final class RequestManagerApproval implements Step<RefundCase> {
        @Override
        public Class<RefundCase> getInputType() {
            return RefundCase.class;
        }

        @Override
        public Wait waitFor(final Context context, final RefundCase input) {
            return Wait.until(MANAGER_DECISIONS.forOne());
        }

        @Override
        public StepDecision execute(final Context context, final RefundCase input) {
            final ManagerDecision decision = MANAGER_DECISIONS.getConditionResults(context).get(0);
            if (decision.approved()) {
                return StepDecision.goTo(IssueRefund.class, input);
            }
            CASE_STATUS.set(context, "denied");
            return StepDecision.goTo(
                    WriteCustomerMessage.class, input.withOutcome("denied", decision.reason()));
        }
    }

impl Step for CheckPolicy {
    type Input = RefundCase;

    fn execute(&self, context: &mut Context, input: Self::Input) -> HandlerResult<StepDecision> {
        let order = &input.order;
        let mut denial_reasons = Vec::new();
        if order.days_since_charge > REFUND_WINDOW_DAYS {
            denial_reasons.push("The charge is outside the 30-day refund window.");
        }
        if order.outage_hours == 0 {
            denial_reasons.push("No service outage was recorded for this charge.");
        }
        if !denial_reasons.is_empty() {
            CASE_STATUS.set(context, CaseStatus::Denied)?;
            let note = denial_reasons.join(" ");
            let denied = ResolvedCase::new(input, RefundOutcome::Denied, note);
            return Ok(StepDecision::go_to(
                &WriteCustomerMessage::new(&self.services),
                denied,
            ));
        }
        if order.amount_cents > MANAGER_APPROVAL_LIMIT_CENTS {
            CASE_STATUS.set(context, CaseStatus::AwaitingManager)?;
            return Ok(StepDecision::go_to(
                &RequestManagerApproval::new(&self.services),
                input,
            ));
        }
        Ok(StepDecision::go_to(
            &IssueRefund::new(&self.services),
            input,
        ))
    }
}

impl Step for RequestManagerApproval {
    type Input = RefundCase;

    fn wait_for(&self, _context: &mut Context, _input: Self::Input) -> HandlerResult<Wait> {
        Ok(Wait::until(MANAGER_DECISIONS.for_one()))
    }

    fn execute(&self, context: &mut Context, input: Self::Input) -> HandlerResult<StepDecision> {
        let decision = MANAGER_DECISIONS
            .condition_results(context)?
            .into_iter()
            .next()
            .ok_or_else(|| HandlerError::new("MissingManagerDecision", "no manager decision"))?;
        if decision.approved {
            return Ok(StepDecision::go_to(
                &IssueRefund::new(&self.services),
                input,
            ));
        }
        CASE_STATUS.set(context, CaseStatus::Denied)?;
        let denied = ResolvedCase::new(input, RefundOutcome::Denied, decision.reason);
        Ok(StepDecision::go_to(
            &WriteCustomerMessage::new(&self.services),
            denied,
        ))
    }
}

An approve RPC and a reject RPC publish the manager's decision to that Channel. Each one requires a reason and checks that `case-status` is `awaiting-manager` before it publishes. In the Python and TypeScript examples, each RPC also declares a Dex Web Action, **Approve refund** or **Reject refund**. Dex Web offers the Actions only while `case-status` is `awaiting-manager`.

The example adds what a production refund needs:

- **Issue refund** and **Send message** pass an idempotency key to billing and email. Steps after a Time Travel point run again, and the keys keep the refund and the email to one each. This holds because every Worker shares the same persistent ledger of the local fake services.
- **Issue refund** retries a payment timeout every 5 seconds. A run can ask for two timeouts first. The final **Issue refund** event in Dex Web then shows that attempt 3 succeeded and keeps the details of the last failure.
- In Python and TypeScript, the Worker uploads the design that `dexcli visualize` generates, so Dex Web draws this graph on each run.
- In Python and TypeScript, with a payload key file, the Worker and the Client encrypt payloads. `case-status` and `customer-email` stay readable.

The Java and Rust examples approve or reject with their own `decide` command. The Java and Rust SDKs cannot declare Dex Web Actions or encrypt payloads. `dexcli visualize` reads Go, Python, and TypeScript sources only, so these Workers upload no design and their runs have no **Design** view in Dex Web.

The example folders for [Python](https://github.com/superdurable/dex/tree/main/examples/python/dex_examples/products/customer_refund), [TypeScript](https://github.com/superdurable/dex/tree/main/examples/typescript/src/products/customer-refund), [Java](https://github.com/superdurable/dex/tree/main/examples/java/src/main/java/io/superdurable/dex/products/customerrefund), and [Rust](https://github.com/superdurable/dex/tree/main/examples/rust/src/products/customer_refund) have the commands for each scenario: approval, a refund that fails and then succeeds, and a missing billing call that Time Travel fixes. The Python and TypeScript folders also show encryption.

## Deterministic policy

`CustomerRefundFlow` in Go runs seven Steps. It checks that the order exists and applies the 30-day rule. It records an idempotency key before it calls the payment provider. When the provider declines the refund, or its result is unknown, the Flow records that outcome as the case status.

<DocsFlowDefinitionGraph graph={deterministicFlow} />

Its Summary shows the charge reference, requested amount, and recommendation. Its Display adds evidence, billing outcome, and an editable operator note. This Flow declares no Action on purpose. It shows that a Flow with an empty Action list is valid for Dex Web.

## Agentic review

`AgenticCustomerRefundFlow` gathers evidence in a loop of Steps. A guardrail then either applies the decision automatically or waits for a manager to approve it. Each manager wait has its own gate key. The Flow records its intent before it runs the billing, subscription, and customer-message effects. These effects are idempotent.

<DocsFlowDefinitionGraph graph={agenticFlow} />

The approval Action appears as a direct button, with no input. The rejection Action asks for a reason. Dex Web fills in a hidden gate key. It takes the key from the Attribute values it read when the detail page opened. Before the RPC publishes a verdict, it compares that key with the current gate. If the gate has changed, the RPC returns an error and the operator must refresh the page.

Both Actions also read the current case status. The visibility condition in Flow Definition Graph 2.0 only controls whether a button appears. It does not authorize anyone.
