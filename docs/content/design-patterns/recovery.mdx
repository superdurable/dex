# Failure recovery

Dex retries failed WaitFor and Execute methods according to their independent
retry policies. When retries are exhausted, a Step failure policy either fails
the Flow or enters an application-defined recovery path.

## WaitFor recovery

`WaitForFailurePolicy.PROCEED` continues to Execute after the final WaitFor
failure. Execute runs in the same workflow run; continue-as-new cannot occur
between the failed WaitFor call and that Execute call. Existing
`context.waitForMethodFailed()` code continues to identify this path, and
`context.getRecoveryError()` provides the complete failure.

```java
@Override
public StepOptions getStepOptions() {
    return StepOptions.newBuilder()
            .waitForRetry(RetryPolicy.newBuilder().maximumAttempts(3).build())
            .waitForFailure(WaitForFailurePolicy.PROCEED)
            .build();
}

@Override
public StepDecision execute(Context context, Order input) {
    WorkerError error = context.getRecoveryError();
    if (error != null) {
        recordWaitFailure(error.getErrorType(), error.getDetail());
    }
    return StepDecision.gracefulComplete();
}
```

## Execute recovery Step

Configure a recovery Step with `onExecuteFailureProceedTo`. The failed
Execute's `WorkerError` is available to both WaitFor and Execute in that
recovery Step. Dex persists it with the queued movement, so it remains available
after continue-as-new.

```java
@Override
public StepOptions getStepOptions() {
    return StepOptions.newBuilder()
            .executeRetry(RetryPolicy.newBuilder().maximumAttempts(3).build())
            .onExecuteFailureProceedTo(compensateOrder)
            .build();
}
```

If the recovery Step's WaitFor method also fails and proceeds, its Execute
receives that newer WaitFor failure instead of the original Execute failure.

## Durability

A method with a failure-policy recovery path defaults to `SYNC`. The
FlowConfig durability cannot override this default. An explicit method-level
Step option remains authoritative and can select `ASYNC` when the application
accepts replay of the earlier method after recovery has begun.

## Dynamic retry delay

Java Steps can request the next retry interval while preserving the original
failure:

```java
throw RetryAfterException.after(Duration.ofSeconds(30), failure);
```

Temporal applies this value to the next Activity retry without changing retry
limits or method timeouts. Cadence cannot apply a dynamic interval; Dex stops
retrying that method and evaluates its failure policy. In both cases the
original cause, rather than `RetryAfterException`, is exposed as the Worker
error.

## Backend failures

When a Worker returns structured error details, recovery receives its detail,
type, stack trace, and retry delay. For timeouts and other failures without a
Worker response, Dex creates a `WorkerError` whose type is the Temporal or
Cadence backend failure type. Backend-generated failures normally have no
Worker stack trace.
