# Fail Fast on Permanent Errors

Use this pattern when a provider call can fail in two ways: a transient error that a retry may fix, and a permanent error that no retry can fix.

An example is an expense claim paid through a payment provider. A timeout is transient: the next attempt may succeed. An invalid bank account is permanent: the provider has rejected the request, and every retry gets the same answer.

Step retry retries every error that Step code raises. A Step with a one-hour retry policy keeps retrying a permanent error for an hour before its failure route runs. Classify the error in `Execute` instead, and route a permanent error at once.

<DocsFlowDefinitionGraph graph={flowDefinition} />

## How it works

- Call the provider in `Execute`. `Execute` sees the provider's error and decides what it means.
- Let a transient error fail the attempt. Throw it or return it. Step retry runs the call again under the Step's own retry policy.
- Catch a permanent error and return a Step decision. Go to a failure-handling Step that records the business failure. Return `ForceFail` instead when the whole Flow must end at once.
- Treat an error as permanent only when the provider confirms it, such as rejected input or an invalid request. Leave an unknown error transient, so retry still covers it.
- Size the retry policy for transient errors only. A permanent error never consumes it.
- Keep calls that can fail permanently in `Execute`. `Execute` returns the decision that routes the failure, in the same call that saw it.

In the example:

1. `ExpenseReimbursementFlow` starts `SubmitPayout` with the claim. The Flow ID is the claim ID and the provider's idempotency key.
2. `SubmitPayout` calls the payment provider. On success, it records the payout in the `PayoutOutcome` Attribute and completes the Flow.
3. When the provider times out, `SubmitPayout` lets the error fail the attempt. Step retry calls the provider again, with backoff, for up to one hour.
4. When the provider rejects the bank account, `SubmitPayout` goes to `RecordRejectedClaim` with the reason. No retry runs.
5. `RecordRejectedClaim` records the rejection in `PayoutOutcome` and completes the Flow.

```go
type SubmitPayout struct {

	provider *FakePaymentProvider

func (SubmitPayout) GetStepOptions() *dex.StepOptions {
	return &dex.StepOptions{
		ExecuteRetry: &dex.RetryPolicy{
			InitialInterval:    time.Second,
			BackoffCoefficient: 2,
			MaximumInterval:    5 * time.Minute,
			TotalDuration:      time.Hour,
		},
	}
}

func (step SubmitPayout) Execute(ctx dex.Context, claim ExpenseClaim) (*dex.StepDecision, error) {
	payoutID, err := step.provider.SubmitPayout(ctx.FlowID(), claim)
	var rejection *PayoutRejectedError
	if errors.As(err, &rejection) {
		return dex.GoTo(RecordRejectedClaim{}, ClaimRejection{Reason: rejection.Reason, SubmitAttempt: ctx.Attempt()}), nil
	}
	if err != nil {
		return nil, dex.ErrorWithStack(err)
	}
	if err := PayoutOutcomeAttribute.Set(ctx, PayoutOutcome{Status: "PAID", Detail: payoutID, SubmitAttempt: ctx.Attempt()}); err != nil {
		return nil, err
	}
	return dex.GracefulComplete(payoutID), nil
}

type RecordRejectedClaim struct {
	dex.StepDefaultsNoWaitFor[ClaimRejection]
}

func (RecordRejectedClaim) Execute(ctx dex.Context, rejection ClaimRejection) (*dex.StepDecision, error) {
	outcome := PayoutOutcome{Status: "REJECTED", Detail: rejection.Reason, SubmitAttempt: rejection.SubmitAttempt}
	if err := PayoutOutcomeAttribute.Set(ctx, outcome); err != nil {
		return nil, err
	}
	return dex.GracefulComplete("rejected: " + rejection.Reason), nil
}
```

```rust
impl Step for SubmitPayout {
    type Input = ExpenseClaim;

    fn options(&self) -> StepOptions<Self::Input> {
        StepOptions::new().execute_retry(
            RetryPolicy::new()
                .initial_interval(Duration::from_secs(1))
                .backoff_coefficient(2.0)
                .maximum_interval(Duration::from_secs(5 * 60))
                .total_duration(Duration::from_secs(60 * 60)),
        )
    }

    fn execute(&self, context: &mut Context, claim: Self::Input) -> HandlerResult<StepDecision> {
        let payout_id = match self.provider.submit_payout(context.flow_id(), &claim) {
            Ok(payout_id) => payout_id,
            Err(PayoutError::Rejected { reason }) => {
                let rejection = ClaimRejection {
                    reason,
                    submit_attempt: context.attempt(),
                };
                return Ok(StepDecision::go_to(&RecordRejectedClaim, rejection));
            }
            Err(error @ PayoutError::Timeout) => return Err(HandlerError::from_error(error)),
        };
        let outcome = PayoutOutcome {
            status: "PAID".to_string(),
            detail: payout_id.clone(),
            submit_attempt: context.attempt(),
        };
        PAYOUT_OUTCOME.set(context, outcome)?;
        Ok(StepDecision::graceful_complete(payout_id))
    }
}

impl Step for RecordRejectedClaim {
    type Input = ClaimRejection;

    fn execute(
        &self,
        context: &mut Context,
        rejection: Self::Input,
    ) -> HandlerResult<StepDecision> {
        let outcome = PayoutOutcome {
            status: "REJECTED".to_string(),
            detail: rejection.reason.clone(),
            submit_attempt: rejection.submit_attempt,
        };
        PAYOUT_OUTCOME.set(context, outcome)?;
        Ok(StepDecision::graceful_complete(format!(
            "rejected: {}",
            rejection.reason
        )))
    }
}
```

## Test both routes

Test with the Step's real retry policy. A test that shortens the policy no longer tests the route.

- Make a fake provider return a permanent error. Assert that the failure-handling Step runs at once, after exactly one provider call. A bounded wait far shorter than the retry policy proves that no retry ran.
- Make the fake provider return a transient error once. Assert that the Step retries and then succeeds.

The examples assert both through the `PayoutOutcome` Attribute, which records the attempt that produced the outcome.

## Compared with Execute Failure Recovery

[Execute Failure Recovery](/design-patterns/failure-handling/execute-failure-recovery) handles a failure that is still there after the retry policy is exhausted. Its `ExecuteFailure` policy moves the Flow to a recovery Step, which receives the failed Step's input.

Fail Fast on Permanent Errors decides before any retry. `Execute` itself returns the decision, so the failure-handling Step receives whatever input `Execute` builds, such as the rejection reason.

Use both together when a Step needs both: fail fast on a confirmed permanent error, and add an `ExecuteFailure` route for transient errors that outlast the retry policy.
