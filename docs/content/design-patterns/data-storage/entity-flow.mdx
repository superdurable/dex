# Entity Flow

Keep one long-lived Flow for each business entity, such as a customer, an order, or an account. The Flow holds the entity's state for as long as the entity exists. Every change goes through the Flow, so Dex saves it durably.

The runnable example keeps one `CustomerAccountFlow` per customer account. It stores a display name, an email address, and a credit balance.

<DocsFlowDefinitionGraph graph={flowDefinition} />

## When to use this pattern

Use an Entity Flow when one business entity needs durable state that several callers change over time. Each change must be validated against the current state. Typical examples are a customer account, a shopping cart, a device, or a subscription record.

To also query the latest state of many entities with SQL, extend this pattern with [Entity Flow with SQL Projection](/design-patterns/entity-store).

## How it works

1. **Open the account.** The application starts a Flow whose ID comes from the account ID, such as `customer-account-42`. The start request sets the initial Attributes. A second start with the same account ID fails while Dex keeps the account's Flow, so each account has exactly one Flow.
2. **Change the contact details.** `UpdateContactDetails` validates the new name and email address, then writes both Attributes.
3. **Adjust the credit balance.** `AdjustCreditBalance` reads the balance, adds the amount, and rejects a result below zero. It locks the balance Attribute, so concurrent adjustments run one at a time.
4. **Read the account.** The application reads the Attributes with the Client. No Worker runs for the read.
5. **Retire the account.** `RetireAccount` checks that the balance is zero, marks the account retired, and moves to `CloseAccountStep`. That Step completes the Flow gracefully.

Between these calls the Flow has no active Step. It keeps running and holds no Worker, so it can live for months or years.

## Core implementation

### Open one Flow per entity

Derive the Flow ID from the entity ID. Start the Flow with no Flow timeout, and set the initial state as Attributes in the start request. Treat an already-started error as "this account exists".

### Change state through RPCs

Each RPC validates its input against the current state, then writes the Attributes. `UpdateContactDetails` replaces values without reading them, so it needs no lock. `AdjustCreditBalance` reads the balance and then writes it. It declares a lock on the balance Attribute, so two adjustments cannot overwrite each other.

```python
@rpc(name="UpdateContactDetails")
def update_contact_details(self, context: Context, input: ContactDetails) -> None:
    input.validate()
    self.display_name.set(context, input.display_name)
    self.email.set(context, input.email)

@rpc(name="AdjustCreditBalance", lock_attributes=(credit_balance.lock(),))
def adjust_credit_balance(
    self, context: Context, input: CreditAdjustment
) -> RPCResult[int]:
    if self.retired.get(context):
        raise ValueError("account is retired")
    if input.amount == 0:
        raise ValueError("amount must not be zero")
    balance = self.credit_balance.get(context) + input.amount
    if balance < 0:
        raise ValueError("credit balance cannot go below zero")
    self.credit_balance.set(context, balance)
    return RPCResult(balance)
```

```go
func (flow *CustomerAccountFlow) GetRPCs() []dex.RPCDef {
	balanceLock := &dex.RPCOptions{
		LockAttributes: []dex.AttributeLock{dex.LockAttribute(CreditBalance)},
	}
	return []dex.RPCDef{
		dex.DefineRPC(flow.UpdateContactDetails, nil),
		dex.DefineRPC(flow.AdjustCreditBalance, balanceLock),
		dex.DefineRPC(flow.RetireAccount, balanceLock),
	}
}

func (*CustomerAccountFlow) AdjustCreditBalance(
	ctx dex.Context,
	adjustment CreditAdjustment,
) (*dex.RPCResult[int64], error) {
	retired, err := Retired.Get(ctx)
	if err != nil {
		return nil, err
	}
	if retired {
		return nil, errors.New("account is retired")
	}
	if adjustment.Amount == 0 {
		return nil, errors.New("amount must not be zero")
	}
	balance, err := CreditBalance.Get(ctx)
	if err != nil {
		return nil, err
	}
	balance += adjustment.Amount
	if balance < 0 {
		return nil, errors.New("credit balance cannot go below zero")
	}
	if err := CreditBalance.Set(ctx, balance); err != nil {
		return nil, err
	}
	return &dex.RPCResult[int64]{Output: balance}, nil
}
```

```java
    if (balance < 0) {
        throw new IllegalArgumentException("credit balance cannot go below zero");
    }
    creditBalance.set(context, balance);
    return RPCResult.of(balance);
}
```

```rust
fn adjust_credit_balance(
    &self,
    context: &mut Context,
    adjustment: CreditAdjustment,
) -> HandlerResult<RpcResult<i64>> {
    if RETIRED.get(context)?.unwrap_or(false) {
        return Err(account_error("account is retired"));
    }
    if adjustment.amount == 0 {
        return Err(account_error("amount must not be zero"));
    }
    let balance = CREDIT_BALANCE.get_required(context)? + adjustment.amount;
    if balance < 0 {
        return Err(account_error("credit balance cannot go below zero"));
    }
    CREDIT_BALANCE.set(context, balance)?;
    Ok(RpcResult::new(balance))
}

fn rpcs(&self) -> RpcList<Self> {
    RpcList::new()
        .procedure(UPDATE_CONTACT_DETAILS, Self::update_contact_details)
        .function(
            ADJUST_CREDIT_BALANCE.lock(CREDIT_BALANCE.lock()),
            Self::adjust_credit_balance,
        )
        .function_without_input(
            RETIRE_ACCOUNT.lock(CREDIT_BALANCE.lock()),
            Self::retire_account,
        )
}
```

### Read state with the Client

Read stored Attributes with the Client's Attribute read. It returns committed values and runs no Worker. Use a read-only RPC instead when the read needs Flow code, such as authorization or a derived view; see [Read-only RPCs](/reference/server/runtime-data#read-only-rpcs-and-terminal-flows).

### Retire the entity

`RetireAccount` holds the same lock as `AdjustCreditBalance`. It checks the balance, sets the `retired` Attribute, and moves to `CloseAccountStep`. That Step returns `GracefulComplete`, and the Flow completes. The completed Flow stays readable with the Client until Dex purges it.

RPCs still run between `RetireAccount` and the end of the Flow. `AdjustCreditBalance` reads `retired` under the same lock and rejects new credits, so the account closes with a zero balance.

<SdkSnippet lang="python">

```python
class CloseAccountStep(Step[None]):
    def execute(self, context: Context, input: None) -> StepDecision:
        return graceful_complete()

@rpc(name="RetireAccount", lock_attributes=(credit_balance.lock(),))
def retire_account(self, context: Context) -> RPCResult[None]:
    if self.credit_balance.get(context) != 0:
        raise ValueError("spend or refund the credit balance before retiring")
    self.retired.set(context, True)
    return RPCResult(None, next_steps=(StepMovement.of(CloseAccountStep, None),))
```

</SdkSnippet>

```go
func (*CustomerAccountFlow) RetireAccount(
	ctx dex.Context,
	_ dex.None,
) (*dex.RPCResult[dex.None], error) {
	balance, err := CreditBalance.Get(ctx)
	if err != nil {
		return nil, err
	}
	if balance != 0 {
		return nil, errors.New("spend or refund the credit balance before retiring")
	}
	if err := Retired.Set(ctx, true); err != nil {
		return nil, err
	}
	return &dex.RPCResult[dex.None]{
		NextSteps: []dex.StepMovement{dex.MovementOf(CloseAccountStep{}, nil)},
	}, nil
}

func (CloseAccountStep) Execute(dex.Context, dex.None) (*dex.StepDecision, error) {
	return dex.GracefulComplete(nil), nil
}
```

```java
@RPC(name = "RetireAccount", lockAttributes = {"credit_balance"})
public RPCResult<Void> retireAccount(final Context context) {
    if (creditBalance.get(context) != 0) {
        throw new IllegalArgumentException(
                "spend or refund the credit balance before retiring");
    }
    retired.set(context, true);
    return RPCResult.of((Void) null, StepMovement.of(CloseAccountStep.class, null));
}

public static final class CloseAccountStep implements Step<Void> {
    @Override
    public Class<Void> getInputType() {
        return Void.class;
    }

    @Override
    public StepDecision execute(final Context context, final Void input) {
        return StepDecision.gracefulComplete();
    }
}
```

An entity Flow that also has a Step waiting on something long, such as a Channel of incoming commands, adds the graceful completion condition to that wait. A completion request then wakes the Step, and the Flow can close. See [Wait for a completion request](/reference/server/step-and-flow-close#graceful-completion-condition).

## Keep the state bounded

Each Attribute holds one value that the Flow rewrites on every change. Keep the entity's current state in plain Attributes. When the entity collects a growing history, such as its orders or audit events, store that history in a [Sequentially Chunked AttributeMap](/design-patterns/sequentially-chunked-attribute-map).
