# Responsive Update

An interactive caller should not have to choose between waiting for an entire Flow and polling its state. A responsive update returns at the boundary that the caller needs, while the Flow continues to own durable work.

Choose the boundary deliberately:

- [Wait for Step Completion](/design-patterns/responsive-update/step-completion) returns after one named Step has completed. Use it when that Step makes the result safe for a client to read or use.
- [Wait for Attribute Match](/design-patterns/responsive-update/attribute-match) returns the current matching Attribute value. Use a revision watermark when callers need to refresh after business state changes.
- [Wait and Stream](/design-patterns/responsive-update/stream) long-polls for the next incremental update and resumes from its token. Use it for progress or a changing feed.

The first two waits observe durable state. They are appropriate for a client-visible boundary, not a substitute for an application timeout or a final Flow result. Streams carry ordered incremental messages; clients keep the latest resume token and use it on the next read.

## Choose the timeout boundary

**RequestTimeout** is the SDK call's total budget. It covers every transparent transport reattachment. A positive value creates a local transport deadline for each attempt and returns a typed request-timeout error when the total budget expires. An already accepted durable Update remains available for a later call using the same logical Request ID.

Leave **RequestTimeout** at 0 for an ordinary durable wait. The wait is then unlimited until it succeeds, the Flow closes, or the caller cancels it. At an HTTP or admission boundary, set the application's response budget explicitly.

The server also caps one transport attempt. That cap is internal. The SDK reattaches with the same logical Request ID, so the cap does not reset **RequestTimeout**, end the Temporal Update handler, or create another Update generation.

**InternalHandlerTimeout** is an advanced Temporal control for protecting Update capacity. [Temporal permits at most 10 in-flight Updates and 2,000 total Updates in History per Workflow Execution](https://docs.temporal.io/evaluate/cloud/limits#per-workflow-execution-update-limits). A request timeout or cancellation ends the SDK call but does not finish an accepted durable Update handler. An abandoned wait can therefore retain one of the 10 in-flight slots until the condition matches or the Flow closes.

Set **InternalHandlerTimeout** to a positive value only when abandoned waits can accumulate enough to approach the in-flight limit. When it expires, the old handler generation completes. An active SDK call transparently creates the next generation and keeps waiting. This does not raise the 10-Update limit. Each rollover counts toward the 2,000 total Updates in History and may increase Temporal Cloud Actions. Prefer a value comfortably longer than normal **RequestTimeout** values and expected reconnect gaps. Keep it at 0 when waits reliably complete or the Flow closes before abandoned handlers become a capacity risk.

| Setting | Default | Behavior |
| --- | --- | --- |
| **RequestTimeout** | 0 | Total caller-visible SDK budget. Zero waits until success, Flow closure, or caller cancellation. |
| **InternalHandlerTimeout** | 0 | Reclaims abandoned accepted handlers before they indefinitely consume in-flight Update slots. Each rollover adds another Update to History. |
| Transport attempt cap | Server-managed | Causes transparent reattachment only. It is not an application-facing timeout. |
