# Responsive Update

An interactive caller should not have to choose between waiting for an entire Flow and polling its state. A responsive update returns at the boundary that the caller needs, while the Flow continues to own durable work. When the Flow itself waits for an external system, use [Polling](/design-patterns/polling).

Choose the boundary deliberately:

- [Wait for Step Completion](/design-patterns/responsive-update/step-completion) returns after one named Step has completed. Use it when that Step makes the result safe for a client to read or use.
- [Wait for Attribute Match](/design-patterns/responsive-update/attribute-match) returns the current matching Attribute value. Use a revision watermark when callers need to refresh after business state changes.
- [Wait and Stream](/design-patterns/responsive-update/stream) long-polls for the next incremental update and resumes from its token. Use it for progress or a changing feed.

The first two waits observe durable state. They are appropriate for a client-visible boundary, not a substitute for an application timeout or a final Flow result. Streams carry ordered incremental messages; clients keep the latest resume token and use it on the next read.

## Choose the timeout boundary

**RequestTimeout** is the SDK call's total budget. It covers every transparent transport reattachment. A positive value creates a local transport deadline for each attempt and returns a typed request-timeout error when the total budget expires. An already accepted wait remains available for a later call using the same logical Request ID.

Leave **RequestTimeout** at 0 for an ordinary durable wait. The wait is then unlimited until it succeeds, the Flow closes, or the caller cancels it. At an HTTP or admission boundary, set the application's response budget explicitly.

The server also caps one transport attempt. That cap is internal. The SDK reattaches with the same logical Request ID, so the cap does not reset **RequestTimeout** or end the accepted wait.

**InternalHandlerTimeout** is an advanced capacity control. On the Temporal backend, one Flow can hold at most 10 in-flight requests that wait inside the Flow, such as accepted waits and locked or transactional RPCs. A request timeout or cancellation ends the SDK call but does not end an accepted wait. An abandoned wait can therefore hold one of those 10 slots until the condition matches or the Flow closes.

Set **InternalHandlerTimeout** to a positive value only when abandoned waits can accumulate enough to approach that limit. When it expires, Dex ends the accepted wait and frees its slot. An active SDK call transparently registers its wait again and keeps waiting. This does not raise the limit. Each new registration is another accepted request on the Flow and may increase Temporal Cloud Actions. Prefer a value comfortably longer than normal **RequestTimeout** values and expected reconnect gaps. Keep it at 0 when waits reliably complete or the Flow closes before abandoned waits become a capacity risk.

| Setting | Default | Behavior |
| --- | --- | --- |
| **RequestTimeout** | 0 | Total caller-visible SDK budget. Zero waits until success, Flow closure, or caller cancellation. |
| **InternalHandlerTimeout** | 0 | Reclaims abandoned accepted waits before they indefinitely hold in-flight slots. An active call registers its wait again after each expiry. |
| Transport attempt cap | Server-managed | Causes transparent reattachment only. It is not an application-facing timeout. |
