# Responsive Update

An interactive caller should not have to choose between waiting for an entire Flow and polling its state. A responsive update returns at the boundary that the caller needs, while the Flow continues to own durable work.

Choose the boundary deliberately:

- [Wait for Step Completion](/design-patterns/responsive-update/step-completion) returns after one named Step has completed. Use it when that Step makes the result safe for a client to read or use.
- [Wait for Attribute Match](/design-patterns/responsive-update/attribute-match) returns the current matching Attribute value. Use a revision watermark when callers need to refresh after business state changes.
- [Wait and Stream](/design-patterns/responsive-update/stream) long-polls for the next incremental update and resumes from its token. Use it for progress or a changing feed.

The first two waits observe durable state. They are appropriate for a client-visible boundary, not a substitute for an application timeout or a final Flow result. Streams carry ordered incremental messages; clients keep the latest resume token and use it on the next read.

## Choose the wait budget

**MaximumWaitTime** bounds the caller-visible wait. It is separate from a caller context, HTTP deadline, or transport long-poll timeout. When a positive budget elapses, the caller receives a typed timeout.

A positive **MaximumWaitTime** is an exceptional safety valve, not a normal request timeout. For routine response deadlines, leave it at 0 and use the caller context or HTTP deadline. Short positive budgets can cause repeated waits to add many Temporal Update accepted and completed events to Workflow history. They may also increase Temporal Cloud Actions. If a positive value is genuinely necessary, start with at least one minute and use a shorter value only for a measured requirement.

| **MaximumWaitTime** | Use it when | Behavior |
| --- | --- | --- |
| 0 | Recommended for ordinary waits. | Waits until the Step completes or the Attribute matches. Use the caller deadline to bound one response. |
| Positive | Rarely, when the wait itself needs a caller-visible maximum duration. Prefer at least one minute. | Returns a typed timeout when the budget expires. Short values can add many Temporal Update events to Workflow history. |
