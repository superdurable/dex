# Parallel SubFlows

Use SubFlows when parallel work needs independent execution histories, retries, and lifecycle control.

## Choose a pattern

- [Basic SubFlow fan-out](/design-patterns/parallel-subflows/basic) — Start a runtime-sized group, wait for half to succeed, and stop the remaining SubFlows.
- [Advanced: long-lived parent](/design-patterns/parallel-subflows/long-lived-parent) — Keep a fixed worker pool alive and accept requests through an RPC that publishes to a Channel.
- [Advanced: short-lived parent](/design-patterns/parallel-subflows/short-lived-parent) — Drain queued requests and atomically complete when the last SubFlow and Channel are both empty.
- [Advanced: multiple parents with partitioning](/design-patterns/parallel-subflows/partitioning) — Route requests across multiple parents so total SubFlow concurrency can grow horizontally.
- [Advanced: back pressure for high availability](/design-patterns/parallel-subflows/back-pressure) — Submit through a retrying Flow when a parent rejects an overloaded request.

The first three pages define the parent Flow shapes. Partitioning and back pressure extend those shapes for higher scale and availability.
