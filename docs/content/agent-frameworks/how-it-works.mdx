# How Durable Agents Work

Each term you know from your agent framework has a counterpart in the Dex session Flow. Your prompts, tools, and model choice stay the same.

<AgentTermMapDiagram markdownDescription="Your app's Client sends a message (send_user_message) into the session Flow, which is the conversation thread. Inside it, the agent loop runs as Steps that Dex records: an LLM call is RunModel, a tool call is CallTool for a read or an idempotent write and CallSingleAttemptTool for any other write, human in the loop is AwaitToolApproval, and ResumeTurn returns the tool results to the model. The chat history lives in the session's Attributes, and live output goes to the AgentEvents Stream. The Steps call your models and tools." />

## Your framework's terms in Dex {#term-map}

| In your framework | In Dex | What changes for you |
| --- | --- | --- |
| Agent | Your agent, wrapped by a Dex adapter into a session Flow | Prompts, tools, and model choice stay as they are. |
| Thread, conversation, session | A **session**: one Flow run. The Flow ID is the session ID. | The session survives crashes and deploys. After it stops, it stays readable for the retention period. |
| Run the agent | The `send_user_message` RPC from a Client (`sendUserMessage` in TypeScript) | Dex records the message before the turn starts. A message sent during a turn waits in a queue. |
| Turn | A **turn**: the Steps from one user message to the reply | **Steer** (`steer_user_message`) ends a turn at the next safe Step boundary. `cancel_turn` also stops a running model call and drops its answer. Neither stops a tool call that has started. |
| LLM call | A `RunModel` Step | Dex records the response. A retry calls the model again. |
| Tool call, function call | A `CallTool` Step for a read or an idempotent write, a `CallSingleAttemptTool` Step for any other write | A write in its own Step runs at most once. When a crash leaves its result unknown, the model sees `outcome_unknown`. |
| Parallel tool calls | Tool Steps that run in parallel, then a `ResumeTurn` Step | `ResumeTurn` waits for every result and gives them to the model. |
| Human in the loop, tool confirmation | An `AwaitToolApproval` Step, answered with the `resolve_interrupt` RPC (`resolveInterrupt` in TypeScript) or in Dex Web | The wait can last days and holds no Worker. |
| Checkpointer, durable execution plugin | Recorded Step results. The adapter keeps the framework's own state between Steps. | A crash repeats only the Step that was running. The agent code needs no determinism rules. |
| Chat history, short-term memory | The session's Attributes | Long-term memory across sessions stays in a store you own, behind a tool. |
| Streaming callbacks | The AgentEvents Stream | It is best effort. `get_agent_snapshot` (`getAgentSnapshot` in TypeScript) reads the recorded conversation. |
| MCP servers, tool integrations | Tool sources. Official Connectors come in through `ConnectorToolSource`. | Each Connector call gets its credentials and an idempotency key. |

Some tools run inside `RunModel` or at the model provider, so they run again when that Step retries. [Framework Support](/agent-frameworks/framework-support#features-by-harness) lists them for each framework.
