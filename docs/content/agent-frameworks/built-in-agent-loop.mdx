# Built-in Agent Loop

The built-in agent loop runs an agent without an agent framework. Dex owns the conversation and builds every model input from durable state. So the agent does not depend on an LLM provider's conversation API.

## When to use it

Use the built-in loop for a new agent. It offers every session feature: questions, durable waits, plans, steering, compaction, and MCP tools. It also lets each session pick its model from a list that the Worker allows.

Use a [framework harness](/agent-frameworks#choose-a-harness) when you already have an agent written with a framework.

## How a session runs

Every model call is one `RunModel` Step. Every tool call is its own Step, so a crash repeats at most the one call that was running.

The Steps, Attributes, Channels, RPCs, and events are the ones every Dex Agents session uses:

```text
StartAgentSession -> AwaitUserMessage -> RunModel
AwaitUserMessage -> steer or cancel_turn -> ApplyTurnControl
RunModel -> final answer -> AwaitUserMessage
RunModel -> failed after three attempts -> RecordTurnFailure -> AwaitUserMessage
RunModel -> CompactContext -> RunModel
RunModel -> tool calls -> AwaitToolApproval -> CallTool or CallSingleAttemptTool
                          CallTool or CallSingleAttemptTool
                          AwaitQuestionAnswer      for ask_user
                          AwaitTimer               for durable_wait
                          ResumeTurn -> RunModel, or ApplyTurnControl when steered
ApplyTurnControl -> RunModel with the steered messages, else AwaitUserMessage
```

This view is simplified. [Crashes and tool call outcomes](/reference/agents/failures) and [Workers and timeouts](/reference/agents/workers) give each Step's retries, timeout, and failure route.

A failed `RunModel` retries. After its third attempt, the turn fails and the session waits for the next message. A read or an idempotent write retries in `CallTool`. Any other write runs once in `CallSingleAttemptTool`, after approval when its policy asks for one.

## The example

The [AI Agent](/use-cases/ai-agent) is a general, long-running agent in Python and TypeScript. It chats with a user and calls trusted MCP tools. It waits for approval before external writes, asks the user questions, suspends itself on a durable Timer, and drafts plans for review before it runs them.

### The session Flow {#the-session-flow}

The application declares the agent in Dex terms and builds its Flow. The Flow type is **AIAgentSession**. One Flow run is one session, and the Flow ID is the session ID.

```python
def build_ai_agent_session_flow(
    models: Sequence[str],
    system_prompt: str,
    context_window_tokens: int,
    mcp_servers: Sequence[McpServerConfig],
    slack_connection: slack.Connection | None,
) -> AgentSessionFlow:
    """Builds the agent; ``models`` are the allowed model names, and the first is the default.

    ``slack_connection`` None leaves out the Slack connector tools.
    """
    clients = {model: _model_client(model) for model in models}
    mcp_tool_sources = (
        [McpToolSource(mcp_servers, resource_and_prompt_tools_enabled=True)] if mcp_servers else []
    )
    definition = AgentDefinition(
        name="ai-agent",
        instructions=system_prompt,
        model=clients[models[0]],
        # Settings hold only a model name; an unknown one gets the default, never a new client.
        resolve_model=lambda settings: clients.get(str(settings.get("model")), clients[models[0]]),
        tool_sources=[*mcp_tool_sources, *build_slack_tool_sources(slack_connection)],
        built_in_tools=frozenset(BuiltInTool),
        plan_mode_enabled=True,
        compaction=CompactionPolicy(context_window_tokens=context_window_tokens),
    )
    return stepwise_agent_session_flow(definition, flow_type=AI_AGENT_SESSION_FLOW_TYPE)
```

The allowed models, the system prompt, the context window, and the MCP servers are Worker configuration, shared by every session. Each session picks one allowed model when it starts. Its session settings hold only the model name, and the Worker maps the name to a model client, so no credential or server command comes from a browser or from Flow input. A changed prompt or model client takes effect at the next model call of every session, including a turn that is waiting, because Dex does not replay a Flow.

## Durable context {#durable-context}

The session stores each user message, model output item, and tool result as a message. The newest messages are `AgentMessages` AttributeMap instances, and older ones move into immutable `AgentMessageChunks` instances. Model output items are kept exactly as the provider returned them, including encrypted reasoning items and thinking signatures, and replayed unchanged.

When the model input nears the configured context window, a `CompactContext` Step summarizes older messages before the next model call. The model then receives the summary and the recent messages. Compaction never separates a tool call from its result. Retention can then delete old summarized messages, so a long session's state stays bounded. See [Compaction and the storage bound](/reference/agents/session-limits#compaction) for the threshold, the retention limits, and how to keep the whole transcript.

## Queued messages and Steer {#queued-messages-and-steer}

A message sent while a turn runs waits in the durable `QueuedUserMessages` queue. The UI shows it with **Steer** and **Delete** controls while it is pending.

**Steer** applies a message at the turn's next safe Step boundary. It never stops a model call or a tool call that has started. Tool calls that have not started, and approvals, questions, and durable waits that are still waiting, record a structured cancellation result. The turn then ends, and a new turn starts with every steered message. **Stop** calls `cancel_turn`, which ends the turn the same way without a new one.

## Questions and durable waits {#questions-and-durable-waits}

The `ask_user` built-in tool asks the user a question and waits in `AwaitQuestionAnswer`. The UI shows the question with choice buttons or a text box, and the answer becomes the tool's result in the same turn.

The `durable_wait` built-in tool waits in `AwaitTimer` on a [Timer](/concepts/primitives/timer). No model call or Worker holds the wait, and it survives Worker and engine restarts. Steering or **Stop** interrupts it. A queued message does not.

## Durable plans {#durable-plans}

Turn on **Plan mode** for a message to ask the agent for a plan. A planning turn can only call the `write_todos` built-in tool, which replaces the `AgentPlan` Attribute and advances its revision. The UI shows the draft, and **Execute plan** calls `execute_plan` with the reviewed revision. A stale revision is refused. A plan that stops with unfinished tasks stays active and can be continued. While a plan is active, other turns can call every tool; only a draft plan limits a turn to `write_todos`.

## MCP tools and approvals {#mcp-tools-and-approvals}

The Worker loads trusted stdio or Streamable HTTP MCP servers from local configuration. The agent takes the `McpToolSource` of Dex Agents as a tool source, so the model sees every server's tools. The Worker refuses configuration keys it does not know, including the per-tool settings of earlier versions of the example. Each MCP call runs in its own tool Step. A server that cannot be listed is left out of that model call and tried again on the next one, so the agent keeps answering when every server is down.

A tool's effect decides how it runs, as [Tool Calls](/agent-frameworks/tool-calls) describes. When a server's annotations are trusted, a read-only tool runs at once. Every other tool waits in `AwaitToolApproval` until the user approves it. Each MCP call carries an idempotency key so the server can drop a duplicate.

With `resource_and_prompt_tools_enabled`, the tool source also offers three read tools that list and read a server's resources and prompts.

## Live events {#live-events}

Text, reasoning summaries, tool activity, approvals, and plan updates arrive on the session's `AgentEvents` [Stream](/concepts/primitives/stream). The Python example serves it to the browser as Server-Sent Events with the library's browser stream helpers. The TypeScript example serves it as an AI SDK UI message stream for `useChat`: a route sends the user message or the tool approvals and streams the turn into the browser's chat.

## Session access {#session-access}

A session ID appears in the page URL, so treat it as public. So every route that names a session also checks the session's token before it calls Dex. **POST /sessions** checks the requested model against the models the Worker allows, picks a new session ID, and returns its token. The token is an HMAC-SHA256 of the session ID under `DEX_AGENT_SESSION_KEY`, so the example stores no token, and every process with the same key accepts it. A route that gets a missing or different **X-Agent-Session-Token** header answers 403.

```python
    def authorize_session(session_id: str) -> str:
        # Every route that names a session checks its token before any Dex call.
        expected = sign_session_id(app_state.config.agent_session_key, session_id)
        if not hmac.compare_digest(request.headers.get(SESSION_TOKEN_HEADER, ""), expected):
            raise Forbidden("this browser has no token for the AI Agent session")
        return session_id

    @blueprint.post("/sessions")
    async def start_session() -> Response:
        body = await request.get_json(silent=True)
        if not isinstance(body, dict):
            raise BadRequest("the request body must be a JSON object")
        model = body.get("model", app_state.config.agent_models[0])
        if model not in app_state.config.agent_models:
            raise BadRequest("model must be one of the models in /settings")
        # The server picks the session ID, so a caller cannot claim an existing session.
        session_id = f"ai-agent-{uuid.uuid4()}"
        # Settings carry only the model name; the Worker resolves it, and keys stay on the Worker.
        await sessions().start_session(session_id, session_settings={"model": model})
        session_token = sign_session_id(app_state.config.agent_session_key, session_id)
        return jsonify(session_id=session_id, session_token=session_token)
```

Both pages keep each token in local storage, keyed by the session ID, and put only the session ID in the page URL, so a copied URL does not grant access. Each sends the header with every request. The Python page reads the event stream with **fetch** instead of `EventSource`, which cannot send a header. The TypeScript page passes the header to the `useChat` transport, both for its requests and for its reconnects. The AI Agent routes send no CORS headers, so a page on another origin cannot call them.

Without `DEX_AGENT_SESSION_KEY`, the process picks a random key when it starts, and a restart ends access to the sessions started before it. A real application replaces the token with its own sign-in and checks that the user may use the session.

The first page shows the Worker's model, prompt, context window, and MCP tools. The start form picks the session's model from the models the Worker allows.

The default demo model needs no credential. It reads slash commands such as `/ask`, `/choose`, `/wait`, and `/tool`, so you can try every feature without a key. In TypeScript, the demo models are `mock/dex` and `mock/dex-mini`, and `/model` names the session's model.

To use real models, set these variables and restart the Worker:

| Variable | Meaning |
| --- | --- |
| `DEX_AGENT_MODEL` | The default model. In Python, a LiteLLM model name. In TypeScript, an AI SDK model such as `openai/gpt-5-mini`. |
| `DEX_AGENT_MODELS` | More models a session may pick, separated by commas. |
| `DEX_AGENT_SYSTEM_PROMPT` | The system prompt. |
| `DEX_AGENT_CONTEXT_TOKENS` | The context window that compaction works against. |
| `DEX_AGENT_MCP_CONFIG` | The MCP server configuration file. |
| `DEX_AGENT_SESSION_KEY` | The key that signs session tokens. |

Put each provider key in the Worker's environment, such as `examples/.env` for Python. The Worker reads it there. It never enters Flow state.

The example page has its own approval buttons. To approve from Dex Web instead, follow [Approve in Dex Web](#approve-in-dex-web) with the Flow type **AIAgentSession**.

## Limits

- Each model call and each tool call adds a Step round trip.
- `AgentEvents` is best effort. Read the session snapshot for the conversation.
- A failed `RunModel` repeats its model call.
- See [Limits for long sessions](/reference/agents/session-limits) for the server limits, and [At-most-once has one exception](/agent-frameworks/tool-calls#tool-runs-twice) for single-attempt tools.
