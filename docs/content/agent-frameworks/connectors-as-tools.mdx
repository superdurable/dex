# Connectors as Tools

An agent can call official [Connector](/concepts/connector) operations as tools. Each call runs in its own tool Step, with the Connector's credentials and idempotency key.

## How it works {#connectors-as-tools}

`ConnectorToolSource` offers the operations you name, and the agent takes it as a tool source (`tool_sources` in Python, `toolSources` in TypeScript). Each call runs one operation in its own tool Step, so the Call ID, the idempotency key, and credentials work as in a Connector Step. The Call ID stays the same on every attempt.

The Connect a Connector section shows the wiring for each framework; the [Built-in agent loop](/agent-frameworks/built-in-agent-loop#connect-connectors) shows it without one. The [Connector tools reference](/reference/agents/connector-tools) covers packages, tool names, result size, and connections.

### Which operations are offered {#connector-tools-offered}

The application names each operation an agent may use, and the Connector's manifest, `dex-connector.json`, must mark it as exposed for agents. Dex refuses any other operation when the agent is defined.

Dex checks the model's arguments against the operation's input schema first. A wrong or missing field fails the call, before the operation runs, with a message the model can correct.

### Effect classes {#connector-tools-effects}

The manifest decides whether a call can run again, and so which Step runs it:

| Operation | Effect class | Runs in |
| --- | --- | --- |
| Query | **read** | `CallTool`, with retries |
| Mutation that the manifest marks retry-safe (**agent.retry: safe**) | `idempotent_write` | `CallTool`, with retries |
| Any other Mutation | `non_idempotent_write` | `CallSingleAttemptTool`, once |

Retry-safe means a repeat with the same Call ID makes no second effect. A call whose attempts run out records **failed** for a Query and `outcome_unknown` for a Mutation.

A session's tool policy for a Connector tool changes only its approval. The effect class always comes from the manifest.

### Approval {#connector-tools-approval}

By default, a Connector tool waits for approval when its manifest recommends it (**agent.approval: recommended**), as for a refund, and other Mutations run directly. The application can override that for each tool, or pass a predicate that decides per call from its arguments, such as refunds above a limit. A predicate that raises asks for approval.

### Outcomes {#connector-tools-outcomes}

The operation ends in one of its branches, and the branch decides the tool call's record: **succeeded**, **failed**, or `outcome_unknown` when a write may have taken effect. [Outcomes](/reference/agents/connector-tools#outcomes) lists every branch and its record.

Reconcile `outcome_unknown` as for any tool; see [Reconcile outcome_unknown](/agent-frameworks/tool-calls#reconcile-outcome-unknown).

### Write order {#connector-tools-write-order}

Connector writes of one model response run one at a time, in the model's order. Reads, and calls of other tools, run in parallel. A write that needs approval asks for it only when its turn comes.

When a write fails, ends `outcome_unknown`, or is rejected, the later Connector writes of that response are skipped. Each records **failed** with **skipped** set and an error that starts "the tool did not run, so it is safe to call again", and Dex Web shows it as skipped.

### Crashes {#connector-tools-crashes}

A Worker crash during a Connector write sends the write at most once. A retry-safe write retries with the same idempotency key, or looks for the earlier write at the provider first; a single-attempt write records `outcome_unknown`. [Crashes](/reference/agents/connector-tools#crashes) shows each case.

## Connect a Connector {#connect-connectors}

The example adds the Slack tool `slack_post_thread_reply`, which replies in a Slack thread.

### The Slack tool in the example {#slack-connector-tool}

With the Slack connection **support-slack** configured, each example agent gets `slack_post_thread_reply`, the Slack operation `postThreadReply`. The Worker opens the connection from `DEX_CONNECTOR_CONFIG_FILE` locally, or from the **DEX_PROJECT_\*** settings when deployed; [Connections](/reference/agents/connector-tools#connector-tools-connection) covers both, and [the Slack tool in the examples](/reference/agents/connector-tools#slack-example) covers the Slack app.

`postThreadReply` is a single-attempt Mutation, so a post runs once, in `CallSingleAttemptTool`, and a Worker crash never sends it twice. The example also sets `requires_approval=True` (**requiresApproval: true** in TypeScript), so every post waits in `AwaitToolApproval` for a person.

    """Returns the Slack tool source, or no source when Slack is not configured."""
    if connection is None:
        return []
    return [

            # The manifest does not ask for approval; this agent asks before every post.

### How a call runs {#connector-tool-calls}

Each call of `slack_post_thread_reply` runs once, in its own `CallSingleAttemptTool` Step, after a person approves it, as [the Slack tool](#slack-connector-tool) explains. Your framework hands the call to that Step this way:

<FrameworkTabs>
<FrameworkTab framework="claude-agent-sdk">

In the Claude Agent SDK, a Connector tool call never runs inside the CLI, not even a read. Every call ends the segment and runs in its own tool Step, because the Connector needs that Step for its Call ID. The resumed CLI then gets the recorded result. The CLI sees the tool as `mcp__tools__slack_post_thread_reply`; tool policies, approvals, and records use `slack_post_thread_reply`.

One call of a model response at a time leaves the turn to run in its tool Step. The adapter refuses a later write of that response inside the turn, so it never runs and leaves no record; the model reads the earlier write's result and then decides whether to call the later write again. Keep Connector tools out of `allowed_tools` (`allowedTools`): their calls must leave the CLI, so such an entry fails the `RunModel` attempt.

</FrameworkTab>
<FrameworkTab framework="google-adk">

The adapter adds one `SourceToolset` to the tools of every `LlmAgent` in the agent tree. It offers the Connector tools only inside the runner's `RunModel`. Elsewhere, the agents run unchanged. The agent's `before_tool_callback` chain still sees each call first.

</FrameworkTab>
<FrameworkTab framework="langchain-langgraph">

`DurableToolCallMiddleware` adds the Connector tools to every model request of a `create_agent` agent, after the agent's own tools. A custom graph binds `get_current_tool_source_tools()` next to its own tools in its model node, and `durable_tool_node` defers their calls like any other. The tool bodies never run inside the graph.

</FrameworkTab>
<FrameworkTab framework="mastra">

The adapter passes the Connector tools to Mastra as client tools without **execute**. A call never runs inside the model call. Mastra approval settings do not apply to it; the source decides approval. With tool sources, a `toolPolicies` entry never makes a tool one that Mastra runs itself; only `mastraRunToolNames` does.

</FrameworkTab>
<FrameworkTab framework="openai-agents-sdk">

Every agent of the graph offers the Connector tools after its own tools. In Python, the adapter builds a function tool for each tool in the source's cached listing, its `cached_tools()`; `ConnectorToolSource` caches its whole listing. In TypeScript, they are non-strict function tools, and a tool's `needsApproval` and input guardrails do not apply to them. A call never runs inside the SDK; the source decides approval.

</FrameworkTab>
<FrameworkTab framework="pi">

Dex runs the loop, so a Connector tool is a tool of the built-in agent loop, next to the Pi tools. A call never runs inside the model call; it runs in its tool Step, and the source decides approval.

</FrameworkTab>
<FrameworkTab framework="pydantic-ai">

The adapter passes the Connector tools to each run as an `ExternalToolset`. Pydantic AI never runs an external tool, so a Connector tool call ends the run, and the call runs in its tool Step.

</FrameworkTab>
<FrameworkTab framework="vercel-ai-sdk">

The adapter offers the Connector tools after the agent's tools, as AI SDK tools without **execute**. A call never runs inside the model call. AI SDK `needsApproval` does not apply to it; the source decides approval.

</FrameworkTab>
</FrameworkTabs>

### Configure the connection {#configure-connector-connection}

To try it, start the example with `DEX_CONNECTOR_CONFIG_FILE` set. Then ask the agent to reply in a Slack thread, with the channel ID and the thread timestamp:

```text
Reply in Slack thread C0123456789 1710000000.000100: Order 1002 ships on Thursday.
```

The post waits for approval, like `cancel_order`.

[Connections](/reference/agents/connector-tools#connector-tools-connection) explains where the Worker finds the **support-slack** connection and what the Slack app needs.
