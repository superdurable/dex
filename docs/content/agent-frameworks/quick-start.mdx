# Agent Quick Start

Run an agent built with your framework as a durable Dex session, then stop it in the middle of a conversation and watch it carry on. It takes about 10 minutes.

Building a new agent without a framework? Start with the [Built-in Agent Loop](/agent-frameworks/built-in-agent-loop).

## What you will build {#what-you-will-build}

A small order support agent. It has two tools on an in-memory order desk:

- **look_up_order** reads an order. It is a read, so Dex may retry it.
- **cancel_order** cancels an order that has not shipped. It is a write, so it runs at most once, and only after a person approves it.

You see what Dex adds to a plain agent, run the example, and ask the agent to cancel an order. While the cancellation waits for approval, you stop the Worker and start it again. Then you approve the call and check what ran. Last, you kill the Worker in the middle of a tool call and see what Dex runs again.

## Before you start {#before-you-start}

- **dexcli**, installed as [Run Locally](/components/run-locally) shows.
- Git, to get the example.
- **Python 3.11 or later with uv**, or **Node.js with npm**, depending on your framework.
- An API key for your framework's model provider, such as **OPENAI_API_KEY** or **ANTHROPIC_API_KEY**. Most Python examples can run on a local demo model without a key; step 3 says which.
- **jq**, to read the JSON that the example returns.

## 1. Get the example {#get-the-example}

Clone the Dex repository. The examples live under **examples**:

```bash
git clone https://github.com/superdurable/dex.git
cd dex
```

Open each terminal in the later steps in this folder. [Use it in your own agent](#use-it-in-your-own-agent) lists the packages to install in your own project.

## 2. Make your agent durable {#make-it-durable}

Dex adds one call to a plain agent. The call wraps the agent in a session Flow and gives each tool a policy. The tools themselves stay plain framework tools.

**look_up_order** is a read. **cancel_order** is a non-idempotent write, so it runs at most once, and by default it waits for approval. [Require approval](/agent-frameworks/tool-calls#require-approval) explains the default.

<SdkSnippet lang="typescript">

```typescript
return createClaudeAgentSessionFlow(
  {
    options: {
      model,
      systemPrompt: orderSupportInstructions,
      // No Claude Code built-in tools: the agent uses only the order tools.
      tools: [],
      // Settings files could approve a tool before Dex asks for approval.
      settingSources: [],
      // Only the variables in cliEnvironment reach the CLI, so no other Claude credential can take over.
      env: { ...cliEnvironment },
    },
    customTools: [lookUpOrder, cancelOrder],
    toolPolicies: {
      look_up_order: { effect: "read" },
      cancel_order: { effect: "non_idempotent_write" },
    },
    toolSources: createSlackConnectorToolSources(slack),
  },
  claudeAgentSdkOrderSupportFlowType,
);
```

The example turns off every built-in Claude Code tool, so the agent uses only the order tools. It also loads no settings files, so no settings file can approve a tool before Dex asks.

<SdkTabs

<SdkSnippet lang="python">

```bash
base=http://127.0.0.1:8081/products/agent-harnesses/claude-agent-sdk
session=$(curl -s -X POST "$base/sessions" -H 'Content-Type: application/json' -d '{}')
id=$(echo "$session" | jq -r .session_id)
token=$(echo "$session" | jq -r .session_token)
curl -s -X POST "$base/messages" -H 'Content-Type: application/json' \
  -H "X-Agent-Session-Token: $token" -d "{\"session_id\": \"$id\", \"text\": \"Cancel order 1002\"}"
until interrupt=$(curl -s "$base/snapshot?session_id=$id" -H "X-Agent-Session-Token: $token" \
  | jq -re '.snapshot.pending_interrupts[0].interrupt_id'); do sleep 1; done
```

## 4. Stop the Worker while the agent waits {#stop-the-worker}

The agent looked up order 1002 and asked to cancel it. **cancel_order** needs approval, so the session waits in **AwaitToolApproval**. The wait holds no Worker.

1. In the second terminal, stop the example with Ctrl-C. The session keeps waiting in Dex.
2. In the same terminal, run the command that started the example again. Leave **dexcli dev** running in the first terminal.
3. Open Dex Web at **http://127.0.0.1:8802**. Open the session's run. Its Flow ID is the session ID, which **$id** holds in the third terminal.
4. Select the **Agent session** tab. Set **Working as** to **order-support.operate**, the permission you rendered into the session graph. Then select **Approve** on the **cancel_order** card.
5. Open the **Timeline**. **look_up_order** and the model calls before the restart ran once. **cancel_order** ran once, after the approval. The agent answered from the recorded results.

## 5. Stop it while a tool runs {#stop-while-a-tool-runs}

Step 4 stopped the Worker while nothing ran. A crash in the middle of a tool call is the harder case. The example can slow each tool call down, so you have time to stop it.

1. In the second terminal, stop the example. Start it again with a 20-second delay on each tool call. Also set a fixed session key, so the session token from the third terminal still works after a restart:

Keep the model variables and the provider key that your framework needs from step 3.

2. In the third terminal, start a new session with the step 3 commands. Change the message to **Look up order 1001**, and skip the last command, which waits for an approval.
3. Within 20 seconds, kill the example as a crash would. Ctrl-C is not a crash: it lets a running call finish first.

<SdkTabs>
<SdkSnippet lang="python">

<SdkSnippet lang="typescript">


4. Start the example again with the command from item 1. About 20 seconds later, the agent answers with the order.
5. Check how the tool call ran:

```bash
dexcli flow history --all "$id" | jq '.events[]
  | select(.payload.context.stepType == "CallTool")
  | .payload.context | {finalAttempt, failure: .lastFailureInfo.details.detail}'
```

**finalAttempt** is **2**. The first attempt failed because the Worker disconnected. **look_up_order** is a read, so Dex ran it again on the new Worker. The model call before it did not run again.

Now try a write. Ask to cancel order 1002 with the full step 3 commands, and approve it in Dex Web as in step 4. Within 20 seconds of approving, kill the example and start it again.

**cancel_order** is a non-idempotent write, so Dex does not run it a second time. The call records **outcome_unknown**, and the agent tells the user so. With the demo model, the reply reads: "The tool call's outcome is unknown: it stopped without returning a result, so it may or may not have taken effect. It will not be retried automatically." Your application then checks the order system before anyone tries again. [Reconcile outcome_unknown](/agent-frameworks/tool-calls#reconcile-outcome-unknown) shows how.

You have run your first durable agent. Its Worker went away in the middle of a conversation, and the session lost nothing and repeated nothing.

### Wire the session into your app {#wire-it-into-your-app}

Your app needs the same four pieces as the example, whatever the framework:

1. A **Registry** with your session Flow, a **Worker** that runs its Steps, and a **Client** that calls it. The Worker connects out to Dex, so it needs no open port. Both open a blob cache, a local cache for large values; [Registry and blob cache](/components/application#blob-cache) explains it.
2. A route that starts a session. The session ID is the Flow ID.
3. A route that sends a user message, and one that reads the session snapshot with the agent's reply. To stream the reply as it is written, read the [AgentEvents Stream](/reference/agents/event-stream#read-the-stream).
4. A route that approves or rejects a waiting tool call. [Approve from your application](/agent-frameworks/approvals#approve-from-your-application) covers it.
