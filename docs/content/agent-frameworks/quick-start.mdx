# Agent Quick Start

Run the agent you already built with your framework as a durable Dex session. Pick your framework in any step, and every step on the page follows that choice.

Building a new agent without a framework? Start with the [Built-in Agent Loop](/agent-frameworks/built-in-agent-loop).

## How your framework runs on Dex {#how-it-runs}

<FrameworkTabs>
<FrameworkTab framework="claude-agent-sdk">

The Claude Agent SDK runs Claude Code as an agent. Its agent loop runs in the Claude Code CLI, a subprocess of the Worker. The Dex adapter runs that loop inside a durable session. It is available for Python and TypeScript.

**When to use it**

Use it when you want the Claude Code agent loop, its context management, and its tools. Use it when your agent already uses the Claude Agent SDK.

Use the [built-in agent loop](/agent-frameworks/built-in-agent-loop) when you want one model call per Step, parallel tool Steps, or Dex compaction.

**How a session runs**

Claude Code runs a whole turn, so the adapter splits a turn into segments. One **RunModel** Step runs the CLI for one segment. Model calls run inside the segment. So do read tools: a deferred read would restart the CLI. A Connector tool call is the exception: it always leaves the segment, even a read. See [Connect Connectors](/agent-frameworks/quick-start/?framework=claude-agent-sdk#connect-connectors).

A write tool call ends the segment. It waits in **AwaitToolApproval** when it needs approval. Then it runs in its own Step: **CallTool** for an idempotent write, **CallSingleAttemptTool** for any other write. **ResumeTurn** then returns to **RunModel**, which resumes the same Claude session. The CLI gets the recorded result and does not run the tool again.

A failed segment retries, up to three attempts, and reruns whole. Model calls and reads inside it run again. A write that ran in its own Step never runs again.

A turn that looks up an order runs one **RunModel** Step. A turn that cancels an order runs **RunModel**, **AwaitToolApproval**, **CallSingleAttemptTool**, **ResumeTurn**, and **RunModel**.

</FrameworkTab>
<FrameworkTab framework="google-adk">

Google ADK, the Agent Development Kit, builds agents and multi-agent trees for Gemini and other models. The Dex adapter runs an ADK agent inside a durable session. It is available for Python.

**When to use it**

Use it when your agent already uses Google ADK, including sequential, loop, and parallel agents. Keep the agent tree and its tools, and let Dex own the session.

**How a session runs**

The adapter adds a plugin to the ADK App. For each tool call, the plugin asks ADK for a confirmation, so ADK pauses before the tool runs. Each **RunModel** Step makes one model call and stores the turn's ADK events.

Each tool call runs in its own Step, in parallel: **CallTool** for a read or an idempotent write, **CallSingleAttemptTool** for any other write. A call that needs approval waits in **AwaitToolApproval** first. The tool Step runs the tool once. The next **RunModel** confirms the paused calls, and the plugin returns the recorded results instead of running the tools again.

A turn that looks up an order runs **RunModel**, **CallTool**, **ResumeTurn**, and **RunModel**.

</FrameworkTab>
<FrameworkTab framework="langchain-langgraph">

LangChain **create_agent** builds a tool-calling agent on LangGraph. The Dex adapter runs a **create_agent** agent or a custom LangGraph graph inside a durable session. It is available for Python.

**When to use it**

Use it when your agent already uses LangChain **create_agent** or a LangGraph graph. Keep the graph, its middleware, and its tools, and let Dex own the session.

**How a session runs**

**DurableToolCallMiddleware** stops each tool call with a LangGraph interrupt, so no tool runs inside **RunModel**. The **RunModel** Step runs the graph to its next tool calls, usually with one model call, and stores the graph checkpoint.

Each tool call runs in its own Step, in parallel: **CallTool** for a read or an idempotent write, **CallSingleAttemptTool** for any other write. A call that needs approval waits in **AwaitToolApproval** first. The tool Step validates the arguments and calls the tool once. The next **RunModel** restores the checkpoint and resumes the graph with the recorded results.

A custom graph builds its tool node with **durable_tool_node** instead of **ToolNode**. Its state must hold the conversation as LangChain messages.

A turn that looks up an order runs **RunModel**, **CallTool**, **ResumeTurn**, and **RunModel**.

</FrameworkTab>
<FrameworkTab framework="mastra">

Mastra is a TypeScript framework for agents, tools, and workflows. The Dex adapter runs a Mastra agent inside a durable session. It is available for TypeScript.

**When to use it**

Use it when your agent already uses Mastra. Keep the agent, its tools, and its model router, and let Dex own the session.

**How a session runs**

Every agent tool, read tools included, goes to Mastra as a client tool. So Mastra stops after the model call with the tool calls. Each **RunModel** Step makes one model call.

Each tool call runs the agent's original tool once, in its own Step, in parallel: **CallTool** for a read or an idempotent write, **CallSingleAttemptTool** for any other write. A call that needs approval waits in **AwaitToolApproval** first. The next **RunModel** adds the recorded results and calls the model again.

A turn that looks up an order runs **RunModel**, **CallTool**, **ResumeTurn**, and **RunModel**.

</FrameworkTab>
<FrameworkTab framework="openai-agents-sdk">

The OpenAI Agents SDK defines an agent with instructions, function tools, and handoffs. The Dex adapter runs the SDK's runner inside a durable session. It is available for Python and TypeScript.

**When to use it**

Use it when your agent already uses the OpenAI Agents SDK, with or without handoffs. Keep the SDK's agent definition, tools, and guardrails, and let Dex own the session.

**How a session runs**

The adapter copies the agent graph once and intercepts every function tool. So the SDK stops right after each model call and returns the tool calls the model asks for. Each **RunModel** Step makes one model call.

Each function tool call runs in its own Step, in parallel: **CallTool** for a read or an idempotent write, **CallSingleAttemptTool** for any other write. A call that needs approval waits in **AwaitToolApproval** first. The next **RunModel** restores the SDK's run state and gives it the recorded results. The tool does not run again.

A handoff is not a function tool. It runs inside **RunModel**, so a Step that hands off also makes the next agent's model call.

A turn that looks up an order runs **RunModel**, **CallTool**, **ResumeTurn**, and **RunModel**.

</FrameworkTab>
<FrameworkTab framework="pydantic-ai">

Pydantic AI defines a typed agent with tools, dependencies, and output types. The Dex adapter runs a Pydantic AI agent inside a durable session. It is available for Python.

**When to use it**

Use it when your agent already uses Pydantic AI. Keep the agent, its tools, and its capabilities, and let Dex own the session. The adapter replaces Pydantic AI's own durable execution integrations.

**How a session runs**

Each **RunModel** Step runs the agent with a capability that marks every function tool as an external tool. Pydantic AI never runs an external tool, so the run ends right after the model asks for tools.

Each tool call runs in its own Step, in parallel: **CallTool** for a read or an idempotent write, **CallSingleAttemptTool** for any other write. A call that needs approval waits in **AwaitToolApproval** first. The tool Step runs the tool once, through the agent, so the agent's tool hooks run there. The next **RunModel** resumes the run with the recorded results.

A turn that looks up an order runs **RunModel**, **CallTool**, **ResumeTurn**, and **RunModel**.

</FrameworkTab>
<FrameworkTab framework="vercel-ai-sdk">

The Vercel AI SDK gives TypeScript one API for many model providers, with typed tools. The Dex adapter runs an AI SDK agent definition inside a durable session. It is available for TypeScript.

**When to use it**

Use it when your TypeScript application already uses AI SDK models and tools. Keep the model, the tools, and **stopWhen**, and let Dex own the session.

**How a session runs**

Every tool reaches the model without its **execute**, so the AI SDK returns the tool calls instead of running them. Each **RunModel** Step makes one model call with **streamText**.

Each tool call runs the tool's original **execute** in its own Step, in parallel: **CallTool** for a read or an idempotent write, **CallSingleAttemptTool** for any other write. A call that needs approval waits in **AwaitToolApproval** first. The next **RunModel** adds the recorded results, checks **stopWhen**, and calls the model again.

A turn that looks up an order runs **RunModel**, **CallTool**, **ResumeTurn**, and **RunModel**.

</FrameworkTab>
</FrameworkTabs>

## The example {#the-examples}

Every framework tab uses the same order support agent. It has two tools on an in-memory order desk:

| Tool | Policy | What Dex does |
| --- | --- | --- |
| **look_up_order** | read | Runs without approval and retries on failure. |
| **cancel_order** | non-idempotent write | Waits in **AwaitToolApproval**, then runs at most once. |

**cancel_order** cancels an order only while it is still processing.

The Python agents are under [examples/python/agent-harnesses](https://github.com/superdurable/dex/tree/main/examples/python/agent-harnesses). The TypeScript agents are under [examples/typescript/src/products/agent-harnesses](https://github.com/superdurable/dex/tree/main/examples/typescript/src/products/agent-harnesses).

```python
def build_claude_agent_sdk_order_support_flow(
    order_desk: OrderDesk, model: str, slack_connection: slack.Connection | None
) -> AgentSessionFlow:
    """Builds the session Flow; ``model`` is a Claude model name, such as "claude-opus-5-5"."""

    # The tools are closures, so they call the OrderDesk passed in here.
    @tool(
        "look_up_order",
        "Look up one order by its order ID and return its items and status.",
        {"order_id": str},
    )
    async def look_up_order(arguments: dict[str, Any]) -> dict[str, Any]:
        order = order_desk.describe_order(arguments["order_id"])
        return {"content": [{"type": "text", "text": order}]}

    @tool(
        "cancel_order",
        "Cancel one order that has not shipped yet.",
        {"order_id": str, "reason": str},
    )
    async def cancel_order(arguments: dict[str, Any]) -> dict[str, Any]:
        result = order_desk.cancel_order(arguments["order_id"], arguments["reason"])
        return {"content": [{"type": "text", "text": result}]}

    # Every session gets the same options, so the factory does not read its context.
    def build_options(context: ClaudeAgentOptionsContext) -> ClaudeAgentOptions:
        return ClaudeAgentOptions(
            model=model,
            env=build_claude_cli_environment(os.environ),
            system_prompt=ORDER_SUPPORT_INSTRUCTIONS,
            # No Claude Code built-in tools: the agent uses only the order tools.
            tools=[],
            # Settings files could approve a tool before Dex asks for approval.
            setting_sources=[],
        )

    return claude_agent_session_flow(
        build_options,
        [look_up_order, cancel_order],
        flow_type=CLAUDE_AGENT_SDK_ORDER_SUPPORT_FLOW_TYPE,
        tool_sources=build_slack_tool_sources(slack_connection),
        tool_policies={
            "look_up_order": ToolPolicy(ToolEffect.READ),
            "cancel_order": ToolPolicy(ToolEffect.NON_IDEMPOTENT_WRITE),
        },
    )
```

</SdkSnippet>

```typescript
export function createClaudeAgentSdkOrderSupportFlow(
  orderDesk: OrderDesk,
  model: string,
  cliEnvironment: Readonly<Record<string, string>>,
  slack: Connection | undefined,
): AgentSessionFlow {
  const lookUpOrder = tool(
    "look_up_order",
    "Look up one order by its order ID and return its items and status.",
    { order_id: z.string() },
    async ({ order_id }) => ({ content: [{ type: "text", text: orderDesk.describeOrder(order_id) }] }),
  );
  const cancelOrder = tool(
    "cancel_order",
    "Cancel one order that has not shipped yet.",
    { order_id: z.string(), reason: z.string() },
    async ({ order_id, reason }) => ({ content: [{ type: "text", text: orderDesk.cancelOrder(order_id, reason) }] }),
  );
  return createClaudeAgentSessionFlow(
    {
      options: {
        model,
        systemPrompt: orderSupportInstructions,
        // No Claude Code built-in tools: the agent uses only the order tools.
        tools: [],
        // Settings files could approve a tool before Dex asks for approval.
        settingSources: [],
        // Only the variables in cliEnvironment reach the CLI, so no other Claude credential can take over.
        env: { ...cliEnvironment },
      },
      customTools: [lookUpOrder, cancelOrder],
      toolPolicies: {
        look_up_order: { effect: "read" },
        cancel_order: { effect: "non_idempotent_write" },
      },
      toolSources: createSlackConnectorToolSources(slack),
    },
    claudeAgentSdkOrderSupportFlowType,
  );
}
```

```typescript
  orderDesk: OrderDesk,
  model: string | Model,
  slack: Connection | undefined,
): AgentSessionFlow {
  const lookUpOrder = tool({
    name: "look_up_order",
    description: "Look up one order by its order ID and return its items and status.",
    parameters: z.object({ order_id: z.string() }),
    // Without errorFunction: null, tool() turns every thrown error into model-visible text.
    errorFunction: null,
    execute: ({ order_id }) => orderDesk.describeOrder(order_id),
  });
  const cancelOrder = tool({
    name: "cancel_order",
    description: "Cancel one order that has not shipped yet.",
    parameters: z.object({ order_id: z.string(), reason: z.string() }),
    errorFunction: null,
    execute: ({ order_id, reason }) => orderDesk.cancelOrder(order_id, reason),
  });
  const agent = new Agent({
    name: "OrderSupport",
    instructions: orderSupportInstructions,
    model,
    tools: [lookUpOrder, cancelOrder],
  });
```

```python
    order_desk: OrderDesk, model: str | Model, slack_connection: slack.Connection | None
```

## Serve the session routes {#session-routes}

Every harness serves the same HTTP routes, so you can try them side by side. Each route is one call on the session Flow: start a session, send a message, or resolve an approval.

Starting a session returns a session token: an HMAC of the session ID under **DEX_AGENT_SESSION_KEY**. Every other route checks the token in the **X-Agent-Session-Token** header and answers 403 without it. Without **DEX_AGENT_SESSION_KEY**, the example picks a random key, so a restart ends every token. A real application uses its own sign-in instead.

<FrameworkTabs>

Every harness serves these same routes. [Session routes](/agent-frameworks/quick-start#session-routes) explains them and the session token.

```python
    @blueprint.post("/sessions")
    async def start_session() -> Response:
        # The server picks the session ID, so a caller cannot claim an existing session.
        session_id = f"{harness_name}-order-support-{uuid.uuid4()}"
        await sessions.start_session(session_id)
        session_token = sign_session_id(app_state.config.session_key, session_id)
        return jsonify(session_id=session_id, session_token=session_token)

    @blueprint.post("/messages")
    async def send_user_message() -> Response:
        body, session_id = await session_request()
        accepted = await sessions.send_user_message(session_id, _required_string(body, "text"))
        return jsonify(accepted=accepted)

    @blueprint.post("/interrupts/resolve")
    async def resolve_interrupt() -> Response:
        body, session_id = await session_request()
        interrupt_id = _required_string(body, "interrupt_id")
        if not isinstance(approved := body.get("approved"), bool):
            raise BadRequest("approved must be a boolean")
        rejection_message = body.get("rejection_message")
        if rejection_message is not None and not isinstance(rejection_message, str):
            raise BadRequest("rejection_message must be a string")
        accepted = await sessions.resolve_interrupt(
            session_id, interrupt_id, approved=approved, rejection_message=rejection_message
        )
        return jsonify(accepted=accepted)

    @blueprint.get("/snapshot")
    async def get_agent_snapshot() -> Response:
        session_id = request.args.get("session_id", "")
        if not session_id:
            raise BadRequest("session_id is required")
        authorize_session(session_id)
        try:
            snapshot = await read_agent_event_stream_snapshot(
                app_state.client, example.session_flow, session_id
            )
        except FlowNotActiveOrNotFoundError as error:
            raise NotFound("the agent session is missing or no longer retained") from error
        return jsonify(snapshot.to_json())
```

## Approve in Dex Web {#approve-in-dex-web}

While an example runs, you can approve a call in Dex Web instead of with an HTTP request:

1. Open the session's run. Its Flow ID is the session ID.
2. Select the **Agent session** tab.
3. Set **Working as** to **order-support.operate**, the permission you rendered into the session graph.
4. Select **Approve** or **Reject** on the **cancel_order** card. Dex Web calls **resolve_interrupt** for you.

Dex Web shows this tab only when it started with the session graph. Each framework tab of [Run it locally](#run-it-locally) renders the graph before it starts Dex. For production, see [Show sessions in Dex Web](/reference/agents/dex-web).

Instead of the last command, you can approve the call in Dex Web. Follow the steps in [Approve in Dex Web](/agent-frameworks/quick-start#approve-in-dex-web).

## Connect Connectors {#connect-connectors}

The agent can call [Connector](/concepts/connector) operations as tools, as [Connectors as tools](/agent-frameworks/tools-and-approvals#connectors-as-tools) describes. The example adds the Slack tool **slack_post_thread_reply**, which replies in a Slack thread.

### The Slack tool in the example {#slack-connector-tool}

When the project configuration has the Slack connection **support-slack**, each example agent also gets **slack_post_thread_reply**. This tool is the Slack Connector operation **postThreadReply**, and the agent uses it to reply in a Slack thread. The Worker opens the connection from **DEX_CONNECTOR_CONFIG_FILE** in local development, or from the **DEX_PROJECT_\*** settings when deployed. [Connections](/reference/agents/connector-tools#connector-tools-connection) covers both. [The Slack tool in the examples](/reference/agents/connector-tools#slack-example) covers what happens without the connection and what the Slack app needs.

Each call runs one Slack operation in its own tool Step, through the Connector SDK. The call keeps the Connector's Call ID and idempotency key. [Which operations are offered](/agent-frameworks/tools-and-approvals#connector-tools-offered) covers how an operation becomes a tool and how Dex checks its arguments.

The Connector's manifest decides whether a call can run again. **postThreadReply** is a Mutation that its manifest does not mark retry-safe, so the call runs once, in **CallSingleAttemptTool**. A Worker crash never sends the post twice. See [Crashes](/agent-frameworks/tools-and-approvals#connector-tools-crashes).

Slack's manifest does not ask for approval of **postThreadReply**. So the example passes **requires_approval=True** in Python and **requiresApproval: true** in TypeScript, and every post waits in **AwaitToolApproval** until a person approves it. [Approval](/agent-frameworks/tools-and-approvals#connector-tools-approval) covers how the manifest and the application decide approval.

When one model response asks for several Connector writes, they run one at a time, in order. See [Write order](/agent-frameworks/tools-and-approvals#connector-tools-write-order).

### How a call runs {#connector-tool-calls}

<FrameworkTabs>
<FrameworkTab framework="claude-agent-sdk">

Each call of **slack_post_thread_reply** runs once, in its own **CallSingleAttemptTool** Step, after a person approves it. [The Slack Connector tool](/agent-frameworks/quick-start#slack-connector-tool) explains why.

In the Claude Agent SDK, a Connector tool call never runs inside the CLI, not even a read. Every call ends the segment and runs in its own tool Step, because the Connector needs that Step for its Call ID. The resumed CLI then gets the recorded result. The CLI sees the tool as **mcp__tools__slack_post_thread_reply**; tool policies, approvals, and records use **slack_post_thread_reply**.

A later write of the same reply is refused inside the turn and leaves no record; see [Write order](/agent-frameworks/tools-and-approvals#connector-tools-write-order). Do not list a Connector tool in **allowed_tools** (**allowedTools**): its calls must leave the CLI, so such an entry fails the **RunModel** attempt.

</FrameworkTab>
<FrameworkTab framework="google-adk">

Each call of **slack_post_thread_reply** runs once, in its own **CallSingleAttemptTool** Step, after a person approves it. [The Slack Connector tool](/agent-frameworks/quick-start#slack-connector-tool) explains why.

The adapter adds one **SourceToolset** to the tools of every **LlmAgent** in the agent tree. It offers the Connector tools only inside the runner's **RunModel**. Elsewhere, the agents run unchanged. The agent's **before_tool_callback** chain still sees each call first.

</FrameworkTab>
<FrameworkTab framework="langchain-langgraph">

Each call of **slack_post_thread_reply** runs once, in its own **CallSingleAttemptTool** Step, after a person approves it. [The Slack Connector tool](/agent-frameworks/quick-start#slack-connector-tool) explains why.

**DurableToolCallMiddleware** adds the Connector tools to every model request of a **create_agent** agent, after the agent's own tools. A custom graph binds **get_current_tool_source_tools()** next to its own tools in its model node, and **durable_tool_node** defers their calls like any other. The tool bodies never run inside the graph.

</FrameworkTab>
<FrameworkTab framework="mastra">

Each call of **slack_post_thread_reply** runs once, in its own **CallSingleAttemptTool** Step, after a person approves it. [The Slack Connector tool](/agent-frameworks/quick-start#slack-connector-tool) explains why.

The adapter passes the Connector tools to Mastra as client tools without **execute**. A call never runs inside the model call. Mastra approval settings do not apply to it; the source decides approval. With tool sources, a **toolPolicies** entry never makes a tool one that Mastra runs itself; only **mastraRunToolNames** does.

</FrameworkTab>
<FrameworkTab framework="openai-agents-sdk">

Each call of **slack_post_thread_reply** runs once, in its own **CallSingleAttemptTool** Step, after a person approves it. [The Slack Connector tool](/agent-frameworks/quick-start#slack-connector-tool) explains why.

Every agent of the graph offers the Connector tools after its own tools. In Python, the adapter builds a function tool for each tool in the source's cached listing, its **cached_tools()**; **ConnectorToolSource** caches its whole listing. In TypeScript, they are non-strict function tools, and a tool's **needsApproval** and input guardrails do not apply to them. A call never runs inside the SDK; the source decides approval.

</FrameworkTab>
<FrameworkTab framework="pydantic-ai">

Each call of **slack_post_thread_reply** runs once, in its own **CallSingleAttemptTool** Step, after a person approves it. [The Slack Connector tool](/agent-frameworks/quick-start#slack-connector-tool) explains why.

The adapter passes the Connector tools to each run as an **ExternalToolset**. Pydantic AI never runs an external tool, so a Connector tool call ends the run, and the call runs in its tool Step.

</FrameworkTab>
