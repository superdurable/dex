# Durable Agents

This page covers running [agent framework](/agent-frameworks) sessions in
production. One Flow execution is one agent session. Every model call is a
**RunModel** Step, and every tool call is its own Step. Server limits on this
page are server-zd defaults. See [Server reference](/reference/server/)
and [Application](/primitives/components/application) for the rest of the setup.

## Install the packages {#install}

Install an adapter with its framework. Python adapters are on PyPI. Each one
brings in the **dex-agents** core and the Dex SDK it supports. They need Python
3.11 or later.

```bash
pip install dex-agents-pydantic-ai "pydantic-ai-slim[openai]"
pip install dex-agents-langgraph
pip install dex-agents-openai-agents
pip install dex-agents-google-adk
pip install dex-agents-claude-agent-sdk
```

TypeScript adapters are on npm. The core and the Dex SDK are peer packages, so
the application owns exactly one copy of each. They need Node 22 or 24.

```bash
npm i @superdurable/dex-agents-vercel-ai @superdurable/dex-agents @superdurable/dex ai zod
npm i @superdurable/dex-agents-mastra @superdurable/dex-agents @superdurable/dex @mastra/core zod
npm i @superdurable/dex-agents-openai-agents @superdurable/dex-agents @superdurable/dex @openai/agents zod
npm i @superdurable/dex-agents-claude-agent-sdk @superdurable/dex-agents @superdurable/dex zod
```

To write a runner of your own, install only the core:

```bash
pip install dex-agents==0.2.0
npm i @superdurable/dex-agents@0.2.0 @superdurable/dex@1.35.0
```

All agents packages share one version line. A Python adapter requires the core
of the same version. An npm adapter peer-depends on it. Each release pins the
Dex SDK it supports and the framework range it was tested with; see the
[compatibility table](https://github.com/superdurable/dex/blob/main/agents/README.md#versions-and-compatibility).
The packages are before 1.0, so a minor release may change their API. Pin exact
versions in your lockfile and read the
[changelog](https://github.com/superdurable/dex/blob/main/agents/CHANGELOG.md)
before an upgrade.

Build the same session Flow in every process that starts sessions or calls
their RPCs.

## Stream backend {#stream-backend}

Live model text, reasoning summaries, tool progress, and approval events go to
the **AgentEvents** [Stream](/primitives/stream). **streamStore.backend**
defaults to **memory** for both **dexcli dev** and a production server, so live
events need no extra server configuration. Do not set the backend to
**disabled** for agents. With **disabled**, a Step write is dropped without
failing the Step, and Client writes and Stream reads fail with
**FAILED_PRECONDITION**. The default is equivalent to:

```yaml
streamStore:
  backend: memory
```

The memory backend keeps Streams in the memory of the active server-zd process.
A server-zd cluster has one active process, so a single node needs nothing more.
A [standby](/reference/server/high-availability#hot-standby) holds no Streams. A
process starts with empty Streams whenever it becomes active: after a restart,
a standby takeover, or a [step down](/reference/server/high-availability#step-down). A standby answers Stream calls with **UNAVAILABLE**, and clients
reconnect to the active process.

Losing Stream data never loses a session. The conversation, tool calls, and
pending approvals live in Attributes. A client that misses events reloads the
session with the **get_agent_snapshot** RPC and keeps reading the Stream from
there. After **turn_completed** or **turn_failed**, a client replaces the turn's
live text with the stored messages. Never treat the Stream as the record of
what happened.

## Size AgentEvents {#size-agent-events}

**AgentEvents** has one capacity for each Flow type and Stream name. Every
session of the agent shares it; it is not a per-session budget. The default is
10 MiB. Set it with **event_stream_capacity_bytes** in the Python
**AgentSessionOptions** or **eventStreamCapacityBytes** in the TypeScript
**createAgentSessionFlow** options.

The server charges each message its serialized value, Flow ID, and source, plus
512 bytes. When usage reaches 90 percent of the capacity, a background trimmer
removes the oldest messages of all sessions until usage is at 80 percent. If
trimming falls behind and usage reaches the capacity, writes are rejected. A
Step drops a rejected write without failing. Size the capacity so it holds the
newest turn of every session that a client watches:

```text
bytes per turn = messages per turn × (average message bytes + 512)
capacity       ≥ concurrent sessions × bytes per turn ÷ 0.8
```

Say a turn writes 200 messages of about 300 bytes each, counting the Flow ID
and source. That is about 162 KB per turn. With 500 sessions streaming at once,
live events take about 81 MB. Dividing by 0.8 gives about 102 MB, so a capacity
of 128 MiB keeps the newest turn of every session. The default 10 MiB keeps
about 50 such turns.

The fixed 512 bytes dominate small text deltas. The Python core writes one
Stream message for each text delta that a runner writes. The TypeScript core
merges consecutive deltas for up to 100 ms or 1,024 characters. Expect more
messages per turn from Python adapters.

One Stream message is at most 100 KiB, set by **streamStore.maxMessageBytes**.
A larger write is dropped. The memory backend keeps every Stream in server
memory, so plan server memory for the sum of the capacities of every agent Flow
type and other Stream.

## Size Workers {#size-workers}

Each running model call, tool call, and RPC handler holds one Worker task slot.
A session that waits for a user message, an approval, or tool results holds
none; the wait lives in Dex Server. Size each Worker pool for the turns that
call the model at the same time, plus the tool calls that run at the same time,
plus the RPC reserve.

The tool calls of one model response run as parallel Steps. Give a Worker at
least enough slots for the largest batch of tool calls that a model makes. The
default task limit is the CPU count. Model calls mostly wait on the network, so
agent Workers usually need a higher **maxConcurrentTasks**. See
[capacity and shutdown](/reference/server/workers#capacity-and-shutdown) for the
option names in each SDK.

Keep the [RPC reserve](/reference/server/workers#reserved-rpc-capacity). A UI
calls **get_agent_snapshot**, **send_user_message**, and **resolve_interrupt**
as RPCs. Without a reserve, they wait behind model calls that fill the Worker.
When you do not set it, the reserve is one slot if the task limit is at least
two, otherwise zero. Steps never use reserved slots. A growing Step task queue
means Steps need more capacity. See
[Step task queue](/reference/server/workers#step-task-queue) for its
metrics.

server-zd allows 256 streams for each app Worker ID by default
(**matching.maxConcurrentTasksCap**). A Worker opens one stream per task slot,
so its task limit must fit within it. To grow past it, run more Worker processes.

Keep headroom. When no Worker has a free slot, a Step waits in the queue. The
wait uses no attempt and counts toward neither the method timeout nor the
heartbeat timeout. A turn or tool call that waits for a slot takes longer.
See [Tool call limits](#never-run-outcome-unknown).

### Long model calls and timeouts {#timeouts}

The packages set these Step options. **run_model_limit** in the Python
**AgentSessionOptions**, or **runModelLimit** in TypeScript, changes the method
timeout and attempts of **RunModel**. **AgentSessionOptions** does not change
the others.

| Step | Method timeout | Heartbeat timeout | Attempts | Failure route |
| --- | --- | --- | --- | --- |
| **RunModel** | 15 minutes | 2 minutes | 3 within 30 minutes | **RecordTurnFailure** |
| **CompactContext** | 15 minutes | 2 minutes | 3 within 30 minutes | **RecordTurnFailure** |
| **CallTool** | 2 hours, the Dex default | 1 minute, the Dex default | 3 | **RecordToolFailure** |
| **CallSingleAttemptTool** | 2 hours, the Dex default | 1 minute, the Dex default | 1 | **RecordToolOutcomeUnknown** |

**RunModel**, **CompactContext**, and both tool Steps send a heartbeat every 20
seconds while the runner works. A model or tool call that is slow but silent therefore stays
within its heartbeat timeout. The method timeout still ends a hung call. In
Python, keep runner and tool code non-blocking: a blocking call on the event
loop also stops the background heartbeat.

One model call must finish within 15 minutes. Set the provider or framework
request timeout below that, so a slow call fails with the provider's error and
later attempts still fit in the 30-minute retry window. See
[Heartbeat](/reference/server/runtime-steps#heartbeat) for how Dex detects a lost attempt.

A Claude Agent SDK session runs a whole turn segment in one **RunModel**: several
model calls and inline tool calls, until the CLI answers or defers a tool call.
By default that segment must finish within 15 minutes. Raise the limit for a
longer one. Any runner can use the option, but a runner that makes one model call
per **RunModel** rarely needs it.

- Heartbeats continue through the segment, so the method timeout is the only cap.
  A hung segment holds its Worker slot until then, so do not set it higher than
  needed.
- The retry budget moves with the limit. It is the method timeout times one less
  than the attempts, and at least twice the method timeout, so a timed-out attempt
  can still retry. Dex checks it only after an attempt fails.
- A failed segment reruns whole and pays for its model calls again. Set the
  attempts to 1 if that costs more than a failed turn.
- **CompactContext** keeps its own limits. It makes one model call.
- A changed limit applies to each **RunModel** scheduled after the Worker restarts.
  An attempt in flight, and its retries, keep their limit.

### Separate Worker pools {#worker-pools}

Dex routes work by Flow type. Every Worker that registers an agent's Flow type
can receive its model calls, tool calls, and RPCs. The packages register every
session Step together, so one agent's model calls and tool calls share a Worker
pool. Split along these lines when one kind of work crowds out another:

- Give each agent its own Flow type and its own Worker deployment, so a busy
  agent cannot take the slots of another.
- Run heavy or special tool work, such as a browser, a sandbox, or a GPU job,
  in a service with its own hosts and scaling. The tool calls that service with
  the call's idempotency key. The session Worker then only waits on the
  network, and the service scales on its own.

## Limits for long sessions {#limits}

A session can stay open for months. These server-zd
[limits](/reference/server/configuration#limits) decide how far it grows.

| Key | Default | What it bounds |
| --- | --- | --- |
| **limits.maxFlowStateBytes** | 64 MiB | The active state of one session: its current state, including the Attribute and Channel values it holds. History and the superseded values that history keeps for time travel do not count. |
| **values.maxValueBytes** | 16 MiB | The largest single value, such as one message, one tool call record, or one framework run state |
| **history.windowEvents** | About 10,000 events | The Flow history kept for each run. Older events are pruned. |
| **retention.closedFlowDuration** | 7 days | How long a stopped session stays readable |

Each run records these values when it starts. A new value applies only to
sessions that start after the server restarts with it.

The packages store state this way:

- **AgentMessages** keeps the newest messages, one AttributeMap instance per
  message. Storing a message writes only that message. When more than 64
  messages are in it, the oldest move into **AgentMessageChunks** instances
  that are never rewritten. A chunk holds at most 32 messages and 1 MiB, so it
  stays well under **values.maxValueBytes**. A larger message skips the window
  and goes straight into a chunk of its own when it is stored, so a message too
  large for **values.maxValueBytes** fails its turn right away, as it did
  before. **AgentMessageIndex** records where the messages are, and changes
  only when chunks are written or deleted. Each message is written twice, once in the window
  and once in its chunk. Once the window copy is removed, it no longer counts
  toward the run budget. With [compaction](#compaction), **RunModel** loads only the
  messages after the summary. Without compaction, every model call loads and
  sends the whole history, and nothing is deleted.
- **FrameworkRunState** holds the framework's state while a turn waits for
  tool results. **RunModel** rewrites it after every model call that asks for
  tools. It holds the turn's work so far, tool outputs included. The OpenAI
  Agents SDK state also holds the turn's input, and the Vercel AI SDK state
  holds each tool output twice. Only the current value counts toward the run
  budget. Each earlier value becomes a superseded value, which history keeps
  for time travel but the run budget does not count.
- **AgentToolCalls** records are deleted when the turn ends. They then no
  longer count toward the run budget.

The server checks the run budget for Step heartbeats, Step completions, and
RPCs that change Flow state, such as **send_user_message**, and only when the
write adds active state. Once a session is over the budget, such a write is
refused. What happens next depends on what was writing.

- **A model call or tool call.** The session ends, because the next turn would
  meet the same limit. Its status becomes **failed**, **last_turn_error** holds
  the reason, such as "active run state of 67492 bytes exceeds the maximum of
  65536 bytes", and the Flow closes failed with the same text. The Step's
  result is not stored. A model answer you paid for is lost, and a tool that ran
  keeps its effect with no stored result. No further model call is made.
- **Any other Step.** A Step without a failure route, such as
  **AwaitUserMessage**, closes the Flow failed with that reason. The same happens
  when recording the failure above does not fit, which is common when turns are
  small. The stored **AgentState** then keeps its last value.
  **AgentSessionClient.get_agent_snapshot** in Python and **readAgentSnapshot** in
  TypeScript read the Flow's close, so they report **failed** and the reason for
  any session that stored a state. Use them, not the **get_agent_snapshot** RPC
  alone. A session that fails before it stores a state has a snapshot with no
  state. Read the reason from the Flow's result.
- **A new message to a failed session.** The closed Flow refuses it.
  **AgentSessionClient.send_user_message** in Python and **sendAgentUserMessage** in
  TypeScript raise **AgentSessionFailedError** with the reason. A direct RPC call
  gets **FlowNotActiveOrNotFoundError**.
- **Queued messages of a failed session.** They never run. They stay readable in
  the snapshot's **queued_messages** until retention deletes the session, so
  you can send them to a new session.
- **A message that does not fit.** **send_user_message** fails with
  **RESOURCE_EXHAUSTED** and the same text, and the message is not queued. No Step
  ran, so the session does not fail: it keeps waiting, and a shorter message
  may still fit. Only the caller sees this error.

A failed session cannot be recovered. Raising the limit applies only to new
sessions. Plan sessions to stay well below 64 MiB.

The Flow history keeps about the newest 10,000 events of a session. Read the
conversation with **get_agent_snapshot** or **list_agent_messages**, not from
Flow history. [Time travel](/reference/server/runtime-client#time-travel) can target
only a point inside the [history window](/reference/server/configuration#history-window).
Time travel to the beginning is always available. A session that rewrites large
values, such as **FrameworkRunState**, can have a shorter window: the window
also removes old events once the superseded values exceed
**history.maxRetainedSupersededBytes**, 256 MiB by default. This never fails
the session.

A session never completes by itself. Stop it with **StopFlow** when it is done.
A stopped session, and its **get_agent_snapshot** RPC, stays available for the
[retention](/reference/server/configuration#retention) period. Then Dex purges
it. Copy a transcript that must outlive the session with
**list_agent_messages** before then.

### Compaction and the storage bound {#compaction}

Compaction, from the agents 0.2.0 packages, keeps the model input under the
context window. Set
**compaction** in **AgentSessionOptions**, or in the agent definition of a
Stepwise agent, with the model's context window in tokens. The runner must
support compaction; Stepwise does, and the framework adapters do not yet.
Before a model call whose input would reach 85 percent of the window, the
session runs a **CompactContext** Step instead. It makes one model call that
folds the earlier messages into a summary, and the next model call receives the
summary and the newest messages. When the earlier messages do not fit in the
window, Stepwise leaves the oldest of them out of the summary call and tells the
model so. A long turn with many tool calls compacts in the middle of the turn.

Enable compaction only after every Worker of the Flow type runs a release that
has the **CompactContext** Step. The clients that read the session's snapshots
need agents 0.2.0 too: a 0.1.0 client cannot read the **compacting_context**
status that a snapshot shows during compaction.

Compaction also bounds the session's storage. Retention deletes the oldest
chunk once every message in it is summarized and at least
**retained_message_limit** messages, 1,000 by default, are stored after it.
The newest 1,000 messages and every message after the summary always stay, so
the stored messages stop growing however long the session runs. Set the limit,
the window size, and the chunk limits in **AgentSessionOptions** as
**retained_message_limit**, **message_window_size**, **message_chunk_size**,
and **message_chunk_max_bytes**. A limit of **None** (**null** in TypeScript)
keeps every message. If you lower **values.maxValueBytes** below about 2 MiB,
lower **message_chunk_max_bytes** with it.

A deleted message is gone from **list_agent_messages** and
**get_agent_snapshot**. Paging stops at the oldest stored message, and each
page's **deleted_before_sequence** says that retention deleted the messages
before it. If the application needs the whole transcript, copy new messages
out with **list_agent_messages** before **retained_message_limit** more
messages are stored after them. A simple rule is to copy after each
**turn_completed** event, starting after the last sequence you copied. When a
turn can store more messages than the limit, raise the limit or set it to
**None**.

Estimate the run budget from the retained messages. In a measured session,
each turn stored a 100-character question and a 600-character answer, about
2.9 KB, and the session compacted at an 8,000-token window. With a limit of
100, the stored messages stayed between 162 KB and 185 KB, and the whole live
state of the session between 167 KB and 191 KB, at turns 200, 400, 600, and
800, while the session stored 2.3 MB of messages over its life. With the
default limit of 1,000, plan for about the limit times the size of a message,
plus the messages after the summary, plus the largest framework run state and
tool call records that one turn holds. Deleted chunks and earlier values of
rewritten Attributes do not count.

To keep long sessions within the budget:

- Start a new session for new, unrelated work instead of growing one session
  forever.
- Keep tool outputs small. Return what the model needs, such as IDs, a summary,
  or the top results, instead of whole documents. Each output is stored in its
  tool call record, in the run state while the turn runs, and in the messages.
- Move large artifacts, such as files, images, and long documents, to your own
  blob storage. Have the tool return a reference to them.

## Approvals and deadlines {#approvals}

A tool call that needs approval waits in its own **AwaitToolApproval** Step.
The wait holds no Worker slot. It survives Worker restarts and deploys.

Without a deadline, an approval waits until someone answers, and the turn waits
with it. New user messages queue until the turn ends. Set **interrupt_deadline**
in the Python **AgentSessionOptions** or **interruptDeadlineMs** in TypeScript.
A call still pending at the deadline is rejected with the message "approval
deadline passed", and the model sees the rejection.

The session computes the deadline when the model asks for the call, from the
Worker clock. Keep Worker clocks synchronized. A changed deadline option applies
only to approvals raised after the change. Dex Timers take whole seconds, so the
deadline Timer is rounded up and can fire up to a second late.
**resolve_interrupt** returns false from the deadline on, so a late answer never
wins.

**resolve_interrupt** can fail with **RpcLockConflictError** while a Step holds
the same lock. A retry is safe. The Python **AgentSessionClient** retries for up
to 5 seconds.

## Find sessions that need a person {#find-sessions}

**ActiveStepTypes** is a built-in search field. It lists the Steps a Flow waits
in, so one query finds every session waiting for a person, across agents:

```text
ActiveStepTypes = "AwaitToolApproval"
ActiveStepTypes = "AwaitQuestionAnswer"
```

A session appears when it enters the wait and leaves when it moves on. The
search needs no indexed Attribute. Read **PendingInterrupts** or the session
snapshot for what the session asks.

The Python **AgentSessionClient.start_session** and the TypeScript
**startAgentSession** turn this on for a new session. They set
**activeStepSearchMode** to the mode that indexes only Steps with a wait, and an
application can set another mode in the start options. A plain **start_flow** or
**startFlow** does not set it, and the server default keeps the session out of
the search. A session started as a SubFlow inherits its parent's mode.

To turn it on for a session that is already running, such as one started on
0.2.0, call **UpdateFlowConfig** for that session. In Python, call
**update_flow_config** with **active_step_search_mode** set to
**AGENT_SESSION_ACTIVE_STEP_SEARCH_MODE**. In TypeScript, call **updateFlowConfig**
with **activeStepSearchMode** set to **agentSessionActiveStepSearchMode**. An
operator can run **dexcli flow update-config**. The session appears within seconds,
even if it is already waiting. To update every running session, page through
**SearchFlows** and update each one:

```text
FlowType = "SupportAgent" AND ExecutionStatus = "Running"
```

A Step that runs straight away, such as **RunModel**, is not indexed. So a
session's search entry changes only when it enters or leaves a wait, which is
twice for a turn with no tool calls. Each change writes the search entry in the
same commit as the Step.

Two things that need a person do not appear, because no Step waits on them: a
tool call that recorded **outcome_unknown**, and a draft plan waiting for
**execute_plan**.

## Spend limits {#spend-limits}

A spend limit is usually per account or per API key, across many sessions. Dex
has no built-in limit. An application implements **ModelSpendLimit** and passes it
as **spend_limit** in the Python **AgentSessionOptions** or **spendLimit** in
TypeScript. Without one, the session makes no checks.

The session calls the interface around each model call of **RunModel** and
**CompactContext**:

| Call | When | What it gets |
| --- | --- | --- |
| **check_model_call** | Before each attempt, after turn control and the compaction decision | The session, turn, Step type, attempt, session settings, and committed usage |
| **report_model_usage** | When the attempt's model call returns, before the Step commits | The same, with the call's usage and a stable report ID |

Counters and limits belong to the application. Put the account or API key
reference in the session settings, and read it from the check. It stays a
reference: session settings are stored.

**A refused call ends the turn.** The session writes **MODEL_CALL_REFUSED_ERROR_PREFIX**
and the application's reason to **AgentState.last_turn_error**, keeps the finished
tool results of the turn with the usual failure note, and waits for the next user
message. That message starts a new turn, which is checked again. A refused
**CompactContext** ends the turn the same way. The session stays alive, and no new
status or interrupt is involved.

**A check that fails is a refusal without a reason.** A check that raises, or takes
longer than 30 seconds, fails the attempt. Dex retries it under the Step's retry
policy, and no model call runs without a check that passed. When the retries run
out, the turn fails with the error. To fail open instead, catch your own errors in
the check and allow the call.

**A failed report changes nothing.** A report that raises or times out is logged and
dropped. Failing the attempt would pay for the call a second time.

**Each attempt reports once.** The report ID is
**flow/turn/step execution/attempt**, so count each ID once. A retry is a new paid
call and has a new ID. A Step that reported and then did not commit, such as when
its Worker died, reports again on its retry. Both calls were paid for, so the
reports exceed **AgentUsage**, which keeps only the committed attempt. A report also
carries the session's usage including the call, so an application that counts per
session recovers from a dropped report on the next one.

Four limits to design for:

- The check bounds the next call, not its cost. Sessions that pass together can
  overshoot.
- A harness, such as a Claude Agent SDK session, is checked once per turn segment,
  and its usage arrives when the segment ends. One segment can overshoot by all its
  model calls. Set the harness's own budget option too, such as **max_budget_usd** in
  Python or **maxBudgetUsd** in TypeScript.
- A call that fails, is cancelled, or is lost with its Worker reports nothing, though
  the provider may bill it. Some frameworks do not expose token counts, so a report
  can show **model_calls** above zero with zero tokens. That means unknown, not free.
  Count such calls by your own rule.
- Reports are not durable. A report runs inside the Step, so a Worker that dies
  between the model's answer and the report loses it. That attempt never commits,
  so **AgentUsage** does not hold the call either, and only the provider's bill does.

## Crashes and redeploys {#worker-failures}

A crash repeats at most the one call that was running.

This table is the crash matrix. Each row is a Step and the moment it is
interrupted. The last three columns name the integration tests for three
failures:

- **Worker kill**: the Worker gets SIGKILL, and a new Worker starts.
- **Server restart**: the Dex Server node gets SIGKILL and restarts on its data
  directory. The Worker keeps running.
- **Takeover**: the active node gets SIGKILL, and a hot standby takes the lease.
  The Worker keeps running.

Each language names the file that holds the test. **Not tested** means that no
test covers the cell yet, so its text states the design, not a checked result.

| Step | Interrupted | What happens | Worker kill | Server restart | Takeover |
| --- | --- | --- | --- | --- | --- |
| **RunModel** | Before any output reaches Dex | That model call runs again, up to 3 attempts within 30 minutes. Then the turn fails. If tools already ran, a note in the history tells the next turn's model not to repeat them. | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |
| **RunModel** | After output reached Dex | The same. | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |
| **CallTool**, for an idempotent write | Before the first heartbeat reaches Dex | The call runs again with the same idempotency key. | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |
| **CallTool**, for an idempotent write | While the tool runs | The same. | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |
| **CallTool**, for a read | While the tool runs | The call runs again. | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |

## Tool call limits {#tool-call-limits}

A single-attempt tool runs in a **CallSingleAttemptTool** Step. That Step serves
**non_idempotent_write** and **unclassified** tools. It should run the tool at
most once, and record **outcome_unknown** when the tool may have run. When the
tool certainly did not run, the call records **failed** instead, so the model
can call the tool again. One case breaks the at-most-once promise. Plan for
it. It follows from how Dex stops any Step attempt. See
[Failure and redelivery](/reference/server/runtime-steps#failure-and-redelivery).

### A single-attempt tool can run twice {#tool-runs-twice}

Dex starts an attempt when it hands the attempt to a Worker. It never hands the
same attempt number to another Worker. If the Worker dies or loses its
connection to Dex while the tool runs, the attempt fails. A single-attempt tool
has no retry left, so the call records **outcome_unknown**. The earlier run may
have finished its effect, so the session does not run the tool again.

Only one narrow case can still run a single-attempt tool twice. Cancellation is
cooperative. When Dex cancels an attempt, an interrupted run may keep running
while the failure route starts.

To make a second run harmless, pass the call's idempotency key to the service
that the tool writes to. Every tool call receives one: the session's Flow ID,
the turn ID, and the tool call ID, joined by slashes, such as
**session-42/turn-3/call-7**. The key is the same for every attempt of the call. When the service deduplicates on it, classify the tool as
**idempotent_write**, so it also retries after a failure.

### A call that never ran can record outcome_unknown {#never-run-outcome-unknown}

When a tool Step fails, its failure route reads **attempt_progress** from the
recovery error. See [Failure and redelivery](/reference/server/runtime-steps#unknown-outcome).
**CallTool** and **CallSingleAttemptTool** use it the same way:

| **attempt_progress** | What the call records |
| --- | --- |
| **NOT_STARTED** | No attempt reached a Worker, so the tool did not run. The call records **failed**. Its error starts with "the tool did not run, so it is safe to call again". The model sees a failed tool call and can call the tool again. A call whose tool already asked the user a question ran before, so it follows the next row. |
| **NOT_COMPLETED**, or **UNSPECIFIED** when the server reported no progress | The tool may have run. A read records **failed**. Any other call records **outcome_unknown**, and the session does not run its tool again. |

To recognize such a call in **get_agent_snapshot** or your own code, compare the
start of its error with **TOOL_CALL_NOT_RUN_ERROR_PREFIX** in Python,
**toolCallNotRunErrorPrefix** in TypeScript, or **ToolCallNotRunErrorPrefix** in
Go.

**NOT_COMPLETED** is conservative, so a call that never ran can still record
**outcome_unknown**. For example, the server crashed after it recorded the
attempt start but before the task reached the Worker. Treat that outcome as
unknown.

When no Worker accepts a tool Step, the call waits in the queue. This happens
when every Worker of the Flow type is at its task limit, or when none is
running. The call does not fail and does not use an attempt. It runs when a
Worker takes it. If the Flow times out or stops first, the call never runs.

Keep tool Steps dispatchable, so calls do not wait long:

- Size each Worker pool as in [Size Workers](#size-workers), with headroom for
  the largest batch of tool calls.
- Keep at least one Worker of every agent Flow type running. When a pool scales
  to zero, a tool call waits in the queue until a Worker starts.
- During a deploy, start the new Workers and wait for them to
  [register](/reference/server/workers#readiness) before you stop the old ones.

### Reconcile outcome_unknown {#reconcile-outcome-unknown}

**outcome_unknown** means the effect may or may not have happened. The session
never retries such a call, and the model sees that the outcome is unknown.
Reconcile it outside the session:

1. Find the call. While the turn runs, **get_agent_snapshot** lists it under
   **tool_calls**, with the failure in **error**. The **AgentEvents** Stream
   has a **tool_call_finished** event with the status **outcome_unknown**.
   After the turn, its tool result in the message history says that the outcome
   is unknown.
2. Check the target system for the effect, by the call's idempotency key or by
   your own business key.
3. A call that Dex knows never ran records **failed**, not **outcome_unknown**.
   If the Flow's history still shows that the tool Step's attempt never reached
   a Worker, such as for a call that started before a server upgrade, the call
   did not run.
4. Tell the session the real outcome with **send_user_message**, so the next
   turn's model works from it.

## Upgrade agent code while sessions wait {#upgrades}

A waiting session runs the code of the Worker that takes its next Step. Nothing
replays the agent loop, so a deploy takes effect at the next model call or tool
call, even in the middle of a turn. During a rolling deploy, two Steps of one
session can run on different versions.

- Keep each agent's Flow type stable. Running sessions resume by it.
- Keep a tool available while a running turn or a pending approval still
  refers to it.
- A recorded tool call keeps the effect and approval rule that applied when the
  model asked for it. Changed tool policies apply to later calls.
- A changed prompt or model takes effect at the next model call. A changed
  tool takes effect at its next call.
- Between the Steps of a turn, **FrameworkRunState** holds state that the
  framework serialized. The framework version on the new Worker must restore
  it. Stay within the framework range that the adapter pins, and upgrade the
  adapter and the framework together.
- Upgrade every reader of a session before the Workers that write the status
  **failed**. A Worker or client from agents 0.2.0 or earlier cannot decode it, so
  its **get_agent_snapshot** of a failed session raises an error. Only failed
  sessions are affected.
- **Upgrading from agents 0.1.0: stop every 0.1.0 Worker of the Flow type
  before any 0.2.0 Worker starts.** Do not run them side by side. A 0.1.0
  session keeps every message in **AgentMessages**. Once a 0.2.0 Worker stores
  a message in it, it moves the older messages into **AgentMessageChunks**, a
  few chunks per Step. If a 0.1.0 Worker then runs a Step of that session, the
  turn fails, because it cannot read the moved messages.

See [Versioning Flow code](/primitives/components/application#versioning-flow-code)
for the general rules.

### Session settings during a rollout {#session-settings-rollout}

Start sessions with session settings, and call **update_session_settings**, only
after every Worker of the Flow type runs agents 0.2.0. A 0.1.0 Worker drops the
settings of a session that it starts, and it neither writes nor reads the copy
of the settings that a turn keeps. A turn that a 0.1.0 Worker starts runs
without settings, so it can use the Worker's default model for some of its
model calls.

## Credentials {#credentials}

Keep model API keys and tool credentials in the Worker's environment or in a
secret store that the Worker reads when a call runs. Each framework reads its
model key from the environment, such as **OPENAI_API_KEY**, **GOOGLE_API_KEY**,
or **ANTHROPIC_API_KEY**. The adapters add no credential handling.

Never pass a credential in the session's start input, a user message, a tool
argument, a tool output, or an Attribute. Session settings are part of the start
input and of the session's state, and **get_agent_snapshot** and the browser
snapshot JSON return them, so they hold only references, such as a model or a
credential name, that the Worker resolves. Dex stores them in Flow history and
state. Dex Web shows them, history keeps superseded values for time travel, and
a stopped session stays readable for the retention period. Any authorized
Client can read **AgentEvents**.

For a credential that belongs to one user, let the tool look it up at call time
from a secret store, with a key that is not the secret itself. When a Flow of
your own must hold a short-lived secret, store it in a
[hard-delete Attribute](/primitives/attribute#hard-delete-attributes) and
delete it when the Flow no longer needs it.

Workers and Clients authenticate to Dex Server with bearer credentials. See
[authentication](/reference/server/authentication).
