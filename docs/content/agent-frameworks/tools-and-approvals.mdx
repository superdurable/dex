# Tools and Approvals

Every durable agent session gives each tool a policy, whatever framework runs the agent. The policy decides whether Dex may run a call again and whether the call waits for a person to approve it.

## A durable agent session {#a-durable-agent-session}

One Flow run is one agent session. The Flow ID is the session ID. Dex Agents builds the session Flow: the **dex-agents** package in Python and **@superdurable/dex-agents** in TypeScript. A framework adapter adds one agent framework to it.

The session stores the conversation in Attributes. A session waits for the next user message without holding a Worker. It can wait for days.

Model calls run in a **RunModel** Step. In most harnesses, each **RunModel** Step makes one model call, and each tool call runs in its own Step. The tool calls of one model response run in parallel. When they finish, the session sends their results to the model. Each Step adds a round trip to Dex.

A crash repeats only the Step that was running. Dex does not replay the loop. So the agent code needs no determinism rules, and a code change takes effect at the next Step.

Two harnesses group more work into one Step:

- **Claude Agent SDK.** The Claude Code CLI runs a turn segment in one **RunModel** Step. The segment holds the model calls and the read tool calls, and a failed segment reruns as a whole. Writes leave the segment one at a time, each in its own Step, so they never run in parallel.
- **LangChain and LangGraph.** One **RunModel** Step runs the graph to its next tool calls. A graph can make several model calls on the way, and a retry repeats them together.

## Tool policies and approvals {#tool-policies-and-approvals}

Each tool gets a **ToolPolicy**. The policy sets the tool's effect class, which decides whether Dex may run a call again. It also says whether a call waits for approval.

### Effect classes {#effect-classes}

| Effect class | What the tool does | Runs in |
| --- | --- | --- |
| **read** | Only reads. Running it again is harmless. | **CallTool**, with retries |
| **idempotent_write** | Writes, and a repeat with the same idempotency key has no further effect. | **CallTool**, with retries |
| **non_idempotent_write** | Writes, and a repeat can repeat the effect. | **CallSingleAttemptTool**, once |
| **unclassified** | Nothing is known about it. Dex treats it as a non-idempotent write. | **CallSingleAttemptTool**, once |

Every attempt of a call gets the same idempotency key: the session's Flow ID, the turn ID, and the tool call ID, joined by slashes, such as **session-42/turn-3/call-7**. Pass it to the service that the tool writes to. When the service drops a repeated key, classify the tool as **idempotent_write**, so Dex can retry it after a failure.

A recorded tool call keeps the effect class and approval rule that applied when the model asked for it. A changed policy applies to later calls.

### Approvals {#approvals}

Approval asks whether a call should happen at all. It is separate from retry: a refund with an idempotency key is still a real refund.

A tool call that needs approval waits in its own **AwaitToolApproval** Step until someone answers. The wait holds no Worker slot, and it survives Worker restarts and deploys. A person approves or rejects the call from your application or from [Dex Web](/reference/web/dex-web#agent-session-view). The model sees a rejection and can react to it.

While an approval waits, the turn waits with it, and new user messages queue until the turn ends. If an approval must not wait forever, set an approval deadline. Dex rejects a call that is still pending at the deadline. See [Approval deadlines](/reference/agents/approvals#approval-deadlines).

## Tool call outcomes {#tool-call-outcomes}

Each tool call ends with one record:

| Record | Meaning |
| --- | --- |
| **succeeded** | The tool returned a result. |
| **failed** | The tool reported a failure, or Dex knows that the tool did not run. |
| **rejected** | A person rejected the call, or its approval deadline passed. |
| **outcome_unknown** | The tool may or may not have taken effect. |

The model reads every record and decides what to do next. A failed or unknown call does not fail the session.

A call that Dex knows never ran records **failed**. Its error starts with "the tool did not run, so it is safe to call again", and the model can call the tool again. A call that may have run records **outcome_unknown** instead, unless it is a read. Dex never runs such a call again. See [A call that never ran](/reference/agents/failures#never-run-outcome-unknown) for how Dex decides.

### At-most-once has one exception {#tool-runs-twice}

A single-attempt tool runs in **CallSingleAttemptTool**. Dex hands each attempt to one Worker and never hands the same attempt to another. If the Worker dies or loses its connection to Dex while the tool runs, the call records **outcome_unknown**, and the session does not run the tool again.

One narrow case can still run a single-attempt tool twice. Dex cannot force a running attempt to stop. When Dex cancels an attempt, the interrupted run may keep going while Dex records the failure and the turn moves on. To make a second run harmless, pass the call's idempotency key to the service that the tool writes to. See [Failure and redelivery](/reference/python/failure-and-retries#failure-and-redelivery).

### Reconcile outcome_unknown {#reconcile-outcome-unknown}

**outcome_unknown** means the effect may or may not have happened. The session never retries such a call, and the model sees that the outcome is unknown. Reconcile it outside the session:

1. Find the call. While the turn runs, **get_agent_snapshot** lists it under **tool_calls**, with the failure in **error**. The **AgentEvents** Stream has a **tool_call_finished** event with the status **outcome_unknown**. After the turn, its tool result in the message history says that the outcome is unknown.
2. Check the target system for the effect, by the call's idempotency key or by your own business key.
3. If the Flow's history shows that the tool Step's attempt never reached a Worker, the tool did not run. This can happen for a call that started before a server upgrade.
4. Tell the session the real outcome with **send_user_message**, so the next turn's model works from it.

No search finds these calls for you, because no Step waits on them.

## Connectors as tools {#connectors-as-tools}

Every harness can call [Connector](/concepts/connector) operations as tools. **ConnectorToolSource** offers the operations you name. The agent takes it as a tool source, through **tool_sources** in Python and **toolSources** in TypeScript. Each call runs one operation in its own tool Step, through the Connector SDK. So the Call ID, the idempotency key, and credential handling work as they do in a Connector Step. The Call ID is the same on every attempt of the tool Step.

Each harness page shows the wiring in its Connect Connectors section, such as [Built-in agent loop](/agent-frameworks/built-in-agent-loop#connect-connectors) and [Claude Agent SDK](/agent-frameworks/quick-start/?framework=claude-agent-sdk#connect-connectors). For packages, tool names, result size, and connections, see the [Connector tools reference](/reference/agents/connector-tools).

### Which operations are offered {#connector-tools-offered}

Nothing is exposed by default. The application names each operation an agent may use. The Connector author must also have reviewed the operation for agent use and marked it as exposed in its manifest, **dex-connector.json**. Dex refuses any other operation when the agent is defined.

Dex checks the model's arguments against the operation's input schema before the operation runs. A misspelled field, a wrong type, or a missing field fails the call with a message the model can correct. The operation does not run.

### Effect classes {#connector-tools-effects}

The manifest decides whether a call can run again, and so which Step runs it:

| Operation | Effect class | Runs in |
| --- | --- | --- |
| Query | **read** | **CallTool**, with retries |
| Mutation that the manifest marks retry-safe (**agent.retry: safe**) | **idempotent_write** | **CallTool**, with retries |
| Any other Mutation | **non_idempotent_write** | **CallSingleAttemptTool**, once |

The Connector author marks a Mutation retry-safe after review. It means that a repeat with the same Call ID cannot make a second effect. A call whose attempts run out records **failed** for a Query and **outcome_unknown** for a Mutation.

A session's tool policy for a Connector tool changes only its approval. The effect class always comes from the manifest.

### Approval {#connector-tools-approval}

By default, a Connector tool waits for approval only when its manifest recommends it (**agent.approval: recommended**), as for a refund. Other Mutations run without approval, because approving every message would make an always-on agent unusable.

The application can override that for each tool, either way. It can also pass a predicate that decides for each call from the call's arguments, such as refunds above a limit. A predicate that raises asks for approval. Arguments that fail the schema check never wait for approval, because the call never runs.

### Outcomes {#connector-tools-outcomes}

The operation ends in one of its branches, and the branch decides the tool call's record. In the manifest, a Connector author marks the branches where nothing took effect as **rejected**, and the branches where the write may have taken effect as **unknown**. Dex uses the first row that matches. Every row above the rejected row, except the success row, records **outcome_unknown**, so doubt never becomes a safe failure:

| Branch | Record | The model sees |
| --- | --- | --- |
| **uncertain** | **outcome_unknown** | That the outcome is unknown |
| A Mutation's **defect** | **outcome_unknown** | That the outcome is unknown |
| A success branch, such as **sent** or **refunded** | **succeeded** | The result value |
| Any other Mutation branch, when its single-dispatch fence cannot prove that nothing was sent | **outcome_unknown** | That the outcome is unknown |
| A branch marked **rejected**, such as **providerRejected** | **failed** | The branch and the provider's message |
| A branch marked **unknown**, or a Mutation branch that is not listed | **outcome_unknown** | That the outcome is unknown |
| A Query branch that is not listed, including **defect** | **failed** | The branch and the message |

A Mutation's **defect** can happen after the provider was called, so the write may have taken effect. A Mutation with a single-dispatch fence records whether its request may have left. If it may have, marking the branch **rejected** does not turn the failure into a rejection.

Reconcile **outcome_unknown** as for any tool; see [Reconcile outcome_unknown](#reconcile-outcome-unknown).

### Write order {#connector-tools-write-order}

Connector writes of one model response run one at a time, in the model's order. Reads, and calls of other tools, run in parallel. A write that needs approval asks for it only when its turn comes.

When a write fails, ends **outcome_unknown**, or is rejected by a person or by its provider, the later Connector writes of that response do not run. Each records **failed** with its **skipped** field set and an error that starts "the tool did not run, so it is safe to call again". Dex Web shows these calls as skipped.

In the Claude Agent SDK adapter, one call of a model response at a time leaves the turn to run in its tool Step. The adapter refuses a later write of that response inside the turn, so it never runs and leaves no record. The model reads the earlier write's result and then decides whether to call the later write again.

### Crashes {#connector-tools-crashes}

A Worker crash during a Connector write never sends the write twice. How a write recovers depends on how the Connector can tell whether the provider got it:

- **Deduplicated by the provider.** The Connector sends the call's idempotency key, and the provider drops a repeated key.
- **Looked up first.** The provider has no idempotency key. Before a retry sends anything, the Connector looks for the earlier write at the provider. The Connector also records, during the attempt, whether the request has left the Worker.

| What happened | Retry-safe write, deduplicated by the provider | Retry-safe write, looked up first | Single-attempt write |
| --- | --- | --- | --- |
| The Worker died before the request was sent | Dex retries with the same key. The write happens once, and the call records **succeeded**. | Dex retries. The lookup finds no write, but nothing proves that the request was never sent, so the retry sends nothing. The call records **outcome_unknown**. | The call records **outcome_unknown**. Nothing was sent. |
| The Worker died after the provider accepted the write | Dex retries with the same key. The provider drops the repeat, and the call records **succeeded**. One write. | Dex retries. If the lookup finds the write, the call records **succeeded**. If not, it records **outcome_unknown**. One write either way. | The call records **outcome_unknown**. One write. |
| The provider asked to retry later, such as for a rate limit | Dex retries. The write happens once. | Dex retries. The write happens once. | The call records **failed**, with "not sent; the provider asked to retry later", if the Connector recorded that the request never left the Worker or that the provider refused it without acting. Otherwise it records **outcome_unknown**. |

A request to retry later does not prove by itself that nothing was sent. So a single-attempt write records **failed** only with the Connector's record as proof. The model can then call it again without anyone checking the provider. The later writes of that response are still skipped.

## Limits by framework {#limits}

<FrameworkTabs>
<FrameworkTab framework="claude-agent-sdk">

- One write call per segment leaves the turn. A reply with two writes costs one more segment and model call. The writes of one reply never run as parallel Steps.
- Tools that run inside the CLI, such as **Bash** or **Edit**, are at least once. They run again when a segment reruns. Files the CLI changes are not recorded.
- A segment must finish within the **RunModel** method timeout, 15 minutes by default. Raise it with **run_model_limit** in Python or **runModelLimit** in TypeScript.
- Dex compaction is not available. Claude Code compacts its own transcript. A long session ends at the state limit, not the context window.
- A recorded tool result keeps text only.
- A write call inside a subagent is denied. The model is asked to call it from the main conversation.

The adapter README lists every limit. See [Limits for long sessions](/reference/agents/session-limits) for the server limits.

</FrameworkTab>
<FrameworkTab framework="google-adk">

- The App root must be a **BaseAgent**. ADK **Workflow** roots are not supported.
- A tool runs outside the ADK run, with a fresh **ToolContext**. Its state and artifact changes are discarded. Pass what it needs as arguments.
- A tool that asks for a confirmation or a credential inside its Step fails.
- Agents that continue without tools make their model calls in the same **RunModel**.
- A **before_tool_callback** runs in the **RunModel** that requests the call, and again if that Step retries.
- Code executors other than **BuiltInCodeExecutor** are refused. Run such code from a tool instead.
- **app:** and **user:** state keys live in the Dex session, not across sessions.

The adapter README lists every limit. See [Limits for long sessions](/reference/agents/session-limits) for the server limits.

</FrameworkTab>
<FrameworkTab framework="langchain-langgraph">

- A graph whose nodes make several model calls before a tool node makes them all in one **RunModel**. Summarization middleware and a planner node are examples. A retry repeats them all.
- Provider-run tools repeat when **RunModel** reruns.
- History is append-only. A graph that edits or removes earlier messages does not change the stored history.
- Only the message list survives between turns. Other state keys start from their defaults on every turn.
- Tools run outside the graph. They cannot use **ToolRuntime**, **InjectedState**, or **InjectedStore**, and cannot return a graph **Command**. **InjectedToolCallId** works.
- The graph may raise no interrupts of its own.

The adapter README lists every limit. See [Limits for long sessions](/reference/agents/session-limits) for the server limits.

</FrameworkTab>
<FrameworkTab framework="mastra">

- Tools Mastra runs itself, such as sub-agents, workflows, and Memory tools, cannot run in a Step. The adapter offers one only when **toolPolicies** names it as a read without approval. It then runs inside **RunModel** and repeats when that Step reruns.
- Mastra Memory is not used. Do not select a Memory thread in the agent's defaults or scopes.
- **beforeToolCall** and **afterToolCall** hooks run only for tools Mastra runs itself.
- A tool result reaches the model as text. **toModelOutput** is not applied.
- A tool that calls **suspend()** fails. Use the session's approval instead.
- Tool names must be at most 63 characters of letters, digits, **_**, and **-**, and must not start with a digit or **-**.

The adapter README lists every limit. See [Limits for long sessions](/reference/agents/session-limits) for the server limits.

</FrameworkTab>
<FrameworkTab framework="openai-agents-sdk">

- Only function tools get their own Steps. Hosted tools, such as web search, run at the provider during the model call. They repeat when **RunModel** reruns.
- Tools the SDK runs itself, such as MCP server tools and local shell tools, cannot wait for approval. The adapter refuses them by default. Wrap a write in a function tool to give it its own Step.
- Function tool names must be unique across the agent graph. The graph is copied when the Flow is built, so later changes to it do not reach the Flow.
- The session is the history. Do not use server-managed conversation state or SDK sessions.
- An agent used as a tool runs its nested run inside one tool Step in Python. TypeScript rejects it; hand off instead.

The adapter README lists every limit. See [Limits for long sessions](/reference/agents/session-limits) for the server limits.

</FrameworkTab>
<FrameworkTab framework="pydantic-ai">

- Retries that Pydantic AI sends to the model itself make another model call in the same **RunModel** Step. Examples are invalid tool arguments and output that fails validation.
- Output functions run inside **RunModel** and are at least once. Put a write in a tool instead.
- Provider-run tools, such as **WebSearchTool**, repeat when **RunModel** reruns.
- A deferred tool returns text to the model. Images and files are lost.
- A tool that asks for approval only while it runs needs a **ToolPolicy** with **requires_approval=True**.
- **UsageLimits** and tool retry budgets apply per Step, not per turn.

The adapter README lists every limit. See [Limits for long sessions](/reference/agents/session-limits) for the server limits.

</FrameworkTab>
<FrameworkTab framework="vercel-ai-sdk">

- A crash in **RunModel** reruns that model call and any provider-executed tools in it.
- A tool's **execute** gets **toolCallId** and **abortSignal**. Its **messages** are empty and its **context** is **undefined**.
- Approval belongs to Dex. AI SDK **toolApproval** is not exposed, and a **needsApproval** function is rejected. Provider-executed tools never wait for approval.
- Every tool runs in Dex, so a tool without **execute**, such as a browser-side tool, is rejected.
- Tool inputs and outputs must survive JSON.
- **prepareStep**, **activeTools**, **output**, and stream transforms are not exposed.

The adapter README lists every limit. See [Limits for long sessions](/reference/agents/session-limits) for the server limits.

</FrameworkTab>
</FrameworkTabs>
