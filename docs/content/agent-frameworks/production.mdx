# Agents in Production

Agent sessions run on the same Dex Server as every other Flow. Check each item before you put sessions in front of users. Each line links to the page with the details.

| Item | What to know | Details |
| --- | --- | --- |
| Dex Server | You run Dex Server yourself, with object storage. One active node serves a cluster. | [Run Dex in Production](/components/production) |
| Authentication | Public API authentication is off by default. Turn it on before the server is reachable from other machines. | [Authentication](/reference/server/authentication) |
| Retention | A closed session stays readable for 7 days by default, then the server may delete it. Keep transcripts you need longer in your own store. | [Retention](/reference/server/configuration#retention) |
| Session size | A session ends when its active state reaches the state limit, 64 MiB by default. Message retention, and compaction where the harness supports it, keep it below that. | [Session limits](/reference/agents/session-limits) |
| Model spend | Dex has no built-in spend limit. Check spend per account or API key around each model call. | [Spend limits](/reference/agents/spend-limits) |
| Credentials | Keep model API keys and tool credentials in the Worker's environment or a secret store, never in session input or messages. | [Credentials](/reference/agents/credentials) |
| Approval deadlines | Without a deadline, an approval waits until someone answers, and the turn waits with it. Set a deadline when a call must not wait forever. | [Approval deadlines](/reference/agents/approvals#approval-deadlines) |
| Upgrades | A deploy takes effect at the next model call or tool call. Keep each agent's Flow type stable, and read the change log before a rolling deploy. | [Upgrades](/reference/agents/upgrades) |
| Workers | Each running model call, tool call, and RPC holds one Worker task slot. Size Workers for parallel tool calls. | [Workers and timeouts](/reference/agents/workers) |
| Streaming | The AgentEvents Stream carries live text to your UI. Size it for your traffic. | [AgentEvents Stream](/reference/agents/event-stream) |
| Tracing | Sessions can emit OpenTelemetry spans for each model call and tool call. Content capture is off by default. | [Tracing](/reference/agents/tracing) |
| Calls during a deploy | **send_user_message** and **resolve_interrupt** are RPCs. They need a running Worker, and a retried **send_user_message** can queue a message twice. | [RPCs during a deploy](#rpcs-during-a-deploy) |
| Unknown outcomes | A write that a crash interrupted records **outcome_unknown** and does not run again. Decide who reconciles it. | [Reconcile outcome_unknown](/agent-frameworks/tool-calls#reconcile-outcome-unknown) |

## RPCs during a deploy {#rpcs-during-a-deploy}

Your application talks to a session through RPCs, such as **send_user_message**
and **resolve_interrupt**. An RPC runs on a Worker. It never waits in a queue:
if no Worker takes it within 10 seconds, the call fails with **Unavailable**.
During a deploy that stops every Worker, these calls fail until a new Worker
connects. The session itself loses nothing.

- **Retry on Unavailable.** Retry with backoff until a Worker is back. A failed
  call with **Unavailable** changed nothing.
- **resolve_interrupt is safe to retry.** An approval that already went through
  returns **False** the second time, and nothing runs again.
- **send_user_message is not.** Dex does not drop a repeated RPC. If the
  response is lost, a retry can queue the same message twice. Before you resend,
  read the session with **get_agent_snapshot** and look for the message in
  **messages** and **queued_messages**. If it is queued twice, remove the copy
  with **delete_queued_message**.

[Limits and Sharp Edges](/intro/limits-and-sharp-edges#requests-that-can-repeat)
lists the other requests that can repeat.
