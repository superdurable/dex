# Storage sync

## Why you need it

Application databases still exist. Teams want Durable Execution state to land in systems they already query (warehouses, OLTP, object stores).

## Custom Attribute Store

Dex can asynchronously copy selected Attribute writes into a deployment-managed
MySQL or PostgreSQL table. The workflow Attribute remains the source of truth;
the external row is a latest-state projection.

Two settings opt in:

1. The Flow selects a named Server store with `AttributeStoreName` (Go),
   `attributeStoreName` (Java and TypeScript), or `attribute_store_name`
   (Python and Rust).
2. The Attribute definition opts in with `SyncToAttributeStore` (Go),
   `syncToAttributeStore` (Java and TypeScript), or `sync_to_attribute_store`
   (Python and Rust).

AttributeMap definitions support the same opt-in. Their SQL column names match
the physical Attribute names produced for individual map instances. SDKs omit
`sync_config` for ordinary definitions and send `enabled = true` for opted-in
definitions across initial, Client, Step, and RPC writes and deletions.

Changing the Flow target affects only new writes. Already queued mutations keep
the target selected when they were enqueued. Clearing the target disables later
sync; enabled writes still update the workflow Attribute and produce an error
metric/log rather than entering a queue with no destination.

## How Dex implements it

Dex first applies the workflow Attribute and existing visibility index update,
then appends a mutation to a workflow-owned durable FIFO. A single synchronizer
groups up to the configured batch size, without crossing target-store boundaries,
and performs one SQL upsert. Duplicate Attribute names inside a batch use the
last write.

The synchronizer tries a Local Activity for at most seven seconds, then falls
back to a regular Activity. Regular attempts default to 30 seconds and retry for
up to one hour. An exhausted batch is logged and skipped; it does not fail the
Flow. Each later batch gets its own retry budget.

Continue-as-New completes only the in-flight batch and carries the remaining
queue to the next Run. Graceful completion, FailFlow, and cooperative CancelFlow
wait for current producers and flush the queue. Signals accepted while a flush
Activity runs are drained, and any resulting Attribute writes trigger another
flush. RPC next steps are not started after terminal processing begins. Hard
Terminate, engine timeout, or direct backend cancellation may lose pending
mutations. Reset does not backfill or reconcile an external row.

Blob-backed string and object values are hydrated inside the Activity before
schema validation. With the Server Attribute blob cache enabled, a recent S3
write normally hydrates from local disk without another S3 read. TinyLFU
admission rejection and oversized values safely fall back to S3.

## Traditional workarounds

Use explicit application writes when every external update must be part of the
business transaction. Attribute sync intentionally favors workflow progress:
schema/type mismatches are filtered item-by-item, and a batch is skipped after
its retry budget expires. There is no backfill in this release.
