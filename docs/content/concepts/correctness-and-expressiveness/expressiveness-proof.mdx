# Expressiveness proof

Dex has a formal expressiveness result with a machine-checked proof. This
page explains what it claims, how it was checked, and what it does not cover.
The full argument is in the paper.

- [Download the paper (PDF)](/papers/dex-expressiveness.pdf)
- [Formal sources on GitHub](https://github.com/superdurable/dex/tree/main/formal)

## The claim {#the-claim}

The paper defines a small concurrent language. It has the usual tools of
concurrent programming:

- threads, with **fork** and **join**;
- shared variables, local variables, and procedures with recursion;
- mutexes and condition variables;
- timers: **sleep**, and a **select** that waits for a message or a timeout;
- cancellation of a thread;
- exceptions;
- external effects, such as sending an email;
- program exit.

The claim is this. Every well-formed program in that language translates
into a Dex Flow that behaves the same, observed from outside.

"Behaves the same" has two parts.

- **The same event sequences.** Every finite sequence of events the program
  can produce, the Flow can produce. Every one the Flow can produce, the
  program can produce.
- **The same outcomes.** Under fair scheduling, the program and the Flow
  complete, get stuck, or run forever under the same conditions.

"Observed from outside" means the inputs, the external effects, and the
result. The Flow's internal Channels and its Attributes are not observed.

## Why it matters to you {#why-it-matters}

Dex has no threads that block, and no locks held across a wait. A Flow is a
set of Steps that read and write Attributes, publish and consume Channel
messages, and wait on Timers. You may wonder what that model cannot express.

The proof answers for a whole class of programs. Any concurrency structure
you can write with the constructs above has a Dex Flow equivalent. The paper
also shows how to build each construct from Steps, Channels, Attributes, and
Timers.

The translation is a construction for the proof. It is not a compiler that
Dex ships. It uses one Step for each statement, which is not how to model an
application. Use it to see that a structure is possible. Model your own Flow
with the [design patterns](/design-patterns).

## How each construct is built {#how-each-construct-is-built}

This table summarizes the translation in the paper.

| Construct | Dex building blocks | Related design pattern |
| --- | --- | --- |
| Thread | A chain of Steps, one for each statement. The thread's position and local state travel in the Step input. A thread is one active Step execution at a time. | |
| **fork** | **GoToMany** to the parent's next Step and the child's first Step. | |
| **join** | The ending thread publishes one message to its join Channel, then returns **DeadEnd**. The joining Step waits with **AnyOf** on that Channel and on its own cancel Channel. | [Await Parallel Steps](/design-patterns/parallel/await) |
| Mutex | A Channel that holds one token while the mutex is free. **lock** waits for the token with **ForOne**. Waiters are served in the order they started waiting. **unlock** publishes the token back. | [Critical Section](/design-patterns/critical-section) |
| Condition variable | An Attribute holds the list of waiting threads. Each waiter has its own Channel. **wait** adds the thread to the list, releases the mutex, waits on its Channel, then takes the mutex again. **signal** removes the first waiter and publishes to its Channel. **broadcast** does this for every waiter. | |
| **sleep** | One timed Step. Its **WaitFor** returns **AnyOf** with a Timer and the thread's cancel Channel. | |
| Timed **select** | The same timed Step. It waits with **AnyOf** on a Timer, the input Channel, and the cancel Channel. Only the winning Condition consumes a message. | [Deferred Choice](/design-patterns/deferred-choice) |
| Cancellation | A message on the cancelled thread's cancel Channel. The thread sees it only at a point where it would block. | |
| Exception | The handler stack travels in the Step input. **throw** is a **GoTo** to the handler's Step. | |
| Exit or failure | **ForceComplete** with the result, or **ForceFail** with the error. | |
| External effect | An **Execute** whose only effect is that external call. | |

The mutex shows why the details matter. An Attribute lock would not work,
because it covers one Step method and not a wait. A Channel token can be held
across many Steps and waits.

## How it was checked {#how-it-was-checked}

The result rests on three parts.

- **A formal semantics of the Dex core.** It describes how Flows, Steps,
  Channels, Attributes, and Timers behave. It was written against the server
  code. Each rule cites the code that implements it. Reviewers checked the
  rules against that code.
- **The translation and the theorems.** The paper defines the translation
  and states the two equalities: same event sequences, and same outcomes
  under fair scheduling.
- **A proof in Lean 4.** The Lean kernel checks every step of the proof.
  No step is left unproved. The proof uses only the three standard axioms of
  Lean. It depends on the Lean core library only.

## What it does not cover {#what-it-does-not-cover}

The scope is narrow on purpose. The paper discusses each limit.

- **No failures.** The model has no crashes, retries, or redelivery. That a
  Flow stays correct under failures is a separate claim. Its proof is future
  work.
- **Well-formed programs only.** A program must hold the mutex when it
  unlocks it or uses its condition variable. Other programs are outside the
  claim.
- **A model of the server.** The Dex side is a model reviewed against the
  server code. It is not extracted from the code.
- **A restricted environment.** The outside world starts the Flow once and
  then publishes messages to its external Channels. It makes no RPC calls
  and never stops the Flow.
- **One timing model.** Timer order follows a fixed count of steps for each
  statement. The claim says nothing about another cost model, or about
  performance.
- **Fairness is assumed.** The outcome part holds for fair runs. It assumes
  that Timers fire, that Steps get to run, and that Workers cooperate: every
  Step method returns, or ends after it is cancelled. A Worker that hangs
  forever is outside that part.
- **One direction.** Every program has a Flow. The claim does not say that
  every Flow is such a program.

## Related evidence {#related-evidence}

The [Workflow Patterns evaluation](/concepts/correctness-and-expressiveness/workflow-patterns)
is complementary evidence. It rates Dex against 43 workflow patterns, each
with a runnable example and a test against a real server. The patterns
