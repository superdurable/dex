# Correctness and expressiveness

This section answers two questions about Dex.

- **Expressiveness**: can Dex express the programs you need?
- **Correctness**: does Dex stay correct when processes, machines, or networks
  fail?

## Expressiveness

The [Workflow Patterns evaluation](/concepts/correctness-and-expressiveness/workflow-patterns)
rates Dex against the 43 control-flow Workflow Patterns. Researchers use these
patterns to compare workflow languages and engines. Each rating comes with a
runnable example and an integration test.

The [Expressiveness proof](/concepts/correctness-and-expressiveness/expressiveness-proof)
shows that any program in a small concurrent language, with threads, locks,
timers, and cancellation, can be written as a Dex Flow that behaves the same.
A computer checks every step of the proof. The
[paper](/papers/dex-expressiveness.pdf) has the full argument.

## Correctness

The [Step guarantees](/concepts/step#guarantees) state what Dex promises when
a Step method fails or runs again.

The [Failure transparency proof](/concepts/correctness-and-expressiveness/failure-transparency-proof)
shows that failures do not change what a Flow does, except that external
effects may repeat. It covers server crashes, standby takeovers, retries,
Workers that keep running after Dex gave up on them, and duplicate results. It
holds under stated assumptions. For example, it covers **SYNC** methods only, and
retries must not run out. A computer checks every step of this proof too. The
same [paper](/papers/dex-expressiveness.pdf) has the full argument.

Together, the two proofs say that a program in the small concurrent language
runs on Dex as if no failure had happened, except that its external effects
may repeat. Repeats can overlap and come late, so an idempotent effect alone
is not enough.
[What this means for your code](/concepts/correctness-and-expressiveness/failure-transparency-proof#what-it-means-for-you)
explains what to do instead.
