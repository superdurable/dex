# Workflow Patterns evaluation

The Workflow Patterns are a catalog of recurring behaviors in business
processes. The Workflow Patterns Initiative defined them, led by Wil van der
Aalst and Arthur ter Hofstede. Researchers use them to compare workflow
languages and engines, such as BPMN, BPEL, and YAWL. Each pattern has an ID, a
name, and a precise definition. See the
[control-flow patterns](http://www.workflowpatterns.com/patterns/control/) for
the definitions.

This page rates Dex against the 43 control-flow patterns, WCP-1 to WCP-43. The
data, resource, and exception-handling patterns are not evaluated here.

## Rating scheme {#rating-scheme}

The ratings use the scheme of the published evaluations.

- **+** means direct support. One Dex construct meets every part of the
  definition. The application keeps no extra state for it.
- **+/-** means indirect support. Dex implements the pattern by composing
  several constructs, such as Channel signals for a join, an Attribute
  counter, a lock, an RPC guard, or a reset Step. In a few rows, one part of
  the definition holds in a limited form, and the row says which. The
  published evaluations call this rating partial support.
- **-** means no support.

## Why many joins are indirect {#why-many-joins-are-indirect}

Dex expresses a join inside one Flow with Channel signals. Each branch
publishes a signal when it finishes, and the join Step waits for the count it
needs. That bookkeeping makes most joins **+/-**. When the work runs
in child Flows, a **SubFlow** wait with **AllOf** is the native join.

## How the ratings were checked {#how-the-ratings-were-checked}

Every pattern has a runnable example in TypeScript, Python, Go, Java, and
Rust. Each example has an integration test against a real Dex Server. The test
asserts the behavior that defines the pattern. For example, the Deferred Choice
test sends two competing responses and checks that exactly one branch runs.

## Summary {#summary}

- 19 patterns have direct support (**+**).
- 24 patterns have indirect support (**+/-**).
- No pattern is unsupported (**-**).

## Comparison with a published evaluation {#comparison-with-a-published-evaluation}

A [published evaluation](https://doi.org/10.1016/j.infsof.2009.02.002) rated six workflow and BPM systems against the
same 43 control-flow patterns. Its authors are Wohed, Russell, ter Hofstede,
Andersson, and van der Aalst. It appeared in Information and Software
Technology 51(8), 2009 ([PDF](https://www.vdaalst.com/publications/p536.pdf)). In its Table 20, each system directly
supports between 11 and 20 patterns. Each system has partial support for up to
6 patterns. Each system does not support between 19 and 32 patterns.

Dex has 19 **+**, 24 **+/-**, and 0 **-**. Read these numbers with care.

- The systems were evaluated in 2009. Their current versions may differ.
- The researchers rated those systems. The Dex ratings are our own
  assessment. We used the same scheme and back each rating with a runnable
  test.
- The scheme gives **+** when one dedicated modeling construct, such as a
  gateway type, covers a pattern. Dex composes a few general constructs in
  code instead. The scheme rates that **+/-**.

## What the ratings rest on {#what-the-ratings-rest-on}

The ratings depend on these Dex behaviors.

- **GracefulComplete** closes the Flow only when no Step is active.
- **DeadEnd** ends one branch and never closes the Flow.
- **ForceComplete** closes the Flow at once and cancels the other Steps.
- **AnyOf** consumes messages only from the condition it selects.
- A Channel message stays queued until a Step consumes it.
- A decision or an RPC cancels Steps by Step type. Cancellation is cooperative.
- Only one Step method or RPC holds an Attribute lock at a time.
- A SubFlow keeps running when its parent closes.

See [Step](/concepts/step), [Channel](/concepts/primitives/channel), and
[SubFlow](/concepts/primitives/subflow) for these concepts.

### WCP-1 Sequence {#wcp-1}

**What it is.** A task starts only after the task before it finishes. Both tasks belong to the same process. See the [official definition](http://www.workflowpatterns.com/patterns/control/basic/wcp1.php).

**How Dex implements it.** Each Step's **Execute** returns **GoTo** for the next Step. The example runs ReceiveOrder, CheckInventory, and ShipOrder in order.

**Rating:** **+**. **GoTo** is the sequence construct.

### WCP-3 Synchronization {#wcp-3}

**What it is.** Two or more branches converge into one. The next branch starts only after every incoming branch has finished. See the [official definition](http://www.workflowpatterns.com/patterns/control/basic/wcp3.php).

**How Dex implements it.** Each branch publishes a signal to a **Channel** when it finishes. The join Step waits for **ForN** signals, one per branch. The split starts the join together with the branches.

**Rating:** **+/-**. The join composes Channel signals with a **ForN** wait. A Flow has no native wait on another Step's completion.

### WCP-9 Structured Discriminator {#wcp-9}

### WCP-31 Blocking Partial Join {#wcp-31}

### WCP-38 General Synchronizing Merge {#wcp-38}

**What it is.** The merge waits for every active branch, or until "it is not possible that any branch that has not yet been enabled will be enabled at any future time". It works in any process, including unstructured ones with loops. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp38.php).

**How Dex implements it.** An **Attribute** counts the threads that can still reach the merge. Every Step that changes it holds one shared lock. The commit that brings the count to 0 publishes a sentinel to a **Channel**, and the merge Step waits for it.

**Rating:** **+/-**. The pattern expects the merge to decide reachability from the process structure. In Dex, application code decides it at each **GoTo**.
