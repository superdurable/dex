# Workflow Patterns evaluation

The Workflow Patterns are a catalog of recurring behaviors in business
processes. The Workflow Patterns Initiative defined them, led by Wil van der
Aalst and Arthur ter Hofstede. Researchers use them to compare workflow
languages and engines, such as BPMN, BPEL, and YAWL. Each pattern has an ID, a
name, and a precise definition. See the
[control-flow patterns](http://www.workflowpatterns.com/patterns/control/) for
the definitions.

This page rates Dex against the 43 control-flow patterns, WCP-1 to WCP-43. The
data, resource, and exception-handling patterns are not evaluated here.

## Rating scheme {#rating-scheme}

The ratings use the scheme of the published evaluations.

- **+** means direct support. One Dex construct meets every part of the
  definition. The application keeps no extra state for it.
- **+/-** means partial support. The pattern needs application bookkeeping,
  such as Channel signals for a join, an Attribute counter, a lock, an RPC
  guard, or a reset Step. Or one part of the definition holds only in a
  limited form.
- **-** means no support.

## Why many joins are partial {#why-many-joins-are-partial}

A Flow has no native wait on the completion of another Step. So a join waits
for Channel signals that the branches publish, and the application supplies
the branch count. That bookkeeping makes most joins **+/-**. When the work runs
in child Flows, a **SubFlow** wait with **AllOf** is the native join.

## How the ratings were checked {#how-the-ratings-were-checked}

Every pattern has a runnable example in TypeScript, Python, Go, Java, and
Rust. Each example has an integration test against a real Dex Server. The test
asserts the behavior that defines the pattern. For example, the Deferred Choice
test sends two competing responses and checks that exactly one branch runs.

## Summary {#summary}

- 19 patterns have direct support (**+**).
- 24 patterns have partial support (**+/-**).
- No pattern is unsupported (**-**).

## Partial support {#partial-support}

Each **+/-** rating has a reason.

- **WCP-3, WCP-7, WCP-13, WCP-14, WCP-33, WCP-37, and WCP-41** (joins). The
  branches publish Channel signals, and the join waits for a count of them. A
  Flow has no native wait on Step completion.
- **WCP-9, WCP-30, and WCP-34** (structured and static partial joins). The
  branches of round k publish to the ChannelMap instance for round k. The join
  fires on the first n signals. A reset Step consumes the rest, then starts the
  next round. A late signal can never count toward a later round.
- **WCP-28 and WCP-31** (blocking joins). The definition says "Subsequent
  enablements of incoming branches are blocked until the Blocking
  Discriminator has reset." Signals are keyed by round in the same way. No Step
  waits for round k + 1 before round k resets, so a next-round signal stays
  queued and has no effect. The reset Step is still bookkeeping.
- **WCP-15 and WCP-36** (instances without a known count). An RPC adds
  instances, and an Attribute counts them. The join waits again after each
  result until its condition holds.
- **WCP-17 and WCP-40** (interleaved routing). One shared Attribute lock keeps
  the tasks apart. The lock covers a single **Execute**. It does not cover a
  **WaitFor** or a task that spans several Steps.
- **WCP-18** (Milestone). A Step cannot test the state of another branch. An
  Attribute marks the milestone. An RPC starts the task only while the
  Attribute is set.
- **WCP-20** (Cancel Case). Client **StopFlow** alone leaves a running SubFlow
  alive. So the Step that starts a SubFlow also waits for a cancel Channel. On
  cancel, it reads the child's Flow ID with **SubFlow.getFlowId**, stops the
  child, and returns **ForceFail**. **ForceFail** cancels every other active
  Step.
- **WCP-23** (Transient Trigger). Channel messages stay queued until a Step
  consumes them. So **WaitFor** records that a Step is waiting. An RPC accepts
  one trigger under a shared Attribute lock and drops the rest.
- **WCP-29, WCP-32, and WCP-35** (cancelling joins). A Channel signal join
  fires, then its decision cancels the remaining branches by Step type.
- **WCP-38** (General Synchronizing Merge). The definition requires the merge
  to fire when "it is not possible that any branch that has not yet been
  enabled will be enabled at any future time." The merge should decide this
  from the process structure. In Dex, the application decides it at each
  **GoTo**. An Attribute counts the threads that can still reach the merge.
  The commit that brings it to 0 publishes a sentinel, and the merge waits for
  it.
- **WCP-39** (Critical Section). An Attribute lock covers one Step method. A
  section of several Steps holds a one-message Channel as a token instead.

## What the ratings rest on {#what-the-ratings-rest-on}

The ratings depend on these Dex behaviors.

- **GracefulComplete** closes the Flow only when no Step is active.
- **DeadEnd** ends one branch and never closes the Flow.
- **ForceComplete** closes the Flow at once and cancels the other Steps.
- **AnyOf** consumes messages only from the condition it selects.
- A Channel message stays queued until a Step consumes it.
- A decision or an RPC cancels Steps by Step type. Cancellation is cooperative.
- Only one Step method or RPC holds an Attribute lock at a time.
- A SubFlow keeps running when its parent closes.

See [Step](/concepts/step), [Channel](/concepts/primitives/channel), and
[SubFlow](/concepts/primitives/subflow) for these concepts.
