# Attribute

An **Attribute** is durable data that belongs to one Flow run. Steps and
RPCs read and write it. Dex stores it with the Flow, so you do not need a
database for intermediate state.

An Attribute lives as long as its Flow. Dex deletes it when it deletes the Flow,
after the [retention period](/components/production#before-you-launch) that follows Flow closure.
To keep the data longer, see [Keep data after the Flow](#attribute-store-projection).

## When to use an Attribute

Use an Attribute for state that the Flow decides on: an order status, a
counter, a customer profile, or the result of an earlier Step. Use a
[Channel](/concepts/primitives/channel) for messages that a Step waits for and consumes.
Use a [Stream](/concepts/primitives/stream) for live progress that a user can afford to
lose.

## Use an Attribute {#define-an-attribute}

Declare each Attribute in the Flow's persistence schema. A Step or RPC can then
read or write it. The Worker rejects an Attribute that the schema does not
declare. Setting an Attribute to null deletes it.

Attribute writes take effect only when the Step method or RPC succeeds. See
[Step guarantees](/concepts/step#guarantees).

    email: Attribute<String>,
    progress: AttributeMap<String>,

    fn default() -> Self {
        let status = Attribute::new("primitive-attribute-status")
            .indexed(AttributeIndex::keyword().with_key("keyword1"));
        let email = Attribute::new("primitive-attribute-email").sync_to_attribute_store();
        let progress = AttributeMap::new("primitive-attribute-progress")
            .indexed(AttributeIndex::keyword().with_key("keyword2"));
        Self {
            start: AttributeStep {
                status: status.clone(),
                progress: progress.clone(),
            },
            status,
            email,
            progress,
        }
    }

impl Flow for AttributeFlow {
    type StartInput = String;

    fn steps(&self) -> StepList<'_, Self::StartInput> {
        StepList::start(&self.start)
    }

    fn persistence(&self) -> PersistenceSchema {
        PersistenceSchema::new()
            .attribute(&self.status)
            .attribute(&self.email)
            .attribute_map(&self.progress)
    }
}

struct AttributeStep {
    status: Attribute<String>,
    progress: AttributeMap<String>,
}

impl Step for AttributeStep {
    type Input = String;

    fn wait_for(&self, context: &mut Context, _input: Self::Input) -> HandlerResult<Wait> {
        self.status.set(context, "processing".to_owned())?;
        self.progress
            .set(context, "payment", "authorized".to_owned())?;
        Ok(Wait::skip_immediately())
    }

    fn execute(&self, context: &mut Context, input: Self::Input) -> HandlerResult<StepDecision> {
        self.status.set(context, "completed".to_owned())?;
        Ok(StepDecision::graceful_complete(input))
    }
}

## AttributeMap {#attributemap}

An **AttributeMap** is a set of Attributes with keys chosen at run time. Use it
for values that grow with your data, such as the status of each payment in an
order. Dex stores each key separately, so a write does not rewrite the whole
collection.

## Read and search Attributes

Code outside the Flow reads Attributes through the [Client](/concepts/client).
See [when a read needs an RPC](/concepts/client#related-primitives) and
[Read Attributes from outside a Flow](/reference/server/runtime-data#read-attributes-from-outside-a-flow).
To set values when the Flow starts, see [Initial values](/reference/server/runtime-data#initial-attribute-values).

An indexed Attribute can be used in `SearchFlows` queries to find Flow
runs; the example above indexes the status Attribute under the shared search
slot `keyword1`. See [Indexes](/reference/server/runtime-data#attribute-indexes)
for how slots are shared across Flow types, and
[PostgreSQL search](/reference/server/search#postgresql-search) for the slot
limits.

## Locks {#locking}

Two Steps or RPCs can write the same Attribute at the same time. Without a
lock, two that read and then write it can overwrite each other's update. See
[Step guarantees](/concepts/step#guarantees). Use an
**Attribute lock** to run them one after the other. Dex acquires the lock before
the Step method or RPC starts and releases it when it finishes. A Step waits for
its lock. An RPC that cannot get a lock fails, and you retry it.

Lock any Attribute that two parallel Steps, or a Step and an RPC, read and
then write. Dex does not detect an unlocked read-then-write. Test it by running
both writers concurrently and checking the final value.

A lock affects only the Steps and RPCs that declare it. A Step or RPC that does
not declare it can still write the Attribute.

Keep locked Steps and RPCs short; an RPC can take a free lock ahead of waiting
Steps (see [Lock order](/reference/server/runtime-data#lock-order)). Make slow external calls in a Step that holds no
lock, and set a short total duration, such as a few minutes, in the locked
method's `StepOptions` retry policy. A failing locked Step holds its lock
through every retry; see
[Lock holding](/reference/server/runtime-data#lock-holding).

`Execute` runs:

## Short-lived secrets {#hard-delete-attributes}

A **hard-delete Attribute** holds a short-lived secret, such as an API key that
a Flow uses a few times and then discards. Deleting it erases the stored value
permanently. Neither Dex APIs nor Flow history can recover it. Unlike other
writes, a hard-delete write takes effect before Dex saves the handler's result.
See
[Hard-delete Attributes](/reference/server/runtime-data#hard-delete-attributes)
for the requirements and their consequences.

## Keep data after the Flow {#attribute-store-projection}

Attribute Store sync copies selected Attributes to PostgreSQL tables that you
own. Each destination is called an **Attribute Store**. The tables keep the data
after Dex deletes the Flow. Your application and your reports query them with
SQL, and you can index them for your own queries.

To sync an Attribute:

1. Create the table before the server starts. Dex never creates, migrates, or
   backfills a table.
2. Configure the store in the server configuration.
3. Mark the Attribute or AttributeMap with `syncToAttributeStore`.
4. List the store name in the Flow's `FlowConfig` when you start the Flow.

The Flow stays the source of truth. A table row holds the latest values, not a
history, so do not make Flow decisions from the table.
[Dex and Your Database](/components/your-database) describes how sync behaves,
including dropped writes and repairs.

The [Attribute Store sync](/reference/server/attribute-store-sync) reference
covers configuration, table requirements, row keys, AttributeMap tables,
retries, metrics, and local development. The
[Entity Store](/design-patterns/entity-store) pattern shows a complete example.
