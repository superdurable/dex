# Flow

A **Flow** is the top-level unit of work in Dex. A Flow type describes one kind
of business process, such as an order, a subscription, or an approval. A Flow
run is one instance of it, such as order 42.

Dex owns the Flow's lifecycle and state. Your code does not need a database
or a job queue to keep the process going across crashes and restarts.

## When to use a Flow {#when-to-use}

Use one Flow for each business identity whose process Dex should own. Put work
that shares that identity and lifecycle into [Steps](/concepts/step) of the
same Flow. Steps can run in parallel inside one Flow.

Start a separate Flow when the work has its own owner and lifecycle. Two Flows
coordinate by calling each other's RPCs. Use a [SubFlow](/concepts/primitives/subflow)
when a parent Step waits for a child Flow, for example to split complex logic
into smaller Flows or to fan out work.

## Guarantees {#guarantees}

A Flow ID has at most one active run at a time. What each Step saves, and when
it can run again, is covered in [Step guarantees](/concepts/step#guarantees).

## What a Flow contains {#implement-a-flow}

You define a Flow by implementing the **Flow** interface in your language. It
declares three things:

- <a id="steps"></a>**Steps**: the start Step and every other Step the Flow can reach.
  [Steps](/concepts/step) run the background work.
- <a id="persistence-schema"></a>**Persistence schema**: the [Attributes](/concepts/primitives/attribute) and
  [Channels](/concepts/primitives/channel) that hold the Flow's durable state. Dex
  rejects reads and writes to names that are not declared.
- <a id="rpc-handlers"></a>**RPC handlers**: methods that a client calls on a running Flow. See
  [RPC](/concepts/primitives/rpc).

The start Step's input type is also the Flow's start input type. This Flow has
two Steps, one Attribute, one Channel, and one RPC.

## Lifecycle {#lifecycle}

A [Client](/concepts/client) starts a Flow with a Flow ID and the start
input. Dex then runs the start Step on a Worker. Each Step returns a decision
that moves to the next Steps or closes the Flow. Several Steps can be active
at the same time.

A Flow closes in one of these ways:

- a Step completes or fails it;
- its timeout fails or cancels it;
- a client stops it;
- a new start with the same Flow ID terminates it; see
  [Flow close by a new start](/reference/server/runtime-data#flow-close-by-new-start).

Instead of failing or canceling the Flow, a timeout can run a handler that
decides the outcome. While the Flow runs, clients read and change it through
its RPCs.

## Identifiers {#identifiers}

The word Flow can mean a Flow definition or a Flow run. These
identifiers keep them apart.

| Identifier | Who sets it | Meaning |
|----------|-------------|---------|
| `FlowType` | Application (via Flow implementation) | Stable type name Dex uses to route Worker calls and search results. |
| **Flow ID** | Application client on start | Business identity for one Flow run. The ID reuse policy controls whether another run may start with the same Flow ID. |
| **Run ID** | Dex Server | Identity of one run of the Flow ID. Time travel keeps it and creates a new run attempt. Address a Flow by its Flow ID; the Run ID is diagnostic. |
| `StepType` | Application (via Step implementation) | Stable name for a Step definition inside the Flow. |
| `StepExecutionID` | Dex Server | One execution of a Step type, formatted as **StepType-Number**. |

Most SDKs use the language's type name as the `FlowType` unless you
override it. Do not change these names while runs are open.

## Start options and configuration {#start-options}

Start with a stable business Flow ID; to make retries safe, set a request ID
and the already-started option.
[StartFlow best practices](/reference/python/start-flow-options#start-flow-best-practices)
shows the safe-retry recipe, and [StartFlowOptions](/reference/python/start-flow-options)
lists every start option (Python reference; each SDK reference has the same
page). `FlowConfig` holds runtime settings that you can
update while the Flow runs.
