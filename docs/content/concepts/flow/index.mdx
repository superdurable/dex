# Flow

A **Flow** is the top-level unit of work in Dex. A Flow type describes one kind
of business process, such as an order, a subscription, or an approval. A Flow
run is one instance of it, such as order 42.

Dex owns the Flow's lifecycle and state. Your code does not need a database
or a job queue to keep the process going across crashes and restarts.

## When to use a Flow {#when-to-use}

Use one Flow for each business identity whose process Dex should own. Put work
that shares that identity and lifecycle into [Steps](/concepts/step) of the
same Flow. Steps can run in parallel inside one Flow.

Start a separate Flow when the work has its own owner and lifecycle. Two Flows
coordinate by calling each other's RPCs. Use a [SubFlow](/concepts/primitives/subflow)
when a parent Step waits for a child Flow, for example to split complex logic
into smaller Flows or to fan out work.

## Guarantees {#guarantees}

A Flow ID has at most one active run at a time. What each Step saves, and when
it can run again, is covered in [Step guarantees](/concepts/step#guarantees).

## What a Flow contains {#implement-a-flow}

You define a Flow by implementing the **Flow** interface in your language. It
declares three things:

- <a id="steps"></a>**Steps**: the start Step and every other Step the Flow can reach.
  [Steps](/concepts/step) run the background work.
- <a id="persistence-schema"></a>**Persistence schema**: the [Attributes](/concepts/primitives/attribute) and
  [Channels](/concepts/primitives/channel) that hold the Flow's durable state. Dex
  rejects reads and writes to names that are not declared.
- <a id="rpc-handlers"></a>**RPC handlers**: methods that a client calls on a running Flow. See
  [RPC](/concepts/primitives/rpc).

The start Step's input type is also the Flow's start input type. This Flow has
two Steps, one Attribute, one Channel, and one RPC.

## Lifecycle {#lifecycle}

A [Client](/concepts/client) starts a Flow with a Flow ID and the start
input. Dex then runs the start Step on a Worker. Each Step returns a decision
that moves to the next Steps or closes the Flow. Several Steps can be active
at the same time.

A Flow closes in one of these ways:

- a Step completes or fails it;
- its timeout fails or cancels it;
- a client stops it;
- a new start with the same Flow ID terminates it; see
  [Flow close by a new start](/reference/server/runtime-data#flow-close-by-new-start).

Instead of failing or canceling the Flow, a timeout can run a handler that
decides the outcome. Active Steps keep running while the handler runs. When
the handler commits a force-complete or force-fail decision, Dex starts
closing the Flow. The handler can commit after the deadline. While the Flow runs, clients read and change it through
its RPCs.

## Child Flows with their own identity {#child-flows}

Some child jobs need their own business identity. People look them up,
retry them, or stop them by their own number, or other systems start them.
Model such a job as its own top-level Flow. A Step of the parent starts it
through a Client, with a stable Flow ID and request ID. A SubFlow does not
fit here, because Dex derives a SubFlow's ID from its parent.

The parent receives each child's result durably:

- The child commits its outcome to an Attribute in one Step. A next Step
  reports to the parent through an RPC that publishes to a Channel. The
  report Step must not run before the outcome commits, so both Steps keep
  the default SYNC durability; see
  [Durability](/reference/python/step-options#durability). The report carries
  a stable request ID. Or a polling Step of the parent waits for the child's
  terminal state.
- The parent keeps one record per child, keyed by its Flow ID, with the
  outcome and the terminal status as separate fields. A report or a read
  fills in what is missing, and a repeat changes nothing.
- The business number is the child Flow ID. A resend of the same start
  request keeps its request ID. A deliberate reopen is a new start request
  with a new request ID. Every ID reuse policy that the starters use rejects
  an active run; see
  [ID reuse policies](/reference/go/start-flow-options#flow-id-request-id-and-already-started).
  The parent tracks the run ID that it claimed. It accepts only reads,
  reports, and stops that it can tie to that run. Describe and the Client
  Attribute read see only the latest run, so the parent confirms the run ID
  around each read; see the
  [Production checklist](/design-patterns/subflows/child-flows-with-business-identity#production-checklist).
  A newer run is another attempt, which the parent handles by business
  policy.
- Every start of the same logical request derives the same Flow ID and
  request ID. Another logical request can still start a run with the same
  Flow ID, even from the same entry point or parent run. Then the start
  reports that the Flow already started: read that run and track it only when
  its stored business identity matches. When it does not match, record a
  rejected admission that the parent lists but never waits for, counts, or
  stops. Rejected is its own state, never ended or failed. The check can be skipped only when the mapping from business
  identity to child Flow ID guarantees that only a replay of the same logical
  request starts it again.
- Each child has its own Flow timeout. Each starter sets it, because it is a
  start option. A child that must report its timeout uses a timeout handler
  that reports, not a Timer Step. A closing parent never stops its children.
- A client stop that cancels, fails, or terminates the child starts no new
  handlers in it, so the child may never report. A client stop targets the
  latest run of the Flow ID. To stop only the claimed run of a child that can
  be reopened, call a child RPC that carries the claimed run ID; the child
  compares it with its own run ID before it stops. A running handler can ignore cancellation, so a report already sent
  can still arrive.
- When the parent does not need to know how a stopped child ended, it stops
  the child and moves on. A parent that needs only a quorum stops the
  remaining children this way.
- When the parent's result or a follow-up action depends on how a stopped
  child ended, such as counting its result, undoing its side effects, or
  showing its outcome, the parent reconciles it from the child's stored state.
  After a stop, a refused stop, or a timer for unreported children, the
  parent describes the child first. It records a closed child's terminal
  status and stored outcome. It reads a running child again later. A child
  that does not exist, or whose latest run is not the claimed one, is
  recorded by business policy, such as "unavailable".
  It returns any other error, so the Step retries. A report that still
  arrives after the stop fills the same record. Children that finish after a
  quorum, or while the parent stops the rest, count in the parent's result as
  the business rule states.

The [Child Flows with Business Identity](/design-patterns/subflows/child-flows-with-business-identity) pattern shows a variant of these rules in runnable code. Its report RPC writes the parent's record directly under a lock instead of publishing to a Channel. A start that finds the number already started is recorded as `rejected` instead of read and matched.

## Identifiers {#identifiers}

The word Flow can mean a Flow definition or a Flow run. These
identifiers keep them apart.

| Identifier | Who sets it | Meaning |
|----------|-------------|---------|
| `FlowType` | Application (via Flow implementation) | Stable type name Dex uses to route Worker calls and search results. |
| **Flow ID** | Application client on start | Business identity for one Flow run. The ID reuse policy controls whether another run may start with the same Flow ID. |
| **Run ID** | Dex Server | Identity of one run of the Flow ID. Time travel keeps it and creates a new run attempt. Address a Flow by its Flow ID; the Run ID is diagnostic. |
| `StepType` | Application (via Step implementation) | Stable name for a Step definition inside the Flow. |
| `StepExecutionID` | Dex Server | One execution of a Step type, formatted as **StepType-Number**. |

Most SDKs use the language's type name as the `FlowType` unless you
override it. Do not change these names while runs are open.

Name every Flow and Step type after its domain. One `StepType` runs the same
work on many inputs. Different kinds of work, such as calls to different
services, get their own Step types, so the graph shows them and each has its
own options.

## Start options and configuration {#start-options}

Start with a stable business Flow ID; to make retries safe, set a request ID
and the already-started option.
[StartFlow best practices](/reference/python/start-flow-options#start-flow-best-practices)
shows the safe-retry recipe, and [StartFlowOptions](/reference/python/start-flow-options)
lists every start option (Python reference; each SDK reference has the same
page). `FlowConfig` holds runtime settings that you can
update while the Flow runs.
