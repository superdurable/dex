# Step

A **Step** is one unit of background work in a [Flow](/concepts/flow). It
can wait durably for something to happen, then do its work, then choose what
runs next. Dex runs Steps on your Workers and records each result.

A native struct or class implements the Step. Its type is the `StepType`.
One Step type can run many times in a Flow, even in parallel. Each run is a
`StepExecution`, identified by a `StepExecutionID` such as
**Charge-2**: the Step type, then the execution number of that type in the Flow.
So **Charge-2** is the second run of **Charge**.

## Step input {#step-input}

Each Step execution has its own typed input. Dex stores it with the execution.
The input tells executions of the same Step type apart. The start Step's input
is the Flow's start input.

## WaitFor and Execute {#waitfor-and-execute}

A Step has one or two methods.

- `WaitFor` is optional. It returns a durable **Wait**. Dex stores the wait,
  checks its conditions for you, and calls `Execute` once they are met.
- `Execute` is required. It does the work and returns a `StepDecision`.

If a Step has no `WaitFor`, `Execute` runs immediately.

## Waiting {#waiting}

A wait does not hold a Worker or a thread. Dex keeps it in the Flow's state
and wakes the Step when a condition is met. A Step can wait on three kinds of
condition:

- a [Timer](/concepts/primitives/timer) fires;
- a message arrives on a [Channel](/concepts/primitives/channel);
- a [SubFlow](/concepts/primitives/subflow) completes.

Combine conditions with `AnyOf` or `AllOf`. `AnyCombinationOf` accepts
any one of several groups of conditions. After the wait, `Execute` reads what
satisfied it, such as the Channel messages it consumed. See
[Waits](/reference/python/waits).

To wait for parallel branches, use a **Join**. It is not another kind of
condition: it waits on a [ChannelMap](/concepts/primitives/channel#channelmap) that the branches report to. See
[Await Parallel Steps](/design-patterns/parallel/await).

## StepDecision {#stepdecision-movements}

`Execute` returns a `StepDecision`. It can go to one next Step or to
several Steps at once. This is how you build branching, loops, and parallel
work. `GoTo` names the next Step by its Step type and passes its input. The
Flow's registered instance of that Step type runs it.

<StepDecisionMovementsDiagram markdownDescription="GoTo: ExampleStep returns GoTo(Complete Flow), which completes the Flow. GoToMany: ExampleStep starts StepA and StepB, which run in parallel. Loop: ExampleStep goes to ProcessStep, and ProcessStep goes back to ExampleStep." />

A decision can also close the Flow or end a branch:

- `GracefulComplete` asks Dex to complete the Flow once no other Step is active.
- `ForceComplete` completes the Flow immediately.
- `ForceFail` fails the Flow immediately.
- `DeadEnd` ends this branch without closing the Flow.

Completing decisions can return the Flow output, which a client reads as the
Flow result. When several completing decisions return an output, the result
keeps each one. Only a Flow that completes keeps these outputs. If the Flow does
not complete because it fails, is canceled, is terminated, or times out, its
result has no outputs.

A decision can also cancel other active Steps. See the
[Parallel Steps](/design-patterns/parallel) and
[Parallel SubFlows](/design-patterns/parallel-subflows) patterns.

## Guarantees {#guarantees}

In short: finished work is saved, unfinished work can repeat.

Four rules matter most. The first two are all you need for a first Flow.
[Advanced guarantees](#advanced-guarantees) explains the details behind the
other two.

- **A finished Step does not run again.** Dex saves its result together with
  the move to the next Step. This holds for SYNC Steps, the default; an ASYNC
  result lost in a server failover reruns, as
  [SYNC and ASYNC Steps](#sync-and-async) explains.
- **A Step that was cut off can run again.** A crash, a timeout, or a retry
  can repeat a method that already called an external system. So a Step runs
  at least once, not exactly once. The next section says how to make that
  safe.
- **A retry sees the state of its first attempt.** A retry of `Execute`
  reuses the state snapshot of the first attempt. It does not see Attribute
  writes made since then. To wait for such a write, have the writer publish a
  Channel message, and wait for it in the next Step's `WaitFor`. Hard-delete
  Attributes are the exception: Dex reads them again on every attempt. See
  [Short-lived secrets](/concepts/primitives/attribute#hard-delete-attributes).
- **Parallel writers can overwrite each other.** Two Steps or RPCs that read
  and then write the same Attribute need a lock on it. See [What Dex saves](#what-dex-saves).

### Idempotency keys {#idempotency-keys}

Send an idempotency key with each external call that changes something, such
as a payment or an email. The service that applies the effect uses the key to
drop a repeat. Build the key from values that stay the same on every attempt:

- the Flow ID and a name for the call, such as **charge-order-1042**, when the
  Flow makes that call once;
- the Flow ID and the `StepExecutionID`, such as `order-1042/Charge-2`,
  when the Step runs more than once in the Flow.

Do not use the attempt number, the time, or a random value in the key. They
change on a retry. Other pages link here instead of repeating this rule.

## StepOptions {#stepoptions}

A Step returns `StepOptions` to control how its methods run. `WaitFor` and
`Execute` each have their own settings.

- **Timeout** limits one attempt of a method.
- **Retry policy** runs the same method again after a failed attempt.
- <a id="waitfor-failure-policy"></a><a id="execute-failure-policy"></a><a id="step-failed-events-and-last-failure-info"></a>**Failure
  policy** decides what happens when retries run out. By default the Flow
  fails. `Execute` can go to a recovery Step instead. `WaitFor` can proceed
  to `Execute`. See [WaitFor failure policy](/reference/python/failure-and-retries#waitfor-failure-policy),
  [Execute failure policy](/reference/python/failure-and-retries#execute-failure-policy), and
  [Last failure info](/reference/python/failure-and-retries#last-failure-info).
- **Durability** chooses when Dex stores the result. **SYNC**, the default,
  stores it before the next work starts. **ASYNC** is faster, but a server
  failure can make the method run again. See
  [SYNC and ASYNC Steps](#sync-and-async).
- **Heartbeat** lets a long method report progress and save a checkpoint.
- **State loading** and **Attribute locks** choose which state the method
  loads and which Attributes it locks.

A `StepDecision` can override the options for one Step execution.

Without StepOptions, each method uses the server defaults. They are the same
for every SDK:

| Setting | Default |
| --- | --- |
| Method timeout, for one attempt | 2 hours |
| Heartbeat timeout | 1 minute |
| Retry attempts | No limit within the total duration |
| Retry total duration | 4 hours from the first hand-out to a Worker |
| Retry backoff | 1 second, doubling up to 100 seconds |
| Durability | SYNC |
| Failure policy | Fail the Flow |

[Timeouts and total duration](/reference/go/step-options#timeouts-and-total-duration)
in the SDK reference explains how these limits interact.

## Advanced guarantees {#advanced-guarantees}

These sections cover what you need once Steps run in parallel, take a long time,
or use ASYNC durability.

### What Dex saves {#what-dex-saves}

In short: a method's writes are saved together, but they are not isolated from
other Steps and RPCs.

Dex saves each `WaitFor` or `Execute` call on its own. It saves the call's
Attribute writes and Channel publications together with its result, and only
when the method succeeds. Calls to external systems are not part of this save.

A Step method's changes take effect all at once. They are not protected from
other Steps and RPCs, though. A method reads the Flow state as it was when Dex
handed the method to a Worker. Other Steps and RPCs can change that state
before the method's changes take effect. Dex does not check that the values
the method read are still current. So two Steps or RPCs that read and then
write the same Attribute can overwrite each other's update. To prevent this,
have both declare a lock on that Attribute. Dex then runs them one at a time.
See [Attribute locks](/concepts/primitives/attribute#locking).

### Failure and redelivery {#failure-and-redelivery-summary}

In short: when Dex cannot tell whether a method finished, it runs the method
again or tells you the outcome is unknown.

These cases repeat a method or leave its outcome unknown. They hold for every
SDK:

- **A Worker stops in the middle of a method.** The attempt fails, and the
  retry policy runs the method again. Its external calls may already have
  happened. A server restart or failover does the same to every attempt that
  a Worker had.
- **Heartbeats are not acknowledged.** A heartbeat checkpoint can be lost, so a
  rerun can start from an older checkpoint.
- **A canceled method keeps running.** Dex does not stop its code. Its
  external calls still take effect.
- **An ASYNC Step can repeat an attempt.** See
  [SYNC and ASYNC Steps](#sync-and-async).
- **Retries can run out without an answer.** The recovery Step then learns
  that the work certainly did not run (`NOT_STARTED`) or that it may have
  run (`NOT_COMPLETED`). On `NOT_COMPLETED`, check the target system by
  the idempotency key before you repeat or report the effect.

Failure and redelivery in the SDK reference gives the exact rules for each
case: [Python](/reference/python/failure-and-retries#failure-and-redelivery) ·
[Go](/reference/go/failure-and-retries#failure-and-redelivery) ·
[Java](/reference/java/failure-and-retries#failure-and-redelivery) ·
[TypeScript](/reference/typescript/failure-and-retries#failure-and-redelivery) ·
[Rust](/reference/rust/failure-and-retries#failure-and-redelivery).

### SYNC and ASYNC Steps {#sync-and-async}

A Step's **durability** chooses when Dex stores its progress.

- **SYNC** is the default. Dex stores the start of each attempt before the
  Worker receives it, and stores the result before the Flow moves on. Each of
  these waits for a write to object storage.
- **ASYNC** hands the task to the Worker, and starts the next work, before the
  start and the result are stored. Dex batches these writes over about 20
  milliseconds. A single Flow runs faster. If a Dex Server node fails before
  the write, Dex runs the same attempt again on a new state snapshot, so it
  can read different Attribute values. Later work that started from the lost
  result runs again too.

Choose **SYNC** for effects that need the tightest guarantees. Choose
**ASYNC** for short Steps where latency matters and a rare rerun is
acceptable. Good ASYNC candidates are fast reads, internal bookkeeping, and
calls that a key already makes safe to repeat. Keep **SYNC** for a payment,
an email, or any call whose rerun on a newer snapshot could send different
arguments. A `StepOptions` setting picks the durability of one Step, and
`FlowConfig` sets it for a whole Flow.
[Performance and Maturity](/intro/performance-and-maturity) gives measured
latency for both.

### Cancellation, completion, and order {#cancellation-completion-order}

Canceling a Step discards everything its current method has not saved: its
Attribute writes, its Channel publications, and its decision. What its
`WaitFor` already saved stays. A decision or an RPC never cancels the Steps that it
starts itself. [Channel guarantees](/concepts/primitives/channel#guarantees)
say what happens to the messages a canceled Step consumed.

Dex does not stop a canceled method's code. The method should check for
cancellation and return. Until it does, its code keeps running. Its calls to external
systems still take effect, even after the Flow has closed.

`GracefulComplete` ends its own branch and asks Dex to complete the Flow. Dex
begins to complete the Flow as soon as no Step is active. Until then, other
Steps and RPCs can still start new Steps, and those Steps delay completion too.
A later branch that ends with `DeadEnd` does not withdraw the request. After
the last Step ends, the Flow can stay `RUNNING` briefly while Dex finishes
pending Attribute Sync writes and transactional RPCs that already started.

Without a pending `GracefulComplete`, a Flow with no active Step keeps
running. An RPC can still start new Steps in it. End the last branch with a
completing decision. If a Flow must not wait forever, set a Flow timeout.

Dex starts ready Steps roughly in the order they became ready, but not
strictly. Do not rely on the order in which parallel Steps start or finish.
Use a Channel or an Attribute lock when the order matters.
