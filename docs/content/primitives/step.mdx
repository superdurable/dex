# Step

A **Step** is the unit of durable control flow. Each Step type may wait (`WaitFor`), then run (`Execute`), then return a movement to another Step — or complete, fail, or start concurrent work.

## Why you need it

Business logic branches, loops, retries, and runs in parallel. Those routes must themselves be durable so recovery does not guess the next action. A Step records the wait, the work, and the next movement in one place.

## WaitFor and Execute

`WaitFor` registers durable Conditions (timers, channels, SubFlows, combinations) and returns without holding a worker. When a Condition completes, Dex rehydrates the Step and calls `Execute`.

`Wait.any_of` / `all_of` accept unnamed Conditions. Any-combination waits need a non-empty user ID on every Condition so combinations can reference them unambiguously; no internal ID is generated.

Omit `WaitFor` (or return `Wait.skipImmediately()`) when the Step should run `Execute` without waiting. Handlers may be async in TypeScript.

See [Timer](/primitives/timer), [Channel](/primitives/channel), and [SubFlow](/primitives/subflow) for the Conditions a Step can wait on.

## Branch and loop

Return a StepDecision that moves to another Step (or the same Step) with an input. Loops are explicit `go_to` movements, not hidden polling threads.

The Dex interpreter records Step movements in Temporal/Cadence history and schedules the next Step execution.

## Cancellation

Parallel work often has a winner: the first acceptable quote, the fastest replica, or the first branch that reaches quorum. Once the result is durable, the remaining work should stop consuming capacity and must not produce a late decision that changes the Flow.

Return the winner's normal next action and select losing Step types in the same decision. Each SDK keeps its language's normal builder style.

        .with_canceling_steps(self.global_quote_timeout)

| SDK | All current executions | Same-source executions |
| --- | --- | --- |
| Java | `withCancelingSteps` | `withCancelingSiblingSteps` |

`RPCResult` does not support sibling selection. Separate invocations of the same RPC name do not share an invocation-scoped Step execution lineage, so treating their Steps as siblings could cancel unrelated work.

Long-running regular Steps should use a heartbeat timeout so cancellation reaches the Worker promptly. The option is `heartbeat_timeout` in Python, `HeartbeatTimeout` in Go, `heartbeatTimeout` in Java, and `heartbeatTimeoutMs` in TypeScript.

Java cancels the handler task with `Future.cancel(true)`, which interrupts the handler thread. Go handlers observe `Context.Done()`. Python's `AsyncWorker` cancels the asyncio task and exposes `Context.is_cancellation_requested()`. TypeScript aborts `Context.cancellationSignal`. CPU-bound or batch-oriented handlers may check cancellation at natural work boundaries; they do not need to poll continuously.

```python
options = StepOptions(heartbeat_timeout=timedelta(seconds=10))

def execute(self, context: Context, job: Job) -> StepDecision:
    while has_next_batch(job):
        if context.is_cancellation_requested():
            break
        process_batch(job)
    return dead_end()
```

### ASYNC local activities and timers

An ASYNC Step first runs as a local activity. The local activity keeps the current backend Workflow Task open until it returns or reaches Dex's seven-second local optimization timeout. While that task is occupied, another Step may be unable to finish `waitFor` and start its durable timer. In that case, the timer starts after the local stage ends.

If the timer was already started, it keeps its original deadline. Dex processes an elapsed deadline when the Workflow Task resumes instead of restarting the timer. In either case, cancellation can arrive up to the local-stage duration later than it would with a SYNC Step. If the local activity successfully returns first, its result is processed first and a later selector is a no-op for that completed execution.

Use SYNC durability when a timer must cancel an executing handler close to its deadline. If the ASYNC local optimization times out, Dex falls back to a regular activity and the timer can cancel that fallback. A backend error without local attempt metadata conservatively consumes one attempt and the elapsed local-stage duration before Dex calculates the regular activity's remaining retry budget.

### Snapshot and completion semantics

When Dex applies a `StepDecision`, it processes cancellation in this order:

1. Finish the Step execution that returned the decision and commit its successful Attribute and Channel writes. That execution cannot cancel itself.
2. Take one snapshot of all other Step executions that are currently queued or active.
3. Resolve both the global and sibling selectors against that same snapshot.
4. Cancel the matched executions.
5. Apply the decision's next or close action. Any Next Steps are created now, after cancellation has been resolved.

For example, suppose an existing `carrierA` execution is active and an existing `recordQuote` execution is queued when the winner returns:

Dex cancels those two existing executions. It then creates the new `recordQuote` execution requested by `goTo(...)`, so the new execution is not canceled by the same decision.

An `RPCResult` follows the same snapshot rule for its global selector, but there is no returning Step execution to exclude. Next Steps created by the RPC result are also created after cancellation has been resolved.

A target that is absent, completed, or already canceled is a successful no-op. Selectors do not cancel descendant Steps or future executions of a selected Step type.

Cancellation wins when the interpreter applies the resolved snapshot. Dex immediately applies the winner's next or close action and does not wait for target handlers to return. A target does not retry, follow a failure policy, publish output, write Flow state, or schedule recovery Steps. Responses arriving after cancellation are ignored. Attribute and Channel side effects committed by an earlier wait-for call remain committed.

Thread interruption and `Context.isCancellationRequested()` cannot make an external API call or database transaction atomic. Use timeouts, idempotency, or compensation where required. Heartbeats make cancellation reach a regular activity promptly; without them the Flow still proceeds, but a handler may run until its natural return or timeout.

Dex calls the backend SDK heartbeat API once per second while the regular Step activity is active. Temporal and Cadence throttle the actual requests sent to the service; Dex does not derive another interval from the configured heartbeat timeout.

Temporal eager regular activities still need heartbeats for prompt handler cancellation. Eager execution reduces activity dispatch latency; it does not change the SDK's heartbeat-based cancellation delivery described by the [Temporal Go SDK activity options](https://github.com/temporalio/sdk-go/blob/main/internal/activity.go).

### State and history

Canceled executions disappear from active Flow state. A queued target receives its normal execution number before cancellation completes. Cancellation does not add a Dex semantic history event; regular activity cancellation remains visible only in the backend workflow history.

## How Dex implements it

Concurrent Steps are separate durable executions under one Flow run, coordinated by the interpreter. Waiting is expressed as durable Conditions; completions rehydrate the Step Execute path. Step failure policies and recovery options are first-class. See [Step options](/references/step-options) for retry, lock keys, durability (`SYNC` / `ASYNC`), and recovery.

## Traditional workarounds

Without Dex, engineers encode branches in job tables, state machines in YAML, or ad-hoc “status” enums updated by cron workers. Homegrown retries live in application loops or queue consumers. Parallel work becomes thread pools plus Futures, or multiple workflows with correlation IDs. Winner flags, polling, and late-write suppression are common — and difficult to make atomic with the winning branch's durable decision.
