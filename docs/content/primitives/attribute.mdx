# Attribute

An **Attribute** lets you store data within a Flow execution, as persistence storage.

This is especially useful for intermediate data during a Flow execution. It eliminates the work of setting up and managing a database dependency.

Dex Attribute is not to replace your databases. An obvious limitation is that Attribute exists only for the lifetime of its Flow execution. Dex deletes it when it deletes the execution history, after the configurable retention period following Flow closure.

However, Dex allows you to sync Attribute values to your application database as permanent storage. This also lets you build more powerful database indexes to query Attributes.

## Use an Attribute {#define-an-attribute}

Define Attributes as part of the persistence schema of a Flow.

Then you can use the attribute within Step or RPC implementation to read or write the attribute. An attribute must be declared via PersistenceSchema before use. Otherwise, the worker will reject the operations.

When updating an attribute, setting it to null will delete it.

        StepList::start(&self.start)

        PersistenceSchema::new()

            .attribute(&self.email)
            .attribute_map(&self.progress)

    progress: AttributeMap<String>,

        self.status.set(context, "processing".to_owned())?;

        self.status.set(context, "completed".to_owned())?;
        Ok(StepDecision::graceful_complete(input))
    }

## AttributeMap {#attributemap}

An **AttributeMap** is a family of Attributes with keys decided at runtime. Use one when a Flow needs a changing set of small values, such as the status of each payment or each item in an order.

The reason for **AttributeMap** is to efficiently store a collection of data. Each Attribute is stored as a blob in Dex Server. Putting all data into a single Attribute means every update rewrites the whole blob. AttributeMap lets Dex Server store each instance as an independent blob for higher efficiency.

## Initial Attribute values {#initial-attribute-values}

**StartFlowOptions** can set initial Attributes when the Flow is created. Initial values and Flow creation are one operation, so the first Step sees them immediately. See [Flow options](/primitives/flow/flow-options#attributes).

Clients use **GetAttributes** and **SetAttributes** with the same registered Attribute definition. A Client can also use **WaitForAttributeEqual** to wait until a singleton Attribute or one AttributeMap instance reaches a scalar value. These are Flow operations through Dex Server; they do not read or write an application database directly. See [Client APIs](/primitives/client-apis).

## Indexed Attributes {#indexed-attributes}

An Attribute is not searchable unless you give its definition an **AttributeIndex**. Dex registers the index with the configured backend when the Worker starts, then updates it whenever that Attribute changes. You can use the field in **SearchFlows** queries.

Choose the index type from the value you plan to write. The index type is part of the Attribute contract. An index is for finding Flows; it is not a second source of truth or a substitute for **GetAttributes**.

| Index type | Value |
| --- | --- |
| **KEYWORD** | One exact string. |
| **FULL_TEXT** | Text for tokenized search. |
| **KEYWORD_ARRAY** | A list of exact strings. |
| **INT**, **DOUBLE**, **BOOL** | The corresponding scalar value. |
| **DATETIME** | A date and time value. |

A singleton Attribute uses its Attribute name as the index field unless you set an explicit index key. An indexed **AttributeMap** must use an explicit index key because all of its dynamic instances share one search field.

## Attribute Store projection {#attribute-store-projection}

Some applications need the same Flow state in their existing MySQL or PostgreSQL read model. Dex can asynchronously project selected Attribute writes to a Server-configured **Attribute Store**.

The Server configures the Store and destination table. The Flow selects it through **FlowConfig**, and each Attribute or AttributeMap definition explicitly opts in to **SyncToAttributeStore** or its SDK equivalent. Initial values and writes from Steps, RPCs, and Clients are then projected. The Flow Attribute remains authoritative: projection failures do not roll back a Flow write, and Dex does not backfill missed writes.

The SQL row is a latest-state projection. Deleting a synced Attribute projects SQL **NULL** when that column allows it. Changing the Attribute Store target changes future writes; mutations already queued keep the target selected when Dex accepted them.

This fits a read model, reporting table, or an entity orchestrated by one long-running Flow. It does not fit an external update that must be in the same business transaction as another database write. See [Entity Store](/design-patterns/entity-store) for a complete pattern.

## Locking {#locking}

One Attribute write is durable with its Step or RPC result. That alone does not make a read-modify-write sequence safe. Declare an Attribute lock on the Step method or RPC that performs that sequence. Dex acquires the requested locks together before invoking the handler, then releases them when that invocation finishes.

**WaitFor** and **Execute** have separate lock options. Add the lock to the method that actually reads and changes the value. Client **GetAttributes** followed by **SetAttributes** is not a locked read-modify-write operation; put that operation in an RPC when it must be serialized.

Keep the locked set small. Locking an unrelated Attribute reduces concurrency, and missing a conflicting Attribute leaves a race. RPC Attribute locking uses Temporal synchronous Updates and is unavailable with Cadence. Step Attribute locks work through normal Step execution.
