# Stream

**Stream** is a typed, best-effort, resumable message feed for low-latency UI updates. A Step or Client writes messages immediately. A Client reads them in order and carries an opaque resume token from one read to the next.

Use a Stream for information that improves the live experience but is not part of workflow correctness:

- LLM reasoning summaries, generated-text chunks, and agent progress
- progress bars, diagnostic events, and live previews
- transient status shown while a Step is still running

Do not use a Stream for commands, payments, approvals, or state needed to recover a Flow. Use [Channel](/primitives/channel), [Attribute](/primitives/attribute), or an external durable store for those.

| Property | Stream | Channel |
|---|---|---|
| Delivery goal | Best effort and low latency | Durable workflow communication |
| Reader | Client | Step wait or Client publish |
| Retention | Approximate shared byte budget | Flow history and persistence |
| Resume | Opaque token | Consumed by a Step condition |
| Affects Flow decisions | No | Yes |

## Define and register a Stream

A Stream has a stable name, a message type, and **maxEstimatedBytes**. Register the same definition in exactly one Flow persistence schema.

This example writes a progress message before its Step returns. The write becomes visible as soon as Dex accepts it; the Client does not wait for the Step to complete.

    def __init__(self, progress: Stream[str]) -> None:

## Step write semantics

A direct Step write has these semantics:

- Dex sends it immediately during **Execute**. It is not buffered until the Step completes.
- A later Step failure does not roll the message back.
- One Step execution can write once to each Stream. Dex derives the idempotency key from the run ID and Step execution ID, so a retry does not append the same message again.
- RPC handlers cannot write through the Step Context.

For token-by-token output from one long LLM call, write through a Client with a stable sequence of idempotency keys. The [AI agent email example](/use-cases/ai-agent-email) uses that pattern inside an async Step.

## Client writes and idempotency

A Client can write even when the Flow instance does not exist or is no longer active. Supply a non-empty idempotency key for every logical message. The key must not contain **#**, which Dex reserves for Step-generated keys.

While a key remains retained, repeating it is a successful first-write-wins no-op. Once trimming removes the message and its idempotency record, the same key may append again. Idempotency therefore has the same best-effort retention window as the message.

## Resumable reads

**ReadStream** returns one message with its value, resume token, creation time, and producer idempotency key.

- An empty token starts at the current retained head.
- A token older than the retained head also starts at that head.
- Pass the returned token unchanged to read the next message.
- When no next message exists, the call long-polls until a message arrives or the wait expires.
- In Go, cancel or bound the read with **context.Context**. Other SDKs also accept an explicit server wait duration.

Resume is best effort. A slow reader can miss messages trimmed before its next read.

## Approximate capacity

**maxEstimatedBytes** is not a per-Flow limit and it is not an exact Redis memory measurement. It is an approximate retained-byte budget shared by every Flow ID with the same Flow type and Stream name.

Dex charges the serialized value, identity bytes, and configured per-message overhead. This estimate deliberately avoids expensive exact memory accounting. When usage crosses the trim trigger, one background trimmer removes the oldest messages across all instances until usage reaches the trim target. A write at full capacity can fail while trimming catches up; callers should drop or retry non-critical updates according to their latency needs.

The server also limits each serialized Stream value separately. The default is 100 KiB.

## Best-effort storage

The Stream Store can use Redis for multi-server deployments or memory for a single local server. Memory contents disappear when that process restarts. Redis survives an application restart, but trimming, Redis loss, disabled storage, or capacity pressure can still remove or reject messages.

Design the UI so missing chunks are acceptable. Durable business state belongs in Flow primitives or an external system of record.
