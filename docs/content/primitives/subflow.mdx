# SubFlow

A **SubFlow** is an independently addressable Dex Flow used as a durable `Wait` Condition. Dex starts it as a normal Temporal or Cadence Workflow and resumes the parent Step only when the declared condition is satisfied.

## Why you need it

Fan-out work, child billing, or a nested durable process should be its own Flow — with its own ID, history, retries, and lifecycle — while the parent waits without polling.

The zero-based result index is the stable order of SubFlow conditions in the current `Wait`. An
`allOf` result is terminal. If another condition wins an `anyOf`, the unfinished SubFlow result has
status `RUNNING` and no outputs. `RUNNING` is the parent’s durable snapshot, not a fresh backend
query.

See the [parent–child](/design-patterns/parent-child) pattern for a smaller example.

## Identity and stopping an `anyOf` loser

Dex generates IDs that application code cannot override:

```text
Flow ID    SubFlow:{parentFlowID}-{stepExecutionID}-{index}
request ID {parentRunID}{stepExecutionID}
```

`FlowResult` contains only status, failure, and output data. Generate the stable SubFlow Flow ID
from the current execution context when the application needs its identity. A losing SubFlow
continues independently; stop it explicitly when that is the application’s desired cleanup policy:

An external worker or service can consume that ID and call `Client.stopFlow`. Completion can race
with the stop request, so callers should treat an already-closed Flow as a successful cleanup.

Dex reserves `:` in application-created Flow IDs so `StartFlow` cannot occupy the
`SubFlow:` namespace. Operations targeting an existing SubFlow, including RPCs and stops, accept
its generated ID. Clients with direct Temporal or Cadence access must also leave this namespace to
Dex. Step types cannot contain `/`, `$`, or `:` because their Step execution IDs are embedded in
generated SubFlow IDs and readable blob paths.

Every SubFlow execution also has the keyword Search Attribute `DexParentFlowID`. Query it to list
all SubFlows for one parent. Together with the generated SubFlow Flow ID, it identifies the source
Step execution ID and condition index without copying parent metadata into workflow input.

## Reuse behavior

`SubFlowOptions` defaults to `RESTART_IF_PREVIOUS_EXITS_ABNORMALLY`:

| Existing execution | `ATTACH` | `RESTART_IF_PREVIOUS_EXITS_ABNORMALLY` | `ALWAYS_RESTART` |
| --- | --- | --- | --- |
| Missing | Start | Start | Start |
| Running | Attach | Attach | Terminate and start |
| Completed | Return result | Return result | Start |
| Failed, canceled, timed out, or terminated | Return result | Start | Start |

The same request ID always attaches or returns the existing result. This makes retries
safe when the backend accepted a start but the local activity response was lost. Backend ID reuse
policies provide only the atomic start operation; Dex describes and resolves the existing execution
before invoking it.

Options also support initial Attributes. Flow ID, request ID, and already-started suppression are
intentionally server-owned.

SubFlow timeouts use the same Dex soft-timeout policies as top-level Flows. A handler policy
targets the child Flow's registered timeout hook; fail and cancel results are reported durably to
the parent before the child backend execution closes.

## Continue-as-new and lifecycle

Across continue-as-new, Dex replaces the SDK declaration with a durable waiting-condition state.
Each SubFlow entry retains only its Condition ID; list position remains its stable index. SubFlow
starting Step input, Step options, SubFlow options, request ID, parent Flow ID, and Flow type are not
copied into the snapshot. Received terminal results remain beside the state so partial `allOf` results
survive without restarting already-started SubFlows.

Parent completion, failure, cancellation, time travel, or restart does not automatically cancel a
SubFlow. A SubFlow reports terminal completion to the current parent execution by parent Flow ID.
If the parent is already closed or no longer exists, Dex records
`PARENT_CLOSED_OR_NOT_FOUND` in the reporting local activity result and completes the SubFlow
normally.

Hard termination and Workflow execution timeout cannot run the reporting local activity. A parent
waiting only for that completion signal may therefore remain waiting. Use cooperative cancellation
when completion delivery is required, or time travel/restart the parent so reuse handling can read the
SubFlow’s terminal result directly.
