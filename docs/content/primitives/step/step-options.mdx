# Step options

This page covers the advanced **StepOptions** features to deeply customize your Step type. See the [Basic Step](/primitives/step/basic#stepoptions) page for the basic features.

## Retry After

Use **RetryAfter** if you want to deeply customize the retry behavior. It overrides the retry schedule of the **RetryPolicy**.

Retries recover from failed attempts. Do not use **RetryAfter** to wait for an external system; use the [Polling](/design-patterns/polling) pattern.

A retry of one **Execute** call reuses the [state snapshot](#selective-state-loading) that Dex took when it handed the first attempt to a Worker, so it does not see Attribute writes made after that. To wait for an external write, have the writer also publish a [Channel](/primitives/channel) message, directly or from an RPC handler, and wait on that message in the **WaitFor** of the next Step. Alternatively, the next Step can wait on a [Timer](/primitives/timer) and read fresh state when it runs.

## Durability {#durability}

**SYNC** durability records the Step completion in Dex Server and persists it to storage synchronously. It also makes the attempt start durable in storage before the Worker receives the task.

**ASYNC** durability does this asynchronously. Dex Server hands the task to the Worker and starts the next work before the start and the completion are persisted, and it batches these commits within about 20 milliseconds. Sustained server throughput is about the same for both modes. **ASYNC** has lower latency, and a single Flow runs faster. On object storage with low write latency, **ASYNC** also makes far fewer requests.

If a Dex Server node fails before the commit, a recent **ASYNC** result is lost. The method runs again, and so does any later work that started from that result. If the node fails before the **ASYNC** start was persisted, Dex rolls the start back and runs the same attempt number again. This consumes no retry, and the attempt can see different input. Two executions of the same attempt number can overlap, and Step Stream writes can repeat in the same source. Make **ASYNC** methods and the work they start idempotent.

For either mode, the attempts of one Step are not strictly sequential. Cancellation is cooperative, so an interrupted execution may still run while the next attempt or the failure route starts.

Choose **SYNC** for effects that need the tightest guarantees. Choose **ASYNC** for short Steps where latency matters and a rare rerun is acceptable. See [Failure and redelivery](/primitives/step/basic#failure-and-redelivery) for the full comparison.

Dex pins the durability when a method call becomes pending. Changing **step_durability** in the Flow config affects only method calls scheduled afterward.

**SYNC** is the default. Dex resolves durability in this order: a method override in **StepOptions**, the Flow's **FlowConfig**, then **SYNC**.

Durability changes when Dex Server persists an attempt start and a result. With **SYNC**, the start is durable before the task goes to the Worker. With **ASYNC**, Dex Server does not wait for the start to be persisted, so the task can go out before the start is durable. Retry policy, method timeout, and heartbeat settings apply to every attempt in both modes. The default method attempt timeout is two hours, and the default heartbeat timeout is one minute.

The method timeout and the heartbeat timeout start when Dex sends the task to the Worker. Waiting for locks or for a Worker does not count. The deadline in the task is the send time plus the method timeout.

The default total retry duration (**TotalDuration**) is four hours for both durability modes. An explicit retry duration may be shorter or longer. **TotalDuration** starts when Dex first hands attempt 1 to a Worker. If attempt 1 was returned without running, the clock resets. Dex uses **TotalDuration** only after an attempt fails, to decide whether to retry. It never cuts a running attempt, so the last attempt can start or end after **TotalDuration**. Only the method timeout limits a single attempt. To bound one long attempt, set **ExecuteMethodTimeout** or **WaitForMethodTimeout**, not **TotalDuration**. The server no longer produces the RETRY_DEADLINE failure kind. The SDK helper **IsRetryTotalDurationExceeded**, and its equivalent in other SDKs, can be true only for records from before the upgrade.

## Heartbeat {#heartbeat}

During an attempt, the Worker must send a heartbeat or a [Stream message](/primitives/stream) before the **HeartbeatTimeout** expires. In other words, sending a Stream message is an implicit heartbeat.

**HeartbeatTimeout** defaults to one minute. The default allowed minimum is 10 seconds.

For example, an **Execute** method timeout of 60 seconds and a **HeartbeatTimeout** of 10 seconds lets Dex retry the Step in about 10 seconds instead of waiting for the full 60 seconds.

To wait for an external system in one heartbeating Step, use the [Polling](/design-patterns/polling) pattern.

A heartbeat can persist a checkpoint value. The next attempt receives the latest value and can resume from it. An explicit heartbeat without a value clears the previous checkpoint. An implicit heartbeat from a Stream message preserves the latest explicit state, including an explicitly cleared state.

```go
	return &dex.StepOptions{

func (step heartbeatStep) Execute(ctx dex.Context, batches int) (*dex.StepDecision, error) {
	completedBatches := 0
	if _, err := ctx.GetLastHeartbeatValue(&completedBatches); err != nil {
		return nil, err
	}
	for batch := completedBatches; batch < batches; batch++ {
		select {
		case <-ctx.Done():
			return dex.DeadEnd(), nil
		default:
		}
		time.Sleep(2 * time.Second)
		if err := ctx.RecordHeartbeat(batch + 1); err != nil {
			return nil, err
		}
	}
	return dex.GracefulComplete("processed"), nil
}
```

## Timeouts and total duration {#timeouts-and-total-duration}

Three options bound the time a Step method can take.

| Limit | Option | Enforcement |
| --- | --- | --- |
| Longest single attempt | **WaitForMethodTimeout** or **ExecuteMethodTimeout** | Dex times out the attempt. Another attempt starts only while **TotalDuration** has time left. |
| Time budget for retries | **TotalDuration** in the retry policy | The budget starts when Dex first hands attempt 1 to a Worker. After an attempt fails, Dex retries only while the budget has time left. It never stops an attempt in progress. |
| Stalled Worker | **HeartbeatTimeout**, one minute by default | Dex times out an attempt that sends no heartbeat or Stream message within this window. The retry policy then starts another attempt. See [Heartbeat](#heartbeat). |

A method timeout defaults to two hours, and the server has no hard cap. **TotalDuration** defaults to four hours.

To bound a long wait, set the method timeout and **TotalDuration** to the same maximum. Dex enforces both, so the Step does not need its own deadline. **TotalDuration** only decides whether to retry after a failure, so the last attempt can end after it. With Workers available, the total wait is at most about **TotalDuration** plus one method timeout. Give the retry policy a few attempts with backoff for transient errors and Worker crashes.

When a timeout expires, Dex fails the attempt with a timeout error. After retries end, the failure policy decides what happens next. If no failure route is configured, the Flow fails. See [Execute Failure Recovery](/design-patterns/failure-handling/execute-failure-recovery). For a long wait on an external system, see [Polling](/design-patterns/polling).

## Selective state loading {#selective-state-loading}

Every **WaitFor**, **Execute**, and timeout-handler call receives all ordinary Attributes and size metadata for every Channel and ChannelMap instance. AttributeMap values and pending Channel messages are not loaded unless that method selects them.

**StepOptions** has separate selections for **WaitFor** and **Execute**. Select an entire AttributeMap or ChannelMap when the method must enumerate current instances. Select an exact map instance when its key is already known. An Attribute lock controls concurrency but does not load the AttributeMap value.

The two methods receive independent snapshots. **Execute** reads its snapshot after the winning Wait conditions consume their messages, so it does not see those consumed messages again. Dex takes the snapshot of attempt 1 when it hands the attempt to a Worker. Retries of one logical method call, and attempts that return to pending, reuse that snapshot.

This Step loads pending **Queued** messages only for **Execute**. It deletes the first pending message in the same successful handler response.

## Attribute locks

Concurrent Steps and RPC invocations can read and write the same Attribute. This can lead to race conditions. To avoid this, use Attribute locks. Dex Server ensures only one Step execution or RPC handling can acquire the lock at a time.

**WaitFor** and **Execute** have separate lock sets. Set them by returning **StepOptions**.

An attempt keeps its locks while it waits to run again after a return, for example when a Worker declined its Step type. Transactional RPCs on those keys get a lock conflict meanwhile.

See [Attribute locking](/primitives/attribute#locking) for more details.

## Provide StepOptions Dynamically {#stepoptions-override-per-stepexecution}

The **StepOptions** returned by a Step implementation apply to every Step execution by default. Sometimes it is useful to override them dynamically for a certain Step execution.

Provide the **StepOptions** override when a **StepDecision** goes to the next Steps.
