# Step Basic Features

**Step** is the basic building block of background execution. This page covers the default shape of a Step: typed input, optional **WaitFor**, required **Execute**, movement with **StepDecision**, and the default **StepOptions** behavior.

A Dex Step is implemented by native code. The struct or class that implements the Step determines the **StepType**. In most languages, the SDK derives the StepType from the native type name unless you override it.

The same Step type can execute multiple times in one Flow. Each execution is a **StepExecution**, identified by a **StepExecutionID** in the form **StepType**-**Number**. Dex assigns and maintains that identifier.

## Step input {#step-input}

A step usually has an input that is uniquely persisted for this step execution.

Since a step can run multiple times and even in parallel, step input is very useful to tell the differences of different StepExecutions of the same step type.

The start Step of a flow is also the input of the flow.

For most languages, step input is strongly typed, when writing code to start a flow, or go to next step(s),


## WaitFor and Execute {#waitfor-and-execute}

A Step implementation has one or two small methods: **WaitFor** -> **Execute**.

**WaitFor** is optional. It returns a durable **Wait** to Dex Server. Dex persists that waiting state, evaluates the conditions on your behalf, and invokes **Execute** after the wait is satisfied.

If a Step does not implement **WaitFor**, **Execute** runs immediately.

**Execute** is required. It returns a **StepDecision** that moves to the next Step, branches to several Steps, or closes the Flow.

Each **WaitFor** or **Execute** invocation is a separate commit boundary. Dex Server stages the Attribute writes and Channel publications from that method, then commits them with its **Wait** or **StepDecision** only after the method returns successfully. If the method fails, none of those durable changes are committed. **WaitFor** and **Execute** do not share a commit. External API calls are outside this atomic boundary.

Before its final **Wait** or **StepDecision**, a handler can send [heartbeat checkpoints](/primitives/step/step-options#heartbeat) and any number of best-effort [Stream messages](/primitives/stream). The response stream must end with exactly one final result. These progress frames are not part of the method's commit, and a Stream Store failure does not fail the Step.

### Durable WaitFor

WaitFor returns **Waiting** to server using **WaitingType** and the conditions to wait for. Server persist the waiting state and evaluate the condition on any related changes happened. So the waiting is **durable**.

There are three waiting types: **AnyOf**,**AllOf**,**AnyCombinationOf**.

AnyOf and AllOf are the most frequently used/needed. See [AnyCombinationOf](/primitives/step/waiting-condition) as advanced feature.

As the name says,

* the waiting condition is met when anyOf conditions is met.
* the waiting condition is met when AllOf conditions are met.

[Timer](/primitives/timer), [Channel](/primitives/channel), and [SubFlow](/primitives/subflow) are the conditions that the waiting type can wait on.

**Until**, **AnyOf**, and **AllOf** accept Conditions without condition IDs. Do
not add IDs merely because a Condition is nested in one of these waits.
**AnyCombinationOf** is the exception: every referenced Condition needs a
unique condition ID.

## StepDecision {#stepdecision-movements}

A StepDecision can go to a single or multiple next steps.

This is how you build branching, looping, and parallel work.

<StepDecisionMovementsDiagram markdownDescription="GoTo: ExampleStep returns GoTo(Complete Flow), which completes the Flow. GoToMany: ExampleStep starts StepA and StepB, which run in parallel. Loop: ExampleStep goes to ProcessStep, and ProcessStep goes back to ExampleStep." />

See more in the [Parallel Steps](/design-patterns/parallel) and [Parallel SubFlows](/design-patterns/parallel-subflows) patterns.

Step Decision can also complete or fail the flow:
* **GracefulComplete** will complete the flow when there are no more steps active in the flow
* **ForceComplete** will complete the flow immediately
* **Fail** will fail the flow immediately

And they all can return flow output so that client can wait and retrieve as **FlowResult**.

See more advanced [Step decision](/primitives/step/step-decision) for **DeadEnd**, **Cancellation**, **forceCompleteIfChannelsEmpty**.



## StepOptions {#stepoptions}

**StepOptions** is extremely powerful to customize the behavior of a step.

Most of the times, you need to customize failing handling -- timeout, retry and failure policy.  There are more advanced [Step options](/primitives/step/step-options) like heartbeat, durability etc.

* **Timeout** customize the timeout of a single attempt of the method(WaitFor/Execute) invocation.
* **Retry policy** — re-invokes the **same** method on the **same** Step execution until attempts are exhausted.
- **Failure policy** — decide what happens **after** retries end. Default is to fail the Flow. But WaitFor can run Execute anyway, or Execute can go to a recovery Step.

Configure by implementing the step method to return a StepOptions.

### WaitFor failure policy

When WaitFor method retries are exhausted:

- **FailFlow** — Fail the flow. This is the default.
- **PROCEED** — Continue to invoke Execute.

With **PROCEED**, the same Step's **Execute** receives the durable input unchanged. **waitForMethodFailed()** returns true. **getRecoveryError()** has the error_type and detail from the final failed WaitFor attempt.

### Step Failed events and last failure info

- Terminal events **StepExecuteFailed** / **StepWaitForFailed** carry failure output when the Step ultimately fails.
- **During retries** (before failure policy runs), Step events and live Flow state expose **lastFailureInfo** — the most recent attempt's error (type, detail, worker metadata).
- In Dex Web, open event details to see **Last failure** while retries are in flight. Active Steps in the Flow overview also show lastFailureInfo.

Last failure info describes **retry attempts**. Failure policy decides what happens once retries end.

## Failure and redelivery {#failure-and-redelivery}

Retries and failure routes handle attempts that fail. Some failures leave Dex without knowing whether the work ran. A Step with an external effect that must not repeat, such as a payment or an email, has to plan for these cases. This section states what an application can rely on today.

### Heartbeats are not acknowledged {#heartbeats-not-acknowledged}

A heartbeat call returns once the Worker has queued or sent it. It does not wait for Dex to store anything. Python's **heartbeat**, Go's **RecordHeartbeat**, Java's and TypeScript's **recordHeartbeat**, and Rust's **record_heartbeat** all behave this way. A returned heartbeat call does not prove that Dex stored the checkpoint. This holds for SYNC Steps too, even though a SYNC Step runs user code only after Dex made the attempt start durable.

Heartbeat checkpoints are lossy. Dex batches them and keeps only the latest value of each batch. A checkpoint can also be lost when the attempt ends, such as on a timeout or a cancellation, or when a Dex Server node fails. After an interruption, the next attempt receives the last checkpoint that Dex stored. That checkpoint can be older than the last one the Step sent. Do not use a checkpoint as the only record that an external effect happened.

### An attempt starts when Dex hands it to a Worker {#same-attempt-redelivery}

A Step attempt starts at the moment Dex hands it to a Worker. Dex first reserves an idle Worker slot. It then records the start. This is the record that pins the attempt's input snapshot and takes its Attribute locks. Dex sends the task last. For a SYNC Step, the start is durable in object storage before the Worker receives the task. An ASYNC Step does not wait for that write.

Once Dex handed an attempt to a Worker, Dex never hands the same attempt number to another Worker. If the Worker crashes or its connection breaks, the attempt fails whether or not it sent output. The retry policy then runs: it consumes a retry and waits for the backoff. If a Worker stops responding without disconnecting, the attempt fails when its heartbeat timeout expires. A server restart or failover does the same for every attempt that was handed out. Those attempts fail with the failure kind STARTED_ATTEMPT_INTERRUPTED. SYNC and ASYNC behave the same in these cases.

A few cases return the attempt to pending instead. The attempt keeps its attempt number, its input snapshot, and its locks, and it consumes no retry. This happens only when the Worker certainly never ran the attempt:

- The Worker declines the Step type as unknown. Dex then avoids that Worker for that Step type.
- The task never reached the Worker, because the stream closed before the send or the send failed.
- A Worker that uses reserved-slot dispatch closes its stream cleanly while the task has no output yet. This is a normal Worker shutdown. A shutting-down Worker finishes its running tasks, sends their results, and then closes. Tasks that arrive while it closes are not run and return to Dex.
- An older SDK Worker declines the task for lack of capacity.

An ASYNC Step has one more case. If a Dex Server node crashes before Dex wrote the ASYNC start to object storage, Dex rolls that start back. The same attempt number then runs again, with no retry consumed and possibly on different input. So for ASYNC, one attempt number can run twice, and the two executions can overlap. Step Stream writes can then repeat in the same source.

For both durabilities, the attempts of one Step are not strictly sequential. Cancellation is cooperative, so an interrupted execution may still run while the next attempt or the failure route starts.

| | SYNC (default) | ASYNC |
| --- | --- | --- |
| Workers one attempt number reaches | At most one, except when the attempt returns to pending as described above. | At most one, except a rollback after a node crash can run the same number again. |
| Start and execution order | The start is durable before the Worker receives the task. | The Worker can run before the start is durable. |
| Worker disconnect or node failover | The attempt fails and the retry policy runs. | The same. A node crash before the start was written is the rollback case. |
| **attempt_progress** | **NOT_STARTED** or **NOT_COMPLETED**. | Always **NOT_COMPLETED**. |
| Overlapping attempts | Possible after cancellation, because cancellation is cooperative. | Possible after cancellation, and between two executions of the same attempt number. |
| Step Stream writes | Can repeat across attempts. | Can also repeat within one attempt number, in the same source. |
| When to use | Effects that need the tightest guarantees. | Short Steps where latency matters and a rare rerun is acceptable. |

### A failure route cannot tell whether the work ran {#unknown-outcome}

A Step attempt that no Worker takes does not fail. It waits in the durable task queue, uses no retry, and runs when a Worker takes it. Only an RPC fails when no Worker takes it within the dispatch wait. A Step attempt that does fail can fail before or after a Worker received it, and its error type and detail alone do not always tell which.

The recovery error (**RecoveryErrorInfo**) also carries **attempt_progress**. It is the furthest progress across all attempts of the failed method call:

- **NOT_STARTED**: no attempt ever reached a Worker that could have run it. The handler certainly did not run.
- **NOT_COMPLETED**: at least one attempt was handed to a Worker and may have run, but none completed.
- **UNSPECIFIED**: an older server did not report progress, or the call started before the upgrade. Treat it like **NOT_COMPLETED**.

ASYNC failures always report **NOT_COMPLETED**, because a rolled-back execution may have run.

**NOT_COMPLETED** is conservative. Dex can report it although the Worker never ran the handler:

- The server crashed after the start was durable but before the task reached the Worker.
- The connection broke right after Dex wrote the task but before the Worker read it.
- The Worker declined the task or closed cleanly, but the server crashed before it recorded that.
- A failure inside the SDK before it called the handler, such as reading input blobs or decoding. Dex reports this as a normal Worker error. A misconfigured **FlowServiceAddress** makes every attempt with blob inputs fail this way. **values.hydrateBeforeDispatch** avoids it.

A failure route can rely on **NOT_STARTED** to mean the work did not run. It cannot rely on **NOT_COMPLETED** to mean the work ran. The Flow's history records what Dex knows, and Dex Web shows it.

### Design for these limits {#design-for-redelivery}

- Make each external effect idempotent. Key it by an ID that stays the same across attempts, such as the Flow ID and the Step execution ID, or your own business key. Send the key to the service that applies the effect, so that it applies the effect once.
- Treat a Step with a single attempt as at most once only within these limits. An interrupted attempt may have made its call, and a cancelled execution may still run. Its failure route can run although the work happened, or although it never ran. For ASYNC, the same attempt number can also run twice.
- Reconcile an unknown outcome. When a failure route sees **NOT_COMPLETED**, check the target system by the idempotency key or your business key before you repeat or report the effect. Record the outcome you find in the Flow.

For the agent packages' single-attempt tool Steps, see [Tool call limits](/production/agents#tool-call-limits).
