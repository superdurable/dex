# Flow

A **Flow** is the top-level primitive in Dex. A Flow type describes one kind
of business process, such as an order, a subscription, or an approval. A Flow
execution is one instance of it, such as order 42.

Dex owns the Flow's lifecycle and state. Your code does not need a database
or a job queue to keep the process going across crashes and restarts.

## When to use a Flow {#when-to-use}

Use one Flow for each business identity whose process Dex should own. Put work
that shares that identity and lifecycle into [Steps](/primitives/step) of the
same Flow. Steps can run in parallel inside one Flow.

Start a separate Flow when the work has its own owner and lifecycle. Two Flows
coordinate through RPCs and Channels. Use a [SubFlow](/primitives/subflow) only
when a parent Step must wait for a child Flow's result.

## Guarantees {#guarantees}

- A Flow ID has at most one active run at a time.
- Each Step method commits its state changes together with its result, or not
  at all.
- With the default SYNC durability, a Step's result is stored durably before
  the next Step starts. It survives Worker crashes and Dex Server restarts.
- A Step that no Worker takes waits in a durable queue. It runs when a Worker
  becomes available.

## What a Flow contains {#implement-a-flow}

You define a Flow by implementing the **Flow** interface in your language. It
declares three things:

- <a id="steps"></a>**Steps**: the start Step and every other Step the Flow can reach.
  [Steps](/primitives/step) run the background work.
- <a id="persistence-schema"></a>**Persistence schema**: the [Attributes](/primitives/attribute) and
  [Channels](/primitives/channel) that hold the Flow's durable state. Dex
  rejects reads and writes to names that are not declared.
- <a id="rpc-handlers"></a>**RPC handlers**: methods that a client calls on a running Flow. See
  [RPC](/primitives/rpc).

The start Step's input type is also the Flow's start input type. This Flow has
two Steps, one Attribute, one Channel, and one RPC.

## Identifiers {#identifiers}

The word Flow can mean a Flow definition or a Flow execution. The context tells
which. These identifiers keep them apart.

| Identifier | Who sets it | Meaning |
|----------|-------------|---------|
| **FlowType** | Application (via Flow implementation) | Stable type name Dex uses to route Worker calls and search results. |
| **Flow ID** | Application client on start | Business identity for one Flow execution. The ID reuse policy controls whether another execution may start with the same Flow ID. |
| **Run ID** | Dex Server | Identity of one run of the Flow ID. Time travel keeps it and creates a new run attempt. Address a Flow by its Flow ID; the Run ID is diagnostic. |
| **StepType** | Application (via Step implementation) | Stable name for a Step definition inside the Flow. |
| **StepExecutionID** | Dex Server | One execution of a Step type, formatted as **StepType-Number**. |

Most SDKs derive the **FlowType** from the native type name unless you override
it. Keep these names stable while executions are open.

## Lifecycle {#lifecycle}

A [Client](/primitives/client) starts a Flow with a Flow ID and the start
input. Dex then runs the start Step on a Worker. Each Step returns a decision
that moves to the next Steps or closes the Flow. Several Steps can be active
at the same time.

A Flow closes when a Step completes or fails it, when its timeout fails or
cancels it, or when a client stops it. A timeout can instead run a handler that
decides the outcome. While it runs, clients read and change it through RPCs
and Channels.

## Start options and configuration {#start-options}

Two sets of options shape a Flow execution:

- **StartFlowOptions** apply once, at start. They set the Flow timeout, the ID
  reuse policy, the start request ID, and initial Attribute values.
- **FlowConfig** holds runtime settings, such as the default Step durability.
  You can update it while the Flow runs.

Start a Flow directly with a stable business Flow ID. Do not read or search
first to avoid a conflict. To retry one start safely, send the same request ID
each time. Dex then returns the same execution instead of an error.
