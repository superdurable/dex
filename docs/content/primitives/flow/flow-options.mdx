# Flow options

Dex allows you to customize the behavior of a Flow execution.

- **StartFlowOptions** apply when a client starts a Flow (or SubFlow). They are immutable after start.
  - They control timeout, ID reuse, cron schedule, initial Attributes, request idempotency, and optional config overrides for that execution.
- **FlowConfig** provide runtime behavior. They are mutable after start.
  - Step durability defaults, Worker routing, active-Step search indexing, continue-as-new thresholds, and Attribute Store projection targets.

## StartFlowOptions {#start-flow-options}

| Field | Purpose                                                                |
|-------|------------------------------------------------------------------------|
| **Timeout** | Flow timeout. Omit it or set zero to disable it.                       |
| **TimeoutPolicy** | What happens when the flow timeout fires.                              |
| **IDReusePolicy** | How to reuse existing Flow ID to start                                 |
| **RequestID** | Idempotency key for retrying one start request.                        |
| **AlreadyStartedOptions** | How to handle an already-started Flow.                                 |
| **CronSchedule** | Cron expression for recurring starts.                                  |
| **RetryPolicy** | Retry policy for one Flow execution after failure.                     |
| **StartDelay** | Delay before the start Step to run.                   |
| **Attributes** | Initial Attribute values.                            |
| **FlowConfig** | Per-execution Flow configuration |

```go
func reliableStartFlowOptions() (sdk.StartFlowOptions, error) {
	initialStatus, err := sdk.InitialAttribute(Status, "queued")
	if err != nil {
		return sdk.StartFlowOptions{}, err
	}
	timeout := 30 * time.Minute
	startDelay := 5 * time.Minute
	requestID := "start-order-123"
	stepDurability := sdk.StepDurabilitySync
	return sdk.StartFlowOptions{
		Timeout:       &timeout,
		TimeoutPolicy: sdk.TimeoutFail,
		StartDelay:    &startDelay,
		IDReusePolicy: sdk.IDReuseDisallow,
		RetryPolicy: &sdk.FlowRetryPolicy{
			InitialInterval:    time.Minute,
			BackoffCoefficient: 2,
			MaximumInterval:    10 * time.Minute,
			MaximumAttempts:    3,
		},
		Attributes: []sdk.InitialAttributeDef{initialStatus},
		ConfigOverride: &sdk.FlowConfig{
			StepDurability: &stepDurability,
		},
		AlreadyStarted: &sdk.AlreadyStartedOptions{IgnoreError: true},
		RequestID:      &requestID,
	}, nil
}
```

### Timeout and TimeoutPolicy {#timeout-and-timeout-policy}

**Timeout** is a durable timer for the whole Flow. A policy is valid only with a positive timeout. **FAIL** fails the Flow with a timeout error, which may be retried by **RetryPolicy**. **CANCEL** cancels the Flow and does not retry it. **HANDLER** invokes the Flow timeout handler once.

When the SDK can inspect the Flow definition, the default policy is **HANDLER** when the Flow implements a timeout handler and **FAIL** otherwise. **HANDLER** without a timeout handler is invalid. Continue-as-new preserves the existing timeout deadline. A retry starts a new timeout budget.

### Flow ID, RequestID, and AlreadyStartedOptions {#flow-id-request-id-and-already-started}

**IDReusePolicy** answers a business-lifecycle question: may a new start use this Flow ID? **RequestID** answers a transport question: is this call a retry of the same start request?

| ID reuse policy | Result |
|-----------------|--------|
| **IDReuseDefault** | Use the server policy. The StartFlow default permits reuse when no run is active. |
| **IDReuseAllowIfPreviousFailed** | Reuse only after a failed run. |
| **IDReuseAllowIfNotRunning** | Reuse after any closed run, but not while one is active. |
| **IDReuseDisallow** | Reject every reuse of the Flow ID. |
| **IDReuseTerminateIfRunning** | Terminate an active run before starting its replacement. |

Use a stable **RequestID** when a caller may retry after losing the StartFlow response. Send the same Flow ID, start input, options, and RequestID again. With **AlreadyStartedOptions.IgnoreError** enabled, Dex returns the existing Run ID only when that existing Flow was started with the same RequestID. A different RequestID remains an already-started conflict; **AlreadyStartedOptions** does not attach to an unrelated Flow.

### RetryPolicy and CronSchedule {#retry-policy-and-cron-schedule}

**RetryPolicy** controls retries of one Flow execution after it fails. **MaximumAttempts** includes the initial execution. **InitialInterval**, **BackoffCoefficient**, and **MaximumInterval** define exponential backoff. A timeout with **FAIL** is one failure that can use this policy; a timeout with **CANCEL** is not retried.

**CronSchedule** asks the configured backend to start recurring executions. It is separate from Flow retry: retries recover a failed execution, while cron creates future scheduled executions. Backend scheduling behavior, including overlap and missed-run handling, is backend-defined. See the [cron schedule pattern](/design-patterns/cron) before using it in production.

### StartDelay {#start-delay}

**StartDelay** accepts the Flow start now and postpones when its start Step becomes eligible. Use it for a one-off deferred start, such as waiting five minutes before processing a newly created order. It does not create a recurring schedule; use **CronSchedule** for that.

### Attributes {#attributes}

**Attributes** initialize durable state before the start Step runs. Each initial value must correspond to an Attribute or Attribute map declared in the Flow persistence schema. Attribute-map values also require an instance key. Dex rejects undeclared names, duplicate values for the same physical key, and definitions whose map, index, or synchronization settings differ from the registered Attribute.

Build initial values with the SDK's **InitialAttribute** and Attribute-map helper rather than manually encoding them. The start Step can read the initialized values normally.

## FlowConfig {#flow-config}

Use **ConfigOverride** in **StartFlowOptions** to customize one Flow's initial effective configuration. Its fields patch the deployment's default **FlowConfig**; it does not replace that configuration wholesale.

At start, **ConfigOverride** applies the supplied **FlowConfig** fields over the server default. Omitted fields retain their server default values.

| Field | Behavior |
|-------|----------|
| **ActiveStepSearchMode** | Index all active Steps, only Steps that have run **WaitFor**, or no active Steps. The default indexes Steps with **WaitFor**. |
| **ContinueAsNewThreshold** | Number of tracked events before Dex automatically continues as new. Zero disables automatic continue-as-new. |
| **ContinueAsNewPageSizeBytes** | Page size for state transferred during continue-as-new. Zero uses 1 MiB. |
| **StepDurability** | Default durability for Step writes. A Step-level override wins; recovery paths use synchronous durability unless explicitly overridden. |
| **WorkerTarget** | WorkerService endpoint for later Step and RPC calls. Use it to move future work to a new Worker. |
| **AttributeStoreName** | Server-configured Attribute Store for Attributes that opt in to asynchronous projection. An explicit empty value disables future projections. |

### Update FlowConfig with a Client {#update-flow-config-with-a-client}

**UpdateFlowConfig** is available while the Flow is active. It is a partial update: send only the fields you want to change. The update affects later Flow decisions and does not recall work that Dex already dispatched.

The following Go example moves future Step and RPC calls to a canary Worker. SDKs that expose this operation use their native naming convention.

	return client.UpdateFlowConfig(ctx, flowID, sdk.FlowConfig{

	})
}

## SubFlow options {#subflow-options}

[SubFlow](/primitives/subflow) conditions use **SubFlowOptions** for timeout, retry, initial Attributes, and **FlowConfig** overrides. A SubFlow also has a reuse policy for its generated Flow ID. Dex owns SubFlow start IDs, so callers cannot override them.

## Operational APIs {#operational-apis}

Starting and configuring a Flow is only half of the lifecycle. [Client APIs](/primitives/client-apis) also cover search, RPC and Channel interaction, waits, stop, timer skip, time travel, and continue-as-new.
