# Workflow Patterns evaluation

The Workflow Patterns are a catalog of recurring behaviors in business
processes. The Workflow Patterns Initiative defined them, led by Wil van der
Aalst and Arthur ter Hofstede. Researchers use them to compare workflow
languages and engines, such as BPMN, BPEL, and YAWL. Each pattern has an ID, a
name, and a precise definition. See the
[control-flow patterns](http://www.workflowpatterns.com/patterns/control/) for
the definitions.

This page rates Dex against the 43 control-flow patterns, WCP-1 to WCP-43. The
data, resource, and exception-handling patterns are not evaluated here.

## Summary {#summary}

- 33 patterns have direct support (**+**).
- 10 patterns have indirect support (**+/-**).
- Every pattern has at least indirect support; none is unsupported (**-**).

## Comparison with a published evaluation {#comparison-with-a-published-evaluation}

A [published evaluation](https://doi.org/10.1016/j.infsof.2009.02.002) rated six workflow and BPM systems against the
same 43 control-flow patterns. Its authors, Wohed, Russell, ter Hofstede,
Andersson, and van der Aalst, are independent of Dex. It appeared in
Information and Software Technology 51(8), 2009
([PDF](https://www.vdaalst.com/publications/p536.pdf)). In its Table 20, each
system directly supports 11 to 20 patterns, partly supports up to 6, and
leaves 19 to 32 unsupported.

The Dex ratings on this page are self-assessed by the Dex team. No independent
author rated Dex.

## Rating scheme {#rating-scheme}

The ratings use the scheme of the published evaluations.

- **+** means direct support. One Dex construct meets every part of the
  definition. The application keeps no extra state for it.
- **+/-** means indirect support. Dex implements the pattern by composing
  several constructs, such as Channel signals, an Attribute counter, a lock,
  an RPC guard, or a loop that waits again. In a few rows, one part of the
  definition holds in a limited form, and the row says which. The published
  evaluations call this rating partial support.
- **-** means no support.

A Dex construct is part of the programming model. It is a Primitive, a Step
decision, a wait, or an SDK API that all five SDKs provide and document as
the standard way to do the job. The **Join** is such an API.

<a id="why-many-joins-are-indirect"></a>
<a id="join-limits"></a>

Ten patterns are **+/-**. WCP-15, WCP-33, WCP-36, and WCP-38 need a join that a per-round count cannot express: instances added while others run, a trigger queue per branch, or a reachability check.
WCP-17 and WCP-40 rest on an Attribute lock, which covers one `Execute` only.
WCP-18, WCP-20, WCP-23, and WCP-39 are not joins; their rows give the reasons. [How the Join works](/design-patterns/parallel/await#how-the-join-works) describes the Join and its limits.

## How the ratings were checked {#how-the-ratings-were-checked}

Every pattern has a runnable example in TypeScript, Python, Go, Java, and
Rust. Each example has an integration test against a real Dex Server. The test
asserts the behavior that defines the pattern. For example, the Deferred Choice
test sends two competing responses and checks that exactly one branch runs.

## What the ratings rest on {#what-the-ratings-rest-on}

The ratings depend on these Dex behaviors.

- `GracefulComplete` closes the Flow only when no Step is active.
- `DeadEnd` ends one branch and never closes the Flow.
- `ForceComplete` closes the Flow at once and cancels the other Steps.
- `AnyOf` consumes messages only from the condition it selects.
- A Channel message stays queued until a Step consumes it.
- A decision or an RPC cancels Steps by Step type. Dex does not stop a canceled
  method's code. The method keeps running until it checks for cancellation and
  returns.
- Only one Step method or RPC holds an Attribute lock at a time.
- A SubFlow keeps running when its parent closes.
- A **Join** keys each round by the Step execution that forked it. Results of
  one round never satisfy the join of another round.
- A Step method publishes only when it succeeds. So a retried branch reports
  its result once.
- A decision can limit its cancellation to sibling Steps. Siblings are the
  Steps that one decision started together. When an RPC forked a round with
  an explicit round key, the branches are siblings of every Step that this
  RPC name ever started. Cancel such branches explicitly by Step type.

See [Step](/concepts/step), [Channel](/concepts/primitives/channel), and
[SubFlow](/concepts/primitives/subflow) for these concepts.

## Pattern details {#pattern-details}

### WCP-1 Sequence {#wcp-1}

**What it is.** A task starts only after the task before it finishes. Both tasks belong to the same process. See the [official definition](http://www.workflowpatterns.com/patterns/control/basic/wcp1.php).

**How Dex implements it.** Each Step's `Execute` returns `GoTo` for the next Step. The example runs ReceiveOrder, CheckInventory, and ShipOrder in order.

**Rating:** **+**. `GoTo` is the sequence construct.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/basic-control-flow.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/basic_control_flow.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/basic_control_flow.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/SequenceFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/basic_control_flow.rs)

### WCP-2 Parallel Split {#wcp-2}

**What it is.** One branch splits into two or more branches. The branches run at the same time. See the [official definition](http://www.workflowpatterns.com/patterns/control/basic/wcp2.php).

**How Dex implements it.** A Step returns `GoToMany` with one Step movement per branch. The example splits an order into packing and payment.

**Rating:** **+**. `GoToMany` is the split construct.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/basic-control-flow.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/basic_control_flow.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/basic_control_flow.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/ParallelSplitSynchronizationFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/basic_control_flow.rs)

### WCP-3 Synchronization {#wcp-3}

**What it is.** Two or more branches converge into one. The next branch starts only after every incoming branch has finished. See the [official definition](http://www.workflowpatterns.com/patterns/control/basic/wcp3.php).

**How Dex implements it.** The split Step calls **Fork** on a **Join**. **Fork** returns the branches and the join Step for one `GoToMany`, and gives each of them the same round token. Each branch ends with `EndBranch`, which reports its result. The join Step waits for `ForAllBranches`.

**Rating:** **+**. The Join is the join construct. **Fork** counts the branches and keys the round, so the application keeps no count.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/basic-control-flow.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/basic_control_flow.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/basic_control_flow.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/ParallelSplitSynchronizationFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/basic_control_flow.rs)

### WCP-4 Exclusive Choice {#wcp-4}

**What it is.** One branch splits into several. Control passes to exactly one of them. A condition picks which one. See the [official definition](http://www.workflowpatterns.com/patterns/control/basic/wcp4.php).

**How Dex implements it.** `Execute` evaluates the condition and returns `GoTo` for one Step. The example routes a claim to manual review or automatic approval by amount.

**Rating:** **+**. A decision with one `GoTo` is the choice construct.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/basic-control-flow.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/basic_control_flow.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/basic_control_flow.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/ExclusiveChoiceSimpleMergeFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/basic_control_flow.rs)

### WCP-5 Simple Merge {#wcp-5}

**What it is.** Two or more branches converge into one. Each arrival passes control on. The pattern assumes only one incoming branch is active at a time. See the [official definition](http://www.workflowpatterns.com/patterns/control/basic/wcp5.php).

**How Dex implements it.** Each branch returns `GoTo` for the same Step type. The example's two review branches both go to CloseClaim.

**Rating:** **+**. A shared `GoTo` target is the merge.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/basic-control-flow.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/basic_control_flow.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/basic_control_flow.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/ExclusiveChoiceSimpleMergeFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/basic_control_flow.rs)

### WCP-6 Multi-Choice {#wcp-6}

**What it is.** One branch splits into several. Control passes to one or more of them. A condition picks the set. See the [official definition](http://www.workflowpatterns.com/patterns/control/advanced_branching/wcp6.php).

**How Dex implements it.** `Execute` builds the list of selected Steps and returns `GoToMany` for them. The example picks email, SMS, or push notifications from the input.

**Rating:** **+**. `GoToMany` with a computed list is the multi-choice construct.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multi-choice-and-merges.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multi_choice_and_merges.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multi_choice_and_merges.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/MultiChoiceSynchronizingMergeFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multi_choice_and_merges.rs)

### WCP-7 Structured Synchronizing Merge {#wcp-7}

**What it is.** Branches started by an earlier Multi-Choice converge into one. The merge waits for every branch that was started, and only those. It belongs to one Multi-Choice in a structured model. See the [official definition](http://www.workflowpatterns.com/patterns/control/advanced_branching/wcp7.php).

**How Dex implements it.** The choosing Step passes only the selected branches to **Fork**. Each branch ends with `EndBranch`. The join waits for `ForAllBranches`, so it waits for exactly the branches that started.

**Rating:** **+**. The branch count comes from **Fork**. The application never passes it to the join.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multi-choice-and-merges.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multi_choice_and_merges.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multi_choice_and_merges.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/MultiChoiceSynchronizingMergeFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multi_choice_and_merges.rs)

### WCP-8 Multi-Merge {#wcp-8}

**What it is.** Several branches converge into one. Each arrival passes control on separately. The next task runs once per arrival. See the [official definition](http://www.workflowpatterns.com/patterns/control/advanced_branching/wcp8.php).

**How Dex implements it.** Each branch returns `GoTo` for the same Step type. Dex starts a new execution of that Step for each arrival.

**Rating:** **+**. Each `GoTo` creates its own Step execution.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multi-choice-and-merges.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multi_choice_and_merges.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multi_choice_and_merges.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/MultiMergeFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multi_choice_and_merges.rs)

### WCP-9 Structured Discriminator {#wcp-9}

**What it is.** After a parallel split, the first branch to arrive passes control on. Later arrivals do not. The construct resets once every branch has arrived. See the [official definition](http://www.workflowpatterns.com/patterns/control/advanced_branching/wcp9.php).

**How Dex implements it.** The split Step forks each round of a **Join**. The join waits for `ForBranches` of 1 and passes control on. It also starts the next round's split Step with the round token. That Step's `WaitFor` waits for `ForRemainingBranches`, which consumes the other results of the round. That is the reset. The Step then forks the next round. The example records the ignored results in an Attribute.

**Rating:** **+**. The Join keys each round by the Step execution that forked it, so a late result never passes control on. The reset needs no extra Step and no round counter.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/partial-joins.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/partial_joins.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/partial_joins.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/StructuredPartialJoinFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/partial_joins.rs)

### WCP-10 Arbitrary Cycles {#wcp-10}

**What it is.** A process can contain a loop with more than one entry point or exit point. See the [official definition](http://www.workflowpatterns.com/patterns/control/structural/wcp10.php).

**How Dex implements it.** Steps `GoTo` each other freely, including Steps that already ran. The example's draft and edit loop has two entry points and two exit points.

**Rating:** **+**. `GoTo` can target any Step.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/iteration.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/iteration.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/iteration.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/ArbitraryCyclesFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/iteration.rs)

### WCP-11 Implicit Termination {#wcp-11}

**What it is.** A process ends when no work remains, now or later. No dedicated end node is needed. See the [official definition](http://www.workflowpatterns.com/patterns/control/structural/wcp11.php).

**How Dex implements it.** Each branch that finishes returns `GracefulComplete`. The Flow closes only when no Step is active.

**Rating:** **+**. `GracefulComplete` waits for the last active Step.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/termination.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/termination.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/termination.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/ImplicitTerminationFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/termination.rs)

### WCP-12 Multiple Instances without Synchronization {#wcp-12}

**What it is.** A task runs as several independent instances in one process instance. Nothing waits for them to finish. See the [official definition](http://www.workflowpatterns.com/patterns/control/multiple_instance/wcp12.php).

**How Dex implements it.** A Step returns `GoToMany` with one execution of the same Step type per instance. The Flow continues on another branch without a join.

**Rating:** **+**. `GoToMany` starts the instances, and no Step waits for them.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multiple-instances.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multiple_instances.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multiple_instances.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/MultipleInstancesWithoutSynchronizationFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multiple_instances/instance_creation.rs)

### WCP-13 Multiple Instances with a priori Design-Time Knowledge {#wcp-13}

**What it is.** The number of instances is fixed in the model. The instances run at the same time. The process continues after all of them finish. See the [official definition](http://www.workflowpatterns.com/patterns/control/multiple_instance/wcp13.php).

**How Dex implements it.** A Step forks a **Join** with a fixed list of instances. Each instance ends with `EndBranch`. The join waits for `ForAllBranches`.

**Rating:** **+**. Each instance is one branch of the Join, and **Fork** counts them.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multiple-instances.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multiple_instances.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multiple_instances.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/StaticPartialJoinForMultipleInstancesFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multiple_instances/instance_partial_joins.rs)

### WCP-35 Cancelling Partial Join for Multiple Instances {#wcp-35}

**What it is.** m instances run. Once n of them complete, the next task starts and the rest are canceled. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp35.php).

**How Dex implements it.** The split Step forks m instances with a **Join**, and the join waits for `ForBranches` of n. Its decision cancels its sibling Steps of the instance Step type.

**Rating:** **+**. As in WCP-32, with instances as the branches.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multiple-instances.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multiple_instances.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multiple_instances.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/CancellingPartialJoinForMultipleInstancesFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multiple_instances/instance_partial_joins.rs)

### WCP-36 Dynamic Partial Join for Multiple Instances {#wcp-36}

**What it is.** Instances can start while others run, until adding is disabled. A completion condition is checked after each instance finishes. When it holds, the next task starts. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp36.php).

**How Dex implements it.** An **RPC** starts a new instance unless an **Attribute** flag says new instances are disabled. The join waits for one result at a time and tests its condition. When the condition holds, the join sets the flag and continues.

**Rating:** **+/-**. The join composes an RPC, an Attribute flag, a shared lock, and a loop that waits again after each result.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multiple-instances.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multiple_instances.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multiple_instances.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/DynamicPartialJoinForMultipleInstancesFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multiple_instances/instance_partial_joins.rs)

### WCP-37 Local Synchronizing Merge {#wcp-37}

**What it is.** Branches converge, and the merge waits for every active branch. It decides how many to wait for from information it has locally. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp37.php).

**How Dex implements it.** As in WCP-7, the diverging Step forks a **Join** with only the active branches. The join waits for `ForAllBranches`.

**Rating:** **+**. The local information is the branch count in the round token, which **Fork** creates.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multi-choice-and-merges.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multi_choice_and_merges.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multi_choice_and_merges.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/MultiChoiceSynchronizingMergeFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multi_choice_and_merges.rs)

### WCP-38 General Synchronizing Merge {#wcp-38}

**What it is.** The merge waits for every active branch, or until "it is not possible that any branch that has not yet been enabled will be enabled at any future time". It works in any process, including unstructured ones with loops. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp38.php).

**How Dex implements it.** An **Attribute** counts the threads that can still reach the merge. Every Step that changes the count declares a lock on that Attribute. The Step that brings the count to 0 also publishes a "done" message to a **Channel**. The merge Step waits for that message.

**Rating:** **+/-**. The pattern expects the merge to decide reachability from the process structure. In Dex, application code decides it at each `GoTo`.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/multi-choice-and-merges.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/multi_choice_and_merges.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/multi_choice_and_merges.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/GeneralSynchronizingMergeFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/multi_choice_and_merges.rs)

### WCP-39 Critical Section {#wcp-39}

**What it is.** Several sub-processes are marked as critical sections. Only one of them runs at a time in a process instance. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp39.php).

**How Dex implements it.** A **Channel** holds a single token message. Each section's first Step waits for the token, and its last Step publishes it back.

**Rating:** **+/-**. An Attribute lock covers one Step method only, so a section of several Steps uses a one-message Channel as a token.

**Design pattern:** [Critical Section](/design-patterns/critical-section).

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/state-based.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/state_based.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/state_based.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/CriticalSectionFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/state_based.rs)

### WCP-40 Interleaved Routing {#wcp-40}

**What it is.** Each task in a set runs once, in any order. No two of them run at the same time. The next task starts after all of them finish. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp40.php).

**How Dex implements it.** Every task's `Execute` declares a lock on the same **Attribute**. A join waits for `ForN` signals from the tasks.

**Rating:** **+/-**. The routing composes a lock with Channel signals. As in WCP-17, the lock covers one `Execute` only.

**Examples:** [TS](https://github.com/superdurable/dex/blob/main/examples/typescript/src/patterns/workflow-patterns/state-based.ts) · [Python](https://github.com/superdurable/dex/blob/main/examples/python/dex_examples/patterns/workflow_patterns/state_based.py) · [Go](https://github.com/superdurable/dex/blob/main/examples/go/patterns/workflow-patterns/state_based.go) · [Java](https://github.com/superdurable/dex/blob/main/examples/java/src/main/java/io/superdurable/dex/patterns/workflowpatterns/InterleavedRoutingFlow.java) · [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/src/workflow_patterns/state_based.rs)

### WCP-41 Thread Merge {#wcp-41}

**What it is.** A given number of threads in one branch merge into a single thread. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp41.php).

**How Dex implements it.** A Step forks a **Join** with the given number of threads, all of one Step type. Each thread ends with `EndBranch`. The merge Step waits for `ForAllBranches`.

**Rating:** **+**. Each thread is one branch of the Join, and **Fork** counts them.

### WCP-43 Explicit Termination {#wcp-43}

**What it is.** A process ends when it reaches a given end node. Remaining work is canceled, and the process is recorded as successful. See the [official definition](http://www.workflowpatterns.com/patterns/control/new/wcp43.php).

**How Dex implements it.** A Step returns `ForceComplete`. Dex closes the Flow at once and cancels every other active Step.

**Rating:** **+**. `ForceComplete` is the explicit end.
