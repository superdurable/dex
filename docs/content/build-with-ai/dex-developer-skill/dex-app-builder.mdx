# Dex App Builder

Dex App Builder is the **primary skill** for creating a Dex application or
process product. It covers the whole path: working out the business process,
building the backend in Go, Python, TypeScript, Java, or Rust, testing
locally, and handing off the result. It asks whether you want your own UI,
Dex Web, or released Connectors, and adds the ones you choose. It also
handles focused SDK work on an application, such as debugging a Flow or
adding a Step.

## Install and use

[Install Dex Skills](/build-with-ai/dex-developer-skill#install-and-use-dex-skills) once; it installs all three Skills. Then call this Skill in your coding agent, for example in Codex and in Claude Code with the Plugin:

```text
$dex-app-builder Design and build an event-registration application.
/superdurable-dex:dex-app-builder Design and build an event-registration application.
```

[Install and use Dex Skills](/build-with-ai/dex-developer-skill#install-and-use-dex-skills) has the invocation for every host.

## When to use it

Use App Builder when the request includes any of these:

- discovering or refining a business process;
- defining roles, permissions, approvals, waits, retries, and recovery;
- building the backend and the application API that your UI or other
  callers use;
- building your own UI, or using Dex Web for operations and management;
- building a new Dex application from the supported template;
- using released Connectors, or finding a Connector that is missing;
- building and testing one complete feature, from the backend to its UI;
- learning Dex and setting it up before you have a process in mind.

For a narrow SDK task, App Builder skips the product workflow. See
[SDK work](#sdk-work). For a standalone official Connector contribution,
invoke [Dex Connector Contributor](./dex-connector-contributor.mdx) instead.

## Get started with Dex

App Builder also helps you learn Dex and set it up. Ask it, for example:

```text
$dex-app-builder Help me understand and set up Dex.
```

It explains the core model in a few sentences and installs `dexcli`. Then it
starts `dexcli dev` and gives you the Dex Web address. Last, it asks whether
to start from an example or from your own process.

## Before implementation

App Builder first checks that the coding-agent host gives it a writable
repository or project, file-editing tools, and command execution.

Without them, App Builder can still work out the process, design the
architecture, and write a plan for implementation. It cannot create files, run
tests, build artifacts, or deploy an application.

## Workflow

### 1. Confirm the business process

The skill starts by talking with you, not by writing code. It works out:

- who maintains, manages, operates, approves, and takes part in the process;
- what each role can do, and the stable permission each human action requires;
- triggers, inputs, outputs, deadlines, waits, retries, recovery, audit, and
  which data is sensitive;
- the external systems, and whether you want a released Connector for each;
- which UI you want: your own, Dex Web, both, or neither;
- whether an existing host application signs users in and maps their roles to
  permissions it trusts.

This step ends with a table of roles, operations, and permissions, a proposed
lifecycle, your UI and Connector choices, and the application API operations
your UI or callers need. The skill settles every open question that matters
with you before any code is written.

<a id="3-design-and-implement-the-flow"></a>

### 2. Design and implement the backend

The backend is the core of the application. It uses the Dex SDK for the application's language: Go, Python,
TypeScript, Java, or Rust. An existing application keeps its language. A new
application uses the language you name, or TypeScript when you name none. App
Builder follows the general SDK rules described in [SDK work](#sdk-work), then
adds stricter rules of its own:

- target strict Dex Web and Flow Definition Graph 2.0 rendering, with the
  directives that the
  [Flow visualization reference](/reference/web/flow-visualization) lists for
  the language;
- call external providers only from `Execute`;
- keep provider calls and Dex changes out of `WaitFor`;
- model each human operation as a typed Action with an explicit permission;
- keep credentials in the runtime environment or Connector configuration,
  not in application code;
- for each system you chose a Connector for, use its released capabilities
  instead of adding a provider client to the application.

Before it writes code, the skill states the Flow's identity, typed input and
output, Steps, transitions, Attributes, Channels, RPCs, Timers, retries,
recovery, and Connector boundaries. When your UI or other callers need an
API, it designs the application's HTTP API contract with the Flow and
generates the server code from it. With no UI and no caller, the application
can ship only its Worker.

<a id="4-verify-and-hand-off"></a>

### 3. Verify and hand off

While it works, the skill runs the tests related to each change. At the end,
it runs the template's full check. This covers the application API and any UI
you chose, when they exist, generated code, the production build, behavior
against a real Dex Server, recovery paths, and the FDG 2.0 analysis.

The handoff lists the product decisions you confirmed, what was built, the
exact test results, the status of any Connector release or contribution, and
known limitations. The work ends in a clean Git commit.

<a id="2-choose-the-application-surface"></a>

## Your UI and Connectors are optional {#ui-and-connectors-are-optional}

App Builder asks about each of these once, while it confirms the business
process. It adds only the ones you choose.

| Option | When to choose it | What gets built |
| --- | --- | --- |
| **Your own UI** | Most products: screens for your users, a participant portal, or a branded application. | The skill builds a React and TypeScript frontend on the application API. When a page choice is still open, it first shows static wireframe pages for you to review. |
| **Dex Web** | You want a ready-made UI for operations and management: Runs, Work Queue, Actions, edits, history, and diagnostics. | The skill adds the Summary, Display, Action, and permission contracts that Dex Web reads. Your own UI repeats these features only when you ask. |
| **Released Connectors** | The process uses an external system, such as Slack or Gmail, and you want a ready-made integration. | The skill uses the released Connector's operations and Triggers. When you decline a Connector, the application calls the system from its own Step code. A Connector you chose but that is missing follows [How Connector gaps are handled](#how-connector-gaps-are-handled). |

You can choose your own UI, Dex Web, both, or neither when callers only use
the application API. Your own UI needs no other justification. Locally, `dexcli dev` always shows your Flows in Dex Web while
the skill works.

## How Connector gaps are handled

Before it writes integration code for a Connector you chose, App Builder
checks what the released Connectors can do. An official Connector may be missing, or an operation,
Trigger, or configuration UI unit the application needs may be missing or
broken. App Builder then loads
[Dex Connector Contributor](./dex-connector-contributor.mdx).

While the contribution is in review, the application can test against a local
copy of the Connector package. The application is not ready for production
until that Connector is released with an exact version. The skill never
commits a branch, commit SHA, pseudo-version, or local replacement as a
production dependency.

## SDK work {#sdk-work}

For focused technical work on an existing application, App Builder skips
discovery and the UI and Connector questions and goes straight to the Flow and SDK rules. It
supports Python, Go, Java, TypeScript, and Rust. Ask it, for example:

```text
$dex-app-builder Add a reminder Step to this approval Flow.
```

This route covers:

- Flows, Steps, waits, transitions, and failure routes;
- Attributes, AttributeMaps, Channels, ChannelMaps, and Streams;
- typed RPCs, Timers, SubFlows, Workers, and Clients;
- retries, timeouts, heartbeats, durability, locks, and recovery;
- SDK version compatibility, testing, troubleshooting, or operations;
- Dex Web, `dexcli`, Flow visualization, and application observability.

The skill works on your application, not on Dex. It does not start changing
Dex Server to solve an application problem unless you explicitly ask it to
work on Dex itself.

### Version and source authority {#version-and-source-authority}

Before it writes code, the skill finds out the application's language,
package manager, installed Dex SDK version, how the Worker and Client start,
and the repository's test commands.

The skill relies on the repository source, the lockfile, the installed SDK,
and the official examples for that SDK version. It keeps the installed version
unless you ask to upgrade. If it cannot find source for that exact version, it
stops after designing the Flow model, which does not depend on a version. It
does not invent an API.

It loads only the handbook for your language and the references the task
needs, not all five languages.

### Model, implement, and verify {#model-implement-and-verify}

For any non-trivial change, the skill writes down the model before it edits
code: the Flow's identity, typed start input and completion output, Steps and
transitions, options, durable state, messages, RPCs, Timers, failure
recovery, and how the application calls the Flow. It uses precise domain
names and prefers official Dex patterns over hand-written coordination loops.

A complete change includes typed inputs, outputs, and failures, Flow and Step
definitions, persistence schema entries, wiring, and an integration test
against a real Dex Server. Running Flows limit what you can rename. The skill
keeps existing Flow, Step, Attribute, Channel, Stream, and RPC names unless you
have an explicit migration plan.

### Diagnostics and operations {#diagnostics-and-operations}

When it diagnoses a problem, the skill only reads by default. It can inspect
Dex Web, `dexcli`, SDK errors, and application logs. Without your permission
it does not stop, time travel, publish to, invoke, delete, edit, or otherwise
change a Flow.

## Expected result

When App Builder finishes, you have:

- a confirmed process and permission model;
- a Dex application in the chosen language, with its application API;
- the UI you chose: your own, Dex Web, both, or neither;
- test evidence from local runs and a real Dex Server;
- a list of Connector releases that still block production, if any;
- a repository ready for review.
