# Why Dex?

Dex is a Durable Execution (D-Ex) platform.
Dex records each Step of your process as it runs.
After a crash or a restart, the process continues from the last recorded Step. It does not start over or stop halfway.

You build with a few [primitives](/concepts). You write a Flow as ordinary code: Steps, Attributes, RPCs, and durable wait conditions on Channels and Timers. Your Workers host the Flow. Your Client calls Dex Server to start Flow instances and interact with them. Dex Server sends Step and RPC tasks to your Workers.

The Application calls Dex Server with startFlow and invokeRPC, and Dex Server invokes Steps and RPCs on the Worker. Dex Server persists Flow instances and their execution." />

A **Step** can wait for a condition in **WaitFor**: a **Channel** message, a **Timer**, or both. The wait survives restarts. When the condition is met, Dex calls the Step's **Execute**. A Step without WaitFor runs Execute right away.

**Execute** returns a decision: which Steps run next, or that the Flow completes. Code in Steps and RPCs can read and write **Attributes**. It can also publish durable **Channel** messages, to deliver external events or to pass messages between Steps that run in parallel in the same Flow.

## Example: order processing

The Flow charges the buyer and then waits for the seller's approval, with reminders while it waits. After approval it ships the item. If the ship call still fails after its retries, the Flow refunds the buyer.
[Compared to Database](/intro/compared-to-database) builds the same process with a database and message queues, and shows where that design breaks.

<DocsFlowDefinitionGraph graph={orderProcessingFlow} />

- **ChargeStep** calls the payment API with a Step retry policy. When it succeeds, it moves to ShipStep.
- **ShipStep** waits for a message on the seller **Channel** or for a **Timer**. If the Timer fires first, it sends a reminder and keeps waiting. When the approval arrives, it ships. If the ship retries run out, it moves to **RefundStep**.
- **RPC approve** publishes the approval to the seller Channel.
- The storefront **start** handler waits for ChargeStep with the Client **wait-for-Step-completion** API. It does not poll a status of its own.
- **Attribute order-status** is indexed, so support staff can search for stuck orders.

The [Order Processing](/use-cases/order-processing) example has the full code of this Flow and its handlers in every SDK.

The frontend waits for "payment received". The **GET /products/order-processing/start** handler starts the Flow and waits for ChargeStep to complete before it returns.


Dex records a Step's result and its move to the next Step together, so a crash cannot leave the Flow between two Steps. Timer and Channel waits continue after a Worker restarts. You declare retries and compensation on the Step.

## How this differs from traditional Durable Execution

Traditional Durable Execution engines rebuild a workflow function's state by **replaying** its event history. Side effects must go in **activities**. You split business logic into **workflow code** and **activity code**, and the two follow different programming models. Workflow code must be **deterministic**: it cannot read the clock, use random numbers, or do IO directly. Event history has a **size limit**. It is also a poor place for application data, because large payloads make it expensive and slow.

Replay-based engines need a large set of special APIs to simulate a normal programming model. Each of these APIs brings implicit rules, which makes the code hard to understand and maintain.

Dex has no replayed workflow function. You declare Steps and the movements between them. Worker handlers are ordinary code. Waits, RPCs, and locking are part of the Flow model; you do not rebuild them from history primitives. **Attribute** data lives in a **blob store**, not in an event history. You can sync it to a database you already run.
