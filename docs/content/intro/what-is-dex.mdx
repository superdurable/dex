# Why Dex?

Dex is a Durable Execution (D-Ex) platform.
Dex records each Step of your process as it runs.
After a crash or a restart, the process continues from the last recorded Step. It does not start over or stop halfway.

A Step that was cut off in the middle can run again, so each call to another system passes an idempotency key: a value that lets that system recognize a repeat and skip it. [Idempotency keys](/concepts/step#idempotency-keys) shows how to build one.

You run Dex Server yourself, next to your Workers; [Get Started](/get-started) says what that takes.

## The problem

An online store charges the buyer and then ships the item. Between the two calls, the server can crash, a deploy can restart it, or the ship API can time out. The buyer is then charged, and the item never ships.

The process also waits. The seller must approve the shipment, maybe a day later. The store reminds the seller while it waits. If shipping keeps failing, the store refunds the buyer.

A database stores the order, but it does not run this process. Teams build the rest themselves: status columns, queues, retry topics, a reminder job, and tools to repair stuck orders. [Compared to Database](/intro/compared-to-database) builds that design step by step.

## How Dex models a process

In Dex, the order process is one **Flow**. The order ID is its Flow ID.

A Flow is made of **Steps**. Each Step does one unit of work, such as the charge call. Dex saves the Step's result and its move to the next Step together, so a crash cannot leave the order between two Steps.

A Step has two parts:

- `WaitFor` waits for a condition: a **Channel** message, such as the seller's approval, or a **Timer**, such as the reminder. The wait lives in Dex, so it survives restarts and holds no thread.
- `Execute` does the work. It returns a decision: the next Steps to run, or that the Flow is complete.

The Flow keeps its data in **Attributes**, such as the order status. An **RPC** lets your application read the Flow or send it a command, such as the approval.

This model has one trade-off. You write the process as Steps and decisions, not as one function. In return, Step code is ordinary code, and Dex never replays it.

## Example: order processing

The Flow charges the buyer and then waits for the seller's approval, with reminders while it waits. After approval it ships the item. If the ship call still fails after its retries, the Flow refunds the buyer.

The graph shows each Step and where it goes next. **Ship** can go back to itself: when the reminder Timer fires before the approval, it sends a reminder and waits again. Three parts sit outside it:

- **RPC approve** publishes the seller's approval to the seller Channel.
- The storefront's start handler starts the Flow and waits for the Charge Step with the Client's wait-for-Step-completion API. It then tells the buyer "payment received". It does not poll a status of its own.
- **Attribute order-status** is indexed, so support staff can search for stuck orders.

Each Step passes an idempotency key built from the order ID.

The [Order Processing](/use-cases/order-processing) example has the full code of this Flow and its handlers in every SDK.

## Where your code runs

Your application contains a **Worker** and a **Client**, both built with the Dex SDK. The Worker hosts the Flow and runs its Steps and RPCs. The Client starts Flows and calls their RPCs. **Dex Server** stores each Flow and sends work to your Workers.

## Coming from another durable execution tool

Dex does not replay your code, so a code change cannot break a running Flow with a replay error. [Compared to Existing Durable Execution](/intro/compared-to-durable-execution) has the details.
