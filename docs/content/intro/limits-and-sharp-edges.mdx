# Limits and Sharp Edges

This page lists what can surprise a team that runs Dex in production. Each item
links to the page that covers it.

## Defaults to change before production

- **Closed Flow runs are deleted after 7 days.** A closed run stays available
  for 7 days by default. After that, the server may delete it, including its
  Step history. Set a longer retention, or copy what you must keep to your own
  database. See [Retention](/reference/server/configuration#retention) and
  [Dex and Your Database](/components/your-database).
- **Public API authentication is off.** Any client that reaches the server can
  call it. Configure an authenticator before you expose the port. See
  [Authentication](/reference/server/authentication).
- **Retries stop after 4 hours, and then the Flow fails.** By default a Step
  method retries without an attempt limit for 4 hours from its first hand-out
  to a Worker. When that time runs out, the default failure policy fails the
  Flow. Set a longer total duration for Steps that wait on slow systems, or a
  failure policy that moves to a recovery Step. See
  [StepOptions](/concepts/step#stepoptions).

## Capacity and availability

- **One active node is the ceiling of a cluster.** Dex divides a cluster's
  Flows and task queues into partitions, and today one node owns every
  partition. So a larger load needs a larger node or a separate cluster. See
  [Grow past one node](#grow-past-one-node) and
  [Performance and Maturity](/intro/performance-and-maturity).
- **Failover takes up to the lease duration plus 1 second.** The lease is 10
  seconds by default. A single-replica setup should use 60 seconds, so it waits
  up to about a minute after a crash. A graceful shutdown hands over at once.
  See [Lease](/reference/server/high-availability#lease).
- **Failover reruns in-flight Steps.** Recovery fails every attempt that a
  Worker had received, and each one consumes a retry. See
  [Failover and Deploys](/concepts/failover-and-deploys).
- **The partition count is fixed at the first start.** The first start
  records **cluster.partitionCount**, 1024 by default for **serve**, and a
  later start with a different count fails. Choose it before the first
  production start. See
  [Partition count](/reference/server/configuration#single-node-partition-count).
- **Some upgrades stop the cluster.** Some server releases need every server
  process stopped, standbys included, before the new version starts. Upgrades
  roll forward only. The upgrades page names each such release, so read it
  before you upgrade. See [Upgrades and compatibility](/reference/server/upgrades).
- **Beta compatibility has no fixed support window.** Published APIs,
  configuration, wire formats, and stored data stay compatible, and a breaking
  change comes with a migration path. No support period for older releases is
  promised. See [Performance and Maturity](/intro/performance-and-maturity#release-status).
- **Version numbers do not decide compatibility.** Dex Server is at 0.1.x and
  the SDKs are at 1.x. A Worker or Client works with a server when their
  protocol ranges overlap. See
  [Upgrades and compatibility](/reference/server/upgrades).

## Grow past one node {#grow-past-one-node}

A cluster has one active node, so its capacity is one node's capacity. Two
options work today:

- **Use a larger node.** The benchmark on a 16-vCPU node reaches several times
  the throughput of a 2-vCPU node. See
  [Performance and Maturity](/intro/performance-and-maturity).
- **Run separate clusters.** Each cluster uses its own object storage prefix,
  since one prefix holds one cluster. Split Flows between clusters by Flow
  type, or by a business key such as the tenant. Point each service's Client
  and Workers at the cluster that owns its Flows.

Separate clusters do not share Flows. A Flow cannot move from one cluster to
another. A SubFlow starts in the same cluster as its parent, and RPCs and
Channel messages reach only Flows in the cluster that the Client is connected
to. See [Install and configure server-zd](/reference/server/configuration).

## Requests that can repeat

- **A Step runs at least once.** A Step that a crash cut off runs again, and so
  do its external calls. Pass an idempotency key. See
  [Idempotency keys](/concepts/step#idempotency-keys).
- **An ASYNC Step can rerun on a new snapshot.** If a server node fails before
  it saves an ASYNC Step's start, the attempt runs again and can read different
  Attribute values. See [SYNC and ASYNC Steps](/concepts/step#sync-and-async).
- **A retried RPC runs again.** Each RPC call is a new request, so a client
  retry can run the handler twice. See [RPC](/concepts/primitives/rpc#guarantees).
- **A repeated Channel publish delivers twice.** A **PublishToChannel**
  request sent again after a lost response stores the message a second time.
  Publishing once through request IDs is planned in
  [issue 1519](https://github.com/superdurable/dex/issues/1519).
- **A retried StopFlow without a run ID can stop a newer run.** Pass the run ID.
  Doing this for you is planned in
  [issue 1520](https://github.com/superdurable/dex/issues/1520).

## Workers and code

- **An RPC never queues.** If no Worker takes it within 10 seconds, the caller
  gets an **Unavailable** error. Steps wait in a durable queue instead. See
  [Routing and availability](/reference/server/workers#routing-and-availability).
- **A canceled method keeps running.** Dex does not stop the code. The method
  should check for cancellation and return. See
  [Step](/concepts/step#guarantees).
- **Parallel writers overwrite each other unless they lock.** Locks are opt-in,
  bind only the methods that declare them, and are held through external calls
  and retries. See [Locks](/concepts/primitives/attribute#locking).
- **Index slots are limited.** With the PostgreSQL search backend, each tenant
  has 10 Keyword slots and 3 for each other index type, shared by every Flow
  type. The registry has no delete. See
  [PostgreSQL search](/reference/server/search#postgresql-search).
