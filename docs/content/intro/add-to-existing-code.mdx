# Add Dex to Existing Code

This page turns code you already run, such as a function, a queue consumer, a cron job, a webhook handler, or a script, into a Flow that continues after a crash, a restart, or a long wait.

<FunctionToFlowDiagram markdownDescription="Before: one function charges the buyer, waits for approval, ships, and refunds; a crash leaves it half done. After: a Flow of Steps, Charge then Ship, which waits for approval or 24 hours, then Done, with Refund when Ship fails." />

<CodingAgentBox>

```text
Turn <function> in <file> into a Dex Flow.

1. Read https://docs.superdurable.io/intro/add-to-existing-code.md and treat it
   as the source of truth.
2. Give each call that changes another system its own Step, move waits into
   WaitFor, and keep state in Attributes.
3. Add an idempotency key to every external write.
4. Add an integration test that runs against dexcli dev.

Rules: keep the existing behavior. Do not invent APIs. Ask me before changing
code outside this function.
```

</CodingAgentBox>

## Install the SDK {#install}

Add the SDK and a Worker to the service that runs this code. [Add Dex to an existing service](/components/application#add-to-a-service) shows the install command for each language and where the Worker and Client go.

## Start from what you have

Take an order process that runs as one function today:

```text
handle_order(order):
    charge the buyer through the payment API
    save status "charged" in the orders table
    wait until the seller approves (poll the approvals table, remind after 24 hours)
    ship the item through the shipping API
    save status "shipped"
    if shipping keeps failing: refund the buyer, save status "refunded"
```

A crash between any two lines leaves the order in the middle. A restart either repeats the charge or forgets the order.

## Split it into Steps

Give each call that changes another system its own Step. A Step is the unit that Dex saves, so a crash repeats at most the Step that was running.

| In your function | In the Flow |
| --- | --- |
| Charge the buyer | A **Charge** Step whose `Execute` calls the payment API and goes to **Ship** |
| Wait for approval, remind after 24 hours | **Ship**'s `WaitFor`: wait for a message on a **Channel** or a 24-hour **Timer**, whichever comes first |
| Send the reminder | **Ship**'s `Execute` when the Timer fired: send the reminder, then go to **Ship** again |
| Ship the item | **Ship**'s `Execute` when the approval arrived |
| Refund after repeated failures | A failure route from **Ship** to a **Refund** Step, used when Ship's retries run out |
| The status column | An **Attribute**, such as **order-status** |
| The approval endpoint | An **RPC** that publishes the approval to the Channel |
| The polling loop and the reminder job | Nothing. Dex holds the wait and fires the Timer. |

### How Ship knows which wait ended

**Ship**'s `WaitFor` returns both conditions, and Dex wakes the Step when the first one is met. `Execute` then asks the context whether the Timer fired. If it did, Ship sends a reminder and goes to itself, which waits again. Otherwise the approval arrived, so Ship ships the order and completes the Flow. [Order Processing](/use-cases/order-processing#2-flow-steps-and-rpcs) shows the whole Step, with its retry and failure route.

	ctx dex.Context,
	order OrderRequest,
) (*dex.StepDecision, error) {
	if ctx.HasTimerFired() {
		step.service.SendEmail(
			order.Email,
			"Reminder: approve shipment",
			"Please approve or provide a tracking number.",
		)
		return dex.GoTo(shipStep{}, order), nil
	}
	if err := step.service.ShipItemWithIdempotencyKey(order.OrderID, order.TestFailAtShipping, "ship-"+order.OrderID); err != nil {
		return nil, err
	}
	if err := OrderStatus.Set(ctx, "shipped"); err != nil {
		return nil, err
	}
	return dex.GracefulComplete("shipped:" + order.OrderID), nil
}

            &input.email,
            "Reminder: approve shipment",

The reminder email passes no idempotency key, because a second reminder does no harm. Ship's ship call does pass one.

Keep two calls in one Step only when they succeed or fail together. A Step with two external calls repeats both when it runs again.

The default retry policy keeps retrying a Step for 4 hours and then fails the Flow; a failure route catches that failure instead. To let a person decide, route the failure to a Step that waits for them, as [Manual Recovery](/design-patterns/failure-handling/manual-recovery) shows. [Execute Failure Recovery](/design-patterns/failure-handling/execute-failure-recovery) shows the automatic route. After you fix the cause of a failed run, [Time Travel](/concepts/change-flow-code#time-travel) can run it again from an earlier point.

## Place the idempotency keys

Give each external call an [idempotency key](/concepts/step#idempotency-keys). Here the order ID is the Flow ID, so **charge-** plus the order ID works for the Charge call.

<a id="when-an-api-takes-no-idempotency-key"></a>

## Make a keyless API call safe {#when-an-api-has-no-idempotency-key}

For an API that takes no key, a repeated call has a second effect. Two approaches make that window small:

- **Check first.** Send your own reference with the call, such as the order ID in a shipment's reference field. At the start of the Step, look the effect up by that reference. If it already exists, skip the call.
- **Record the attempt.** If the API has no lookup, write a row keyed like an idempotency key, such as **ship-order-1042**, to your own database in the same Step, just before the call. On a rerun, a row that is already there means the call may have happened. Stop and check by hand, or go to a recovery Step, instead of calling again.

A crash after the call and before Dex saves the Step still leaves one case where you cannot tell whether the call happened. Each approach turns a silent repeat into a case you can see and handle.

## Keep your database writes

You can keep the orders table that support and reporting read. Write to it from a Step with an upsert keyed by the order ID, so a repeat writes the same row. Start the Flow from the handler that creates the order, with the order ID as the Flow ID. [Dex and Your Database](/components/your-database) covers both, including what happens when one of the two writes fails.

## Checklist

- Each call that changes another system is in its own Step, or shares a Step only with calls that succeed or fail together.
- Each such call passes an idempotency key built from the Flow ID, not from the time, a random value, or the attempt number.
- Each wait is a `WaitFor` on a Channel, a Timer, or both, not a loop that polls.
- Each command from outside, such as an approval, is an RPC.
- Status that other code reads is an Attribute, or an upsert into your own table.
- Each Step's retry policy fits the call, not the [default](/concepts/step#stepoptions).
- Each failure that needs a business answer, such as a refund, has a [failure route](#route-a-failure-to-a-recovery-step) to a recovery Step.
- Only when two Steps, or a Step and an RPC, can run at the same time and read then write the same Attribute, they declare a [lock](/concepts/primitives/attribute#locking) on it. A sequential Flow needs no lock.
- The handler starts the Flow with a stable Flow ID and a request ID, so a retried request does not start a second Flow. [A minimal service](/components/application#minimal-service) shows the handler.
