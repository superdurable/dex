# Dex vs. Temporal

Dex and Temporal both run processes that survive crashes, restarts, and long waits. Temporal replays workflow code against an Event History kept in a database, while Dex saves each Step's result and runs as one binary on object storage.

## Differences at a glance {#differences-at-a-glance}

Measured numbers come from the [dex-vs-temporal-demo](https://github.com/superdurable/dex-vs-temporal-demo) repository and the Dex [Performance](/intro/performance) page.

| Topic | Temporal | Dex |
| --- | --- | --- |
| [Worker memory and CPU](/intro/compared-to-temporal/performance#worker) | In a 512 MB container, the Worker was [OOM-killed](https://github.com/superdurable/dex-vs-temporal-demo/tree/f5aa9f90a5c4a51ae86387e13a5d0d48bb31bb3a/bench/results/temporal-default-cache-512m), and 715 messages got no reply. With 2 GB and a cache of 50 Workflows, it peaked at [581.6 MiB and 36.3% CPU](https://github.com/superdurable/dex-vs-temporal-demo/tree/f5aa9f90a5c4a51ae86387e13a5d0d48bb31bb3a/bench/results/temporal-cache50-2g). | In 512 MB, the Worker peaked at [85.5 MiB](https://github.com/superdurable/dex-vs-temporal-demo/tree/f5aa9f90a5c4a51ae86387e13a5d0d48bb31bb3a/bench/results/dex-512m) and answered all 3,000 messages. With 2 GB, it peaked at [79.8 MiB and 17.4% CPU](https://github.com/superdurable/dex-vs-temporal-demo/tree/f5aa9f90a5c4a51ae86387e13a5d0d48bb31bb3a/bench/results/dex-2g). |
| [Server throughput](/intro/compared-to-temporal/performance#server) | Temporal Cloud's default limit is [500 actions per second per Namespace](https://docs.temporal.io/cloud/limits). | One Dex Server node on S3 ran [1,772 SYNC Steps per second on 2 vCPU and 8,403 on 16 vCPU](/intro/performance). The 16 vCPU node answered 67.3k Attribute-read RPCs per second. |
| [Running the server](/intro/compared-to-temporal/operations#run-the-server) | [Frontend, History, Matching, and Worker services](https://docs.temporal.io/temporal-service/temporal-server) on Cassandra, MySQL, or PostgreSQL, plus a Visibility store. | One binary. Its only required dependency is object storage, such as Amazon S3, or db9. |
| [Long-running processes](/intro/compared-to-temporal/operations#history-limit) | An Event History holds at most [51,200 events or 50 MB](https://docs.temporal.io/workflow-execution/limits). A longer process needs Continue-As-New in your code. | Dex keeps each run's newest events and prunes older ones. The run keeps going without a new run. |
| [Data size](/intro/compared-to-temporal/operations#data-size) | A payload holds at most [2 MB](https://docs.temporal.io/troubleshooting/blob-size-limit-error). A self-hosted server warns at 512 KB. | A value holds up to 16 MiB, and a Flow run up to 64 MiB of active state, by [default](/reference/server/configuration#limits). |
| [Going back to an earlier point](/intro/compared-to-temporal/experience#time-travel) | [Reset](https://docs.temporal.io/cli/workflow) terminates the current run and starts a new run with a new Run ID. | Time Travel moves the same run back to an earlier point. The Run ID stays the same. |
| [Features only in Dex](/intro/compared-to-temporal/features) | The page lists the nearest Temporal mechanism for each feature. | Flow designs drawn from source, forms generated in Dex Web, Clone fork, Connectors, `SkipTimer`, waits for a Step or an Attribute, and reads without a Worker. |
| [Changing code](/intro/compared-to-temporal/programming-model#change-code) | A deploy that changes the commands of an open run fails its Workflow Task with a nondeterminism error. [Patching](https://docs.temporal.io/develop/python/workflows/versioning#patching) or [Worker Versioning](https://docs.temporal.io/worker-versioning) keeps open runs working. | Each Step runs the code of the Worker that takes it. The demo's change needed no versioning code. |
| [Writing code](/intro/compared-to-temporal/programming-model#more-code) | Workflow code must be [deterministic](#the-main-difference-an-explicit-step-graph-not-replayed-code). The demo's reply-with-approval Workflow has 26 lines. | Steps are ordinary code. The same Flow has 26 lines. |

## Architecture {#architecture}

The Temporal Worker [caches Workflow state in memory](https://docs.temporal.io/sticky-execution). The Dex Worker reads large values through a [blob cache](/components/application#blob-cache) on disk.

<TemporalArchitectureDiagram markdownDescription="Temporal: your Worker keeps an in-memory cache of Workflow state and talks to the Temporal Service, which runs Frontend, History, Matching, and Worker services on a database (Cassandra, MySQL, or PostgreSQL). Dex: your Worker keeps a blob cache on disk and talks to one Dex Server binary, which keeps current state in a local disk store and writes to object storage." />

## Replay and saved Step results {#the-main-difference-an-explicit-step-graph-not-replayed-code}

The two engines continue a run in different ways after a Worker stops.

<RecoveryModelDiagram markdownDescription="A Worker stops mid-run. Temporal: the Event History holds every command and result; a new Worker replays the workflow function from the top to the last await, so workflow code must be deterministic. Dex: Step results and Attributes are saved with each decision; a Worker continues from that saved progress with the next Step, and work that was in progress may be retried under its retry policy, so each external effect must be idempotent." />

**Temporal.** A Workflow is one function. The server records an Event History, "a complete and durable log of everything that has happened in the lifecycle of a Workflow Execution". When the run is not in a Worker's cache, a Worker runs the function again from the beginning. Recorded Activity results are returned instead of running the Activities again. The commands the code produces are checked against the history, and a mismatch is a nondeterminism error. Clock reads, random numbers, and I/O go through Temporal APIs or into Activities.

**Dex.** A Flow is a set of Steps. Each Step returns a decision that names the next Steps or completes the Flow. Dex saves each finished Step's result, its Attribute writes, and the decision together. A Worker continues from that saved state with the next Step. Work that was in progress may be retried under its retry policy. [Failover and Deploys](/concepts/failover-and-deploys) lists what runs again in each case.

## What they share {#what-they-share}

- A server records each run's progress outside your process. After a crash, the run continues from that record.
- Workers in your own process pull tasks from the server. Your code never runs inside the server.
- Timers are durable. A run that waits on a Timer or a message holds no Worker.
- Temporal Activities and Dex Step methods have a retry policy and timeouts. Their default backoff is the same: 1 second, doubling up to 100 seconds, with no attempt limit. Dex also stops retrying a Step after 4 hours by default; see [Limits](/intro/limits). A Temporal Workflow Task retries on its own schedule, and a Temporal Workflow Execution has no retry policy by default.
- A run has a business ID. At most one run with that ID is open at a time.
- A unit of work can run more than once. Code that calls another system passes an idempotency key.

## Terms map {#term-map}

| Temporal | Dex | Notes |
| --- | --- | --- |
| Workflow, Workflow ID, Run ID | [Flow](/concepts/flow), Flow ID, Run ID | Same roles. |
| Workflow code between Activities | Step decisions: `GoTo`, `GoToMany`, `GracefulComplete`, `DeadEnd` | Control flow is data that Dex saves with each Step. |
| Activity | The `Execute` method of a [Step](/concepts/step) | One retry unit. Give each durable call its own Step. |
| Local Activity | Closest: an ASYNC Step | Both trade some durability for latency. See [SYNC and ASYNC Steps](/correctness-and-expressiveness/step-guarantees#sync-and-async). |
| Timer, `sleep` | [Timer](/concepts/primitives/timer) in a Step's `WaitFor` | Both durable. |
| Signal | [Channel](/concepts/primitives/channel) message | Temporal accepts a Signal with no Worker online. In Dex, the FlowService request `PublishToChannel` stores a Channel message with no Worker online. See [Send a command at most once](/concepts/client#inbound-commands). |
| Query | Read-only [RPC](/concepts/primitives/rpc) | |
| Update | [RPC](/concepts/primitives/rpc) that writes Attributes or publishes to a Channel | Both need a Worker. |
| Workflow variables | [Attributes](/concepts/primitives/attribute) | Dex saves them. Temporal rebuilds them by replay. |
| Child Workflow | [SubFlow](/concepts/primitives/subflow) | |
| Task Queue | Task queue | A Flow names its task queue at start and keeps it. Inside a task queue, Dex routes by Flow type. |
| Sticky execution | Best-effort sticky routing | Dex first offers a task to the Worker that served the Flow before. Recovery needs no history cache in the Worker. |
| Search Attributes | Indexed Attributes | |
| Workflow ID Conflict Policy, for an open Workflow ID. Workflow ID Reuse Policy, for a closed one. | ID reuse policy, for open and closed Flow IDs. Start request ID. | The start request ID lets Dex recognize a retried start request. See [StartFlowOptions](/reference/python/start-flow-options). |
| Cancellation | An RPC cancels Steps by Step type. `StopFlow` stops the Flow. | In both, your Worker code stops its external work cooperatively. Dex discards anything a canceled attempt returns later. See [Cancel running Steps](/reference/server/runtime-data#cancel-running-steps). |
| Reset | [Time Travel](/components/operate-and-debug#time-travel) | See [Going back to an earlier point](/intro/compared-to-temporal/experience#time-travel). |
| Continue-As-New, to keep the history small | No new run needed for history size | See [The history limit](/intro/compared-to-temporal/operations#history-limit). |
| Patching, Worker Versioning | Keep old Step types and change data additively | See [Changing code](/intro/compared-to-temporal/programming-model#change-code). |
| Schedule | A Flow that loops on a Timer | See [Cron schedule](/design-patterns/durable-timer/cron). |
| Nexus | No direct equivalent | A service in another team starts a Flow or calls an RPC over the FlowService API. |
| Temporal Web UI | [Dex Web](/components/web) | |

Dex evolved from iWF. An iWF State corresponds to a Dex Step, and `WaitUntil` corresponds to `WaitFor`.
