# Dex vs. Temporal

Dex and Temporal both run processes that survive crashes, restarts, and long waits. This page maps each core Temporal capability onto Dex. For each one, it says how Dex provides it, what the difference costs, and where Temporal is the better fit. The [last section](#other-engines) covers other durable execution tools.

Temporal facts on this page come from the [Temporal documentation](https://docs.temporal.io). Dex facts link to the page that covers them.

## What they share {#what-they-share}

- A server records each run's progress outside your process. After a crash, the run continues from that record.
- Workers in your own process pull tasks from the server. Your code never runs inside the server.
- Timers are durable. A run that waits on a Timer or a message holds no Worker.
- Each unit of work has a retry policy and timeouts. The default backoff is the same: 1 second, doubling up to 100 seconds, with no attempt limit.
- A run has a business ID. At most one run with that ID is open at a time, and a reuse policy decides what happens to the next start.
- A unit of work can run more than once. Code that calls another system passes an idempotency key.

## Dex saves Step results, Temporal replays code {#the-main-difference-an-explicit-step-graph-not-replayed-code}

The two engines rebuild a run in different ways after a Worker stops.

<RecoveryModelDiagram markdownDescription="A Worker stops mid-run. Temporal: the Event History holds every command and result; a new Worker replays the workflow function from the top to the last await, so workflow code must be deterministic. Dex: Step results and Attributes are saved with each decision; a new Worker runs only the next Step, and finished Steps never run again, so each external effect must be idempotent." />

**Temporal.** A Workflow is one function. The server records an Event History, "a complete, ordered log of everything that has already happened". To continue a run, a Worker runs the function again from the beginning. Recorded Activity results are returned instead of running the Activities again. The commands the code produces are checked against the history. A mismatch is a nondeterminism error. So workflow code must make the same calls in the same order for the same input. Clock reads, random numbers, and I/O go through Temporal APIs or into Activities.

**Dex.** A Flow is a set of Steps. Each Step returns a decision that names the next Steps or completes the Flow. Dex saves the Step's result, its Attribute writes, and the decision together. To continue a run, a Worker runs only the next Step. It reads the saved Attributes. Nothing is replayed.

| | Temporal | Dex |
| --- | --- | --- |
| Shape of the code | One function, read top to bottom | A graph of Steps and decisions |
| A loop or a branch | Ordinary `while` and `if` | A Step that moves to itself, a decision with two targets |
| Clock, random values, libraries in orchestration code | Only through deterministic APIs | Allowed. Step code is ordinary code. |
| A code change to a running process | Can cause a nondeterminism error | Cannot cause a replay error |
| How state is kept | Rebuilt from the history, cached on the Worker | Saved as Attributes after each Step |
| The rule you must follow | Determinism, plus idempotent Activities | Idempotent external effects |

### Determinism moves to the idempotency key {#determinism-moved-it-did-not-vanish}

Dex removes the replay rule. It does not remove every rule. A Step can run more than once, so each external effect depends only on what Dex passes the Step; see [Idempotency keys](/concepts/step#idempotency-keys). Temporal asks the same of Activities, so this duty is not new. The [failure transparency proof](/correctness-and-expressiveness/failure-transparency-proof) assumes it.

Clock and random values are fine in a Step's decisions and in saved data. They stay out of idempotency keys and out of any effect that must be identical on a rerun.

### The same process in both models {#the-same-process-in-both-models}

A reminder loop sends a reminder at each interval until the person opts out. In Temporal, the loop is ordinary code that the engine replays. This sketch is illustrative, not from the Dex examples:

```python
@workflow.defn
class ReminderWorkflow:
    def __init__(self) -> None:
        self.opted_out = False

    @workflow.signal
    def opt_out(self) -> None:
        self.opted_out = True

    @workflow.run
    async def run(self) -> None:
        while True:
            try:
                await workflow.wait_condition(
                    lambda: self.opted_out, timeout=REMINDER_INTERVAL
                )
                return
            except asyncio.TimeoutError:
                await workflow.execute_activity(
                    send_reminder, start_to_close_timeout=timedelta(seconds=30)
                )
```

In Dex, the loop is a Step that moves to itself. It waits for the Timer or the opt-out Channel, and its decision chooses what comes next. This excerpt is from the runnable [Reminder](/design-patterns/durable-timer/reminder) pattern:

```python
class ReminderStep(Step[None]):
    def __init__(
        self,
        service: ServiceDependency,
        opt_out: Channel[None],
    ) -> None:
        self.service = service
        self.opt_out = opt_out

    def wait_for(self, context: Context, input: None) -> Wait:
        return Wait.any_of(
            Timer.by_duration(REMINDER_INTERVAL),
            self.opt_out.for_one(),
        )

    def execute(self, context: Context, input: None) -> StepDecision:
        if not context.has_timer_fired():
            return graceful_complete()
        self.service.send_email("Reminder: please respond", "Hello, ...")
        return go_to(ReminderStep, None)
```

The reminder passes no idempotency key, because a second reminder does no harm. In Rust, `has_any_timer_fired` asks whether any Timer of the Wait fired.

The Temporal version reads top to bottom. The opt-out is a Signal handler that sets a variable, and replay rebuilds the variable. The Dex version names the waiting state. The Timer and the Channel are one Wait, and the decision chooses what comes next.

## Each core capability, side by side {#capabilities}

| Capability | Temporal | Dex |
| --- | --- | --- |
| Durable state | Workflow variables, rebuilt by replaying the Event History. A Worker caches the state in memory. | Attributes, saved with each Step result. A Worker reads them and keeps no cache. |
| Durable waits | A Timer holds no Worker. A workflow can also wait on a condition that a Signal handler sets. | A Step's `WaitFor` returns a Timer, Channel, or SubFlow condition, or several with `AnyOf` and `AllOf`. No Worker is held. |
| Retries | Activities retry by default: 1 second, doubling to 100 seconds, no attempt limit. Workflows do not retry by default. | Every Step method retries by default with the same backoff, up to 4 hours in total. A Flow-level retry policy is not supported. See [Step options](/concepts/step). |
| Timeouts | Start-To-Close or Schedule-To-Close is required on an Activity. Heartbeat is off by default. | A method timeout of 2 hours and a heartbeat timeout of 1 minute by default. |
| Failure handling | Catch an Activity error in workflow code. | A failure policy on the Step routes to a recovery Step. See [Failure Handling](/design-patterns/failure-handling). |
| Parallel work | Start several Activities and `await` them in one thread. | `GoToMany` runs Steps in parallel on different Workers. |
| Recover after a bug fix | Reset a run to an earlier event. | Time Travel restores Attributes, Channel messages, and waiting Steps at an earlier point, with the same Run ID. |
| Search | Search Attributes in the Visibility store. | Indexed Attributes. Built-in search by default, PostgreSQL or ParadeDB for heavy use. |
| Languages | Go, Java, Python, TypeScript, .NET, Ruby, PHP, Rust | Go, Python, Java, TypeScript, Rust |

The rows below need more than a table cell.

### Concurrency defaults {#concurrency-defaults}

A Temporal Workflow runs on a single thread. Signal and Update handlers can still interleave with the main function at each `await`. Temporal recommends a workflow mutex for handlers that read, wait, and then write.

Dex runs the Steps of one Flow in parallel on different Workers. An RPC can run alongside them. They share the Flow's Attributes. You choose which Attributes need a [lock](/concepts/primitives/attribute#locking). Without a lock, two writers that read and then write can overwrite each other. Dex has no lint for this today.

The gap is smaller than "one thread versus many" suggests, but it is real. Temporal gives one writer by default. Dex gives parallel Steps by default and asks you to declare locks.

### Messages and requests {#messages-and-requests}

| | Temporal | Dex |
| --- | --- | --- |
| Asynchronous message | Signal. The client does not wait for a Worker. | Channel publish. Stored with no Worker online. |
| A repeated message | A retried client call is deduplicated by request ID. For other repeats, Temporal recommends an idempotency key in the Signal. | A publish sent again after a lost response is stored twice. Request-ID deduplication is planned in [issue 1519](https://github.com/superdurable/dex/issues/1519). |
| Synchronous request | Update. Waits for the Worker to accept it. Deduplicated by Update ID within a run. | RPC. Needs a Worker within 10 seconds. A retried RPC runs again. |
| Read | Query. Adds nothing to the history. | Read-only RPC. |

[Send a command at most once](/concepts/client#inbound-commands) gives the Dex pattern that drops a repeated command. [Limits](/intro/limits#requests-that-can-repeat) lists every request that can repeat.

### Long-running Flows {#long-running-flows}

Temporal limits each run's Event History. The server logs a warning after 10,240 events. It terminates a run past 51,200 events, 2,000 Updates, or 10,000 Signals. Continue-As-New starts a new run with a fresh history and carries the state over.

Dex keeps a window of each run's newest history events, 50,000 by default on a production server, and prunes older ones. Pruning never fails a Flow, so a long-lived Flow needs no Continue-As-New. The trade-off: events older than the window are gone. See [History window](/reference/server/configuration#history-window).

### Versioning {#versioning}

In Temporal, a code change that alters the order of commands breaks replay for open runs. Temporal offers two tools. Worker Versioning pins a run to Workers on a given code revision, and Temporal calls it the recommended way. Patching branches inside the code with `Patched` or `GetVersion`.

Open Dex Flows run the new code from their next Step. Dex never replays, so a code change cannot cause a replay error. The rules move to your data and Step types: keep old Step types until old Flows finish, and change Attributes and inputs additively. [Change Flow Code](/concepts/change-flow-code#versioning-flow-code) gives the rules. [Check before you deploy](/concepts/change-flow-code#check-before-you-deploy) gives a manual check. Dex has no automatic check yet.

### Run the server {#run-the-server}

| | Temporal Service | Dex Server |
| --- | --- | --- |
| Processes | Frontend, History, Matching, and Worker services. They can share a process. Temporal recommends separate processes in production. | One binary. One active node holds a lease in object storage. Standby nodes take over when it stops. See [Dex Server](/components/server). |
| Required storage | A database: Cassandra, MySQL, or PostgreSQL. SQLite for development only. | Object storage, such as Amazon S3, or db9 in its place. |
| Search storage | A Visibility store. Elasticsearch is recommended in production. | Built-in by default. PostgreSQL or ParadeDB optional. |
| Scale | Scales each service out. | One active node is the ceiling of a cluster. Past it, run separate clusters. See [Limits](/intro/limits#grow-past-one-node). |
| Hosted option | Temporal Cloud | [Dex Cloud](/components/choose-how-to-run#dex-cloud) |
| Release status | A longer production record | Beta. Dex Server is at 0.1.x. See [Release status](/intro/limits#release-status). |
| License | MIT | Sustainable Use License 1.0, source-available. See [License](/intro/limits#license). |

When the active Dex node fails over, every in-flight Step attempt runs again. See [Failover and Deploys](/concepts/failover-and-deploys). [Performance](/intro/performance) gives measured throughput and latency for one Dex node.

## When Temporal is the better fit {#when-another-tool-is-the-better-fit}

- **You want to write the process as one straight-line function.** Temporal lets you do that. Dex asks you to model it as Steps and decisions.
- **You need a mature server today.** Dex Server is at 0.1.x. Temporal has a longer production record.
- **You need more than one node's capacity in one cluster.** Temporal scales its services out. One active Dex node serves a cluster.
- **You want one writer per run with no locks to declare.** A Temporal Workflow gives that by default.
- **You need deduplicated messages today.** Temporal deduplicates Updates by ID. Dex runs a repeated RPC or Channel publish again.
- **You need .NET, Ruby, or PHP.** Dex has no SDK for them.
- **You need a built-in Schedule with pause, backfill, and overlap policies.** Dex has a cron pattern, not a Schedule object.
- **Your team already runs Temporal at scale.** A move costs more than the differences on this page, unless replay or versioning errors are a real problem for you.
- **You need an OSI open source license.** The Temporal server is MIT licensed. Dex is source-available.

Dex fits when you want orchestration code that is ordinary code, versioning without replay, one binary on object storage, and parallel Steps by default.

If you know iWF, Dex grew out of it. A Dex Step is an iWF State, and `WaitFor` is `WaitUntil`.

## Other engines {#other-engines}

<a id="replay-based-workflow-engines"></a>

**Replay-based engines.** Cadence works like Temporal. The comparison above applies to it.

### Journal-based runtimes {#journal-based-durable-function-runtimes}

Restate is an example. A handler runs each side effect through the runtime context, which records the result in a journal. After a failure, the handler runs again and gets the recorded results. A virtual object holds state under a key with one writer per key.

| Restate | Dex |
| --- | --- |
| Workflow, service handler | Flow |
| Journaled action (`ctx.run`) | Step `Execute` |
| Virtual object and its key | A long-lived Flow per key, with the key as the Flow ID. A closed Flow is deleted after retention. A virtual object lives on. |
| Object state | Attributes |
| Awakeable or durable promise | A Channel message that a Step waits for |
| Durable sleep | Timer |

Handler code between journaled calls must be deterministic, because it runs again. Restate deduplicates invocations by idempotency key. Dex deduplicates Flow starts by Flow ID and request ID.

### Database-backed libraries {#database-backed-workflow-libraries}

DBOS is an example. Workflows and steps are annotated functions in your application. DBOS checkpoints them in your PostgreSQL database and adds no other server. The workflow function must be deterministic between steps. DBOS `send` takes an idempotency key.

| DBOS | Dex |
| --- | --- |
| Workflow, Workflow ID | Flow, Flow ID |
| Step | Step `Execute` |
| Send and receive | Channel |
| Events | Attributes, read by RPC |
| Queue | The Flow type's queue. Each Worker's task slots bound its work. |

Dex runs its own server on object storage. It can copy Attribute values to your database with [Attribute Store sync](/components/your-database#attribute-store-sync).

### Step function services {#step-function-services}

AWS Step Functions is an example: a state machine in a JSON definition language, with each state calling a service. Both record an explicit graph of states. Dex Steps and decisions are code in your language. They run on your Workers, so a Step can call any library.

### Agent framework checkpoints {#agent-framework-checkpoints}

LangGraph is an example. A checkpointer saves graph state after each node under a thread ID, and an interrupt pauses the graph for a person. A checkpointer saves state. Restarting a crashed run or waking it on a timer needs a hosted platform or your own code. Dex Server does both for every session.

| Agent framework | Dex |
| --- | --- |
| Thread ID | Session ID, which is the Flow ID |
| Checkpoint | The session's Attributes after each model call or tool call |
| Interrupt for human input | A tool call waiting for approval, or a question |

With [Durable Agents](/agent-frameworks), you keep your framework. The adapter wraps the agent in a session Flow.

### Agent frameworks on a durable execution engine {#agent-frameworks-on-a-durable-execution-engine}

The OpenAI Agents SDK on Temporal, Pydantic AI on Temporal, DBOS, or Prefect, and the LangGraph platform record each model call and wrapped tool call as a unit of the engine. A crash repeats only the running call. Dex adds three things:

- Each tool has an effect class. A read may run again. A non-idempotent write runs in one attempt by default. If it is cut off, the model gets `outcome_unknown`. See [Tool Calls](/agent-frameworks/tool-calls).
- The effect class also sets the default approval. An approval wait holds no Worker, for minutes or days. See [Approvals](/agent-frameworks/approvals).
- One adapter model and one session Flow cover every supported framework.
