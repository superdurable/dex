# Dex vs. Temporal

Dex and Temporal both run processes that survive crashes, restarts, and long waits. They differ in two design choices. Temporal replays workflow code to rebuild a run, and Dex saves the result of each Step. Temporal's service runs on a database, and Dex runs as one binary on object storage. This page starts with those two differences and what they mean for your code and operations. The [terms map](#term-map) and [other engines](#other-engines) come after.

Temporal facts on this page come from the [Temporal documentation](https://docs.temporal.io). Dex facts link to the page that covers them.

## Replay and saved Step results {#the-main-difference-an-explicit-step-graph-not-replayed-code}

The two engines rebuild a run in different ways after a Worker stops.

<RecoveryModelDiagram markdownDescription="A Worker stops mid-run. Temporal: the Event History holds every command and result; a new Worker replays the workflow function from the top to the last await, so workflow code must be deterministic. Dex: Step results and Attributes are saved with each decision; a new Worker runs only the next Step, and finished Steps never run again, so each external effect must be idempotent." />

**Temporal.** A Workflow is one function. The server records an Event History, "a complete and durable log of everything that has happened in the lifecycle of a Workflow Execution". When the run is not in a Worker's cache, a Worker runs the function again from the beginning to continue it. Recorded Activity results are returned instead of running the Activities again. The commands the code produces are checked against the history. A mismatch is a nondeterminism error. Workflow code must therefore make the same calls in the same order for the same input. Clock reads, random numbers, and I/O go through Temporal APIs or into Activities.

**Dex.** A Flow is a set of Steps. Each Step returns a decision that names the next Steps or completes the Flow. Dex saves the Step's result, its Attribute writes, and the decision together. To continue a run, a Worker runs only the next Step. It reads the saved Attributes. Nothing is replayed.

The table lists what each design means for your code, most important first.

| | Temporal: replays workflow code | Dex: saves each Step's result |
| --- | --- | --- |
| Orchestration code | Must be deterministic. Clock reads, random values, and I/O go through Temporal APIs or into Activities. | Ordinary code. A Step can read the clock, use random values, and call any library. |
| A code change while runs are open | A change in the order of commands fails replay with a nondeterminism error. Patching or Worker Versioning keeps old runs on the old path. | Open Flows run the new code from their next Step. Keep old Step types until old Flows finish, and change data additively. See [Deploy Code Changes](/concepts/change-flow-code#versioning-flow-code). |
| A run that lasts months | The Event History has a cap: a warning at 10,240 events or 10 MB, and termination past 51,200 events or 50 MB. Continue-As-New starts a fresh run. | Dex keeps a window of each run's newest events, 50,000 by default, and prunes older ones. The Flow keeps running. See [History window](/reference/server/configuration#history-window). |
| Recover after a bug fix | Reset starts a new run from an earlier event. | Time Travel restores Attributes, Channel messages, and waiting Steps at an earlier point, with the same Run ID. |
| State after a Worker stops | Rebuilt by replaying the Event History, and cached on a Worker between tasks | Read from the Attributes saved with each Step. A Worker keeps no cache. |

## Run the server {#run-the-server}

Temporal needs a database. Dex needs only object storage.

| | Temporal Service | Dex Server |
| --- | --- | --- |
| Processes | Frontend, History, Matching, and Worker services. They can share a process. Temporal recommends separate processes in production. | One binary. One active node holds a lease in object storage. Standby nodes take over when it stops. See [Dex Server](/components/server). |
| Required storage | A database: Cassandra, MySQL, or PostgreSQL. SQLite for development only. | Object storage, such as Amazon S3, or db9 in its place. |
| Search storage | A Visibility store. Elasticsearch is recommended in production. | Built-in by default. PostgreSQL or ParadeDB optional. |

When the active Dex node fails over, every in-flight Step attempt runs again. See [Failover and Deploys](/concepts/failover-and-deploys). [Performance](/intro/performance) gives measured throughput and latency for one Dex node.

## Concurrency defaults {#concurrency-defaults}

Temporal gives each Workflow one writer by default. Dex runs a Flow's Steps in parallel and asks you to declare locks.

A Temporal Workflow runs on a single thread. Signal and Update handlers can still interleave with the main function at each `await`. Temporal recommends a workflow mutex for handlers that read, wait, and then write.

Dex runs the Steps of one Flow in parallel on different Workers. An RPC can run alongside them. They share the Flow's Attributes. You choose which Attributes need a [lock](/concepts/primitives/attribute#locking). Without a lock, two writers that read and then write can overwrite each other.

## What they share {#what-they-share}

- A server records each run's progress outside your process. After a crash, the run continues from that record.
- Workers in your own process pull tasks from the server. Your code never runs inside the server.
- Timers are durable. A run that waits on a Timer or a message holds no Worker.
- Each unit of work has a retry policy and timeouts. The default backoff is the same: 1 second, doubling up to 100 seconds, with no attempt limit.
- A run has a business ID. At most one run with that ID is open at a time, and a reuse policy decides what happens to the next start.
- A unit of work can run more than once. Code that calls another system passes an idempotency key.

## The same process in both models {#the-same-process-in-both-models}

A reminder loop sends a reminder at each interval until the person opts out. In Temporal, the loop is ordinary code that the engine replays. The following sketch is illustrative and is not part of the Dex examples.

```python
@workflow.defn
class ReminderWorkflow:
    def __init__(self) -> None:
        self.opted_out = False

    @workflow.signal
    def opt_out(self) -> None:
        self.opted_out = True

    @workflow.run
    async def run(self) -> None:
        while True:
            try:
                await workflow.wait_condition(
                    lambda: self.opted_out, timeout=REMINDER_INTERVAL
                )
                return
            except asyncio.TimeoutError:
                await workflow.execute_activity(
                    send_reminder, start_to_close_timeout=timedelta(seconds=30)
                )
```

In Dex, the loop is a Step that moves to itself. It waits for the Timer or the opt-out Channel, and its decision chooses what comes next. This excerpt is from the runnable [Reminder](/design-patterns/durable-timer/reminder) pattern:

```python
class ReminderStep(Step[None]):
    def __init__(
        self,
        service: ServiceDependency,
        opt_out: Channel[None],
    ) -> None:
        self.service = service
        self.opt_out = opt_out

    def wait_for(self, context: Context, input: None) -> Wait:
        return Wait.any_of(
            Timer.by_duration(REMINDER_INTERVAL),
            self.opt_out.for_one(),
        )

    def execute(self, context: Context, input: None) -> StepDecision:
        if not context.has_timer_fired():
            return graceful_complete()
        self.service.send_email("Reminder: please respond", "Hello, ...")
        return go_to(ReminderStep, None)
```

impl Step for ReminderStep {

        }
        self.service

        Ok(StepDecision::go_to(&ReminderStep::default(), ()))
    }

The reminder omits an idempotency key because a duplicate reminder is harmless. In Rust, `has_any_timer_fired` reports whether any Timer in the Wait has fired.

The Temporal version reads top to bottom. The opt-out is a Signal handler that sets a variable, and replay rebuilds the variable. The Dex version names the waiting state. The Timer and the Channel are one Wait, and the decision chooses what comes next.

## Terms map {#term-map}

| Temporal | Dex | Notes |
| --- | --- | --- |
| Workflow, Workflow ID, Run ID | [Flow](/concepts/flow), Flow ID, Run ID | Same roles. |
| Workflow code between Activities | Step decisions: `GoTo`, `GoToMany`, `GracefulComplete`, `DeadEnd` | Control flow is data that Dex saves, not code that runs again. |
| Activity | The `Execute` method of a [Step](/concepts/step) | One retry unit. Give each durable call its own Step. |
| Local Activity | Closest: an ASYNC Step | Both trade some durability for latency. See [SYNC and ASYNC Steps](/correctness-and-expressiveness/step-guarantees#sync-and-async). |
| Timer, `sleep` | [Timer](/concepts/primitives/timer) in a Step's `WaitFor` | Both durable. |
| Signal | [Channel](/concepts/primitives/channel) message | Both are accepted with no Worker online. |
| Query | Read-only [RPC](/concepts/primitives/rpc) | |
| Update | [RPC](/concepts/primitives/rpc) that writes Attributes or publishes to a Channel | Both need a Worker. |
| Workflow variables | [Attributes](/concepts/primitives/attribute) | Dex saves them. Temporal rebuilds them by replay. |
| Child Workflow | [SubFlow](/concepts/primitives/subflow) | |
| Task Queue | The Flow type's queue | To use a separate Worker pool, give the work its own Flow type. |
| Sticky execution | Best-effort sticky routing | Dex first offers a task to the Worker that served the Flow before. A Worker keeps no history cache. |
| Search Attributes | Indexed Attributes | |
| Workflow ID Reuse and Conflict Policy | ID reuse policy and start request ID | See [Flow identity](/concepts/flow). |
| Cancellation | An RPC cancels Steps by Step type. `StopFlow` stops the Flow. | Cooperative in both. See [Cancel running Steps](/reference/server/runtime-data#cancel-running-steps). |
| Reset | [Time Travel](/components/operate-and-debug#time-travel) | Time Travel keeps the Run ID. |
| Continue-As-New | No equivalent needed | Dex prunes old history events. See [Replay and saved Step results](#the-main-difference-an-explicit-step-graph-not-replayed-code). |
| Patching, Worker Versioning | Keep old Step types and change data additively | See [Replay and saved Step results](#the-main-difference-an-explicit-step-graph-not-replayed-code). |
| Schedule | A Flow that loops on a Timer | See [Cron schedule](/design-patterns/durable-timer/cron). |
| Nexus | No direct equivalent | A service in another team starts a Flow or calls an RPC over the FlowService API. |
| Temporal Web UI | [Dex Web](/components/web) | |

Dex evolved from iWF. An iWF State corresponds to a Dex Step, and `WaitUntil` corresponds to `WaitFor`.

## Other engines {#other-engines}

<a id="replay-based-workflow-engines"></a>

**Replay-based engines.** Cadence uses the same replay model as Temporal, so the comparison above also applies to Cadence.

### Journal-based runtimes {#journal-based-durable-function-runtimes}

Restate is an example. A handler runs each side effect through the runtime context, which records the result in a journal. After a failure, the handler runs again and gets the recorded results. A virtual object holds state under a key with one writer per key.

| Restate | Dex |
| --- | --- |
| Workflow, service handler | Flow |
| Journaled action (`ctx.run`) | Step `Execute` |
| Virtual object and its key | A long-lived Flow per key, with the key as the Flow ID. A closed Flow is deleted after its retention period, while a virtual object persists. |
| Object state | Attributes |
| Awakeable or durable promise | A Channel message that a Step waits for |
| Durable sleep | Timer |

Handler code between journaled calls must be deterministic, because it runs again. Restate deduplicates invocations by idempotency key. Dex deduplicates Flow starts by Flow ID and request ID.

### Database-backed libraries {#database-backed-workflow-libraries}

DBOS is an example. Workflows and steps are annotated functions in your application. DBOS checkpoints them in your PostgreSQL database and adds no other server. The workflow function must be deterministic between steps. DBOS `send` takes an idempotency key.

| DBOS | Dex |
| --- | --- |
| Workflow, Workflow ID | Flow, Flow ID |
| Step | Step `Execute` |
| Send and receive | Channel |
| Events | Attributes, read by RPC |
| Queue | The Flow type's queue. Each Worker's task slots bound its work. |

Dex runs its own server on object storage and can copy Attribute values to your database with [Attribute Store sync](/components/your-database#attribute-store-sync).

### When Restate or DBOS fits better {#when-restate-or-dbos-fits}

- **Your process is one short function in one service, and you already run PostgreSQL.** A database-backed library adds no new server.
- **You want one writer per key with no locks to declare.** A Restate virtual object gives that by default. In Dex you declare Attribute locks.

### Step function services {#step-function-services}

AWS Step Functions is an example: a state machine in a JSON definition language, with each state calling a service. Both record an explicit graph of states. Dex Steps and decisions are code in your language. They run on your Workers, so a Step can call any library.

### Agent framework checkpoints {#agent-framework-checkpoints}

LangGraph is an example. A checkpointer saves graph state after each node under a thread ID, and an interrupt pauses the graph for human input. The checkpointer only saves state. Resuming a crashed run or waking it on a timer requires a hosted platform or custom code. Dex Server does both for every session.

| Agent framework | Dex |
| --- | --- |
| Thread ID | Session ID, which is the Flow ID |
| Checkpoint | The session's Attributes after each model call or tool call |
| Interrupt for human input | A tool call waiting for approval, or a question |

With [Durable Agents](/agent-frameworks), you keep your framework. The adapter wraps the agent in a session Flow.

### Agent frameworks on a durable execution engine {#agent-frameworks-on-a-durable-execution-engine}

The OpenAI Agents SDK on Temporal, Pydantic AI on Temporal, DBOS, or Prefect, and the LangGraph platform record each model call and wrapped tool call as a unit of the engine. After a crash, only the in-progress call runs again. Dex adds two capabilities:

- Each tool has an effect class. A read may run again. A non-idempotent write runs in one attempt by default. If it is interrupted, the model receives `outcome_unknown`. See [Tool Calls](/agent-frameworks/tool-calls).
- The effect class also sets the default approval. An approval wait holds no Worker, for minutes or days. See [Approvals](/agent-frameworks/approvals).
