# Dex vs. Temporal in Depth

This page is the text version of the Dex vs. Temporal video series, one section per part of each episode. Episode 1 builds the same AI support conversation on both engines, changes its code while conversations are open, and lets one conversation run for a long time. Every number comes from a script in the [dex-vs-temporal-demo](https://github.com/superdurable/dex-vs-temporal-demo) repository.

Both servers ran in their local development mode on one laptop, with default limits. The AI reply and the sentiment analysis are local mocks, not a real model. The demo repository lists the [versions used](https://github.com/superdurable/dex-vs-temporal-demo/tree/aa48a175f38bf62663c9ad9d95784b9c7812b38a#versions-used-for-the-numbers-below). Temporal facts come from the [Temporal documentation](https://docs.temporal.io).

## The scenario {#scenario}

[Watch at 0:40](https://youtu.be/fzl88JWt734?t=40)

An AI support agent answers a customer. One Temporal workflow or one Dex Flow runs per conversation.

- The conversation starts with the customer's first message.
- Each customer message gets one AI reply.
- After a reply, a 10-minute idle timer starts. A follow-up message is answered, and the timer starts again after that reply.
- If the customer sends nothing for 10 minutes, the application sends a nudge email. One hour after the nudge with no message, the conversation closes.

The demos use 30 seconds in place of 10 minutes. In the timer demo, the first message arrives at second 0 and a follow-up at second 20. The nudge is due 30 seconds after the second reply, at second 50.

## The natural Temporal code {#natural-temporal-code}

[Watch at 3:55](https://youtu.be/fzl88JWt734?t=235)

This is one direct way to write the timer. The Signal handler replies to the message and sets a `nudge_at` field. The main function sleeps until `nudge_at`, then sends the nudge. See [naive_conversation_workflow.py](https://github.com/superdurable/dex-vs-temporal-demo/blob/aa48a175f38bf62663c9ad9d95784b9c7812b38a/temporal/naive_conversation_workflow.py).

### Why the timer fires early {#why-the-timer-fires-early}

[Watch at 5:49](https://youtu.be/fzl88JWt734?t=349)

Temporal runs workflow code as [workflow tasks](https://docs.temporal.io/tasks). The Worker completes each workflow task with [commands](https://docs.temporal.io/references/commands): "A Command is an action a Worker requests from the Temporal Service when it completes a Workflow Task Execution."

A timer is one of those commands. The call to `sleep` sends a StartTimer command, and the server records the timer with the first value of `nudge_at`. The Signal handler later changes `nudge_at`. Changing a variable sends no command. So the first timer still fires at second 30.

The code is valid Python, and the Timer fired as scheduled. The application logic changed `nudge_at` and never started a new Timer. The code does not show which statements become commands, or when.

## The correct Temporal code {#correct-temporal-code}

[Watch at 8:06](https://youtu.be/fzl88JWt734?t=486)

The correct workflow follows the official [updatable timer sample](https://github.com/temporalio/samples-python/tree/main/updatable_timer). It gets five things right:

1. The Signal handler only puts the message in a queue. It does no work.
2. The main function is a loop.
3. Each pass answers every queued message, in order.
4. `workflow.wait_condition` with a timeout waits for a new message or the end of the idle window.
5. The timeout raises `asyncio.TimeoutError`, which the code catches.

See [conversation_workflow.py](https://github.com/superdurable/dex-vs-temporal-demo/blob/aa48a175f38bf62663c9ad9d95784b9c7812b38a/temporal/conversation_workflow.py). It sent the nudge at second 50.0.

## The Dex Flow {#dex-flow}

[Watch at 9:28](https://youtu.be/fzl88JWt734?t=568)

A Step says what it waits for and where it goes next. `WaitForCustomerStep` waits for any of two conditions: a message on the `CustomerMessages` Channel, or a Timer for the idle window. If the Timer fired, the Flow moves to `NudgeCustomerStep`. Otherwise it moves to `GenerateReplyStep`, which replies and moves back to `WaitForCustomerStep`. Each time `WaitForCustomerStep` starts, it starts a new Timer. The `post_message` RPC publishes each customer message to the Channel. See [flow.py](https://github.com/superdurable/dex-vs-temporal-demo/blob/aa48a175f38bf62663c9ad9d95784b9c7812b38a/dex/support_conversation/flow.py). It sent the nudge at second 50.4.

The [Inactiveness Tracker Timer](/design-patterns/durable-timer/inactiveness-tracker-timer) pattern has the same shape in every SDK. Notice the two conditions in `WaitFor` and the decision in `Execute`, which moves the Step to itself on activity:

```python
class Tracker(Step[None]):
    def __init__(
        self,
        process_inactiveness: ProcessInactiveness,
        active_channel: Channel[None],
    ) -> None:
        self.process_inactiveness = process_inactiveness
        self.active_channel = active_channel

    def wait_for(self, context: Context, input: None) -> Wait:
        return Wait.any_of(
            Timer.by_duration(TRACKER_DURATION),
            self.active_channel.for_one(),
        )

    def execute(self, context: Context, input: None) -> StepDecision:
        if context.has_timer_fired():
            return go_to(ProcessInactiveness, None)
        return go_to(Tracker, None)
```

struct Tracker;

impl Step for Tracker {
    type Input = ();

    fn wait_for(&self, _context: &mut Context, _input: ()) -> HandlerResult<Wait> {
        Ok(Wait::any_of([
            Timer::by_duration(Duration::from_secs(300)),
            ACTIVE_CHANNEL.for_one(),
        ]))
    }

    fn execute(&self, context: &mut Context, _input: ()) -> HandlerResult<StepDecision> {
        if context.has_any_timer_fired() {
            return Ok(StepDecision::go_to(&ProcessInactiveness, ()));
        }
        Ok(StepDecision::go_to(&Tracker, ()))
    }
}

The Step has one wait and one decision. The Timer and the Channel are the same Wait, so the code needs no queue, loop, or caught exception.

## Changing the code {#change-code}

[Watch at 10:54](https://youtu.be/fzl88JWt734?t=654)

A new requirement arrives while conversations are open: analyze the sentiment of each customer message before replying.

**Temporal.** Version 2 runs an `analyze_sentiment` activity before `generate_reply`. Conversation A started on version 1. After the deploy, its next message is accepted and never answered. The workflow task fails and is retried, and the run stays open:

```text
[TMPRL1100] Nondeterminism error: Activity type of scheduled event 'generate_reply' does not match activity type of activity command 'analyze_sentiment'
```

Queries to conversation A fail too. A conversation started on version 2 works. Temporal documents two fixes:

- **[Patching](https://docs.temporal.io/develop/python/workflows/versioning#patching).** Guard the new code with `workflow.patched`. Temporal describes three steps. First, patch in the new code and run it alongside the old code. Second, remove the old code and mark the patch with `deprecate_patch()`. Third, remove `deprecate_patch()` once no open Workflow Execution runs the previous version of the code. For the second and third steps, Temporal also says to wait until the Workflows started with the pre-patch code "have left retention". In the demo, version 3 with `workflow.patched` let conversation A recover without a reset. Conversation A never runs the sentiment activity, because its history has no patch marker. In the demo, conversation B had started on the unguarded version 2. On version 3, it failed with the mirrored non-determinism error.
- **[Worker Versioning](https://docs.temporal.io/worker-versioning).** "A Pinned Workflow is guaranteed to complete on a single Worker Deployment Version." Other versions can keep polling "to allow pinned Workflows to finish executing". An Auto-Upgrade Workflow moves to its target version, which is the Current Version or the Ramping Version of its Task Queue. Auto-Upgrade Workflows "need to be kept replay-safe manually", with patching.

**Dex.** Version 2 adds `AnalyzeSentimentStep`. `WaitForCustomerStep` and `WaitAfterNudgeStep` now move to it instead of `GenerateReplyStep`. See [flow_v2.py](https://github.com/superdurable/dex-vs-temporal-demo/blob/aa48a175f38bf62663c9ad9d95784b9c7812b38a/dex/support_conversation/flow_v2.py).

- Conversation A was waiting in `WaitForCustomerStep`, which a version 1 Worker had started. After the deploy, a version 2 Worker handled its next message. The message went through `AnalyzeSentimentStep`, then got its reply.
- A conversation started on version 2 begins at `AnalyzeSentimentStep`.
- A wait that started before the deploy keeps its Timer. In a variation that also shortens the idle window, the old 60-second Timer fired at 60.1 seconds. The next wait used the new 10-second window.

[Deploy Code Changes](/concepts/change-flow-code) covers what a deploy changes for open Flows and how to keep them working.

## The history limit and Continue-As-New {#history-limit}

[Watch at 15:02](https://youtu.be/fzl88JWt734?t=902)

Temporal limits each Workflow Execution. Temporal Cloud has fixed [limits](https://docs.temporal.io/evaluate/cloud/limits). A self-hosted server has [defaults](https://docs.temporal.io/self-hosted-guide/defaults), and the history limits are configurable there:

| Limit | Temporal Cloud | Self-hosted default |
| --- | --- | --- |
| Event History | 51,200 events or 50 MB. Warns after 10,240 events or 10 MB. | Errors at 51,200 events or 50 MB. Warns at 10,240 events or 10 MB. |
| Payload | 2 MB per request | Errors at 2 MB. Warns at 512 KB. |
| Event History transaction | 4 MB | Not listed |
| Signals per Workflow Execution | 10,000 | Not listed |

A warning comes when either threshold is reached. The demos ran a local development server with the default limits. Temporal writes the limits in MB and KB. The measured byte counts below are exact, and the payload limit the server applied was 2 MiB, 2,097,152 bytes.

### The conversation that keeps going {#history-limit-flood}

The load test sends follow-up messages at 8 per second, about 200 bytes each, and gets one AI reply per message. The correct workflow has no Continue-As-New.

- 4,266 follow-up messages were accepted and answered in 533 seconds. The 4,267th was rejected: `workflow execution already completed`.
- The server terminated the workflow at 51,201 history events: `Workflow history count exceeds limit.` The history size was 9 MB, far below 50 MB.
- Each customer message adds 12 history events: 1 Signal, 2 workflow tasks of 3 events each, 1 activity of 3 events, 1 timer canceled, and 1 timer started.

### Continue-As-New {#continue-as-new}

[Continue-As-New](https://docs.temporal.io/develop/python/workflows/continue-as-new) ends the run and starts a new one with fresh history. The new run keeps the same Workflow ID and gets a new Run ID. The workflow code does this itself:

1. Check `workflow.info().is_continue_as_new_suggested()`.
2. Wait until every Signal and Update handler has finished. Temporal's guidance: "Complete all handlers before using Continue-as-New."
3. Take a snapshot of the state: the transcript, every unanswered message, the agent, the status, and the timer deadline.
4. Pass the snapshot as the next run's input, and restore the state from it in the new run.

The demo's [conversation_workflow_inline_transcript.py](https://github.com/superdurable/dex-vs-temporal-demo/blob/aa48a175f38bf62663c9ad9d95784b9c7812b38a/temporal/conversation_workflow_inline_transcript.py) does this in 249 lines. The workflow without Continue-As-New has 148. It chains runs at the server's suggestion, about 4,100 events per run.

The snapshot is a payload, so it is limited to 2 MB. After 3,531 answered follow-up messages, the next run's input was 2,199,782 bytes. The limit is 2,097,152 bytes. The workflow task failed:

```text
[TMPRL1103] Attempted to upload payloads with size that exceeded the error limit.
```

The workflow stayed Running and kept accepting Signals, and it stopped replying. The stop point moves with the timing of each Continue-As-New.

Temporal's answer for large payloads is [External Storage](https://docs.temporal.io/external-storage), in Public Preview. It stores a payload outside the Event History and records a reference token in its place. With a local directory as the store, the demo answered 10,000 messages, each once. The stored objects stayed after the workflow completed. Temporal documents that it "does not automatically delete payloads from your external store".

### The conversation context in each activity {#context-in-activity}

This implementation gives each reply the whole transcript as context. `ConversationWithContextWorkflow` passes the transcript to each reply activity as a regular input. It has no Continue-As-New and no External Storage. Temporal records each activity's input in its `ActivityTaskScheduled` event. So each reply copies the transcript into the history again, and the history grows with the square of the message count.

| Messages | Follow-up messages accepted | Terminated at |
| --- | --- | --- |
| 200 bytes, 8 per second | 408, of which 407 were answered in 51 s | 4,907 events, 52,602,112 to 52,602,325 history bytes |
| 8 KiB, 2 per second | 109, of which 108 were answered in 54 s | 1,319 events, 52,719,073 to 52,719,369 history bytes |

Both runs ended with `Workflow history size exceeds limit.` The 50 MB history size limit was reached first. The 2 MB payload limit was not. No workflow task failed, and the Worker logged no error before the termination. These numbers hold for a regular activity that receives the full transcript on each call. The demo did not measure other designs.

### Dex {#history-limit-dex}

The Dex Flow ran the same load for 30 minutes. It answered all 14,138 follow-up messages that were sent and kept running, with no backlog at the end. The load driver dropped 262 of 14,400 planned sends by back-pressure during a slow period of about three minutes.

Dex keeps a window of each run's newest events and prunes older ones. The window pruned the old history, and the Flow kept running. The [History window](/reference/server/configuration#history-window) reference gives the defaults. The demo repository lists the [event counts it measured](https://github.com/superdurable/dex-vs-temporal-demo/tree/aa48a175f38bf62663c9ad9d95784b9c7812b38a#3-a-conversation-that-keeps-going).

The Flow keeps the transcript in an AttributeMap of chunks, within 32 MiB of the run's 64 MiB state budget. When an append does not fit, `TrimTranscriptStep` folds the oldest chunks into a summary and deletes them. With 8 KiB messages, the transcript reached 33.2 MB and stayed under the budget. 64 chunks went into the summary, and the Flow kept running.

### Data size {#data-size}

Temporal limits a payload to 2 MB. A self-hosted server warns at 512 KB by default. The payload limit covers an activity input and a Continue-As-New snapshot. Dex limits a value, such as an Attribute value or a Channel message, to 16 MiB by default. A Flow run holds up to 64 MiB of active state by default. The history and the superseded values kept for Time Travel do not count toward it. See [Limits](/reference/server/configuration#limits) and [Flow state budget](/reference/server/configuration#flow-state-budget).

## Run the server {#run-the-server}

Temporal needs a database. Dex Server is one binary on object storage or db9.

| | Temporal Service | Dex Server |
| --- | --- | --- |
| Processes | Frontend, History, Matching, and Worker services. They can share a process. Temporal recommends separate processes in production. | One binary. One active node holds a lease in object storage. Standby nodes take over when it stops. See [Dex Server](/components/server). |
| Required storage | A database: Cassandra, MySQL, or PostgreSQL. SQLite for development and testing only. | Object storage, such as Amazon S3, or [db9](/reference/server/object-storage#db9) in its place. |
| Search storage | A Visibility store: Elasticsearch, OpenSearch, MySQL, PostgreSQL, or SQLite. Temporal recommends Elasticsearch in production. | Built-in by default. PostgreSQL or ParadeDB optional. |

The Temporal facts come from [Temporal Server](https://docs.temporal.io/temporal-service/temporal-server), [Persistence](https://docs.temporal.io/temporal-service/persistence), and [Visibility](https://docs.temporal.io/self-hosted-guide/visibility).

When the active Dex node fails over, Dex fails every Step attempt that a Worker had received. Each attempt is retried under its Step's retry policy. See [Failover and Deploys](/concepts/failover-and-deploys). [Performance](/intro/performance) gives measured throughput and latency for one Dex node.

## Concurrency defaults {#concurrency-defaults}

A Temporal Python Workflow runs its coroutines on one thread, and they interleave at each `await`. Dex runs the Steps of parallel branches in parallel, and you declare locks where needed.

In a Temporal Python Workflow, Signal and Update handlers run alongside the main function, and they switch at each `await`. Temporal recommends an [`asyncio.Lock`](https://docs.temporal.io/develop/python/workflows/message-passing#use-asynciolock-to-prevent-concurrent-handler-execution) to protect an update that spans an `await`.

When a Flow has parallel branches, Dex runs their Steps in parallel, on one Worker or on several. An RPC can run alongside them. They share the Flow's Attributes. Use a [lock](/concepts/primitives/attribute#locking) for a read-modify-write that must run alone. Without a lock, two writers that read and then write can overwrite each other.
