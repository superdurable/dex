# Performance and Maturity

This page gives measured numbers for one Dex Server node, the release status of Dex, and its license. The [benchmark README](https://github.com/superdurable/dex/blob/main/benchmark/README.md) has every run, its settings, and the steps to repeat it.

## How the benchmark ran

The numbers below were measured on 2026-11-09 in AWS us-west-2:

- **Server:** one Dex Server node on a c7gd.large (2 vCPU) or a c7gd.4xlarge (16 vCPU). Its local store was on the instance's NVMe disk. Its log went to S3 Standard in the same Region.
- **Load:** a separate c7g.8xlarge in the same Availability Zone ran the benchmark tool with a Go SDK Worker. Its CPU stayed below 38%.
- **Versions:** Dex Server (server-zd) v0.1.23 for Steps, Flows, and Channel wakes; v0.1.25 for RPCs and reads.
- **Runs:** each point had a 10-second warmup and a 45-second measurement on a new server. Most points ran three times, and the tables show the median. Flow starts ran once per point.
- **Load model:** a fixed number of concurrent clients, each sending its next request when the last one returns. Latency grows with the client count once the server is busy.

## Peak throughput

| Operation | c7gd.large | c7gd.4xlarge |
| --- | ---: | ---: |
| SYNC Steps | 1,772 per second | 8,403 per second |
| ASYNC Steps | 2,105 per second | 10.1k per second |
| Flows started and completed, one Step each | 1,111 per second | 5,626 per second |
| RPCs that read one Attribute | 15,392 per second | 67.3k per second |
| RPCs that lock and update one Attribute | 2,165 per second | 13.8k per second |
| Reads of ten 16 KiB Attributes, without a Worker | 5,941 per second | 11.3k per second |
| Channel messages that wake a waiting Step | 460 per second | 2,278 per second |

## Latency below the peak

These rows ran at about half of peak throughput. Latency is in milliseconds. The client count differs by row, and latency grows with it. The SYNC rows ran with 96 clients on c7gd.large and 1,024 on c7gd.4xlarge. So the larger node shows a higher SYNC latency because it carried more than ten times the load, not because it is slower.

| Operation | Instance | Throughput | p50 | p99 |
| --- | --- | ---: | ---: | ---: |
| SYNC Step | c7gd.large | 846 per second | 105 | 285 |
| SYNC Step | c7gd.4xlarge | 4,527 per second | 218 | 382 |
| ASYNC Step | c7gd.large | 1,224 per second | 1.3 | 4.9 |
| ASYNC Step | c7gd.4xlarge | 4,766 per second | 1.6 | 3.3 |
| RPC that reads one Attribute | c7gd.large | 7,501 per second | 0.5 | 0.9 |
| RPC that reads one Attribute | c7gd.4xlarge | 35.0k per second | 0.6 | 2.1 |
| Channel wake | c7gd.4xlarge | 1,400 per second | 139 | 308 |

The Channel wake throughput includes untimed setup before each publish. Only its latency, from the publish to the start of the woken Step, measures Dex.

## What the numbers mean

- **A SYNC Step waits for S3.** A SYNC Step waits for two log commits: its attempt start and its result. Each commit is one S3 PUT, and one commit can carry the commands of many Flows. At the SYNC peaks, a commit took 41 to 98 milliseconds on average. Under load, a SYNC Step also waits for its batch, so it needs many concurrent Flows to reach peak throughput.
- **What a Flow adds.** At the half-peak load on c7gd.large (96 concurrent clients), a SYNC Step took 105 milliseconds at p50. A Flow with five SYNC Steps in a row therefore spends about half a second waiting on Dex commits, plus the time of your own code. Agent sessions use SYNC Steps for model calls and tool calls, so each one adds a commit to a turn.
- **At low load.** The benchmark did not measure SYNC Steps at low load. A lightly loaded SYNC Step still waits for its two commits, the start and the result, so a handler that waits for `Charge` sees about two object-storage writes in a row, plus your own code. Those writes averaged 41 to 98 milliseconds at the peaks; at low load, expect your object store's single-write latency. This is an estimate, not a measurement.
- **An ASYNC Step does not wait.** The Flow moves on before the commit, so a Step takes 1 to 2 milliseconds at low load. [SYNC and ASYNC Steps](/concepts/step#sync-and-async) explains the trade-off.
- **S3 requests follow batches, not Steps.** Dex Server groups writes into log batches. A busy node made 23 to 98 log PUTs per second, whatever its size. At USD 0.005 per 1,000 PUTs, that is at most about USD 1.8 per busy hour per node. An idle node renews its lease with about 0.3 PUTs per second.
- **CPU is the limit.** The 2-vCPU node used 93 to 99% of its CPU at every peak. The 16-vCPU node used 68 to 87% at most peaks. Reads of large Attributes on the 16-vCPU node were limited by its 15 Gbps network instead.
- **Reads need no Worker.** An RPC runs on a Worker. A direct Attribute read goes only to Dex Server.
- **These peaks are the ceiling of one cluster.** One active node serves a cluster. [Limits and Sharp Edges](/intro/limits-and-sharp-edges#capacity-and-availability) covers that ceiling, failover, and upgrades.

## What it costs to run

Dex Server needs one instance, an optional standby instance, and object storage. Price the instances and the stored bytes at your provider's rates. The S3 requests follow from the numbers above, at USD 0.005 per 1,000 PUTs:

| Setup | PUTs per second | PUTs per 30-day month | PUT cost per month |
| --- | ---: | ---: | ---: |
| Idle node, lease renewals only | about 0.3 | about 0.78 million | about USD 4 |
| Busy node, low end of the measured range | 23 | about 60 million | about USD 300 |
| Busy node at the highest measured rate, all month | 98 | about 254 million | about USD 1,270 |

Most deployments sit between the first two rows, because a node is busy only part of the time.

A worked example for a light load: 1 million orders a month, each a Flow with five SYNC Steps, is 5 million Steps. A SYNC Step stores its start and its result, and each log commit is one PUT. At light load a batch rarely holds more than one commit, so the upper bound is about 2 PUTs per Step: 10 million PUTs, about USD 50 a month, plus about USD 4 for lease renewals. Under heavier load several commits share a batch, so the cost per Step falls. The monthly total is then:

- instances: the active node, plus a standby if you run one, at your provider's hourly price;
- PUTs: the estimate above, or the table's rows for a node that stays busy;
- stored bytes: the runs kept in the retention window, at your provider's price. The benchmark did not measure stored bytes per Flow. Closed runs are deleted after [retention](/intro/limits-and-sharp-edges#defaults-to-change-before-production), so storage follows the number of runs in that window.

To repeat a point on your own AWS account, run `benchmark/aws/reproduce.sh`. [Reproduce a result](https://github.com/superdurable/dex/blob/main/benchmark/README.md#reproduce-a-result) lists its inputs.

## Release status

| Part | Where it stands |
| --- | --- |
| Dex | Beta. Published APIs, configuration, wire formats, and stored data stay compatible. |
| Dex Server (server-zd) | Version 0.1.x. Upgrades roll forward only, and some stop the cluster. |
| SDKs | Version 1.x, in Go, Python, Java, TypeScript, and Rust. |
| Compatibility | Decided by protocol ranges, not version numbers. A Worker or Client works with a server when their ranges overlap. |

[Upgrades and compatibility](/reference/server/upgrades) gives the protocol ranges.
[Limits and Sharp Edges](/intro/limits-and-sharp-edges#capacity-and-availability)
covers upgrades that stop the cluster.

- **Breaking changes come with a migration path.** A breaking change needs an explicit decision first.
- **Some options are not supported yet.** A Flow start delay and a Flow-level retry policy are rejected. An Attribute Store, the optional database that receives copies of chosen Attributes, can only be PostgreSQL. Flow state itself always stays in Dex Server. [Unsupported features](/reference/server#unsupported-features) links each open issue.
- **Five SDKs, one model.** Go, Python, Java, TypeScript, and Rust have the same Flow model.
- **dexcli dev runs a pinned server.** Each dexcli release archive includes the **dex-server-zd** release it was tested with, and **dexcli dev** runs that one. [Run Locally](/components/run-locally) shows how to install and update it.
