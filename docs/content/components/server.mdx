# Dex Server

Dex Server stores every Flow's state and hands Steps and RPCs to Workers. It
ships as one binary, **dex-server-zd**; its releases and the
[Server reference](/reference/server/) call it **server-zd**.

## What it depends on {#dependencies}

| Dependency | Required? | What you lose without it |
| --- | --- | --- |
| Object storage, such as Amazon S3 or an S3-compatible store | Yes, or db9 in its place | Dex Server cannot run: this is the record of every Flow |
| db9, instead of object storage | No | Nothing; it is an alternative store |
| A PostgreSQL or ParadeDB search backend | No | The built-in search, the default, scans each partition's search documents with a budget. An external backend serves large or frequent searches from SQL. See [Search backends](/reference/server/search). |
| A PostgreSQL Attribute Store | No | Copies of selected Attributes in your own tables. See [Keep data after the Flow](/concepts/primitives/attribute#attribute-store-projection). |
| A metrics listener | No | Prometheus metrics. See [Metrics](/reference/server/metrics). |

db9 is a separate database product that speaks the PostgreSQL wire protocol.
Dex Server can keep its command logs, lease, snapshots, and values there
instead of in S3. Stock PostgreSQL is not a supported production store for
this today, although the db9 provider's tests also run against PostgreSQL 16.
The database must give durable transactions, row locks, and strongly
consistent reads, so a read replica does not qualify. See
[db9 provider](/reference/server/object-storage#db9).

## How it works

Object storage is the record. Dex Server keeps a local store only as a cache,
and a node rebuilds that cache from object storage after a restart.

When Dex reports that something happened, such as a started Flow or a SYNC
Step result, Dex has already written it to object storage.
An ASYNC Step is the exception: Dex moves the Flow on first and writes the
result in a batch about 20 milliseconds later. See
[SYNC and ASYNC Steps](/concepts/step#sync-and-async).

One active process serves a cluster. It holds a lease in object storage, so a
second process cannot write at the same time. You can run standby processes
that take over when the active process stops.

Today the one active node serves every Flow in a cluster, so its capacity is
the cluster's ceiling. [Limits and Sharp Edges](/intro/limits-and-sharp-edges)
covers this and other limits, and
[Performance and Maturity](/intro/performance-and-maturity) gives measured
throughput and latency for one node.

## How it fits with the other components

- [Workers and Clients](/components/application) connect to the
  server's API port. Workers open outbound streams; the server never calls in.
- [Dex Web](/components/web) runs as a separate process and reads
  Flows through the same API.
- [dexcli](/components/cli) calls the same API. **dexcli dev** also
  starts Dex Server on your machine.
- Dex Server stores one Flow Definition Graph for each Flow type. That graph
  is a map of the Flow's Steps and every move their code can make.
  **dexcli visualize** builds it by reading your Flow's source code, without
  running it, so the graph lists possible moves, not the moves of one run.
  Workers or **dexcli** publish it. Each graph records when it was generated. A graph with
  a later generation time replaces an older one, whatever the upload order. Dex
  Web reads it to draw the Flow.
- Dex Server can write selected Attributes to PostgreSQL. See
  [Keep data after the Flow](/concepts/primitives/attribute#attribute-store-projection).

## Run it

For local development, run **dexcli dev**. It starts Dex Server with embedded
object storage, together with Dex Web.

In production, run **dex-server-zd serve** with one YAML configuration file. The
release publishes binaries and a container image. On Kubernetes, run it as a
StatefulSet.

```bash
dex-server-zd serve --config /etc/dex-server-zd/config.yaml
```

To run one production node on local disk without external object storage, run
**dex-server-zd local**. It keeps an embedded object store in its data
directory and has no standby.
