# Application (Worker and Client)

Your Dex application is the code you deploy. It has two parts:

- A **Worker** hosts Flow definitions. It runs **WaitFor**, **Execute**, and RPC
  handlers when Dex hands it work.
- A **Client** starts Flows, calls RPCs, reads Attributes, and searches Flows.
  See [Client](/concepts/client).

A process can run a Worker, a Client, or both.

## How it fits with the other components

Workers and Clients connect to Dex Server. Every Worker is a
pull Worker. It opens outbound task streams to the server and never listens for
calls. So a Worker needs no inbound port and can run behind NAT or a firewall.

Dex sends every Flow, SubFlow, Step, and RPC call to your Workers. There is no
Worker address to configure. A Flow that [Dex Web](/components/web)
or **dexcli** starts also runs on your Workers.

A Worker can publish the Flow Definition Graphs of its Flows to the server when
it starts. Dex Web reads them there to draw each Flow.

## Add Dex to an existing service {#add-to-a-service}

Dex adds a library to your service, not a framework around it. Install the SDK
for your language:

~~~bash
pip install dex-python-sdk                       # Python
go get github.com/superdurable/dex/sdk-go@latest # Go
npm install @superdurable/dex                    # TypeScript
cargo add dex-sdk                                # Rust
~~~

For Java, add **io.superdurable:dex-sdk** from Maven Central to your Gradle or
Maven build.

The Worker can run in two places:

- **Inside your service process.** Start it next to your HTTP server, as the
  [Order Processing](/use-cases/order-processing) example does. One deployment
  then serves requests and runs Steps.
- **In its own process.** Deploy it separately when Steps need different
  scaling, resources, or release timing than your API. The
  [Quick Start](/quick-start) runs its Worker this way.

Either way, the Worker only makes outbound connections, so it needs no load
balancer or inbound port. Your handlers create a Client to start Flows and call
RPCs. [Dex and your database](/components/your-database) explains how Steps
write to the database your service already has.

## Start a Worker {#enable-pull-mode}

Configure the Worker with the server address. A Client needs only the server
address too. You can also set pull options to tune task capacity,
registration, and shutdown.

### Registry and blob cache {#blob-cache}

A Worker and a Client each take two more objects:

- **A Registry of your Flows.** The Worker runs the Steps and RPCs of the
  Flows in it. The Client uses the same definitions to encode a Flow's start
  input and its RPC arguments, and to decode results. So a Client builds the
  Flow objects too, even though it never runs a Step.
- **A blob cache.** Dex sends a large value, such as a big Attribute, as a
  reference. The blob cache is a local, size-limited directory that keeps
  those values, so the process does not download them again. Give each Worker
  and Client process its own directory. The cache holds only copies, so
  deleting it loses no data.

Each SDK reference has a runnable startup example:
[Go](/reference/go/workers), [Python](/reference/python/workers),
[Java](/reference/java/workers), [TypeScript](/reference/typescript/workers),
and [Rust](/reference/rust/workers).

## Pass services to the Flow {#pass-services-to-the-flow}

Pass each service that a Flow calls, such as a payment API, to the Flow constructor. Then every Step has its services from the moment the Worker registers the Flow, and a test can pass a fake service the same way. A setter or a global variable leaves a window in which a Step can run without its service.

## Start a Flow from a handler {#start-a-flow-from-a-handler}

A **start** handler starts the Flow. When the caller needs to know that the first Step finished, such as a charge before the order page shows "paid", the handler waits for that Step with the Client **wait-for-Step-completion** API. The wait ends when Dex records the Step, so the handler needs no status table or polling loop of its own.

```go
// StartOrder starts the order's Flow once, however often the request is retried.
// It returns after Charge completes.
func StartOrder(ctx context.Context, client *dex.Client, flow *OrderFlow, orderID string) error {
	requestID := "start-" + orderID
	options := dex.StartFlowOptions{
		RequestID:      &requestID,
		AlreadyStarted: &dex.AlreadyStartedOptions{IgnoreError: true},
	}
	if _, err := client.StartFlow(ctx, flow, orderID, orderID, options); err != nil {
		return err
	}
	return client.WaitForStepCompletion(ctx, orderID, dex.StepExecutionID{StepType: "Charge"},
		dex.WaitForStepCompletionOptions{RequestTimeout: 30 * time.Second})
}
```

```rust
/// Starts the order's Flow once, however often the request is retried. Returns after Charge.
pub fn start_order(client: &Client, order_flow: &OrderFlow, order_id: &str) -> SdkResult<()> {
    let options = StartFlowOptions::new()
        .request_id(format!("start-{order_id}"))
        .ignore_already_started(true);
    client.start_flow_with_options(order_flow, order_id, order_id.to_string(), options)?;
    client.wait_for_step_completion(

        StepExecutionId::of(&order_flow.charge),

    )
}
```

Three start options make a retried request safe:

- The **order ID is the Flow ID**. Dex keeps one Flow for each ID, and its default ID reuse policy rejects a second start.
- The **request ID** is **start-** plus the order ID. It is the same on every retry of this request.
- The **already-started option** returns the existing run when its request ID matches. It is **ignore_already_started** in Python and Rust, **ignoreAlreadyStarted** in Java and TypeScript, and **AlreadyStarted.IgnoreError** in Go. A different request ID for the same order still gets an already-started error, which the service answers with 409.

So when a client sends the request twice, the order is charged once. [Start options and configuration](/concepts/flow#start-options) lists the options, and [Dex and your database](/components/your-database#write-your-row-and-start-the-flow) shows the handler that also writes your own table. Run the service from the example folder, then send an order:

```bash
curl -X POST localhost:8080/orders -d '{"orderId": "order-1"}'
```

## Send commands and read state through RPCs {#send-commands-through-rpcs}

A handler that changes a Flow calls an RPC, such as **approve**. The RPC publishes the message to a Channel, and the waiting Step wakes. A handler that reads a Flow calls a read RPC, such as **describe**. An RPC runs against the Flow's current state on a Worker, so the handler reads and writes the same state that the Steps use. The handlers get the Client and the Flow from their constructor or factory arguments.

The [Order Processing](/use-cases/order-processing) example shows these three patterns in full code.

## Capacity and shutdown

A Worker opens one stream for each task slot. Dex sends a task only to a free
slot, so a Worker never has to decline work for lack of capacity. A Step that no Worker takes
waits in a durable task queue. An RPC fails when no Worker takes it in time.
Stop Workers gracefully during a deployment, so running tasks can finish.

[Workers and the task queue](/reference/server/workers) describes readiness,
routing, capacity, shutdown, and network settings.
