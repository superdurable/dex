# Your Application

Your Dex application is the code you deploy. It has two parts:

- A **Worker** hosts Flow definitions. It runs `WaitFor`, `Execute`, and RPC
  handlers when Dex hands it work.
- A **Client** starts Flows, calls RPCs, reads Attributes, and searches Flows.
  See [Client](/concepts/client).

A process can run a Worker, a Client, or both.

## How it fits with the other components

Workers and Clients connect to Dex Server. Every Worker is a
pull Worker. It opens outbound task streams to the server and never listens for
calls. So a Worker needs no inbound port and can run behind NAT or a firewall.

Dex sends every Flow, SubFlow, Step, and RPC call to your Workers. There is no
Worker address to configure. A Flow that [Dex Web](/components/web)
or `dexcli` starts also runs on your Workers.

A Worker can publish the Flow Definition Graphs of its Flows to the server when
it starts. Dex Web reads them there to draw each Flow.

## Add Dex to an existing service {#add-to-a-service}

Dex adds a library to your service, not a framework around it. Install the SDK
for your language:

~~~bash
pip install dex-python-sdk==1.45.0                       # Python
go get github.com/superdurable/dex/sdk-go@v1.45.0        # Go
npm install @superdurable/dex@1.45.0                     # TypeScript
cargo add dex-sdk@=1.45.0                                # Rust
~~~

For Java, add `io.superdurable:dex-sdk:1.45.0` from Maven Central to your Gradle or
Maven build.

These lines pin the version the Quick Start uses. Each Quick Start example shows the same pin in its build file:
[Python](https://github.com/superdurable/dex/blob/main/examples/python/quick-start/pyproject.toml),
[Go](https://github.com/superdurable/dex/blob/main/examples/go/quick-start/go.mod),
[Java](https://github.com/superdurable/dex/blob/main/examples/java/quick-start/build.gradle),
[TypeScript](https://github.com/superdurable/dex/blob/main/examples/typescript/quick-start/package.json), and
[Rust](https://github.com/superdurable/dex/blob/main/examples/rust/quick-start/Cargo.toml). An SDK and a Dex Server work together when their protocol ranges overlap,
whatever their version numbers; [Upgrades](/reference/server/upgrades)
explains the rule.

The Worker can run in two places:

- **Inside your service process.** Start it next to your HTTP server, as the
  [Order Processing](/use-cases/order-processing) example does. One deployment
  then serves requests and runs Steps.
- **In its own process.** Deploy it separately when Steps need different
  scaling, resources, or release timing than your API. The
  [Quick Start](/quick-start) runs its Worker this way.

Either way, the Worker only makes outbound connections, so it needs no load
balancer or inbound port. Your handlers create a Client to start Flows and call
RPCs. [Dex and your database](/components/your-database) explains how Steps
write to the database your service already has. [Test Your Flows](/components/testing) shows how to test them against a real Dex Server.

## Start a Worker {#enable-pull-mode}

Configure the Worker with the server address. A Client needs only the server
address too. You can also set pull options to tune task capacity,
registration, and shutdown.

A Worker and a Client each take two more objects: a Registry and a blob cache.

### Registry {#registry}

A Registry holds your Flows. The Worker runs the Steps and RPCs of the Flows
in it. The Client uses the same definitions to encode a Flow's start input and
its RPC arguments, and to decode results. So a Client builds the Flow objects
too, even though it never runs a Step. Pass stand-ins for the Flow's services
in a process that only starts Flows, because the Client never calls them;
[Start Flows from an API service](/concepts/client#start-from-an-api-service)
explains this. A service in another language either has the Flow code in its
own language, or calls the FlowService `StartFlow` request over gRPC with the
Flow type and an input that the Flow can decode, as `dexcli flow start` does.

### An API-only process {#api-only-process}

A process that only starts Flows builds the Flow with a stand-in service and
registers it for its Client. The Quick Start's start program is one: its mock
API is never called.

### Blob cache {#blob-cache}

Dex sends a large value, such as a big Attribute, as a reference. The blob
cache is a local, size-limited directory that keeps those values, so the
process does not download them again. Give each Worker and Client process its
own directory. The cache holds only copies, so deleting it loses no data.

Each SDK reference has a runnable startup example:
[Go](/reference/go/workers), [Python](/reference/python/workers),
[Java](/reference/java/workers), [TypeScript](/reference/typescript/workers),
and [Rust](/reference/rust/workers).

## Pass services to the Flow {#pass-services-to-the-flow}

Pass each service that a Flow calls, such as a payment API, to the Flow constructor. Then every Step has its services from the moment the Worker registers the Flow, and a test can pass a fake service the same way. A setter or a global variable leaves a window in which a Step can run without its service.

## Start a Flow from a handler {#start-a-flow-from-a-handler}

A **start** handler starts the Flow. When the caller needs to know that the first Step finished, such as a charge before the order page shows "paid", the handler waits for that Step with the Client's wait-for-Step-completion call: `wait_for_step_completion` in Python and Rust, `WaitForStepCompletion` in Go, and `waitForStepCompletion` in Java and TypeScript. The wait ends when Dex records the Step, so the handler needs no status table or polling loop of its own.

// StartOrder starts the order's Flow once, however often the request is retried.
// It returns after Charge completes.
func StartOrder(ctx context.Context, client *dex.Client, flow *OrderFlow, orderID string) error {
	requestID := "start-" + orderID
	options := dex.StartFlowOptions{
		RequestID:      &requestID,
		AlreadyStarted: &dex.AlreadyStartedOptions{IgnoreError: true},
	}
	if _, err := client.StartFlow(ctx, flow, orderID, orderID, options); err != nil {
		return err
	}
	return client.WaitForStepCompletion(ctx, orderID, dex.StepExecutionID{StepType: "Charge"},
		dex.WaitForStepCompletionOptions{RequestTimeout: 30 * time.Second})
}

Three start options make a retried request safe:

- The **order ID is the Flow ID**. Dex keeps one Flow for each ID, and its default ID reuse policy rejects a second start.
- The **request ID** is **start-** plus the order ID. It is the same on every retry of this request.
- The **already-started option** returns the existing run when its request ID matches. It is `ignore_already_started` in Python and Rust, `ignoreAlreadyStarted` in Java and TypeScript, and `AlreadyStarted.IgnoreError` in Go. A different request ID for the same order still gets an already-started error, which the service answers with 409.

So when a client sends the request twice, the order is charged once. This holds only while the run exists; see [How long these protections last](/components/your-database#how-long-protections-last). [Start options and configuration](/concepts/flow#start-options) lists the options, and [Dex and your database](/components/your-database#write-your-row-and-start-the-flow) shows the handler that also writes your own table. Run the service, then send an order.

## Send commands and read state through RPCs {#send-commands-through-rpcs}

A handler that changes a Flow calls an RPC, such as **approve**. An RPC needs a running Worker ([RPC guarantees](/concepts/primitives/rpc#guarantees)). To store a message while no Worker runs, see [Deliver an event when no Worker runs](/concepts/client#deliver-without-a-worker). The RPC publishes the message to a Channel, and the waiting Step wakes. A handler that reads a Flow calls a read RPC, such as **describe**. An RPC runs against the Flow's current state on a Worker, so the handler reads and writes the same state that the Steps use. The handlers get the Client and the Flow from their constructor or factory arguments.

The [Order Processing](/use-cases/order-processing) example shows these three patterns in full code.

## Capacity and shutdown

A Worker opens one stream for each task slot. Dex sends a task only to a free
slot, so a Worker never has to decline work for lack of capacity. A Step that no Worker takes
waits in a durable task queue. An RPC fails when no Worker takes it in time.
Stop Workers gracefully during a deployment, so running tasks can finish.

[Workers and the task queue](/reference/server/workers) describes readiness,
routing, capacity, shutdown, and network settings.

## Run in containers {#run-in-containers}

A Worker and a Client fit a stateless container:

- **Network.** A Worker only opens outbound connections to Dex Server, so its
  container needs no inbound port or load balancer for Dex. Set the server
  address in each process's configuration, such as an environment variable.
- **Credentials.** When the server requires authentication, mount the token
  as a file and pass a file credential through the `credential` option. See
  [Send credentials from Workers and Clients](/reference/server/authentication#sdk-credentials).
- **Blob cache.** The [blob cache](#blob-cache) is a local cache of copies.
  An ephemeral directory, such as the container's scratch disk, is enough.
  Give each process its own directory. A new container starts with an empty
  cache and loads values again as it needs them.
- **Same Flow definitions.** Build every Worker and Client image from code
  that registers the same Flows, so the Client encodes inputs the way the
  Worker decodes them. During a rolling deployment, an older Worker that lacks
  a Step type hands that call to a newer one. See
  [Failover and Deploys](/concepts/failover-and-deploys).
- **Graceful stop.** Send the stop signal and give the process time to finish
  running tasks before the container is killed. See
  [Capacity and shutdown](#capacity-and-shutdown).
