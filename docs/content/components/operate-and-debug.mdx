# Operate and Debug

Dex Web and `dexcli` read Flows through the same Dex Server API as your Workers. Dex Web shows a run in application terms. `dexcli` prints the same data as JSON, for scripts and incident records.

## Find and read a Flow {#find-a-flow}

In Dex Web, **Search** and **Summary** find Flows and show their state. A run's page shows its active Steps, Attributes, and Channels. Its **Timeline** lists each event of the run, with its inputs, outputs, and Attribute changes.

From a terminal, read the same run with its Flow ID and Run ID. These commands only read, and they print JSON:

```bash
dexcli flow inspect FLOW_ID --run-id RUN_ID

dexcli flow history FLOW_ID --run-id RUN_ID --all
```

**dexcli flow inspect** returns the current summary and state. **dexcli flow history** returns the run's events. The [CLI reference](/reference/cli/) lists every command.

## A Flow is stuck {#flow-does-not-advance}

A Flow advances only when a Worker takes its next Step. When a Step stays active or its retry count grows, check the Worker first:

1. Collect the Flow ID, Run ID, Flow type, Worker version, and Dex Server address.
2. Read the Worker logs for handler exceptions, registration failures, and startup configuration.
3. Check that the Worker's outbound streams to Dex Server are connected, with the right address, TLS, and credentials.
4. Check that the deployed Worker registers the Flow, Step, and RPC names that the open Flow uses.
5. Open the Step in Dex Web. Its attempt, Worker error, gRPC status, and stack trace tell an unavailable Worker from an application failure.

After you fix the Worker, an active retry continues on its own. Do not restart or time travel a Flow only to test connectivity.

## A Flow failed {#flow-failed}

A Flow fails when a Step handler fails and its retries run out, or when its Flow timeout is set to fail it. By default, Step retries stop after 4 hours. In Dex Web, select the failed event in **Timeline**. Its **Failure** panel shows the attempt, the error, and the gRPC status. Expand **Stack trace** before you hand the failure to the team that owns the code.

[Troubleshoot a Flow run](/reference/web/debugging) has the full read-only workflow, with screenshots.

## Recover a Flow with Time Travel {#time-travel}

Time Travel moves a run back to an earlier point in its history and runs it again from there. Use it after you deploy a fix for a Step that failed. Verify the fix with a new run first. The run keeps its Run ID and starts a new attempt.

Every Step after that point runs again, with its external calls, so each call needs an [idempotency key](/concepts/step#idempotency-keys).

Time Travel restores the run's state at that point: its Attributes, its Channel messages, and the Steps that were waiting or ready. Input that came from outside the run after that point is then applied again by default: RPC calls, Channel publications, and Attribute writes. This is **write reapply**. Turn it off with `skip_writes_reapply` (`dexcli`: `-skip-writes-reapply`) when that input should not count again.

The target point must be inside the run's recent history window. Time Travel to the beginning of the run is always available.

Start Time Travel from Dex Web, a Client, or `dexcli flow time-travel`; the [CLI reference](/reference/cli) lists its flags. [Time travel](/reference/server/runtime-client#time-travel) in the server reference covers the request, the history window, and the limits.

## What runs again after a crash {#what-runs-again}

Dex saves each finished Step, so a crash repeats only the work that was in progress.

| Event | What runs again |
| --- | --- |
| A Worker crashes or stops | The Step attempts it was running |
| A Dex Server node fails over | Every attempt that a Worker had received |
| You deploy new Step code | Nothing that already finished |
| You run Time Travel | Every Step after the chosen point |

[Failover and Deploys](/concepts/failover-and-deploys) covers each event, including ASYNC Steps.
