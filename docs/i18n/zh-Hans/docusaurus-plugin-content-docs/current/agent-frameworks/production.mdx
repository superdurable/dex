# 在生产环境运行 Agent

Agent Session 和其他所有 Flow 运行在同一个 Dex Server 上。把 Session 交给用户使用之前，逐项检查下面的内容。每一行都链接到包含详情的页面。

| 事项 | 需要知道什么 | 详情 |
| --- | --- | --- |
| 认证 | Public API 认证默认关闭。在 server 能被其他机器访问之前打开它。 | [Authentication](/reference/server/authentication)（英文） |
| Credential | 把模型 API key 和 tool credential 放在 Worker 的环境或 secret store 中，永远不要放进 Session input 或 message。 | [Credentials](/reference/agents/credentials)（英文） |
| Dex Server | Dex Server 运行在 Dex Cloud 上，或者运行在你自己带对象存储的基础设施上。一个集群由一个活动节点提供服务。 | [在哪里运行 Dex Server](/components#where-to-run)、[在生产环境运行 Dex](/components/production) |
| 保留期 | 已停止的 Session 默认在 7 天内仍可读取，之后 server 可能删除它。每个 run 保留它启动时的值；新值只作用于重启之后启动的 run。需要保存更久的对话记录，请放在你自己的存储中。 | [Retention](/reference/server/configuration#retention)（英文） |
| 未知结果 | 被崩溃打断的写操作会记录为 `outcome_unknown`，并且不会再次运行。决定由谁来核对它。 | [核对 outcome_unknown](/agent-frameworks/tool-calls#reconcile-outcome-unknown) |
| 升级 | 部署在下一次模型调用或 Tool Call 时生效。对标记为不兼容的版本，启动新 Worker 之前，先优雅地停掉所有旧 Worker。强制停止会让正在运行的单次尝试 tool 变成 `outcome_unknown`。 | [Upgrades](/reference/agents/upgrades#in-flight-calls)（英文） |
| 部署期间的调用 | `send_user_message` 和 `resolve_interrupt` 是 RPC。它们需要正在运行的 Worker，而重试的 `send_user_message` 可能把同一条消息排队两次。 | [部署期间的 RPC](#rpcs-during-a-deploy) |
| Worker | 每个正在运行的模型调用、Tool Call 和 RPC 都占用一个 Worker task slot。按并行 Tool Call 的数量确定 Worker 规格。 | [Workers and timeouts](/reference/agents/workers)（英文） |
| Session 大小 | Session 的 active state 达到 state 上限（默认 64 MiB）时，Session 结束。Message 保留策略，以及 harness 支持时的 compaction，会让它保持在上限以下。 | [Session limits](/reference/agents/session-limits)（英文） |
| 模型花费 | 在每次模型调用前后，按账号或 API key 检查花费；Dex 把花费上限留给你的代码。 | [Spend limits](/reference/agents/spend-limits)（英文） |
| 审批期限 | 调用不能无限期等待时，设置一个期限。没有期限的审批会一直等到有人答复，turn 也随之等待。 | [Approval deadlines](/reference/agents/approvals#approval-deadlines)（英文） |
| 流式传输 | AgentEvents Stream 把实时文本送到你的 UI。按你的流量确定它的规格。 | [AgentEvents Stream](/reference/agents/event-stream)（英文） |
| Tracing | Session 可以为每次模型调用和 Tool Call 输出 OpenTelemetry span。内容采集默认关闭。 | [Tracing](/reference/agents/tracing)（英文） |
| 部署形态 | Web replica 持有 Client。Worker 进程运行 Session Flow。 | [部署形态](#deployment-shape) |

## 部署形态 {#deployment-shape}

生产环境有三类进程：

<AgentDeploymentDiagram markdownDescription="用户访问 Web 应用副本，它们持有 Client，向 Dex Server 发送 RPC 和读取请求。Worker 进程通过出站连接从 Dex Server 拉取任务，运行 Session Flow：模型调用、Tool Call 和审批。Dex Server 把 Session 状态保存在对象存储中。" />

- **Web app replica** 持有 Client。它们启动 Session、发送消息并流式返回回复。它们需要 Session Flow 的定义来编码调用，但从不运行 Step。
- **Worker 进程** 通过 Dex Agents 适配器，用你的框架或内置 Agent Loop 运行 Session Flow：每次模型调用、Tool Call 和审批等待。对小应用来说，web 进程也可以同时托管 Worker，Agent 快速开始程序就是这样做的。
- **Dex Server** 保存每个 Session。Worker 主动向外连接它，所以不需要入站端口。

滚动部署期间，每个 Step 运行的是接手它的那个 Worker 的代码。[部署新代码](/concepts/failover-and-deploys#you-deploy-new-code)和 [Upgrades](/reference/agents/upgrades)（英文）说明 Dex 怎样路由 Step，以及哪些版本需要先停掉所有旧 Worker。

## 部署期间的 RPC {#rpcs-during-a-deploy}

应用通过 RPC 与 Session 通信，例如 `send_user_message` 和 `resolve_interrupt`。RPC 在 Worker 上运行。它从不在队列中等待：如果 10 秒内没有 Worker 接手，调用就会以 **Unavailable** 失败。在停掉所有 Worker 的部署期间，这些调用会一直失败，直到新的 Worker 连上。Session 本身不会丢失任何东西。

- **遇到 Unavailable 时重试。** 用 backoff 重试，直到 Worker 恢复。没有 Worker 接手的 RPC 什么都没有改变，但响应丢失的调用也可能以 **Unavailable** 结束，所以请按下一项的方式重试 `send_user_message`。
- **resolve_interrupt 可以安全重试。** 已经生效的审批第二次会返回 **False**，什么都不会再次运行。
- **send_user_message 可能发送两次。** 它每次调用都会发送新的 request ID，所以从你的代码再次调用它，它就会再次运行。如果响应丢失，重试可能把同一条消息排队两次。重新发送之前，用 `get_agent_snapshot` 读取 Session，在 **messages** 和 `queued_messages` 中查找这条消息。如果它排队了两次，用 `delete_queued_message` 删除多出的副本。

[只发送一次消息](/agent-frameworks/sessions#send-a-message-once)给出了每个 SDK 的辅助函数。

其他可能重复的请求，参见 [限制](/intro/limits#requests-that-can-repeat)。
