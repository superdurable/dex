# Durable Agents

本页介绍如何在生产环境中运行 [agent framework](/agent-frameworks) 的 session。
一次 Flow 执行就是一个 agent session。每次模型调用是一个 **RunModel** Step，每个
tool call 是独立的 Step。本页中的服务器限制都是 server-zd 的默认值。其余配置见
[Server 参考](/reference/server/) 和
[Application](/components/application)。

## 安装包 {#install}

连同 framework 一起安装 adapter。Python adapter 发布在 PyPI 上。每个 adapter 都会带上
**dex-agents** 核心包和它支持的 Dex SDK。需要 Python 3.11 或更高版本。

```bash
pip install dex-agents-pydantic-ai "pydantic-ai-slim[openai]"
pip install dex-agents-langgraph
pip install dex-agents-openai-agents
pip install dex-agents-google-adk
pip install dex-agents-claude-agent-sdk
```

TypeScript adapter 发布在 npm 上。核心包和 Dex SDK 是 peer 依赖，所以应用只持有各自的
一份副本。需要 Node 22 或 24。

```bash
npm i @superdurable/dex-agents-vercel-ai @superdurable/dex-agents @superdurable/dex ai zod
npm i @superdurable/dex-agents-mastra @superdurable/dex-agents @superdurable/dex @mastra/core zod
npm i @superdurable/dex-agents-openai-agents @superdurable/dex-agents @superdurable/dex @openai/agents zod
npm i @superdurable/dex-agents-claude-agent-sdk @superdurable/dex-agents @superdurable/dex zod
```

如果要自己编写 runner，只安装核心包：

```bash
pip install dex-agents==0.2.0
npm i @superdurable/dex-agents@0.2.0 @superdurable/dex@1.35.0
```

所有 agents 包共用一条版本线。Python adapter 要求同一版本的核心包，npm adapter 以
peer 依赖的方式依赖它。每个版本都固定了它支持的 Dex SDK，以及测试过的 framework 版本范围，
见[兼容性表](https://github.com/superdurable/dex/blob/main/agents/README.md#versions-and-compatibility)。
这些包还没到 1.0，minor 版本可能改变 API。在 lockfile 中固定确切版本，升级前先读
[changelog](https://github.com/superdurable/dex/blob/main/agents/CHANGELOG.md)。

在每个启动 session 或调用其 RPC 的进程中，构建同一个 session Flow。

## Stream 后端 {#stream-backend}

模型的实时文本、推理摘要、tool 进度和审批事件都写入 **AgentEvents**
[Stream](/concepts/primitives/stream)。无论是 **dexcli dev** 还是生产 server，**streamStore.backend**
的默认值都是 **memory**，所以实时事件不需要额外的服务器配置。不要为 agent 把后端设为
**disabled**。设为 **disabled** 时，Step 写入会被丢弃，但不会让 Step 失败；Client 写入和
Stream 读取则返回 **FAILED_PRECONDITION**。默认配置等同于：

```yaml
streamStore:
  backend: memory
```

memory 后端把 Stream 保存在 active server-zd 进程的内存中。一个 server-zd 集群只有一个
active 进程，所以单节点不需要额外配置。[standby](/reference/server/high-availability#hot-standby)
不保存 Stream。进程每次成为 active 进程时，Stream 都从空开始：重启之后、standby 接管之后，
以及[让位](/reference/server/high-availability#step-down)之后。standby 对 Stream 调用返回
**UNAVAILABLE**，客户端会重新连接到 active 进程。

丢失 Stream 数据不会丢失 session。对话、tool call 和待审批项都保存在 Attribute 中。
错过事件的客户端用 **get_agent_snapshot** RPC 重新加载 session，然后从那里继续读取
Stream。收到 **turn_completed** 或 **turn_failed** 后，客户端用已保存的消息替换这一轮的
实时文本。不要把 Stream 当作事实记录。

## 规划 AgentEvents 容量 {#size-agent-events}

**AgentEvents** 的容量按 Flow type 和 Stream name 计算。同一个 agent 的所有 session
共享这份容量，它不是每个 session 的预算。默认值是 10 MiB。在 Python 中用
**AgentSessionOptions** 的 **event_stream_capacity_bytes** 设置，在 TypeScript 中用
**createAgentSessionFlow** 选项的 **eventStreamCapacityBytes** 设置。

服务器为每条消息计入序列化后的值、Flow ID 和 source，再加 512 字节。用量达到容量的
90% 时，后台 trimmer 会删除所有 session 中最旧的消息，直到用量降到 80%。如果 trim
跟不上，用量达到容量，写入会被拒绝。Step 会丢弃被拒绝的写入，但不会失败。容量应能装下
每个有客户端在看的 session 的最新一轮：

```text
bytes per turn = messages per turn × (average message bytes + 512)
capacity       ≥ concurrent sessions × bytes per turn ÷ 0.8
```

假设一轮写入 200 条消息，每条约 300 字节（含 Flow ID 和 source），那么每轮约 162 KB。
500 个 session 同时输出时，实时事件约占 81 MB。除以 0.8 约为 102 MB，所以 128 MiB 的容量
可以保留每个 session 的最新一轮。默认的 10 MiB 大约只能保留 50 个这样的轮次。

固定的 512 字节在小文本增量中占大头。Python 核心包为 runner 写入的每个文本增量写一条
Stream 消息。TypeScript 核心包会把连续的增量合并，最多合并 100 ms 或 1,024 个字符。
Python adapter 每轮的消息数会更多。

一条 Stream 消息最大 100 KiB，由 **streamStore.maxMessageBytes** 设置，更大的写入会被丢弃。
memory 后端把所有 Stream 都放在服务器内存中，所以服务器内存要按所有 agent Flow type
和其他 Stream 的容量之和来规划。

## 规划 Worker 容量 {#size-workers}

每个正在运行的模型调用、tool call 和 RPC handler 都占用一个 Worker task slot。等待用户
消息、审批或 tool 结果的 session 不占用 slot，等待发生在 Dex Server 中。每个 Worker 池的
容量应覆盖同时调用模型的轮次、同时运行的 tool call，以及 RPC 预留。

同一次模型响应中的 tool call 作为并行 Step 运行。Worker 的 slot 至少要够模型一次发出的
最大一批 tool call。默认的 task 上限是 CPU 数量。模型调用大部分时间在等网络，所以 agent
Worker 通常需要更高的 **maxConcurrentTasks**。各 SDK 的选项名见
[容量和关闭](/reference/server/workers#capacity-and-shutdown)。

保留 [RPC 预留容量](/reference/server/workers#reserved-rpc-capacity)。UI 以 RPC 的形式调用
**get_agent_snapshot**、**send_user_message** 和 **resolve_interrupt**。没有预留时，这些
调用要排在占满 Worker 的模型调用后面。不设置时，task 上限至少为 2 则预留一个 slot，否则为零。
Step 从不使用预留 slot。Step 任务队列持续增长，说明 Step 需要更多容量。相关指标见
[Step 任务队列](/reference/server/workers#step-task-queue)。

server-zd 默认为每个 app Worker ID 允许 256 个 stream
（**matching.maxConcurrentTasksCap**）。一个 Worker 为每个 task slot 打开一个 stream，
所以它的 task 上限要落在这个范围内。需要更多时，运行更多 Worker 进程。

留出余量。没有 Worker 有空闲 slot 时，Step 会在队列中等待。等待不消耗 attempt，
也不计入 method timeout 和 heartbeat timeout。等待 slot 的一轮或一次 tool call 会花更长时间。
见 [Tool call 的限制](#never-run-outcome-unknown)。

### 长时间模型调用和超时 {#timeouts}

这些 Step 选项由包设置。Python **AgentSessionOptions** 中的 **run_model_limit**，或 TypeScript
中的 **runModelLimit**，可以修改 **RunModel** 的方法超时和 attempt 次数。其他选项
**AgentSessionOptions** 不能修改。

| Step | 方法超时 | Heartbeat 超时 | Attempt | 失败路由 |
| --- | --- | --- | --- | --- |
| **RunModel** | 15 分钟 | 2 分钟 | 30 分钟内 3 次 | **RecordTurnFailure** |
| **CompactContext** | 15 分钟 | 2 分钟 | 30 分钟内 3 次 | **RecordTurnFailure** |
| **CallTool** | 2 小时，Dex 默认值 | 1 分钟，Dex 默认值 | 3 | **RecordToolFailure** |
| **CallSingleAttemptTool** | 2 小时，Dex 默认值 | 1 分钟，Dex 默认值 | 1 | **RecordToolOutcomeUnknown** |

runner 工作时，**RunModel**、**CompactContext** 和两种 tool Step 每 20 秒发送一次 heartbeat。所以慢但没有输出
的模型调用或 tool call 仍然在 heartbeat 超时之内。方法超时依然会结束卡住的调用。在 Python
中，runner 和 tool 代码要保持非阻塞：在 event loop 上的阻塞调用也会让后台 heartbeat 停下来。

一次模型调用必须在 15 分钟内完成。把 provider 或 framework 的请求超时设得比它短，这样慢
调用会带着 provider 的错误失败，后续 attempt 也还能落在 30 分钟的重试窗口内。Dex 如何发现
丢失的 attempt，见 [Heartbeat](/reference/python/flows-and-steps/step-options#heartbeat)。

Claude Agent SDK session 在一个 **RunModel** 中运行整段轮次：多次模型调用和内联 tool call，
直到 CLI 给出回答或推迟一个 tool call。默认情况下这一段必须在 15 分钟内完成。更长的段需要
提高这个限制。所有 runner 都能用这个选项，但每个 **RunModel** 只做一次模型调用的 runner 很少
需要它。

- heartbeat 在这一段中持续发送，所以方法超时是唯一的上限。卡住的段会占用 Worker slot 直到
  超时，所以不要设得比需要的更高。
- 重试预算随限制一起变化。它等于方法超时乘以 attempt 次数减一，并且至少是方法超时的两倍，
  这样超时的 attempt 仍然可以重试。Dex 只在 attempt 失败后才检查它。
- 失败的段会整段重跑，并再次为其中的模型调用付费。如果这比一轮失败代价更高，把 attempt 次数
  设为 1。
- **CompactContext** 保持自己的限制，因为它只做一次模型调用。
- 修改后的限制对 Worker 重启后调度的每个 **RunModel** 生效。进行中的 attempt 及其重试保持
  原来的限制。

### 分开的 Worker 池 {#worker-pools}

Dex 按 Flow type 路由工作。注册了某个 agent Flow type 的每个 Worker，都可能收到它的模型
调用、tool call 和 RPC。包会一起注册 session 的所有 Step，所以同一个 agent 的模型调用和
tool call 共用一个 Worker 池。某类工作挤占另一类工作时，可以这样拆分：

- 给每个 agent 独立的 Flow type 和独立的 Worker 部署，这样繁忙的 agent 不会占用其他 agent
  的 slot。
- 把重量级或特殊的 tool 工作，比如浏览器、沙箱或 GPU 任务，放到有自己主机和扩缩容的服务中。
  tool 用这次调用的幂等键调用该服务。session Worker 只需要等待网络，服务可以独立扩缩容。

## 长 session 的限制 {#limits}

一个 session 可以持续几个月。以下 server-zd [限制](/reference/server/configuration#limits)
决定它能增长到多大。

| Key | 默认值 | 限制对象 |
| --- | --- | --- |
| **limits.maxFlowStateBytes** | 64 MiB | 一个 session 的活动状态：当前状态，包括它持有的 Attribute 和 Channel 值。history 以及 history 为 time travel 保留的被替换值不计入。 |
| **values.maxValueBytes** | 16 MiB | 单个值的上限，比如一条消息、一条 tool call 记录或一份 framework run state |
| **history.windowEvents** | 约 50,000 个事件；**dev** 和 **local** 为 5,000 个 | 每个 run 保留的 Flow history。更早的事件会被裁剪。 |
| **retention.closedFlowDuration** | 7 天 | 已停止的 session 还能读取多久 |

每个 run 在启动时记录这些值。新值只对服务器带着新值重启之后启动的 session 生效。

包这样保存状态：

- **AgentMessages** 保存最新的消息，每条消息一个 AttributeMap 实例。保存一条消息只写这一条。
  其中超过 64 条消息时，最早的消息移入不再重写的 **AgentMessageChunks** 实例。一个 chunk 最多
  32 条消息、1 MiB，因此远低于 **values.maxValueBytes**。更大的消息不进入窗口，保存时直接放进
  自己的 chunk，所以超过 **values.maxValueBytes** 的消息会让它所在的轮次立即失败，和以前一样。
  **AgentMessageIndex** 记录消息所在的位置，只在写入或删除 chunk 时改变。每条消息写两次：一次在窗口中，一次在
  它的 chunk 中。窗口副本移除后，就不再计入 run 预算。启用[压缩](#compaction)时，**RunModel** 只加载
  摘要之后的消息。不启用压缩时，每次模型调用都加载并发送完整历史，也不会删除任何消息。
- **FrameworkRunState** 在一轮等待 tool 结果时保存 framework 的状态。每次模型调用请求 tool
  后，**RunModel** 都会重写它。它保存这一轮到目前为止的工作，包括 tool 输出。OpenAI Agents
  SDK 的状态还包含这一轮的输入，Vercel AI SDK 的状态会把每个 tool 输出保存两次。只有当前值
  计入 run 预算。之前的每个值都成为被替换值，history 会为 time travel 保留它，但 run 预算
  不计入它。
- **AgentToolCalls** 记录在一轮结束时删除，之后不再计入 run 预算。

服务器会对 Step heartbeat、Step 完成，以及改变 Flow 状态的 RPC（比如 **send_user_message**）检查 run 预算，并且只在写入增加活动状态时检查。session 超出预算后，这样的写入会被拒绝。接下来发生什么，取决于写入来自哪里。

- **模型调用或 tool call。** session 结束，因为下一轮会碰到同一个上限。它的状态变为 **failed**，**last_turn_error** 保存原因，比如 "active run state of 67492 bytes exceeds the maximum of 65536 bytes"，Flow 也以同样的文本关闭为失败。这个 Step 的结果不会保存。已付费的模型回答会丢失，已经运行的 tool 保留它的效果，但没有保存结果。之后不再调用模型。
- **其他 Step。** 没有失败路由的 Step，比如 **AwaitUserMessage**，会以这个原因让 Flow 关闭为失败。上面的失败记录写不下时也一样，而轮次较小时这很常见。此时保存的 **AgentState** 保持最后的值。Python 的 **AgentSessionClient.get_agent_snapshot** 和 TypeScript 的 **readAgentSnapshot** 会读取 Flow 的关闭记录，所以对保存过状态的 session，它们会报告 **failed** 和原因。请使用它们，不要只调用 **get_agent_snapshot** RPC。在保存状态之前就失败的 session，其 snapshot 没有状态，原因要从 Flow 的结果读取。
- **发给已失败 session 的新消息。** 已关闭的 Flow 会拒绝它。Python 的 **AgentSessionClient.send_user_message** 和 TypeScript 的 **sendAgentUserMessage** 会抛出带原因的 **AgentSessionFailedError**。直接调用 RPC 得到的是 **FlowNotActiveOrNotFoundError**。
- **已失败 session 中排队的消息。** 它们不会运行。在保留期删除 session 之前，它们都能从 snapshot 的 **queued_messages** 读到，所以你可以把它们发给新的 session。
- **写不下的消息。** **send_user_message** 以 **RESOURCE_EXHAUSTED** 和同样的文本失败，消息不会进入队列。没有 Step 运行，所以 session 不会失败：它继续等待，更短的消息可能还能写入。只有调用方能看到这个错误。

已失败的 session 无法恢复。提高上限只对新 session 生效。规划时让 session 远低于 64 MiB。

Flow history 大约保留一个 session 最新的 50,000 个事件；**dev** 和 **local** 为 5,000 个。
读取对话用 **get_agent_snapshot** 或 **list_agent_messages**，不要从 Flow history 读。
[Time travel](/reference/server/runtime-client#time-travel) 只能以
[history 窗口](/reference/server/configuration#history-window)内的时间点为目标。
Time travel 到起点始终可用。运维人员可以调整 **history.windowEvents** 和每个 run 的 history 窗口；
参见 [history 窗口配置](/reference/server/configuration#history-window)。

session 不会自己结束。完成后用 **StopFlow** 停止它。已停止的 session 及其
**get_agent_snapshot** RPC 在[保留期](/reference/server/configuration#retention)内仍可用，
之后 Dex 会清除它。需要比 session 保存更久的对话记录，要在此之前用
**list_agent_messages** 复制出来。

### 压缩与存储上限 {#compaction}

压缩从 agents 0.2.0 包开始提供，用来让模型输入保持在上下文窗口之内。在
**AgentSessionOptions** 中，或者在 Stepwise agent 的定义中设置 **compaction**，并给出模型的
上下文窗口 token 数。runner 必须支持压缩。Stepwise 支持。从 agents 0.3.0 包开始，OpenAI Agents
SDK、Pydantic AI、LangChain 与 LangGraph、Google ADK、Vercel AI SDK 和 Mastra 的 adapter 也支持。
当一次模型调用的输入将达到窗口的 85% 时，session 会先运行一个 **CompactContext** Step。它用
一次模型调用把较早的消息折叠成一份摘要，下一次模型调用收到的是这份摘要和最新的消息。如果
较早的消息放不进窗口，runner 会在摘要调用中略去其中最早的部分，并告诉模型。使用 Stepwise 时，
一个包含很多 tool call 的长轮次会在轮次中途压缩。

framework adapter 的压缩方式不同，因为模型输入由框架构建：

- **只在轮次之间压缩。** adapter 在一个轮次的第一次模型调用之前压缩，从不摘要正在运行的轮次。
  tool call 之后继续同一轮次的模型调用不会压缩，所以一个轮次新增的内容必须放得进窗口剩余的部分。
  如果一个轮次可能新增超过窗口约 15% 的内容，请调低 **trigger_ratio**（**triggerRatio**）。
- **偏高的估算。** adapter 把每条已保存消息的 3 个字节算作一个 token，这比提供方对英文文本的计数更多。
  它还会加上自己能看到的 instructions 和工具定义。对它看不到的部分，例如已编译 LangGraph 图中的
  system prompt、动态 instructions 或 MCP 工具，请在策略中设置
  **reserved_input_tokens**（**reservedInputTokens**）。
- **不带工具的摘要调用。** 摘要调用以纯文本接收较早的轮次，并使用 agent 的模型，除非你传入摘要模型。
  LangGraph 必须传入，因为已编译的图不暴露它的模型。
- **记录保存在 Dex 中。** 框架自带的压缩，例如摘要 middleware 或提供方侧的压缩，只改变该框架的模型输入。
  无论如何 Dex 都保存每条消息，并且只有 Dex 的摘要能让 retention 删除消息。两者选用其一。使用 Google ADK
  时，摘要还会保留 session state 和最后回复的 agent。
- **Claude Agent SDK 不支持。** Claude Code 在 CLI 内部压缩自己的 transcript。adapter 保存每条
  transcript 记录，包括 Claude Code 的压缩记录，并且不接受压缩策略。它保存的消息没有 Dex 摘要，
  所以 retention 从不删除它们。

只有在该 Flow 类型的每个 Worker 都运行带有 **CompactContext** Step 的版本之后，才启用压缩。
读取 session 快照的客户端也需要 agents 0.2.0：0.1.0 客户端无法读取压缩期间快照中的
**compacting_context** 状态。

压缩也限定了 session 的存储。当最早的 chunk 中每条消息都已被摘要，且它之后至少还保存着
**retained_message_limit**（默认 1,000）条消息时，保留策略会删除这个 chunk。最新的 1,000 条
消息和摘要之后的每条消息始终保留，所以无论 session 运行多久，保存的消息都不再增长。在
**AgentSessionOptions** 中用 **retained_message_limit**、**message_window_size**、
**message_chunk_size** 和 **message_chunk_max_bytes** 设置上限、窗口大小和 chunk 限制。上限设为
**None**（TypeScript 中为 **null**）时保留每条消息。如果把 **values.maxValueBytes** 调到约 2 MiB
以下，也要同时调低 **message_chunk_max_bytes**。

被删除的消息不再出现在 **list_agent_messages** 和 **get_agent_snapshot** 中。分页在最早保存的
消息处结束，每一页的 **deleted_before_sequence** 表示保留策略删除了它之前的消息。如果应用
需要完整对话，就在消息之后又保存 **retained_message_limit** 条消息之前，用
**list_agent_messages** 把新消息复制出去。一个简单的做法是在每个 **turn_completed** 事件之后，
从上次复制到的序号之后开始复制。如果一轮可能保存的消息多于上限，就提高上限或设为 **None**。

根据保留的消息估算 run 预算。在一个实测的 session 中，每轮保存一个 100 字符的问题和一个
600 字符的回答，约 2.9 KB，session 在 8,000 token 的窗口下压缩。上限为 100 时，在第 200、
400、600 和 800 轮，保存的消息都在 162 KB 到 185 KB 之间，session 的全部活动状态在 167 KB 到
191 KB 之间，而 session 一共保存了 2.3 MB 的消息。使用默认上限 1,000 时，按上限乘以一条消息的
大小，加上摘要之后的消息，再加上一轮持有的最大 framework run state 和 tool call 记录来规划。
被删除的 chunk 和被重写 Attribute 的旧值不计入。

让长 session 保持在预算之内：

- 新的、无关的工作开一个新 session，不要让一个 session 无限增长。
- 让 tool 输出保持小。返回模型需要的内容，比如 ID、摘要或排名靠前的结果，而不是整份文档。
  每个输出都会保存在它的 tool call 记录中、这一轮运行期间的 run state 中，以及消息中。
- 把文件、图片和长文档等大型产物放到你自己的 blob 存储中，让 tool 返回它们的引用。

## 审批和截止时间 {#approvals}

需要审批的 tool call 在独立的 **AwaitToolApproval** Step 中等待。等待不占用 Worker slot，
也不受 Worker 重启和部署影响。

没有截止时间时，审批会一直等到有人回答，这一轮也跟着等待。新的用户消息会排队，直到这一轮
结束。在 Python 的 **AgentSessionOptions** 中设置 **interrupt_deadline**，或在 TypeScript
中设置 **interruptDeadlineMs**。到截止时间仍未处理的调用会被拒绝，消息是
"approval deadline passed"，模型会看到这次拒绝。

session 在模型请求调用时，用 Worker 的时钟计算截止时间。保持 Worker 时钟同步。修改截止时间
选项后，只对之后产生的审批生效。Dex Timer 以整秒为单位，所以截止时间的 Timer 会向上取整，
最多晚一秒触发。从截止时间起，**resolve_interrupt** 返回 false，所以迟到的回答不会生效。

Step 持有同一把锁时，**resolve_interrupt** 可能以 **RpcLockConflictError** 失败。重试是
安全的。Python 的 **AgentSessionClient** 最多重试 5 秒。

RPC 的锁由调用方发送。SDK Client 和 Dex Web 会带上 RPC 声明的锁。直接发送的
**InvokeRPC** 请求（例如 **dexcli api call**）要在 **lock_attribute_keys** 里列出这些锁。
不带锁时 RPC 不加锁运行，同一个审批的两个答复可能都成功。

## Connector tool {#connector-tools}

Stepwise agent 可以把 [Connector](/components/connector) 的 operation 当作 tool 调用。**ConnectorToolSource** 提供这些 tool，方式和 **McpToolSource** 提供 MCP server 的 tool 一样。每次调用在自己的 tool Step 中通过 Connector SDK 运行一个 operation，所以 Call ID、幂等键、凭证处理和 single-dispatch fence 的行为和 Connector Step 中相同。Python 和 TypeScript core 提供这项功能。Python 的 Claude Agent SDK adapter 也通过 **tool_sources** 接受它。Go core 只支持 function tool，其他 framework adapter 暂时也不提供 connector tool。

安装带 Connector SDK 的 core，以及 agent 用到的每个 Connector 包：

```bash
pip install 'dex-agents[connectors]' dex-connector-stripe
npm i @superdurable/dex-agents @superdurable/connectors-sdk @superdurable/connector-stripe
```

有些 Python Connector 包先在 GitHub 发布，之后才上 PyPI。这时从它的 release tag 安装。 release notes 里有确切的命令：

```bash
pip install "dex-connector-<name> @ git+https://github.com/superdurable/dex-connectors-library@<tag>#subdirectory=connectors/<name>/python"
```

固定你测试过的版本。Connector tool 需要 **dex-connector.json** 带有 agent 元数据的 Connector 包，分析导入这些包的 Flow 需要 Dex CLI 1.38.0 或更高版本。

### 提供哪些 operation {#connector-tools-offered}

默认不暴露任何 operation。应用用 Python 的 **connector_tool** 或 TypeScript 的 **connectorTool** 列出 agent 可以使用的每个 operation。只有 Connector 作者审查过、在 **dex-connector.json** 中标记了 **agent.exposed** 的 operation 才能成为 tool。其他 operation 在构建 agent 定义时就会被拒绝。tool 名称默认是 Connector ID 加上 snake case 形式的 operation，例如 **stripe_create_refund**。描述和参数 schema 来自 manifest。

模型给出的参数先按 operation 的 **inputSchema** 检查，再解码成 operation 的输入类型。拼错的字段、错误的类型或缺少的字段会让这次调用失败，并给出模型可以据此修正的消息。operation 不会运行。

### Effect class {#connector-tools-effects}

manifest 决定一次调用能否再次运行，也就决定由哪个 Step 运行它：

| Operation | Effect class | 运行于 |
| --- | --- | --- |
| Query | **read** | **CallTool**，会重试 |
| 带 **agent.retry: safe** 的 Mutation | **idempotent_write** | **CallTool**，会重试 |
| 其他 Mutation | **non_idempotent_write** | **CallSingleAttemptTool**，只运行一次 |

**agent.retry: safe** 是 Connector 作者审查后做出的声明：用同一个 Call ID 重复调用不会产生第二次效果。没有这个声明时，调用只运行一次。**CallTool** 重试时 Call ID 不变，因为 Call ID 由 Flow ID 和 tool Step 的 execution ID 派生。重试不超出 operation 自己的 Execute 重试策略和超时，也最多三次 attempt。attempt 用尽时，Query 记录为 **failed**，Mutation 记录为 **outcome_unknown**。

session 的 **tool_policies**（**toolPolicies**）中针对 connector tool 的条目只改变它的审批。effect class 始终来自 manifest。

### 审批 {#connector-tools-approval}

审批回答的是这次调用该不该发生。它和重试是两个问题：带幂等键的退款仍然是真实的退款。默认情况下，只有 manifest 写明 **agent.approval: recommended** 的 connector tool 才等待审批，例如退款。其他 Mutation 不需要审批就会运行，因为每条消息都要审批的话，常驻 agent 就没法用了。

应用可以按 tool 覆盖这个默认值，两个方向都可以。应用还可以传入一个谓词，根据每次调用的参数决定是否审批，例如超过限额的退款。谓词抛出异常时会要求审批。没有通过 schema 检查的参数不会运行，所以也不会等待审批。

### 结果 {#connector-tools-outcomes}

operation 选中的 branch 决定 tool call 的记录。Connector 作者在 **agent.branches** 中列出需要说明的 branch：**rejected**（什么都没有生效）或 **unknown**（写入可能已经生效）。规则在不确定时按最保守的方式处理：

| Branch | 记录 | 模型看到 |
| --- | --- | --- |
| 成功 branch，例如 **sent** 或 **refunded** | **succeeded** | 结果值 |
| 列为 **rejected** 的 branch，例如 **providerRejected** | **failed** | branch 和 provider 的消息 |
| **defect** | **failed** | branch 和消息 |
| 未列出的 Query branch | **failed** | branch 和消息 |
| **uncertain**、列为 **unknown** 的 branch，或未列出的 Mutation branch | **outcome_unknown** | 结果未知 |

被拒绝或失败的调用不会让 session 失败。模型读到结果后可以做出反应。和其他 tool 一样处理 **outcome_unknown**，见[核对 outcome_unknown](#reconcile-outcome-unknown)。

### 写入顺序 {#connector-tools-write-order}

同一次模型回复中的 connector 写入按模型给出的顺序逐个运行。读取以及其他 tool 的调用照旧并行运行。需要审批的写入轮到它时才请求审批。一次写入失败、以 **outcome_unknown** 结束，或者被人或 provider 拒绝时，这次回复中后面的 connector 写入都不会运行。它们各自记录为 **failed**， **skipped** 字段为 true，错误以 "the tool did not run, so it is safe to call again" 开头。 Dex Web 把这些调用显示为已跳过。

在 Claude Agent SDK adapter 中，一次模型回复的调用每次只有一个离开 turn，在自己的 tool Step 中运行。这次回复中后面的写入在 turn 内被拒绝，所以它不会运行，也不留下记录。模型先读到前一次写入的结果，再决定是否重新调用后面的写入。

### 结果大小 {#connector-tools-result-size}

结果以键排序的紧凑 JSON 交给模型。超过 64 KiB 文本的结果会被截断，模型会在截断处之后读到 "[Dex] truncated, N bytes" 这条说明。记录的 **truncated_output_bytes** 保存完整大小。可以在 source 上或单个 tool 上修改这个上限。

### 崩溃 {#connector-tools-crashes}

connector 写入期间 Worker 崩溃，绝不会把一次写入发送两次：

| 故障 | **CallTool** 中可安全重试的写入 | **CallSingleAttemptTool** 中的写入 |
| --- | --- | --- |
| 请求发出前 Worker 退出 | 用同一个 Call ID 重试。还没记录 claim 的 fenced 写入会回读，以 **outcome_unknown** 结束，什么都没发送 | **outcome_unknown**，什么都没发送 |
| provider 接受后 Worker 退出 | provider 丢弃重复的键，或者 fenced 写入回读并确认已发送。一次写入 | **outcome_unknown**，一次写入 |
| provider 限流 | 重试并只发送一次 | 写入的 fence 记录了未发送时为 **failed**，错误为 "not sent; the provider asked to retry later"；否则为 **outcome_unknown** |

只运行一次的写入请求重试时，通常以 **outcome_unknown** 结束，因为重试请求本身不能证明什么都没发送。single-dispatch fence 可以证明这一点：它记录请求从未离开进程，或者 provider 没有处理就拒绝了请求。有了这个证明，调用记录为 **failed**，模型可以再次调用，也不需要有人去核对 provider。这次回复中后面的写入仍然会被跳过。

凭证留在 Worker。和 Connector Step 一样，connector tool 只随调用保存逻辑 connection 名称，见 [凭证](#credentials)。

## 查找需要人处理的 session {#find-sessions}

**ActiveStepTypes** 是内置的搜索字段。它列出 Flow 正在等待的 Step，所以一条查询就能跨 agent
找到所有等待人处理的 session：

```text
ActiveStepTypes = "AwaitToolApproval"
ActiveStepTypes = "AwaitQuestionAnswer"
```

session 进入等待时出现在结果中，继续往下走时离开。这个搜索不需要带索引的 Attribute。session
具体在问什么，读 **PendingInterrupts** 或 session snapshot。

Python 的 **AgentSessionClient.start_session** 和 TypeScript 的 **startAgentSession** 会为
新 session 打开这个搜索。它们把 **activeStepSearchMode** 设为只索引带等待的 Step 的模式，应用
可以在启动选项中改用别的模式。直接调用 **start_flow** 或 **startFlow** 不会设置它，服务器默认值
会让这个 session 留在搜索之外。作为 SubFlow 启动的 session 继承父 Flow 的模式。

要为已经在运行的 session 打开搜索，比如在 0.2.0 上启动的 session，对这个 session 调用
**UpdateFlowConfig**。在 Python 中，调用 **update_flow_config**，把 **active_step_search_mode**
设为 **AGENT_SESSION_ACTIVE_STEP_SEARCH_MODE**。在 TypeScript 中，调用 **updateFlowConfig**，把
**activeStepSearchMode** 设为 **agentSessionActiveStepSearchMode**。运维人员也可以运行
**dexcli flow update-config**。即使 session 已经在等待，它也会在几秒内出现。要更新所有
运行中的 session，分页调用 **SearchFlows**，再逐个更新：

```text
FlowType = "SupportAgent" AND ExecutionStatus = "Running"
```

**RunModel** 这类直接运行的 Step 不会被索引。所以 session 的搜索记录只在进入或离开等待时变化，
没有 tool call 的一轮变化两次。每次变化都和 Step 在同一次提交中写入搜索记录。

有两种需要人处理的情况不会出现，因为没有 Step 在等待它们：记录了 **outcome_unknown** 的
tool call，以及等待 **execute_plan** 的草稿计划。

## 在 Dex Web 中查看 session {#dex-web}

[Dex Web](/reference/web/dex-web) 根据 Flow Definition Graph 绘制 Flow，并提供它的 Action。
**dexcli visualize** 读不了 session Flow，因为这个 Flow 定义在 agents 包里，而 Flow 类型由每个应用
自己选择。所以 Python 和 TypeScript 包直接附带 session 图。为每个 agent 生成一次，填入这个 agent 的
Flow 类型和它的 Action 需要的权限：

```bash
dex-agents-session-graph --flow-type SupportAgent --permission support-agent.operate \
  --out definitions/support-agent.json
```

两个包都会安装 **dex-agents-session-graph** 命令，生成的字节完全相同。在代码中，Python 调用
**render_session_flow_graph**，TypeScript 调用 **renderSessionFlowGraph**。然后让 Dex Web 读取这个
目录：

```bash
dex-web --flow-rendering-dir ./definitions
```

在开发机上，**dexcli dev --flow-rendering-dir ./definitions** 的作用相同。在发布 Worker 的构建或部署步骤中生成这些文件，再把目录挂载给 Dex Web。Worker 不需要发布任何东西。
Dex Web 在启动时读取目录，所以文件变化后要重启它。升级 agents 包之后，重新生成这些文件。

这张图显示每个 session Step、它的等待条件、RPC，以及它们之间的 Channel。图中不包含 Attribute 的读写。
Dex Web 提供四个 Action：**resolve_interrupt**、**answer_question**、**steer_user_message** 和
**cancel_turn**。每个 Action 以对应请求的字段作为输入，比如 interrupt ID 和审批结果，并要求你选择的
权限。这些 Action 没有条件，因为每个 RPC 自己检查 session 的状态。session 运行期间，Dex Web 一直提供
这四个 Action；不适用的 RPC 返回 false。interrupt ID 可以从 run 状态中的 **PendingInterrupts** 读取，
也可以从 session snapshot 读取。

session 的 run 页面还有一个 **Session** 标签页。它按对话顺序显示消息，每个工具调用都画在 agent 发起它的位置。每个待审批的调用各有一张审批卡片，底部有 **Steer** 和 **Stop turn**。这个标签页直接读取 session 的 Attribute，所以 Worker 停机时仍能显示 session。详见 [Agent session view](/reference/web/dex-web#agent-session-view)。

session 没有声明 Summary 或 Display 字段，所以 Dex Web 显示 session 时不调用 Worker。Action 仍然需要
Worker。

只有 **Working as** 选了某个权限的用户，Dex Web 才显示需要这个权限的 Action 表单。session 的 Action 没有条件，所以这个选择不会隐藏这个 agent 的任何 session：Working as 列出 Flow type 提供这个权限的所有 session。

Work Queue 的 agent 模式列出等待人处理的 session，按 agent 分组，并在侧边面板中直接回答。见 [Agent inbox](/reference/web/dex-web#agent-inbox)。只有当 session 的 Flow 开启了按活动 Step 类型搜索时，它才会出现在这里；**start_session** 默认开启。

Go 核心只注册了 session Flow 的一部分，所以这张图不能描述由 Go Worker 运行的 session。

## 花费限制 {#spend-limits}

花费限制通常按账户或 API key 计算，跨越许多 session。Dex 没有内置限制。应用实现
**ModelSpendLimit**，并通过 Python **AgentSessionOptions** 的 **spend_limit** 或 TypeScript
的 **spendLimit** 传入。不传时，session 不做任何检查。

session 在 **RunModel** 和 **CompactContext** 的每次模型调用前后调用这个接口：

| 调用 | 时机 | 收到的内容 |
| --- | --- | --- |
| **check_model_call** | 每次 attempt 之前，在轮次控制和压缩判断之后 | session、轮次、Step 类型、attempt、session settings 和已提交的用量 |
| **report_model_usage** | attempt 的模型调用返回时，Step 提交之前 | 同上，外加这次调用的用量和稳定的报告 ID |

计数器和限额都属于应用。把账户或 API key 的引用放在 session settings 中，再在检查时读取。
它只能是引用，因为 session settings 会被存储。

**被拒绝的调用会结束这一轮。** session 把 **MODEL_CALL_REFUSED_ERROR_PREFIX** 和应用给出的
原因写入 **AgentState.last_turn_error**，保留这一轮已完成的 tool 结果和通常的失败说明，然后
等待下一条用户消息。那条消息开始新的一轮，并再次检查。被拒绝的 **CompactContext** 同样结束
这一轮。session 保持存活，不涉及新的状态或 interrupt。

**失败的检查等同于没有原因的拒绝。** 检查抛出异常或超过 30 秒时，这次 attempt 失败。Dex 按
Step 的重试策略重试，没有通过检查就不会有模型调用。重试用完后，这一轮带着错误失败。要改成
放行，在检查中捕获自己的错误并允许调用。

**失败的报告不改变任何事。** 报告抛出异常或超时时，只记录日志并丢弃。让 attempt 失败会为这次
调用再付一次费。

**每次 attempt 只报告一次。** 报告 ID 是 **flow/turn/step execution/attempt**，所以每个 ID 只
计一次。重试是一次新的付费调用，ID 也是新的。Step 已报告但没有提交时，比如 Worker 崩溃，
重试时会再报告一次。两次调用都付了费，所以报告的总量会超过 **AgentUsage**，后者只保留已提交的
attempt。报告还带有包含这次调用的 session 用量，按 session 计数的应用可以在下一次报告时
弥补被丢弃的报告。

设计时要考虑四个限制：

- 检查限制的是下一次调用，不是它的花费。同时通过检查的 session 可能超出限额。
- Claude Agent SDK session 这样的 harness 每个轮次段只检查一次，用量在段结束时才到达。一段可能
  因为其中所有模型调用而超出限额。同时设置 harness 自己的预算选项，比如 Python 的
  **max_budget_usd** 或 TypeScript 的 **maxBudgetUsd**。
- 失败、被取消或随 Worker 丢失的调用不会报告，但 provider 可能仍然计费。有些框架不提供 token
  数，所以报告可能显示 **model_calls** 大于零而 token 为零。这表示未知，不是免费。按你自己的
  规则计算这些调用。
- 报告不是持久的。报告在 Step 内运行，所以 Worker 在模型回答之后、报告之前崩溃时，这次报告会
  丢失。这次 attempt 不会提交，所以 **AgentUsage** 中也没有这次调用，只有 provider 的账单有记录。

## 崩溃和重新部署 {#worker-failures}

崩溃最多重跑当时正在运行的那一次调用。

下表就是崩溃矩阵。每一行是一个 Step 和它被中断的时刻。最后三列列出针对三种故障的集成测试：

- **Worker 被杀**：Worker 收到 SIGKILL，新的 Worker 启动。
- **Server 重启**：Dex Server 节点收到 SIGKILL，并在原来的数据目录上重启。Worker 继续运行。
- **接管**：active 节点收到 SIGKILL，hot standby 取得 lease。Worker 继续运行。

每种语言都链接到包含该测试的文件。**未测试**表示这一格还没有测试覆盖，所以其中的文字是设计行为，
不是已验证的结果。

| Step | 中断时刻 | 结果 | Worker 被杀 | Server 重启 | 接管 |
| --- | --- | --- | --- | --- | --- |
| **RunModel** | 任何输出到达 Dex 之前 | 这次模型调用重新运行，30 分钟内最多 3 次 attempt，之后这一轮失败。如果 tool 已经运行过，history 中的一条说明会告诉下一轮的模型不要重复它们。 | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |
| **RunModel** | 输出已到达 Dex 之后 | 同上。 | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |
| **CallTool**，幂等写入 | 第一个 heartbeat 到达 Dex 之前 | 用同一个幂等键再次运行。 | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |
| **CallTool**，幂等写入 | tool 运行期间 | 同上。 | [Python][py-kills], [TypeScript][ts-kills] | [Python][py-server], [TypeScript][ts-server] | [Python][py-server], [TypeScript][ts-server] |

优雅停止 Worker 时，它会在 drain 超时内等待正在运行的 handler，默认 30 秒，然后取消它们。
被取消的模型调用会重新运行，被取消的 **CallTool** 会重试。因取消而停止的单次尝试 tool 会记录

## Tool call 的限制 {#tool-call-limits}

单次尝试的 tool 在 **CallSingleAttemptTool** Step 中运行。这个 Step 负责
**non_idempotent_write** 和 **unclassified** tool。它应当最多运行一次 tool，并在 tool 可能
已经运行过时记录 **outcome_unknown**。tool 确定没有运行时，这次调用改为记录 **failed**，模型
可以再次调用这个 tool。有一种情况会打破“最多运行一次”这一承诺，要提前准备。它源于 Dex 停止任何
Step attempt 的方式。见[失败与重新投递](/reference/python/flows-and-steps/failure-and-redelivery)。

### 单次尝试的 tool 可能运行两次 {#tool-runs-twice}

Dex 在把 attempt 交给 Worker 时开始这个 attempt，并且不会再把同一个 attempt 编号交给另一个
Worker。如果 Worker 在 tool 运行期间停掉，或者断开了与 Dex 的连接，这个 attempt 会失败。单次
尝试的 tool 没有剩余的 retry，所以这次调用记录 **outcome_unknown**。之前的那次运行可能已经
完成了副作用，因此 session 不会再次运行这个 tool。

只有一种很窄的情况仍可能让单次尝试的 tool 运行两次。取消是协作式的。Dex 取消一个 attempt 时，
被中断的运行可能仍在继续，而 failure route 已经开始。

要让第二次运行无害，把这次调用的幂等键传给 tool 写入的服务。每个 tool call 都会收到一个幂等键：
session 的 Flow ID、轮次 ID 和 tool call ID，用斜杠连接，例如 **session-42/turn-3/call-7**。
同一次调用的每次 attempt 都使用同一个键。服务按这个键去重时，把这个 tool 归类为
**idempotent_write**，这样它失败后也会重试。

### 从未运行的调用也可能记录 outcome_unknown {#never-run-outcome-unknown}

tool Step 失败时，它的 failure route 会从 recovery error 中读取 **attempt_progress**。见
[失败与重新投递](/reference/python/flows-and-steps/failure-and-redelivery#unknown-outcome)。**CallTool** 和
**CallSingleAttemptTool** 的处理方式相同：

| **attempt_progress** | 这次调用记录的结果 |
| --- | --- |
| **NOT_STARTED** | 没有 attempt 到达 Worker，所以 tool 没有运行。这次调用记录 **failed**，错误信息以 "the tool did not run, so it is safe to call again" 开头。模型会看到一次失败的 tool call，可以再次调用这个 tool。如果这次调用的 tool 已经向用户提过问题，说明它之前运行过，按下一行处理。 |
| **NOT_COMPLETED**，或 server 没有报告进度时的 **UNSPECIFIED** | tool 可能已经运行过。**read** 调用记录为 **failed**，其他调用记录为 **outcome_unknown**，session 不会再次运行它的 tool。 |

要在 **get_agent_snapshot** 或你自己的代码中识别这种调用，把它的错误信息开头与 Python 的
**TOOL_CALL_NOT_RUN_ERROR_PREFIX**、TypeScript 的 **toolCallNotRunErrorPrefix** 或 Go 的
**ToolCallNotRunErrorPrefix** 比较。

**NOT_COMPLETED** 是保守的结果，所以从未运行的调用仍可能记录 **outcome_unknown**。例如，
server 在记录了 attempt 的开始之后、任务到达 Worker 之前崩溃。请把这种结果当作未知。

如果没有 Worker 接收 tool Step，这次调用会在队列中等待。当这个 Flow 类型的每个 Worker 都达到
task 上限，或者一个 Worker 都没有运行时，就会这样。调用不会失败，也不消耗 attempt，有 Worker
接收后才运行。如果 Flow 先超时或被停止，这次调用就不会运行。

让 tool Step 始终能被分发，避免调用长时间等待：

- 按[规划 Worker 容量](#size-workers)规划每个 Worker 池，并为最大的一批 tool call 留出余量。
- 每个 agent Flow 类型至少保持一个 Worker 在运行。Worker 池缩容到零时，tool call 会在队列中等待，
  直到有 Worker 启动。
- 部署时，先启动新 Worker，等它们[注册](/reference/server/workers#readiness)完成，再停止旧
  Worker。

### 核对 outcome_unknown {#reconcile-outcome-unknown}

**outcome_unknown** 表示效果可能发生了，也可能没有。session 从不重试这样的调用，模型会看到结果
未知。在 session 之外核对它：

1. 找到这次调用。在这一轮运行期间，**get_agent_snapshot** 会在 **tool_calls** 中列出它，失败
   信息在 **error** 中。**AgentEvents** Stream 中有一条状态为 **outcome_unknown** 的
   **tool_call_finished** 事件。这一轮结束后，消息 history 中它的 tool 结果会说明结果未知。
2. 用这次调用的幂等键或你自己的业务键，在目标系统中检查效果是否发生。
3. Dex 确定从未运行的调用会记录 **failed**，而不是 **outcome_unknown**。如果 Flow 的 history
   仍然显示 tool Step 的 attempt 从未到达 Worker，例如在 server 升级之前开始的调用，这次调用就
   没有运行。
4. 用 **send_user_message** 把实际结果告诉 session，让下一轮的模型基于它工作。

## 在 session 等待时升级 agent 代码 {#upgrades}

等待中的 session 运行的是接手它下一个 Step 的 Worker 上的代码。agent 循环不会重放，所以
部署在下一次模型调用或 tool call 时生效，即使在一轮中间也一样。滚动部署期间，同一个
session 的两个 Step 可能运行在不同版本上。

- 保持每个 agent 的 Flow type 不变。运行中的 session 靠它恢复。
- 只要运行中的轮次或待处理的审批还引用某个 tool，就保留这个 tool。
- 已记录的 tool call 保留模型请求它时适用的 effect 和审批规则。修改后的 tool policy 对之后
  的调用生效。
- 修改后的 prompt 或模型在下一次模型调用时生效。修改后的 tool 在它下一次被调用时生效。
- 在一轮的各个 Step 之间，**FrameworkRunState** 保存 framework 序列化的状态。新 Worker 上的
  framework 版本必须能恢复它。保持在 adapter 固定的 framework 版本范围内，并且同时升级
  adapter 和 framework。
- 先升级 session 的所有读取方，再升级会写入状态 **failed** 的 Worker。agents 0.2.0 及更早版本的 Worker 和 client 无法解码这个状态，所以它们对已失败 session 调用 **get_agent_snapshot** 时会报错。只有已失败的 session 受影响。
- **从 agents 0.1.0 升级时：先停止该 Flow type 的所有 0.1.0 Worker，再启动任何 0.2.0
  Worker。** 不要让两者同时运行。0.1.0 的 session 把每条消息都保存在 **AgentMessages** 中。
  0.2.0 Worker 一旦在其中保存消息，就会把较早的消息移入 **AgentMessageChunks**，每个 Step 移动
  少量 chunk。此后如果 0.1.0 Worker 运行这个 session 的 Step，这一轮会失败，因为它读不到被移走
  的消息。

通用规则见 [Flow 代码版本控制](/components/application#versioning-flow-code)。

### 滚动部署期间的 session settings {#session-settings-rollout}

只有在该 Flow type 的每个 Worker 都运行 agents 0.2.0 之后，才用 session settings 启动
session，或调用 **update_session_settings**。0.1.0 的 Worker 会丢弃它启动的 session 的
settings，也不会写入或读取一轮所保留的 settings 副本。由 0.1.0 Worker 启动的一轮没有
settings，所以它的部分模型调用可能使用 Worker 的默认模型。

## 凭证 {#credentials}

把模型 API key 和 tool 凭证放在 Worker 的环境中，或放在 Worker 调用时读取的 secret store
中。每个 framework 都从环境中读取自己的模型 key，比如 **OPENAI_API_KEY**、
**GOOGLE_API_KEY** 或 **ANTHROPIC_API_KEY**。adapter 本身不处理凭证。

不要在 session 的启动输入、用户消息、tool 参数、tool 输出或 Attribute 中传递凭证。Session
settings 属于启动输入和 session 状态，**get_agent_snapshot** 和浏览器 snapshot JSON 都会
返回它们，所以其中只放 Worker 能解析的引用，比如 model 名称或凭证名称。Dex 会把
它们保存在 Flow history 和状态中。Dex Web 会显示它们，history 会为 time travel 保留被替换
的值，已停止的 session 在保留期内仍可读取。任何获得授权的 Client 都能读取 **AgentEvents**。

属于某个用户的凭证，让 tool 在调用时从 secret store 中查找，查找用的 key 不能是凭证本身。
当你自己的 Flow 必须持有短期 secret 时，把它存放在
[hard-delete Attribute](/concepts/primitives/attribute#hard-delete-attributes) 中，Flow 不再需要时
删除它。

Worker 和 Client 使用 bearer 凭证向 Dex Server 认证。见
[身份验证](/reference/server/authentication)。
