# Dex Web

Dex Web 使用两个 URL 前缀。**v1** 是原有的 Flows 搜索、run 详情和 Flow Rendering。**v2** 是操作工作区：左边是 run 列表和过滤器，右边是该 Flow type 的 Flow Definition Graph。

不带 JSON 目录启动 Dex 时，打开 **v1** 的 **/v1/flows**。使用 **--flow-rendering-dir** 启动时，默认打开 **v2** 的 **/v2**。右上角 Version 菜单可以回到 **v1**。

```bash
dexcli visualize ./refund_flow.go --schema-version 2.0 --json --out ./build/refund
dexcli dev --flow-rendering-dir ./build
```

**v2** 按一个 Flow type 搜索 current run。Run 列表会排除因 continue-as-new 关闭的 execution，因为它们属于同一个逻辑 Flow；相关 event 仍可在该 Flow 的 history 中查看。画布使用该 Flow type 已生成的 definition，因此不必再选 JSON 文件。历史 run 仍在 **v1**。

Version 1 仍是默认 analyzer schema，并支持 Go 与 Python。Version 2 第一版只支持 Go。Version 1 与 Version 2 definition 可以共存。Dex Web 会在启动时拒绝格式错误的 Version 2 文件，以及同一 Flow type 的多个有效 Version 2 definition。Analyzer 输出中的 **valid: false** 文件仍可在 **v1** Flow Rendering 中查看 diagnostic，但不会作为 **v2** Flow type 出现。

## 具名 directive

Version 2 directive 使用具名值。同一行内的参数位置没有语义。包含空格的字符串使用 JSON 双引号，多值使用 JSON array。


未知或重复参数、缺少必填参数以及非法 JSON 都会产生 blocking diagnostic。多条 indexed Attribute、field、Action 与 input 声明保留源码顺序；这个顺序就是列、详情字段、Action 和表单顺序，不需要额外的 order 属性。

每个已注册 Step 都必须有一个 group 声明和一个 explanation 声明。explanation 用一句话说明该 Step 做什么。Group 顺序由第一个成员在 **GetSteps** 中的注册位置决定，组内 Step 顺序也使用 **GetSteps**。

## 启动 Flow

当所选 definition 包含自动生成的 start schema，且 permission mode 为 **local-selector** 时，Run 工作区会显示 **Start Flow**。弹窗要求填写 Flow ID、明文 Worker gRPC address 和 start input。它支持嵌套 object、array、string-key map、enum、boolean、datetime、optional field 和显式 null。固定数组保持声明的长度。Integer 在浏览器中一直保存为十进制文本，到序列化时才写入 JSON，因此 int64 不会损失精度。

Worker address 失去焦点以及正式启动前，Dex Web 都会从后端检查 Worker host 和 port。端口不可达时，界面显示 warning 并阻止启动。操作员必须明确选择 **Bypass worker health check** 才能继续。该检查只建立 TCP connection，不会调用 Worker method。

Go analyzer 从通过 **DefineStartStep** 注册的 Step 输入类型生成 schema。它遵循 JSON field name、忽略字段、pointer 和 **omitempty**，并支持嵌套或 imported struct、具名 string/integer constant、**time.Time**、普通数值宽度、slice、固定数组和 string-key map。递归或不支持的输入会产生 warning 并省略 start schema，但不会隐藏 definition 的其余部分。

Server 会重新加载当前 definition revision，并在调用 **StartFlow** 前完整验证 input。未知 object field、缺失 required field、非法 null，以及 type、enum、range、datetime、array 或 map 错误都会被拒绝。除非操作员选择 bypass，否则 Server 还会再次检查 Worker port。Server 选择 start Step type 并生成 request ID。浏览器不能选择 headless routing。

通过 **web.startFlowWorkerTargetHeadless** 或 **DEX_WEB_START_FLOW_WORKER_TARGET_HEADLESS** 为整个 Dex Web instance 配置 headless routing。默认值为 false。当操作员填写 Kubernetes headless Service target 时，将它设为 true。**trusted-header** mode 不提供 Start Flow。

## 搜索与 Summary

Indexed Attribute 声明绑定 Dex Attribute key、物理搜索 index key、index type、应用 value type 和 description。Analyzer 会把每个值与 Go 定义和 SDK 计算出的有效 index 配置比较。

物理 key 可以是 **CustomKeyword2** 这样的通用 namespace 槽位。此工作区已选定 Flow type 来限定它的含义，因此不同 Flow type 复用该槽位不会改变 UI 行为。

**v2** 列表每次搜索一个 Flow type。过滤条件包括 Flow ID、execution status、开始和结束时间，以及声明的 indexed Attribute。Dex Web 会把这些控件编译成 visibility query，不接收浏览器提供的原始 query。不同字段使用 AND，同一字段的多个值使用 OR。

每一行都会针对逻辑 Flow ID 的 current run 调用 **GetDexSummary**。该 RPC 接受 **dex.None** 并返回 **map[string]any**。Dex Web 最多并发加载八个 Summary，每次调用超时五秒，单条失败只影响对应行。Indexed Attribute 显示在 Summary 字段之前。

## Display 与编辑

点击一行会把 Flow ID 留在 URL 中，而不是 run ID。**GetDexDisplay**、Attribute 读取、编辑和 Action 都省略 run ID，因此 Dex 会定位 current run。Continue-as-New 后，刷新同一个 URL 会自动指向新 run。

在 **v2** 中，选中 Step 会打开分为 **Definition** 与 **Execution** 的面板。Definition 展示 Step 的 **explanation**、WaitFor 与 Execute 分支；过长内容可滚动，以便 Execution 仍可见。Execute 分支超过三条时默认折叠。若该 Step 执行过多次，Execution 提供下拉框选择某次执行，再以与 **v1** Selected event 相同的结构化方式展示所选 WaitFor 或 Execute history 事件的 **Input**、**Output** 和 **Context**。执行 payload 默认 Details，可切换为已水合 payload 的 Raw JSON。十进制数字形式的 AttributeMap / ChannelMap instance 按数值排序，行为与 **v1** 一致。Execute 显示该次 run 决策里的 live next Steps，而不是 FDG 上的全部出口。若 Continue-as-New 把该 Step 留在上一 hop，使用 Load more from previous run。

字段还可以声明它所填充的 UI slot：**title**、**subtitle**、**status**、**recommendation** 或 **reason**。UI slot 说明该字段承担什么角色，因此一套模板可以服务所有 Flow，而每个 Flow 把自己的 Attribute 映射进去。UI slot 是可选的，多数字段不填任何 UI slot。

run 列表的每一行读取 **title** 和 **status**；当 Flow 两者都未声明时，回退为 Flow ID 与 execution status。选中 run 的面板读取全部五个 UI slot，按 UI slot 顺序排在其余字段之前。**title**、**subtitle**、**status** 和 **recommendation** 各只允许一个字段。**reason** 允许多个，因为一条 recommendation 可以有不止一个依据。

一行只携带 indexed Attribute 和 Summary 字段。若某个 UI slot 绑定的 Attribute 两者都不属于，它只在面板中显示，不在行中显示。UI slot 不是索引：它只说明值应出现在哪里，不表示该值可被搜索。

其余 Display 字段按照 directive 行排序。String、integer、double、boolean 和 datetime 字段可以编辑。JSON、object、array 和 AttributeMap 只读。缺失字段必须返回 null。后端会拒绝遗漏、未声明或类型错误的值。

只有 current run 仍为 active 时才能编辑。Dex Web 通过 **SetAttributes** 写入 Attribute；如果该 Attribute 已建立索引，还会附带声明的 index 配置。仅当被编辑的 Attribute 是 Action condition source 时，Dex Web 才会同时发送完整的 Action permission mapping；其它编辑不会发送。

## Action

Action 是通过 **RPCOptions.Action** 注册的 RPC。**DefineAction** 接收 label、Attribute condition 和一个 **ActionRequiresPermission** option。Visualizer 会直接读取这个强类型 Go 注册。Dex Web 会在调用 RPC 前重新读取 condition Attribute。

无输入 Action 接受 **dex.None**，直接显示为按钮。有输入 Action 接受具名 Go struct。来自用户的字段按 directive 顺序渲染控件；来自 Attribute 的字段保持隐藏，并使用当前选中 run 的 Attribute snapshot。

每个 Action 要求一个 permission，例如 **refund.manage**。Permission key 以小写字母开头，只包含小写字母、数字、点或连字符。当一次成功的 Worker invocation 写入 Action condition source 时，Worker 会在 response 中附带完整 mapping。无关写入和 query-only RPC 不会附带 mapping。

Server 会把业务写入覆盖到权威 Attribute state 上，并在同一个 Workflow Task 中计算 mapping。它对当前可用 Action 的 permission 排序、去重，再把新匹配的 permission 加入内部 KeywordList Search Attribute **DexWorkQueuePermissions**。permission 一旦加入，就会在该 Flow execution 中一直保留，即使当前已没有匹配的 Action。维护投影不要求应用 Step 锁住每个 Action source。

permission 历史会跨 Continue-as-New 继承，并在完成后继续可搜索。Server 升级会保留仍然存在的 permission，但不会重建升级前已经删除的 permission。新的独立 Flow execution 会从自己的初始 Attribute 开始。修改后的 Action definition 会在后续 source write 发送 mapping 或新 Flow 启动时首次生效。删除或重命名 Action permission 不会清除已有 permission 历史中的旧值。

Work Queue 会列出所选 Flow type 声明的 permission。在 **Working as** 中选择一个 permission 后，浏览器通过 **POST /api/v2/search** 的 **workQueuePermissions** 发送它。Superverse 等调用方也可以发送从多个用户 role 得到的多个 permission。只要 run 的 permission 历史包含任意一个请求 permission 就会匹配；这组 permission 与 Flow type 和其他 filter 之间使用 AND。

permission 匹配表示某个 Action 当前可用或曾经可用，并不表示它现在仍然可用。带 key 的 gate 还需要它当前的 key，而列表读取的是最终一致的索引。当前真正可用的 Action 仍由打开后的该 run 决定。

浏览器中的 condition 只控制展示。每个 Action RPC 都必须在修改持久化状态或发布 Channel message 前再次检查当前状态。当检查与 effect 必须保持原子性时，应使用 lock。

Work Queue 不增加登录，也不执行授权。**Working as** 只是选择工作，不会授予所选 permission。Superverse 等可信应用边界仍负责用户认证、把 role 映射到 permission，并限制它发送哪些 permission。请把 Dex Web 部署在该边界之后。

## 可信 reverse-proxy mount

经过认证的 host application 可以把 Dex Web 暴露在 **/apps/project-1/dex** 这类每个
request 独立的 URL 下。只有当 8802 端口仅允许可信 reverse proxy 访问时，才启用
**web.trustForwardedEmbeddingHeaders** 或
**DEX_WEB_TRUST_FORWARDED_EMBEDDING_HEADERS**。默认值为 false；未启用 trust 时，Dex
会拒绝所有包含 forwarded embedding metadata 的 request。

Proxy 在转发前移除 public prefix，删除浏览器提供的以下 header，并为每个必需 header
注入一个 canonical value：

~~~text
X-Forwarded-Prefix: /apps/project-1/dex
X-Dex-Web-Embedded: true
X-Dex-Web-CSRF-Token: host-generated-token
~~~

Prefix 必须是 **/** 或没有 trailing slash、query、fragment、authority、dot segment 与
encoded separator 的绝对 canonical path。Embedded value 只能是 **true** 或 **false**。
Dex 将 CSRF bootstrap token 视为 optional，但 hosted page 应当提供它。
Token 必须使用不含空格的 visible ASCII。

Response bootstrap 只为当前 request 配置 router、asset、link 和 API request。Embedded
page 会删除重复的 product chrome，并允许同源 iframe。Standalone page 会拒绝 iframe。
HTML 不会被 cache，并对可信 metadata 设置 Vary，因此两个 project 可以共用一个 Dex Web
service，而不会复用对方的 mount path 或 token。

对于 POST、PATCH、PUT、DELETE 和其他 mutation method，浏览器会把 bootstrap token 放在
**X-CSRF-Token** 中。Host proxy 应先根据已认证 session 验证它，再移除该 header 后继续
转发。Dex 负责把 token 传给浏览器，但不负责 host user authentication、project
authorization 或 host CSRF state validation。
