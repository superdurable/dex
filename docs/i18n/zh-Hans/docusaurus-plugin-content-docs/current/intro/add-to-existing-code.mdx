# 把 Dex 加入现有代码

本页把你已经在运行的代码，例如一个函数、一个队列消费者、一个 cron 任务、一个 webhook handler 或一个脚本，改成一个 Flow，让它在崩溃、重启或长时间等待之后继续运行。

## 安装 SDK {#install}

在运行这段代码的服务里加入 SDK 和一个 Worker。[把 Dex 加入现有服务](/components/application#add-to-a-service)给出每种语言的安装命令，以及 Worker 和 Client 放在哪里。

## 从现有代码出发 {#start-from-what-you-have}

假设订单流程现在是一个函数：

```text
handle_order(order):
    charge the buyer through the payment API
    save status "charged" in the orders table
    wait until the seller approves (poll the approvals table, remind after 24 hours)
    ship the item through the shipping API
    save status "shipped"
    if shipping keeps failing: refund the buyer, save status "refunded"
```

在任意两行之间崩溃，订单都会停在半路。重启后，要么重复扣款，要么把这笔订单忘掉。

## 拆成 Step {#split-it-into-steps}

每个会改变其他系统的调用，都放进自己的 Step。Step 是 Dex 保存进度的单位，所以崩溃最多让正在运行的那个 Step 重新运行。

| 在你的函数里 | 在 Flow 里 |
| --- | --- |
| 向买家扣款 | 一个 **Charge** Step，它的 `Execute` 调用支付 API，然后转到 **Ship** |
| 等待审批，24 小时后提醒 | **Ship** 的 `WaitFor`：等待 **Channel** 上的一条消息，或者一个 24 小时的 **Timer**，先到者为准 |
| 发送提醒 | Timer 触发时 **Ship** 的 `Execute`：发送提醒，然后再次转到 **Ship** |
| 发货 | 审批到达时 **Ship** 的 `Execute` |
| 多次失败后退款 | 从 **Ship** 到 **Refund** Step 的失败路由，在 Ship 的重试用尽时使用 |
| status 列 | 一个 **Attribute**，比如 **order-status** |
| 审批接口 | 一个 **RPC**，把审批发布到 Channel |
| 轮询循环和提醒任务 | 都去掉。Dex 负责等待，并触发 Timer。 |

### Ship 怎么知道哪个等待结束了 {#how-ship-knows-which-wait-ended}

**Ship** 的 `WaitFor` 返回这两个条件，第一个条件满足时 Dex 唤醒这个 Step。然后 `Execute` 向 context 询问 Timer 是否已触发。如果触发了，Ship 发送提醒并转到自己，重新开始等待。否则就是审批到了，Ship 发货并完成 Flow。[订单处理](/use-cases/order-processing#2-flow-steps-and-rpcs)给出完整的 Step，包括它的重试和失败路由。

	dex.Context,
	OrderRequest,

		SellerOK.ForOne(),
		dex.Timer(24*time.Hour),

func (step shipStep) Execute(
	ctx dex.Context,
	order OrderRequest,
) (*dex.StepDecision, error) {
	if ctx.HasTimerFired() {
		step.service.SendEmail(
			order.Email,
			"Reminder: approve shipment",
			"Please approve or provide a tracking number.",
		)
		return dex.GoTo(shipStep{}, order), nil
	}
	if err := step.service.ShipItemWithIdempotencyKey(order.OrderID, order.TestFailAtShipping, "ship-"+order.OrderID); err != nil {
		return nil, err
	}
	if err := OrderStatus.Set(ctx, "shipped"); err != nil {
		return nil, err
	}
	return dex.GracefulComplete("shipped:" + order.OrderID), nil
}

提醒邮件不带幂等键，因为多发一次提醒没有坏处。Ship 的发货调用则带了幂等键。

只有当两个调用一起成功或一起失败时，才把它们放在同一个 Step 里。一个 Step 里有两个外部调用，重新运行时两个都会重复。

### 把失败路由到恢复 Step {#route-a-failure-to-a-recovery-step}

默认的重试策略会把一个 Step 重试 4 小时，然后让 Flow 失败；失败路由会接住这个失败。要让人来决定，就把失败路由到一个等待人工处理的 Step，见 [人工恢复](/design-patterns/failure-handling/manual-recovery)。[Execute 失败恢复](/design-patterns/failure-handling/execute-failure-recovery) 给出自动处理的路由。修复一次失败 run 的原因之后，[Time Travel](/concepts/change-flow-code#time-travel) 可以让它从更早的某个点重新运行。

## 安排幂等键 {#place-the-idempotency-keys}

每个外部调用都带一个[幂等键](/concepts/step#idempotency-keys)。这里订单 ID 就是 Flow ID，所以 Charge 调用可以用 **charge-** 加订单 ID。

<a id="when-an-api-takes-no-idempotency-key"></a>

## 安全地调用无幂等键的 API {#when-an-api-has-no-idempotency-key}

对于不接受幂等键的 API，重复调用会产生第二次效果。下面两种做法可以把这个窗口缩小：

- **先检查。** 调用时带上你自己的引用，比如把订单 ID 填进发货单的 reference 字段。在 Step 开始时，用这个引用查一下效果是否已经发生。已经存在就跳过这次调用。
- **记录这次尝试。** 如果 API 没有查询接口，就在同一个 Step 里、紧挨着调用之前，往你自己的数据库写一行，key 的构造方式和幂等键一样，比如 **ship-order-1042**。重新运行时，如果这一行已经存在，说明调用可能已经发生过。这时停下来人工核对，或者转到一个恢复 Step，而不是再调用一次。

如果在调用之后、Dex 保存这个 Step 之前崩溃，仍然有一种情况你无法判断调用是否发生过。这两种做法都能把悄无声息的重复变成一种你看得到、也能处理的情况。

## 保留你的数据库写入 {#keep-your-database-writes}

客服和报表读取的订单表可以继续保留。在一个 Step 里用以订单 ID 为 key 的 upsert 写入它，这样即使重复执行，写入的也是同一行。在创建订单的 handler 里启动 Flow，用订单 ID 作为 Flow ID。[Dex 与你的数据库](/components/your-database)讲了这两点，也讲了两次写入中有一次失败时会怎样。

## 在你的服务中运行 {#run-it-in-your-service}

三个部分把 Flow 接入你已有的服务：

- **Worker 运行 Step。** 在你的服务进程中启动它，和 HTTP server 放在一起。如果 Step 需要和 API 不同的扩缩容、资源或发布节奏，就把它部署成独立的进程。Worker 只发起出站连接，所以不需要负载均衡器或入站端口。
- **Flow 的构造函数接收你的服务。** 把 Step 调用的每个服务，例如支付 API，传给 Flow 的构造函数。这样从 Worker 注册 Flow 的那一刻起，每个 Step 都有它的服务，测试也可以用同样的方式传入一个假的服务。
- **Client 在你的 handler 里启动 Flow。** 创建订单的 handler 启动 Flow，用订单 ID 作为 Flow ID，并带一个 request ID，这样重试的请求不会启动第二个 Flow。调用方需要知道 Charge 已经完成时，handler 用 Client 的等待 Step 完成调用来等这个 Step。Dex 记录下这个 Step 时等待就结束，所以 handler 不需要自己的状态表或轮询循环。

[你的应用](/components/application)给出每个部分的代码，包括 Worker 在同一进程中的[一个最小的服务](/components/application#minimal-service)。它还讲了 Worker 的容量、关闭和容器。

## 检查清单 {#checklist}

- 每个会改变其他系统的调用都在自己的 Step 里，或者只和一起成功、一起失败的调用共用一个 Step。
- 每个这样的调用都带一个由 Flow ID 构造的幂等键，而不是用时间、随机值或尝试序号。
- 每个等待都是一个在 Channel、Timer 或两者上的 `WaitFor`，而不是一个轮询循环。
- 每个来自外部的命令，比如审批，都是一个 RPC。
- 其他代码要读的状态是一个 Attribute，或者是写入你自己表里的 upsert。
- 每个 Step 的重试策略都按这个调用来设置，而不是沿用[默认值](/concepts/step#stepoptions)。
- 每个需要业务处理的失败，比如退款，都有一条到恢复 Step 的[失败路由](#route-a-failure-to-a-recovery-step)。
- 只有当两个 Step，或者一个 Step 和一个 RPC，可能同时运行，并且先读后写同一个 Attribute 时，它们才在这个 Attribute 上声明[锁](/concepts/primitives/attribute#locking)。顺序执行的 Flow 用不到锁。
- handler 用稳定的 Flow ID 和 request ID 启动 Flow，这样重试的请求不会启动第二个 Flow。[一个最小的服务](/components/application#minimal-service)给出这个 handler。
