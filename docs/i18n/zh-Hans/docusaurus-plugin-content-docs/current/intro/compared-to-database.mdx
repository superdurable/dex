# Dex vs. 数据库

大多数后端把状态存在数据库里，再围绕数据库搭建每个流程。下面先用这种方式一种设计一种设计地搭一个订单流程，再用 Dex Flow 实现同一个流程。

**用惯了队列和数据库？** 按这个顺序阅读：本页、[Dex 和你的数据库](/components/your-database)、[Step 保证](/concepts/step#guarantees)、[故障转移和部署](/concepts/failover-and-deploys)，以及[限制](/intro/limits)。

这就是[为什么是 Dex？](/intro/what-is-dex)里的订单流程：扣款，等卖家审批并在等待期间提醒卖家，发货，发货一直失败就退款。每种设计为此需要的部件如下：

## 数据库把哪些事留给你的代码 {#what-a-database-does-not-do}

PostgreSQL、MySQL、S3 这类数据库和存储服务，负责保存数据，并在你查询时返回数据。它们是被动的：只有你的代码调用它们时，它们才会做事。

可靠的后端需要的不只是存储。它要跑在多台机器上，这样一台出故障不会让服务停下，也能承接更多流量。一个 API 常常要调用好几个别的 API 和服务，一次数据库事务覆盖不了。

一个典型的后端 API 还要：

- 串行或并行地调用多个 API。
- 安排之后要做的事，比如提醒和业务超时。
- 等待其他系统，比如人工审批或外部事件。
- 处理失败：重试、回滚，以及用于人工修复的死信队列（DLQ）。每一步的策略可能都不一样。
- 能看到每一步的输入、错误，以及还没做完的工作。
- 流量增长时，依然可用、够快、成本可控。

这些数据库都不提供。每个服务都要把这些代码重新写一遍。

## 起点：连续两次 API 调用 {#start-two-api-calls-in-a-row}

最简单的版本只做两次 API 调用：

* **向买家扣款。**
* **发货。**

做原型时，会直接依次调用这两个 API：

只要不出错，这样就能用。如果扣款成功后进程崩溃，或者发货调用超时，买家已经付了钱，货却永远不会发出。

### 设计 1：数据库行加轮询 worker {#design-1-a-database-row-and-polling-workers}

下一个想法是：插入一行 **status = pending** 的订单，返回给客户端，再让后台 worker 去取这一行来处理。

<ExecutionApproachDiagram approach="table-poll" markdownDescription="前端 API 插入一行 status 为 pending 的订单，并返回 request id。Worker A 用 SELECT … FOR UPDATE 抢占行，Worker B 扫描同一张表，两个 Worker 争抢同一张订单表中的行。" />

订单保存下来了，但新问题也来了：

* 多个 worker 怎么取行，才不会抢到同一行？
* worker 取到一行之后、处理完之前崩溃了，怎么办？

### 设计 2：步骤之间用消息队列 {#design-2-a-message-queue-between-steps}

有经验的团队通常会改用消息队列，每一步一个队列：**charge-requests** 和 **ship-requests**。订单先作为一条消息进入 **charge-requests**。扣款消费者处理完这条消息，再往 **ship-requests** 发一条消息。

<ExecutionApproachDiagram approach="message-queue" markdownDescription="消息队列在执行连续操作的消费者之间传递任务。每个消费者必须协调操作与消息确认，以处理失败。" />

队列解决了设计 1 的问题，但带来了更难的问题：

- 大多数队列把「扣款完成」和「发出发货消息」分开提交。如果发货消息已经发出，但扣款消息的确认超时了，队列会再投递一次扣款消息。于是同一笔订单在发货的同时，扣款步骤又运行了一次。
  - 团队通常再加一行数据库记录作为唯一可信来源，用来去重。
  - 标准的解决办法是 **transactional outbox**。消费者在一次数据库事务里写入「扣款完成」和一行 outbox 记录。一个 relay 进程读取 outbox，发出发货消息。relay 可能把一条消息发两次，所以每个消费者仍要按订单 ID 去重。
- 带退避的重试和 DLQ 往往要自己补。
  - 比如 Kafka 要额外建重试 topic，SQS 要靠 visibility timeout 绕过去。
  - 查看和恢复 DLQ 里消息的工具，也得自己做。
- 前端可能要在扣款成功后马上返回（「已付款，订单处理中」）。这时它只能轮询数据库，既别扭又浪费。

业务还会不断变化。订单流程常常还要：

- 发货 API 重试后仍然失败时给买家退款，比如连续失败一小时后退款。
- 发货前等卖家审批，或者让卖家手动填写运单号。
- 提醒卖家去审批或填写运单号。

在队列设计里，每一项都要加队列、消费者、表或 cron job。

这种设计能用，很多团队也把它运行得很好。它的代价是业务逻辑周围的代码：outbox relay、去重检查、重试 topic、DLQ 工具和提醒任务。每个需要同样保证的服务都要再搭一遍。

## 用 Dex Flow 实现同一个流程 {#the-same-process-as-a-dex-flow}

在 Dex 里，你把业务逻辑写成 Step。重试、Timer、等待、崩溃后恢复，以及每个 Step 的记录，都由 Dex 提供。有一项职责仍由你负责：每次外部调用都要传入一个[幂等键](/concepts/step#idempotency-keys)。

<ExecutionApproachDiagram approach="dex" markdownDescription="前端 API 通过 Client 启动 Flow。Dex Server 把每个 Step 任务派给你的某一个 Worker，Step 再调用扣款、发货和退款 API。" />

这个 Flow 有一个 Charge Step、一个等待审批并在等待期间发提醒的 Ship Step，以及一个 Refund Step。前端调用一个 Client API，等 Charge Step 完成后显示「已付款」。

<DocsFlowDefinitionGraph graph={orderProcessingFlow} markdownReference="/intro/what-is-dex#example-order-processing" markdownReferenceLabel="为什么是 Dex？" />

Dex 记录每个 Step 的输入、输出和错误。运维人员可以查看每一笔订单，并在修复后从之前的某个 Step 重新运行（time travel）。

| 问题 | 数据库和队列 | Dex Flow |
| --- | --- | --- |
| 两步之间崩溃 | 用 outbox 和 relay 把两步绑在一起。没有它们，买家可能已扣款，货却一直没发。 | Dex 把每个 Step 的结果和到下一个 Step 的推进一起记录。 |
| 扣款调用中途崩溃 | 消费者会再运行一次，所以支付调用需要幂等键。 | Charge Step 会再运行一次，所以支付调用需要同样的键。 |
| 多个 worker | 自己实现抢行，或依赖队列投递加去重检查。 | Dex 把每个任务派给你的某一个 Worker。 |
| 单步延迟 | 本地数据库事务提交 outbox 行，通常只要几毫秒。 | SYNC Step 要等对象存储的两次提交，一次记录开始、一次记录结果：在[基准测试](/intro/performance)中，半峰值负载下 p50 约 105 ms。ASYNC Step 不用等。 |
| 你要运行的东西 | 一个数据库和一个队列 broker，加上 relay 和消费者。 | Dex Server、一个对象存储 bucket 和一个可选的备用节点，加上你的 Worker。带索引的搜索不需要另一个数据库；搜索量大时可以选用 PostgreSQL 搜索后端。你的数据库继续保存你自己的表。[Dex Server](/components/server#dependencies) 列出了所有依赖。 |

### 你自己的表 {#your-own-tables}

系统其他部分要读的表，你继续保留，比如供报表和客服工具使用的订单表。Dex 保存流程状态：哪个 Step 运行过，订单正在等什么。Step 像其他调用一样写你的表，用以订单 ID 为键的 upsert，所以重新运行时写入的还是同一行。[Dex 和你的数据库](/components/your-database) 介绍了这种模式，也说明了什么时候改让 Dex 把 Attribute 复制到你的数据库。

### 需求变化时 {#when-requirements-change}

每个新需求都会改动两种设计：

<RequirementChangeComparison markdownTable={{
  header: ['新需求', '数据库、队列和 outbox', 'Dex'],
  rows: [
    ['发货失败一小时后给买家退款', '一个 refund-requests 队列和退款消费者。发货消费者记下第一次失败，一小时后放弃。', '一个 Refund Step。Ship Step 重试一小时，然后进入 Refund Step。'],
    ['发货前等卖家审批', '一张审批表和一个审批接口。由审批接口写入 ship-requests，扣款消费者不再写。', '一个 approve RPC。Ship Step 等待卖家 Channel 上的消息。'],
    ['提醒卖家', '一个提醒 cron job，扫描审批表，找出还在等的订单。', '不加新部件。Ship Step 同时等一个 Timer，Timer 到了就发提醒，然后继续等。'],
  ],
}} />

Ship Step 一小时的重试窗口和进入 Refund 的路径都在它的选项里设置；[把失败转到恢复 Step](/intro/add-to-existing-code#route-a-failure-to-a-recovery-step) 解释了这些选项。[订单处理](/use-cases/order-processing) 用每种 SDK 给出了这个 Flow 的可运行代码。[快速开始](/quick-start) 运行一个更小的版本，只有 Charge Step 和 Ship Step。
