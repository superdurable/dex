# Dex vs. Temporal

Dex 和 Temporal 都能让流程在崩溃、重启和长时间等待之后继续运行。它们在两个设计选择上不同。Temporal 通过重放 workflow 代码来重建一次运行，Dex 保存每个 Step 的结果。Temporal 的服务运行在数据库上，Dex 以一个二进制运行在对象存储上。本页先讲这两点区别，以及它们对你的代码和运维意味着什么。[术语对照](#term-map)和[其他引擎](#other-engines)在后面。

本页关于 Temporal 的事实来自 [Temporal 文档](https://docs.temporal.io)。关于 Dex 的事实链接到对应的页面。

## 重放与保存的 Step 结果 {#the-main-difference-an-explicit-step-graph-not-replayed-code}

Worker 停止之后，两个引擎用不同的方式重建一次运行。

<RecoveryModelDiagram markdownDescription="Worker 运行中途停止。Temporal：Event History 记录每条命令和结果；新的 Worker 从头重放 workflow 函数，直到最后一个 await，所以 workflow 代码必须是确定的。Dex：Step 结果和 Attribute 与每个决定一起保存；新的 Worker 只运行下一个 Step，完成的 Step 不再运行，所以每个外部效果必须是幂等的。" />

**Temporal。** 一个 Workflow 是一个函数。服务器记录 Event History，即 Workflow Execution 生命周期中发生的每件事的完整、持久的日志。运行不在 Worker 缓存中时，Worker 从头再运行这个函数来继续它。已记录的 Activity 结果直接返回，Activity 不再运行。代码产生的命令会和历史比对。不一致就是非确定性错误。所以对同样的输入，workflow 代码必须以同样的顺序发出同样的调用。读取时钟、随机数和 I/O 要通过 Temporal 的 API，或者放进 Activity。

**Dex。** 一个 Flow 是一组 Step。每个 Step 返回一个决定，指明接下来运行哪些 Step，或者完成 Flow。Dex 把 Step 的结果、它写入的 Attribute 和这个决定一起保存。要继续一次运行，Worker 只运行下一个 Step。它读取保存的 Attribute。没有任何重放。

下表列出每种设计对你的代码意味着什么，最重要的在前。

| | Temporal：重放 workflow 代码 | Dex：保存每个 Step 的结果 |
| --- | --- | --- |
| 编排代码 | 必须是确定性的。读取时钟、随机值和 I/O 要通过 Temporal 的 API，或者放进 Activity。 | 普通代码。Step 可以读取时钟、使用随机值，调用任何库。 |
| 运行未结束时修改代码 | 改变命令顺序的修改会让重放失败，报非确定性错误。Patching 或 Worker Versioning 让旧的运行走旧路径。 | 未结束的 Flow 从下一个 Step 开始运行新代码。保留旧的 Step 类型直到旧 Flow 结束，并以增量方式修改数据。见[部署代码变更](/concepts/change-flow-code#versioning-flow-code)。 |
| 持续数月的运行 | Event History 有上限：10,240 个事件或 10 MB 时警告，超过 51,200 个事件或 50 MB 时终止。Continue-As-New 开始一次新的运行。 | Dex 保留每次运行最新的一段事件，默认 50,000 个，并清理更早的事件。Flow 继续运行。见 [History window](/reference/server/configuration#history-window)（英文）。 |
| 修复 bug 后恢复 | Reset 从较早的事件开始一次新的运行。 | Time Travel 恢复较早时间点的 Attribute、Channel 消息和等待中的 Step，Run ID 不变。 |
| Worker 停止后的状态 | 通过重放 Event History 重建，在两次任务之间缓存在 Worker 上 | 从每个 Step 一起保存的 Attribute 读取。Worker 不保留缓存。 |

## 运行服务器 {#run-the-server}

Temporal 需要一个数据库。Dex 只需要对象存储。

| | Temporal Service | Dex Server |
| --- | --- | --- |
| 进程 | Frontend、History、Matching 和 Worker 服务。它们可以共用一个进程。Temporal 建议在生产环境中分开运行。 | 一个二进制。一个活跃节点在对象存储里持有 lease。活跃节点停止时，备用节点接管。见 [Dex Server](/components/server)。 |
| 必需的存储 | 一个数据库：Cassandra、MySQL 或 PostgreSQL。SQLite 只用于开发。 | 对象存储，例如 Amazon S3，或者用 db9 代替。 |
| 搜索存储 | Visibility 存储。生产环境推荐 Elasticsearch。 | 默认内置。PostgreSQL 或 ParadeDB 可选。 |

活跃的 Dex 节点故障转移时，每个进行中的 Step 尝试都会再次运行。见[故障转移和部署](/concepts/failover-and-deploys)。[性能](/intro/performance)给出单个 Dex 节点实测的吞吐量和延迟。

## 并发的默认行为 {#concurrency-defaults}

Temporal 默认每个 Workflow 只有一个写入方。Dex 并行运行一个 Flow 的多个 Step，要求你声明锁。

Temporal Workflow 在单线程上运行。Signal 和 Update handler 仍然可能在每个 `await` 处和主函数交错执行。对于先读、再等待、再写入的 handler，Temporal 建议使用 workflow mutex。

Dex 在不同的 Worker 上并行运行同一个 Flow 的多个 Step。RPC 也可以和它们同时运行。它们共享 Flow 的 Attribute。由你选择哪些 Attribute 需要[锁](/concepts/primitives/attribute#locking)。没有锁时，两个先读后写的写入方可能互相覆盖。

## 共同点 {#what-they-share}

- 服务器在你的进程之外记录每次运行的进度。崩溃之后，运行从这份记录继续。
- 你自己进程里的 Worker 从服务器拉取任务。你的代码从不在服务器里运行。
- Timer 是持久化的。等待 Timer 或消息的运行不占用 Worker。
- 每个工作单元都有 retry 策略和超时。默认 backoff 相同：1 秒，每次翻倍，最多 100 秒，不限次数。Dex 默认在 4 小时后停止重试一个 Step；见[限制](/intro/limits)。
- 每次运行有一个业务 ID。同一个 ID 同时最多有一个打开的运行，复用策略决定下一次启动怎样处理。
- 一个工作单元可能运行不止一次。调用其他系统的代码要传入幂等键。

## 同一个流程的两种写法 {#the-same-process-in-both-models}

一个提醒循环每隔一段时间发送一次提醒，直到对方选择退出。在 Temporal 里，循环是由引擎重放的普通代码。以下代码仅作示意，不属于 Dex 示例。

```python
@workflow.defn
class ReminderWorkflow:
    def __init__(self) -> None:
        self.opted_out = False

    @workflow.signal
    def opt_out(self) -> None:
        self.opted_out = True

    @workflow.run
    async def run(self) -> None:
        while True:
            try:
                await workflow.wait_condition(
                    lambda: self.opted_out, timeout=REMINDER_INTERVAL
                )
                return
            except asyncio.TimeoutError:
                await workflow.execute_activity(
                    send_reminder, start_to_close_timeout=timedelta(seconds=30)
                )
```

在 Dex 里，循环是一个转到自己的 Step。它等待 Timer 或退出 Channel，它的决定选择接下来做什么。这段代码摘自可运行的[提醒](/design-patterns/durable-timer/reminder)模式：

```python
class ReminderStep(Step[None]):
    def __init__(
        self,
        service: ServiceDependency,
        opt_out: Channel[None],
    ) -> None:
        self.service = service
        self.opt_out = opt_out

    def wait_for(self, context: Context, input: None) -> Wait:
        return Wait.any_of(
            Timer.by_duration(REMINDER_INTERVAL),
            self.opt_out.for_one(),
        )

    def execute(self, context: Context, input: None) -> StepDecision:
        if not context.has_timer_fired():
            return graceful_complete()
        self.service.send_email("Reminder: please respond", "Hello, ...")
        return go_to(ReminderStep, None)
```

提醒不带幂等键，因为重复发送提醒不会造成影响。在 Rust 中，`has_any_timer_fired` 返回这个 Wait 中是否有 Timer 已触发。

Temporal 版本从上往下读。退出是一个设置变量的 Signal handler，重放会重建这个变量。Dex 版本给等待状态起了名字。Timer 和 Channel 是同一个 Wait，由决定选择接下来做什么。

## 术语对照 {#term-map}

| Temporal | Dex | 说明 |
| --- | --- | --- |
| Workflow、Workflow ID、Run ID | [Flow](/concepts/flow)、Flow ID、Run ID | 角色相同。 |
| Activity 之间的 workflow 代码 | Step 决定：`GoTo`、`GoToMany`、`GracefulComplete`、`DeadEnd` | 控制流是 Dex 保存的数据，不是再次运行的代码。 |
| Activity | [Step](/concepts/step) 的 `Execute` 方法 | 一个 retry 单元。每个需要持久化的调用放在自己的 Step 里。 |
| Local Activity | 最接近的是 ASYNC Step | 两者都用一部分持久性换取延迟。见 [SYNC 和 ASYNC Step](/correctness-and-expressiveness/step-guarantees#sync-and-async)。 |
| Timer、`sleep` | Step 的 `WaitFor` 里的 [Timer](/concepts/primitives/timer) | 两者都是持久化的。 |
| Signal | [Channel](/concepts/primitives/channel) 消息 | 两者都能在没有 Worker 在线时被接收。 |
| Query | 只读 [RPC](/concepts/primitives/rpc) | |
| Update | 写入 Attribute 或发布到 Channel 的 [RPC](/concepts/primitives/rpc) | 两者都需要 Worker。 |
| Workflow 变量 | [Attribute](/concepts/primitives/attribute) | Dex 保存它们。Temporal 通过重放重建它们。 |
| Child Workflow | [SubFlow](/concepts/primitives/subflow) | |
| Task Queue | Task queue | Flow 在启动时指定自己的 task queue，之后保持不变。在一个 task queue 内，Dex 按 Flow 类型路由。 |
| Sticky execution | 尽力而为的 sticky 路由 | Dex 先把任务交给上次服务这个 Flow 的 Worker。Worker 不保留历史缓存。 |
| Search Attributes | 带索引的 Attribute | |
| Workflow ID 复用策略和冲突策略 | ID 复用策略和启动 request ID | 见 [Flow 标识](/concepts/flow)。 |
| 取消 | RPC 按 Step 类型取消 Step。`StopFlow` 停止 Flow。 | 两者都是协作式的。见[取消运行中的 Step](/reference/server/runtime-data#cancel-running-steps)。 |
| Reset | [Time Travel](/components/operate-and-debug#time-travel) | Time Travel 保留 Run ID。 |
| Continue-As-New | 不需要对应机制 | Dex 会裁剪旧的历史事件。见[重放与保存的 Step 结果](#the-main-difference-an-explicit-step-graph-not-replayed-code)。 |
| Patching、Worker Versioning | 保留旧的 Step 类型，以增量方式修改数据 | 见[重放与保存的 Step 结果](#the-main-difference-an-explicit-step-graph-not-replayed-code)。 |
| Schedule | 在 Timer 上循环的 Flow | 见 [Cron 定时](/design-patterns/durable-timer/cron)。 |
| Nexus | 没有直接对应 | 其他团队的服务通过 FlowService API 启动 Flow 或调用 RPC。 |
| Temporal Web UI | [Dex Web](/components/web) | |

Dex 由 iWF 演进而来。iWF 的 State 对应 Dex 的 Step，`WaitUntil` 对应 `WaitFor`。

## 其他引擎 {#other-engines}

<a id="replay-based-workflow-engines"></a>

**基于重放的引擎。** Cadence 与 Temporal 采用相同的重放模型，因此上面的对比同样适用于 Cadence。

### 基于日志的运行时 {#journal-based-durable-function-runtimes}

Restate 是一个例子。handler 通过运行时 context 执行每个副作用，运行时把结果记录在日志里。失败之后，handler 再次运行，并拿到已记录的结果。virtual object 按 key 保存状态，每个 key 只有一个写入方。

| Restate | Dex |
| --- | --- |
| Workflow、service handler | Flow |
| 记录在日志里的操作（`ctx.run`） | Step `Execute` |
| Virtual object 和它的 key | 每个 key 一个长期运行的 Flow，key 就是 Flow ID。关闭的 Flow 在保留期后删除，而 virtual object 会持续存在。 |
| Object 状态 | Attribute |
| Awakeable 或 durable promise | Step 等待的 Channel 消息 |
| Durable sleep | Timer |

日志调用之间的 handler 代码必须是确定的，因为它会再次运行。Restate 按幂等键对调用去重。Dex 按 Flow ID 和 request ID 对 Flow 启动去重。

### 基于数据库的库 {#database-backed-workflow-libraries}

DBOS 是一个例子。Workflow 和 step 是你应用里加了注解的函数。DBOS 把它们的 checkpoint 存在你的 PostgreSQL 数据库里，不增加其他服务器。workflow 函数在 step 之间必须是确定的。DBOS 的 `send` 接受幂等键。

| DBOS | Dex |
| --- | --- |
| Workflow、Workflow ID | Flow、Flow ID |
| Step | Step `Execute` |
| Send 和 receive | Channel |
| Events | Attribute，通过 RPC 读取 |
| Queue | Task queue。每个 Worker 的任务槽限制它的工作量。 |

Dex 在对象存储上运行自己的服务器，并可以用 [Attribute Store 同步](/components/your-database#attribute-store-sync)把 Attribute 值复制到你的数据库。

### Restate 或 DBOS 更合适的情况 {#when-restate-or-dbos-fits}

- **你的流程是一个服务里的一个短函数，而你已经在运行 PostgreSQL。** 基于数据库的库不会增加新的 server。
- **你希望每个 key 只有一个写入方，而且不用声明锁。** Restate 的 virtual object 默认就是这样。在 Dex 里，你要声明 Attribute 锁。

### Step function 服务 {#step-function-services}

AWS Step Functions 是一个例子：用 JSON 定义语言写的状态机，每个状态调用一个服务。两者都记录一张显式的状态图。Dex 的 Step 和决定是用你的语言写的代码。它们在你的 Worker 上运行，所以 Step 可以调用任何库。

### Agent 框架的 checkpoint {#agent-framework-checkpoints}

LangGraph 是一个例子。checkpointer 在每个节点之后按 thread ID 保存图的状态，interrupt 让图暂停以等待人工输入。checkpointer 只保存状态。恢复崩溃的运行，或在 timer 到期时唤醒它，需要托管平台或自定义代码。Dex Server 为每个 session 做这两件事。

| Agent 框架 | Dex |
| --- | --- |
| Thread ID | Session ID，也就是 Flow ID |
| Checkpoint | 每次模型调用或工具调用之后 session 的 Attribute |
| 等待人工输入的 interrupt | 等待审批的工具调用，或者一个问题 |

使用[持久化 Agent](/agent-frameworks)，你可以保留自己的框架。adapter 把 agent 包装在一个 session Flow 里。

### 运行在 durable execution 引擎上的 Agent 框架 {#agent-frameworks-on-a-durable-execution-engine}

运行在 Temporal 上的 OpenAI Agents SDK，运行在 Temporal、DBOS 或 Prefect 上的 Pydantic AI，以及 LangGraph 平台，都把每次模型调用和包装后的工具调用记录为引擎的一个单元。崩溃后，只有正在进行的那次调用会再次运行。Dex 增加了两项能力：

- 每个工具有一个效果类别。读取可以再次运行。非幂等的写入默认只尝试一次。如果它被中断，模型会收到 `outcome_unknown`。见[工具调用](/agent-frameworks/tool-calls)。
- 效果类别也决定默认的审批方式。审批等待不占用 Worker，可以持续几分钟或几天。见[审批](/agent-frameworks/approvals)。
