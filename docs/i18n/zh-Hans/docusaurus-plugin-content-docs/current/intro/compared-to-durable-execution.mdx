# Dex vs. Temporal

Dex 和 Temporal 都能让流程在崩溃、重启和长时间等待之后继续运行。本页把 Temporal 的每项核心能力对应到 Dex。对每一项，本页说明 Dex 怎样提供它、差别的代价是什么，以及 Temporal 在哪些地方更合适。[最后一节](#other-engines)介绍其他 durable execution 工具。

本页关于 Temporal 的事实来自 [Temporal 文档](https://docs.temporal.io)。关于 Dex 的事实链接到对应的页面。

## 共同点 {#what-they-share}

- 服务器在你的进程之外记录每次运行的进度。崩溃之后，运行从这份记录继续。
- 你自己进程里的 Worker 从服务器拉取任务。你的代码从不在服务器里运行。
- Timer 是持久化的。等待 Timer 或消息的运行不占用 Worker。
- 每个工作单元都有 retry 策略和超时。默认 backoff 相同：1 秒，每次翻倍，最多 100 秒，不限次数。
- 每次运行有一个业务 ID。同一个 ID 同时最多有一个打开的运行，复用策略决定下一次启动怎样处理。
- 一个工作单元可能运行不止一次。调用其他系统的代码要传入幂等键。

## Dex 保存 Step 结果，Temporal 重放代码 {#the-main-difference-an-explicit-step-graph-not-replayed-code}

Worker 停止之后，两个引擎用不同的方式重建一次运行。

<RecoveryModelDiagram markdownDescription="Worker 运行中途停止。Temporal：Event History 记录每条命令和结果；新的 Worker 从头重放 workflow 函数，直到最后一个 await，所以 workflow 代码必须是确定的。Dex：Step 结果和 Attribute 与每个决定一起保存；新的 Worker 只运行下一个 Step，完成的 Step 不再运行，所以每个外部效果必须是幂等的。" />

**Temporal。** 一个 Workflow 是一个函数。服务器记录 Event History，即已经发生的每件事的完整有序日志。要继续一次运行，Worker 从头再运行这个函数。已记录的 Activity 结果直接返回，Activity 不再运行。代码产生的命令会和历史比对。不一致就是非确定性错误。所以对同样的输入，workflow 代码必须以同样的顺序发出同样的调用。读取时钟、随机数和 I/O 要通过 Temporal 的 API，或者放进 Activity。

**Dex。** 一个 Flow 是一组 Step。每个 Step 返回一个决定，指明接下来运行哪些 Step，或者完成 Flow。Dex 把 Step 的结果、它写入的 Attribute 和这个决定一起保存。要继续一次运行，Worker 只运行下一个 Step。它读取保存的 Attribute。没有任何重放。

| | Temporal | Dex |
| --- | --- | --- |
| 代码的形状 | 一个函数，从上往下读 | Step 和决定组成的图 |
| 循环或分支 | 普通的 `while` 和 `if` | 转到自己的 Step，有两个目标的决定 |
| 编排代码里的时钟、随机值和库 | 只能通过确定性 API | 可以使用。Step 代码就是普通代码。 |
| 修改正在运行的流程的代码 | 可能导致非确定性错误 | 不会导致重放错误 |
| 状态怎样保存 | 从历史重建，缓存在 Worker 上 | 每个 Step 之后保存为 Attribute |
| 你必须遵守的规则 | 确定性，加上幂等的 Activity | 幂等的外部效果 |

### 确定性要求转移到了幂等键上 {#determinism-moved-it-did-not-vanish}

Dex 去掉了重放规则，但没有去掉所有规则。Step 可能运行不止一次，所以每个外部效果只能依赖 Dex 传给这个 Step 的内容；见[幂等键](/concepts/step#idempotency-keys)。Temporal 对 Activity 也有同样的要求，所以这项责任并不新。[故障透明性证明](/correctness-and-expressiveness/failure-transparency-proof)以它为前提。

时钟和随机值可以用在 Step 的决定和保存的数据里。不要把它们用在幂等键里，也不要用在重新运行时必须完全一致的效果里。

### 同一个流程的两种写法 {#the-same-process-in-both-models}

一个提醒循环每隔一段时间发送一次提醒，直到对方选择退出。在 Temporal 里，循环是由引擎重放的普通代码。下面这段代码只是示意，不来自 Dex 示例：

```python
@workflow.defn
class ReminderWorkflow:
    def __init__(self) -> None:
        self.opted_out = False

    @workflow.signal
    def opt_out(self) -> None:
        self.opted_out = True

    @workflow.run
    async def run(self) -> None:
        while True:
            try:
                await workflow.wait_condition(
                    lambda: self.opted_out, timeout=REMINDER_INTERVAL
                )
                return
            except asyncio.TimeoutError:
                await workflow.execute_activity(
                    send_reminder, start_to_close_timeout=timedelta(seconds=30)
                )
```

在 Dex 里，循环是一个转到自己的 Step。它等待 Timer 或退出 Channel，它的决定选择接下来做什么。这段代码摘自可运行的[提醒](/design-patterns/durable-timer/reminder)模式：

    def __init__(
        self,
        service: ServiceDependency,
        opt_out: Channel[None],
    ) -> None:
        self.service = service
        self.opt_out = opt_out

            self.opt_out.for_one(),

提醒不带幂等键，因为多发一次提醒没有坏处。在 Rust 里，`has_any_timer_fired` 询问这个 Wait 中是否有任意一个 Timer 已触发。

Temporal 版本从上往下读。退出是一个设置变量的 Signal handler，重放会重建这个变量。Dex 版本给等待状态起了名字。Timer 和 Channel 是同一个 Wait，由决定选择接下来做什么。

## 核心能力逐项对比 {#capabilities}

| 能力 | Temporal | Dex |
| --- | --- | --- |
| 持久化状态 | Workflow 变量，通过重放 Event History 重建。Worker 在内存里缓存状态。 | Attribute，和每个 Step 结果一起保存。Worker 读取它们，不保留缓存。 |
| 持久化等待 | Timer 不占用 Worker。Workflow 也可以等待一个由 Signal handler 设置的条件。 | Step 的 `WaitFor` 返回 Timer、Channel 或 SubFlow 条件，或者用 `AnyOf` 和 `AllOf` 组合多个条件。不占用 Worker。 |
| Retry | Activity 默认会 retry：1 秒，每次翻倍，最多 100 秒，不限次数。Workflow 默认不 retry。 | 每个 Step 方法默认用同样的 backoff retry，总时长最多 4 小时。不支持 Flow 级别的 retry 策略。见 [Step 选项](/concepts/step)。 |
| 超时 | Activity 必须设置 Start-To-Close 或 Schedule-To-Close。Heartbeat 默认关闭。 | 默认方法超时 2 小时，heartbeat 超时 1 分钟。 |
| 失败处理 | 在 workflow 代码里捕获 Activity 错误。 | Step 上的失败策略转到一个恢复 Step。见[失败处理](/design-patterns/failure-handling)。 |
| 并行工作 | 启动多个 Activity，在一个线程里 `await` 它们。 | `GoToMany` 在不同的 Worker 上并行运行 Step。 |
| 修复 bug 后恢复 | 把运行重置到更早的事件。 | Time Travel 恢复更早时刻的 Attribute、Channel 消息和等待中的 Step，Run ID 不变。 |
| 搜索 | Visibility 存储里的 Search Attributes。 | 带索引的 Attribute。默认是内置搜索，大量使用时用 PostgreSQL 或 ParadeDB。 |
| 语言 | Go、Java、Python、TypeScript、.NET、Ruby、PHP、Rust | Go、Python、Java、TypeScript、Rust |

下面几项一个表格单元写不下。

### 并发的默认行为 {#concurrency-defaults}

Temporal Workflow 在单线程上运行。Signal 和 Update handler 仍然可能在每个 `await` 处和主函数交错执行。对于先读、再等待、再写入的 handler，Temporal 建议使用 workflow mutex。

Dex 在不同的 Worker 上并行运行同一个 Flow 的多个 Step。RPC 也可以和它们同时运行。它们共享 Flow 的 Attribute。由你选择哪些 Attribute 需要[锁](/concepts/primitives/attribute#locking)。没有锁时，两个先读后写的写入方可能互相覆盖。Dex 目前没有针对这种情况的检查。

这个差距比"单线程对多线程"听起来小，但它是真实存在的。Temporal 默认只有一个写入方。Dex 默认并行运行 Step，要求你声明锁。

### 消息和请求 {#messages-and-requests}

| | Temporal | Dex |
| --- | --- | --- |
| 异步消息 | Signal。客户端不等待 Worker。 | Channel 发布。没有 Worker 在线时也会保存。 |
| 重复的消息 | 重试的客户端调用按 request ID 去重。其他重复，Temporal 建议在 Signal 里带幂等键。 | 响应丢失后再次发送的发布会保存两次。按 request ID 去重计划在 [issue 1519](https://github.com/superdurable/dex/issues/1519) 中实现。 |
| 同步请求 | Update。等待 Worker 接受它。在一次运行内按 Update ID 去重。 | RPC。需要 10 秒内有 Worker 接手。重试的 RPC 会再次运行。 |
| 读取 | Query。不向历史添加任何内容。 | 只读 RPC。 |

[最多发送一次命令](/concepts/client#inbound-commands)给出了 Dex 里丢弃重复命令的模式。[限制](/intro/limits#requests-that-can-repeat)列出了所有可能重复的请求。

### 长时间运行的 Flow {#long-running-flows}

Temporal 限制每次运行的 Event History。超过 10,240 个事件后，服务器记录警告。超过 51,200 个事件、2,000 个 Update 或 10,000 个 Signal 时，运行会被终止。Continue-As-New 用新的历史开始一次新的运行，并把状态带过去。

Dex 保留每次运行最新的一段历史事件，生产服务器默认 50,000 个，更早的会被裁剪。裁剪从不让 Flow 失败，所以长期运行的 Flow 不需要 Continue-As-New。代价是：窗口之外的旧事件就没有了。见[历史窗口](/reference/server/configuration#history-window)。

### 版本管理 {#versioning}

在 Temporal 里，改变命令顺序的代码修改会让打开的运行重放失败。Temporal 提供两种工具。Worker Versioning 把运行固定到某个代码版本的 Worker 上，Temporal 称它为推荐的方式。Patching 用 `Patched` 或 `GetVersion` 在代码里分支。

打开的 Dex Flow 从下一个 Step 开始运行新代码。Dex 从不重放，所以代码修改不会导致重放错误。规则转移到了你的数据和 Step 类型上：在旧 Flow 结束前保留旧的 Step 类型，以增量方式修改 Attribute 和输入。[部署代码变更](/concepts/change-flow-code#versioning-flow-code)给出这些规则。[部署前检查](/concepts/change-flow-code#check-before-you-deploy)给出手动检查方法。Dex 还没有自动检查。

### 运行服务器 {#run-the-server}

| | Temporal Service | Dex Server |
| --- | --- | --- |
| 进程 | Frontend、History、Matching 和 Worker 服务。它们可以共用一个进程。Temporal 建议在生产环境中分开运行。 | 一个二进制。一个活跃节点在对象存储里持有 lease。活跃节点停止时，备用节点接管。见 [Dex Server](/components/server)。 |
| 必需的存储 | 一个数据库：Cassandra、MySQL 或 PostgreSQL。SQLite 只用于开发。 | 对象存储，例如 Amazon S3，或者用 db9 代替。 |
| 搜索存储 | Visibility 存储。生产环境推荐 Elasticsearch。 | 默认内置。PostgreSQL 或 ParadeDB 可选。 |
| 扩展 | 每个服务可以横向扩展。 | 一个活跃节点就是一个集群的上限。超过它，就运行多个独立集群。见[限制](/intro/limits#grow-past-one-node)。 |
| 托管选项 | Temporal Cloud | [Dex Cloud](/components/dex-cloud) |
| 发布状态 | 生产使用的时间更长 | Beta。Dex Server 处于 0.1.x。见[发布状态](/intro/limits#release-status)。 |
| 许可证 | MIT | Sustainable Use License 1.0，源码可见。见[许可证](/intro/limits#license)。 |

活跃的 Dex 节点故障转移时，每个进行中的 Step 尝试都会再次运行。见[故障转移和部署](/concepts/failover-and-deploys)。[性能](/intro/performance)给出单个 Dex 节点实测的吞吐量和延迟。

## 何时 Temporal 更合适 {#when-another-tool-is-the-better-fit}

- **你想把流程写成一个从头到尾的函数。** Temporal 可以这样写。Dex 要求你把它建模成 Step 和决定。
- **你现在就需要成熟的服务器。** Dex Server 处于 0.1.x。Temporal 的生产使用记录更长。
- **一个集群需要超过一个节点的容量。** Temporal 可以横向扩展各个服务。一个集群由一个活跃的 Dex 节点服务。
- **你想要每次运行只有一个写入方，而且不用声明锁。** Temporal Workflow 默认就是这样。
- **你现在就需要去重的消息。** Temporal 按 ID 去重 Update。Dex 会再次运行重复的 RPC 或 Channel 发布。
- **你需要 .NET、Ruby 或 PHP。** Dex 没有这些语言的 SDK。
- **你需要内置的 Schedule，带暂停、回填和重叠策略。** Dex 提供 cron 模式，没有 Schedule 对象。
- **你的团队已经在大规模运行 Temporal。** 迁移的成本高于本页列出的差别，除非重放或版本错误对你来说是真实的问题。
- **你需要 OSI 开源许可证。** Temporal 服务器采用 MIT 许可证。Dex 是源码可见的。

如果你希望编排代码就是普通代码、版本管理不依赖重放、服务器是对象存储上的一个二进制、Step 默认并行，Dex 更合适。

如果你了解 iWF：Dex 由它发展而来。Dex 的 Step 就是 iWF 的 State，`WaitFor` 就是 `WaitUntil`。

## 其他引擎 {#other-engines}

<a id="replay-based-workflow-engines"></a>

**基于重放的引擎。** Cadence 的工作方式和 Temporal 相同。上面的对比同样适用于它。

### 基于日志的运行时 {#journal-based-durable-function-runtimes}

Restate 是一个例子。handler 通过运行时 context 执行每个副作用，运行时把结果记录在日志里。失败之后，handler 再次运行，并拿到已记录的结果。virtual object 按 key 保存状态，每个 key 只有一个写入方。

| Restate | Dex |
| --- | --- |
| Workflow、service handler | Flow |
| 记录在日志里的操作（`ctx.run`） | Step `Execute` |
| Virtual object 和它的 key | 每个 key 一个长期运行的 Flow，key 就是 Flow ID。关闭的 Flow 在保留期后删除。virtual object 会一直存在。 |
| Object 状态 | Attribute |
| Awakeable 或 durable promise | Step 等待的 Channel 消息 |
| Durable sleep | Timer |

日志调用之间的 handler 代码必须是确定的，因为它会再次运行。Restate 按幂等键对调用去重。Dex 按 Flow ID 和 request ID 对 Flow 启动去重。

### 基于数据库的库 {#database-backed-workflow-libraries}

DBOS 是一个例子。Workflow 和 step 是你应用里加了注解的函数。DBOS 把它们的 checkpoint 存在你的 PostgreSQL 数据库里，不增加其他服务器。workflow 函数在 step 之间必须是确定的。DBOS 的 `send` 接受幂等键。

| DBOS | Dex |
| --- | --- |
| Workflow、Workflow ID | Flow、Flow ID |
| Step | Step `Execute` |
| Send 和 receive | Channel |
| Events | Attribute，通过 RPC 读取 |
| Queue | Flow 类型的队列。每个 Worker 的任务槽限制它的工作量。 |

Dex 在对象存储上运行自己的服务器。它可以用 [Attribute Store 同步](/components/your-database#attribute-store-sync)把 Attribute 值复制到你的数据库。

### Step function 服务 {#step-function-services}

AWS Step Functions 是一个例子：用 JSON 定义语言写的状态机，每个状态调用一个服务。两者都记录一张显式的状态图。Dex 的 Step 和决定是用你的语言写的代码。它们在你的 Worker 上运行，所以 Step 可以调用任何库。

### Agent 框架的 checkpoint {#agent-framework-checkpoints}

LangGraph 是一个例子。checkpointer 在每个节点之后按 thread ID 保存图的状态，interrupt 让图暂停，等人处理。checkpointer 只保存状态。重启崩溃的运行，或者在 timer 到期时唤醒它，需要托管平台或你自己的代码。Dex Server 为每个 session 做这两件事。

| Agent 框架 | Dex |
| --- | --- |
| Thread ID | Session ID，也就是 Flow ID |
| Checkpoint | 每次模型调用或工具调用之后 session 的 Attribute |
| 等待人工输入的 interrupt | 等待审批的工具调用，或者一个问题 |

使用[持久化 Agent](/agent-frameworks)，你可以保留自己的框架。adapter 把 agent 包装在一个 session Flow 里。

### 运行在 durable execution 引擎上的 Agent 框架 {#agent-frameworks-on-a-durable-execution-engine}

运行在 Temporal 上的 OpenAI Agents SDK，运行在 Temporal、DBOS 或 Prefect 上的 Pydantic AI，以及 LangGraph 平台，都把每次模型调用和包装后的工具调用记录为引擎的一个单元。崩溃只会重复正在运行的那次调用。Dex 增加了三点：

- 每个工具有一个效果类别。读取可以再次运行。非幂等的写入默认只尝试一次。如果它被中断，模型会得到 `outcome_unknown`。见[工具调用](/agent-frameworks/tool-calls)。
- 效果类别也决定默认的审批方式。审批等待不占用 Worker，可以持续几分钟或几天。见[审批](/agent-frameworks/approvals)。
- 一种 adapter 模型和一个 session Flow 覆盖所有支持的框架。
