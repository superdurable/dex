# 为什么是 Dex？

Dex 是一个 Durable Execution（D-Ex）平台。
Dex 会在流程运行时记录它的每个 Step。
进程崩溃或重启后，流程从最后记录的 Step 继续，不会从头再来，也不会停在半路。

一个在中途被打断的 Step 可能再运行一次，所以每次调用其他系统都要带上幂等键：这个值让对方系统认出重复的请求并跳过它。[幂等键](/concepts/step#idempotency-keys)说明怎样构造它。

## 问题在哪里 {#the-problem}

一家网店先向买家扣款，再发货。在两次调用之间，服务器可能崩溃，部署可能重启它，发货 API 也可能超时。结果买家被扣了款，商品却一直没有发出。

这个流程还要等待。卖家必须批准发货，可能要等一天。等待期间，网店会提醒卖家。如果发货一直失败，网店就给买家退款。

数据库能保存订单，但不会运行这个流程。剩下的部分团队只能自己搭：状态列、队列、重试 topic、提醒任务，以及修复卡住订单的工具。[与数据库对比](/intro/compared-to-database)一步步搭出了这种设计。

## Dex 怎样建模一个流程 {#how-dex-models-a-process}

在 Dex 里，订单流程是一个 **Flow**。订单 ID 就是它的 Flow ID。

Flow 由多个 **Step** 组成。每个 Step 做一件事，例如扣款调用。Dex 把 Step 的结果和转到下一个 Step 的动作一起保存，所以崩溃不会让订单停在两个 Step 之间。

一个 Step 有两部分：

- `WaitFor` 等待一个条件：一条 **Channel** 消息，例如卖家的批准；或者一个 **Timer**，例如提醒。等待保存在 Dex 里，所以它能撑过重启，也不占用线程。
- `Execute` 做实际的工作。它返回一个决定：接下来运行哪些 Step，或者 Flow 已经完成。

Flow 把数据保存在 **Attribute** 里，例如订单状态。**RPC** 让你的应用读取 Flow，或者给它发命令，例如批准。

这个模型有一个取舍。你要把流程写成 Step 和决定，而不是一个函数。换来的是 Step 代码就是普通代码，Dex 也从不 replay 它。

## 你的代码在哪里运行 {#where-your-code-runs}

你的应用包含一个 **Worker** 和一个 **Client**，都用 Dex SDK 构建。Worker 托管 Flow，运行它的 Step 和 RPC。Client 启动 Flow 并调用它们的 RPC。**Dex Server** 保存每个 Flow，并把工作发给你的 Worker。

## 和基于 replay 的 durable execution 有什么不同 {#how-this-differs-from-replay-based-durable-execution}

<a id="和传统-durable-execution-的区别"></a>

基于 replay 的引擎通过重放事件历史来重建 workflow 的状态。所以 workflow 代码必须是确定性的，读取时间和随机值都要通过引擎的 API。Dex 不重放代码。Step 代码就是普通代码，可以读时钟，也可以调用任何库。修改代码不会让正在运行的 Flow 因为 replay 而出错。
