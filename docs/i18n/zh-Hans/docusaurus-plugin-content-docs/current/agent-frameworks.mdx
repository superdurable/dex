# Agent Framework

Dex 把 AI Agent 作为 durable agent session 运行。你可以用 Dex Agents 的内置 agent loop 构建 Agent，也可以保留已经用 agent framework 写好的 Agent。两者都运行在同一个 session Flow 上，所以无论选哪种，session 的行为都相同。

## Durable agent session {#a-durable-agent-session}

一次 Flow run 就是一个 agent session。Flow ID 就是 session ID。Dex Agents 负责构建 session Flow：Python 版是 **dex-agents** package，TypeScript 版是 **@superdurable/dex-agents**。Framework adapter 在它之上接入一个 agent framework。

Session 把对话保存在 Attribute 中。Session 等待下一条用户消息时不占用 Worker，可以等上好几天。

模型调用在 **RunModel** Step 中运行。在大多数 harness 中，每个 **RunModel** Step 调用一次模型，每个 tool call 在自己的 Step 中运行。同一次模型回复中的 tool call 并行运行。它们完成后，session 把结果交给模型。每个 Step 都会增加一次与 Dex 的往返。

崩溃时只会重跑当时正在运行的那个 Step，Dex 不会重放整个循环。因此 Agent 代码不需要遵守确定性规则，代码改动会在下一个 Step 生效。

有两个 harness 会把更多工作放进一个 Step：

- **Claude Agent SDK。** Claude Code CLI 在一个 **RunModel** Step 中运行一个 turn segment。Segment 包含模型调用和 read tool call，失败的 segment 会整体重跑。写操作逐个离开 segment，每个都在自己的 Step 中运行，因此它们永远不会并行。
- **LangChain 和 LangGraph。** 一个 **RunModel** Step 把 graph 运行到下一批 tool call 为止。Graph 在途中可能多次调用模型，重试会把这些调用一起重复。

## Tool policy 和审批 {#tool-policies-and-approvals}

每个 tool 都有一个 **ToolPolicy**。Policy 设定 tool 的 effect class，由它决定 Dex 能否再次运行一次调用。Policy 还规定调用是否要先经审批。

### Effect class {#effect-classes}

| Effect class | Tool 做什么 | 在哪个 Step 中运行 |
| --- | --- | --- |
| **read** | 只读。再运行一次没有影响。 | **CallTool**，会重试 |
| **idempotent_write** | 写操作，用同一个幂等键重复执行不会产生额外效果。 | **CallTool**，会重试 |
| **non_idempotent_write** | 写操作，重复执行可能重复产生效果。 | **CallSingleAttemptTool**，只运行一次 |
| **unclassified** | 对它一无所知。Dex 把它当作 non-idempotent write 处理。 | **CallSingleAttemptTool**，只运行一次 |

同一次调用的每次尝试都使用同一个幂等键：session 的 Flow ID、turn ID 和 tool call ID 用斜杠连接，例如 **session-42/turn-3/call-7**。把它传给 tool 要写入的服务。如果这个服务会丢弃重复的键，就把 tool 归为 **idempotent_write**，这样 Dex 能在失败后重试它。

已经记录的 tool call 保留模型请求它时生效的 effect class 和审批规则。改过的 policy 只对之后的调用生效。

### 审批 {#approvals}

审批决定的是这次调用该不该发生。它和重试无关：带幂等键的退款仍然是一笔真实的退款。

需要审批的 tool call 会在自己的 **AwaitToolApproval** Step 中等待，直到有人回复。等待期间不占用 Worker slot，Worker 重启和部署也不影响它。审批人可以在你的应用中，也可以在 [Dex Web](/reference/web/dex-web#agent-session-view) 中批准或拒绝这次调用。模型能看到拒绝结果，并据此做出反应。

审批等待时，turn 也一起等待，新的用户消息会排队到 turn 结束。如果审批不能一直等下去，就设置审批 deadline。到 deadline 时仍未处理的调用会被 Dex 拒绝。见 [审批 deadline](/reference/agents/approvals#approval-deadlines)。

## Tool call 的结果 {#tool-call-outcomes}

每个 tool call 最终会得到一条记录：

| 记录 | 含义 |
| --- | --- |
| **succeeded** | Tool 返回了结果。 |
| **failed** | Tool 报告了失败，或者 Dex 确定 tool 没有运行。 |
| **rejected** | 有人拒绝了这次调用，或者审批 deadline 已过。 |
| **outcome_unknown** | Tool 可能生效了，也可能没有。 |

模型会读到每条记录，并决定下一步做什么。失败或结果未知的调用不会让 session 失败。

Dex 确定从未运行的调用记为 **failed**。它的错误以 "the tool did not run, so it is safe to call again" 开头，模型可以再次调用这个 tool。可能已经运行过的调用则记为 **outcome_unknown**（read 除外），Dex 不会再次运行它。Dex 如何判断，见 [从未运行的调用](/reference/agents/failures#never-run-outcome-unknown)。

### 最多一次有一个例外 {#tool-runs-twice}

Single-attempt tool 在 **CallSingleAttemptTool** 中运行。Dex 把每次尝试只交给一个 Worker，不会把同一次尝试再交给另一个 Worker。如果 tool 运行期间 Worker 崩溃或与 Dex 断开连接，这次调用会记为 **outcome_unknown**，session 不会再次运行这个 tool。

只有一种很少见的情况仍会让 single-attempt tool 运行两次。Dex 无法强制停止正在运行的尝试。Dex 取消一次尝试后，被中断的那次运行可能还在继续，而 Dex 已经记录了失败，turn 也继续往下走。为了让第二次运行无害，把这次调用的幂等键传给 tool 要写入的服务。见 [Failure and redelivery](/reference/python/failure-and-retries#failure-and-redelivery)。

### 处理 outcome_unknown {#reconcile-outcome-unknown}

**outcome_unknown** 表示效果可能发生了，也可能没有。Session 永远不会重试这样的调用，模型会看到结果未知。在 session 之外核对它：

1. 找到这次调用。Turn 运行期间，**get_agent_snapshot** 在 **tool_calls** 下列出它，失败信息在 **error** 中。**AgentEvents** Stream 中有一个状态为 **outcome_unknown** 的 **tool_call_finished** 事件。Turn 结束后，消息历史里它的 tool 结果会说明结果未知。
2. 在目标系统中用这次调用的幂等键，或你自己的业务键，检查效果是否发生。
3. 如果 Flow 的历史显示 tool Step 的尝试从未到达 Worker，那么 tool 没有运行。服务器升级前开始的调用可能出现这种情况。
4. 用 **send_user_message** 把真实结果告诉 session，让下一个 turn 的模型据此工作。

没有搜索能替你找出这些调用，因为没有 Step 在等待它们。

## 把 Connector 用作 tool {#connectors-as-tools}

每个 harness 都可以把 [Connector](/concepts/connector) 的 operation 当作 tool 调用。**ConnectorToolSource** 提供你指定的 operation。Agent 通过 Python 的 **tool_sources** 或 TypeScript 的 **toolSources** 把它作为 tool source 接收。每次调用都在自己的 tool Step 中通过 Connector SDK 运行一个 operation，因此 Call ID、幂等键和凭据处理都与 Connector Step 中相同。同一个 tool Step 的每次尝试使用同一个 Call ID。

每个 harness 页面的“连接 Connector”一节展示了接入方式，例如 [内置 Agent Loop](/agent-frameworks/built-in-agent-loop#connect-connectors) 和 [Claude Agent SDK](/agent-frameworks/claude-agent-sdk#connect-connectors)。安装包、tool 名称、结果大小和 connection 见 [Connector tools reference](/reference/agents/connector-tools)。

### 提供哪些 operation {#connector-tools-offered}

默认不暴露任何 operation。应用要逐个指定 Agent 可以使用的 operation。Connector 作者还必须审查过这个 operation 是否适合 Agent 使用，并在 manifest **dex-connector.json** 中把它标为可暴露。其他 operation 在定义 Agent 时就会被 Dex 拒绝。

Operation 运行前，Dex 会用它的 input schema 检查模型给出的参数。字段拼错、类型不对或缺少字段时，调用失败，并返回模型可以据此修正的信息。Operation 不会运行。

### Effect class {#connector-tools-effects}

Manifest 决定调用能否再次运行，从而决定由哪个 Step 运行它：

| Operation | Effect class | 在哪个 Step 中运行 |
| --- | --- | --- |
| Query | **read** | **CallTool**，会重试 |
| Manifest 标为可安全重试（**agent.retry: safe**）的 Mutation | **idempotent_write** | **CallTool**，会重试 |
| 其他 Mutation | **non_idempotent_write** | **CallSingleAttemptTool**，只运行一次 |

Connector 作者审查后才会把 Mutation 标为可安全重试。它的意思是：用同一个 Call ID 重复执行不会产生第二次效果。尝试次数用完后，Query 记为 **failed**，Mutation 记为 **outcome_unknown**。

Session 对 Connector tool 设置的 tool policy 只改变它的审批。Effect class 始终来自 manifest。

### 审批 {#connector-tools-approval}

默认情况下，只有 manifest 建议审批（**agent.approval: recommended**）的 Connector tool 才会等待审批，例如退款。其他 Mutation 无需审批就会运行，因为每条消息都要审批的话，长期运行的 Agent 就没法用了。

应用可以为每个 tool 改变这个默认值，开启或关闭审批都可以。应用也可以传入一个 predicate，根据每次调用的参数决定是否审批，例如超过某个金额的退款。Predicate 抛出异常时会要求审批。没有通过 schema 检查的参数不会等待审批，因为这次调用根本不会运行。

### 结果 {#connector-tools-outcomes}

Operation 以它的某个 branch 结束，这个 branch 决定 tool call 的记录。Connector 作者在 manifest 中把没有产生效果的 branch 标为 **rejected**，把写操作可能已经生效的 branch 标为 **unknown**。Dex 取第一个匹配的行。rejected 那一行之前的各行，除了成功的 branch，都记为 **outcome_unknown**，所以拿不准时绝不会记成可以放心重试的失败：

| Branch | 记录 | 模型看到的内容 |
| --- | --- | --- |
| **uncertain** | **outcome_unknown** | 结果未知 |
| Mutation 的 **defect** | **outcome_unknown** | 结果未知 |
| 成功的 branch，例如 **sent** 或 **refunded** | **succeeded** | 结果值 |
| Mutation 的其他任何 branch，而它的 single-dispatch fence 无法证明请求没有发出 | **outcome_unknown** | 结果未知 |
| 标为 **rejected** 的 branch，例如 **providerRejected** | **failed** | Branch 和 provider 的消息 |
| 标为 **unknown** 的 branch，或没有列出的 Mutation branch | **outcome_unknown** | 结果未知 |
| 没有列出的 Query branch，包括 **defect** | **failed** | Branch 和消息 |

Mutation 的 **defect** 可能发生在调用 provider 之后，所以写入可能已经生效。使用 single-dispatch fence 的 Mutation 会记录请求是否可能已经发出。如果可能已经发出，即使 branch 标为 **rejected**，也不会把失败记成拒绝。

**outcome_unknown** 的处理方式与其他 tool 相同，见 [处理 outcome_unknown](#reconcile-outcome-unknown)。

### 写操作顺序 {#connector-tools-write-order}

同一次模型回复中的 Connector 写操作按模型给出的顺序逐个运行。读操作和其他 tool 的调用并行运行。需要审批的写操作轮到它时才会请求审批。

当一个写操作失败、结果为 **outcome_unknown**，或被审批人或 provider 拒绝时，这次回复中后面的 Connector 写操作都不会运行。它们各自记为 **failed**，设置 **skipped** 字段，错误以 "the tool did not run, so it is safe to call again" 开头。Dex Web 把这些调用显示为已跳过。

在 Claude Agent SDK adapter 中，同一次模型回复每次只有一个调用离开 turn，在自己的 tool Step 中运行。这次回复中后面的写操作会在 turn 内被 adapter 拒绝，因此不会运行，也不会留下记录。模型读到前一个写操作的结果后，再决定是否重新调用后面的写操作。

### 崩溃 {#connector-tools-crashes}

Connector 写操作期间 Worker 崩溃，永远不会让写操作发送两次。写操作如何恢复，取决于 Connector 怎样判断 provider 是否收到了它：

- **由 provider 去重。** Connector 发送这次调用的幂等键，provider 会丢弃重复的键。
- **先查询。** Provider 没有幂等键。重试发送任何内容之前，Connector 先在 provider 那里查找之前的写操作。Connector 还会在尝试过程中记录请求是否已经离开 Worker。

| 发生了什么 | 可安全重试的写操作，由 provider 去重 | 可安全重试的写操作，先查询 | Single-attempt 写操作 |
| --- | --- | --- | --- |
| 请求发出前 Worker 崩溃 | Dex 用同一个键重试。写操作只发生一次，调用记为 **succeeded**。 | Dex 重试。查询没有找到写操作，但没有证据表明请求从未发出，所以重试什么也不发送。调用记为 **outcome_unknown**。 | 调用记为 **outcome_unknown**。没有发送任何内容。 |
| Provider 接受写操作后 Worker 崩溃 | Dex 用同一个键重试。Provider 丢弃重复请求，调用记为 **succeeded**。只写一次。 | Dex 重试。查询找到写操作时，调用记为 **succeeded**；找不到时记为 **outcome_unknown**。两种情况都只写一次。 | 调用记为 **outcome_unknown**。只写一次。 |
| Provider 要求稍后重试，例如限流 | Dex 重试。写操作只发生一次。 | Dex 重试。写操作只发生一次。 | 如果 Connector 记录了请求从未离开 Worker，或 provider 拒绝了请求且没有执行，调用记为 **failed**，错误为 "not sent; the provider asked to retry later"。否则记为 **outcome_unknown**。 |

仅凭“稍后重试”的要求，不能证明什么都没发送。所以只有 Connector 的记录可以作为证明时，single-attempt 写操作才会记为 **failed**。这时模型可以再次调用它，不需要有人去 provider 那里核对。这次回复中后面的写操作仍会被跳过。

## 选择 harness {#choose-a-harness}

Harness 是运行 agent loop 的代码：内置 loop 或某个 framework。下面每个页面都有安装命令、可运行的 example 以及在本地运行它的步骤。

| Harness | 语言 | Loop 如何映射到 Step | 何时选择 |
| --- | --- | --- | --- |
| [内置 Agent Loop](/agent-frameworks/built-in-agent-loop) | Python、TypeScript | 每个 **RunModel** Step 调用一次模型。每个 tool call 是独立的 Step。 | 开发新的 Agent。希望由 Dex 管理模型输入，并使用提问、durable wait、plan 和 MCP tool。 |
| [Claude Agent SDK](/agent-frameworks/claude-agent-sdk) | Python、TypeScript | Claude Code CLI 在一个 **RunModel** Step 中运行一个 turn segment。Read 在其中运行。写操作会结束 segment，并在自己的 Step 中运行。 | 需要 Claude Code 的 agent loop 和它的 tool。 |
| [OpenAI Agents SDK](/agent-frameworks/openai-agents-sdk) | Python、TypeScript | 每个 **RunModel** Step 调用一次模型。每个 function tool call 是独立的 Step。 | 已有 OpenAI Agents SDK Agent，无论是否使用 handoff。 |
| [Pydantic AI](/agent-frameworks/pydantic-ai) | Python | 每个 **RunModel** Step 调用一次模型。每个 tool call 是独立的 Step。 | 已有 Pydantic AI Agent。 |
| [LangChain 和 LangGraph](/agent-frameworks/langchain-langgraph) | Python | 一个 **RunModel** Step 把 graph 运行到下一批 tool call 为止。每个 tool call 是独立的 Step。 | 已有 LangChain **create_agent** Agent 或 LangGraph graph。 |
| [Google ADK](/agent-frameworks/google-adk) | Python | 每个 **RunModel** Step 调用一次模型。每个 tool call 是独立的 Step。 | 已有 Google ADK Agent。 |
| [Vercel AI SDK](/agent-frameworks/vercel-ai-sdk) | TypeScript | 每个 **RunModel** Step 调用一次模型。每个 tool call 是独立的 Step。 | TypeScript 应用中已有 AI SDK 的 tool 和模型。 |
| [Mastra](/agent-frameworks/mastra) | TypeScript | 每个 **RunModel** Step 调用一次模型。每个 Agent tool call 是独立的 Step。 | 已有 Mastra Agent。 |

想在终端里试用某个 harness、又不想写应用，可以运行它的 CLI 命令。见 [CLI commands](/reference/agents/cli)。

## Example {#the-examples}

每个 framework 页面都使用同一个订单客服 Agent。它在一个内存中的订单系统上有两个 tool：

| Tool | Policy | Dex 的处理 |
| --- | --- | --- |
| **look_up_order** | read | 无需审批就会运行，失败时会重试。 |
| **cancel_order** | non-idempotent write | 先在 **AwaitToolApproval** 中等待，然后最多运行一次。 |

**cancel_order** 只能取消仍在处理中的订单。

Python 版 Agent 位于 [examples/python/agent-harnesses](https://github.com/superdurable/dex/tree/main/examples/python/agent-harnesses)。TypeScript 版 Agent 位于 [examples/typescript/src/products/agent-harnesses](https://github.com/superdurable/dex/tree/main/examples/typescript/src/products/agent-harnesses)。

内置 Agent Loop 页面改用 [AI Agent](/use-cases/ai-agent) example。它展示了 session 的全部功能。

### Session route {#session-routes}

每个 harness 都提供相同的 HTTP route，因此可以并排试用。每个 route 对应 session Flow 上的一次调用：启动 session、发送消息或处理审批。

启动 session 会返回 session token，它是用 **DEX_AGENT_SESSION_KEY** 对 session ID 计算的 HMAC。其他每个 route 都会检查 **X-Agent-Session-Token** header 中的 token，缺少时返回 403。没有设置 **DEX_AGENT_SESSION_KEY** 时，example 会随机选一个 key，因此进程重启后所有 token 都会失效。真实的应用会改用自己的登录。

### 在 Dex Web 中审批 {#approve-in-dex-web}

Example 运行时，你也可以不发 HTTP 请求，改在 Dex Web 中审批：

1. 打开这个 session 的 run。它的 Flow ID 就是 session ID。
2. 选择 **Agent session** tab。
3. 把 **Working as** 设为 **order-support.operate**，也就是渲染 session graph 时指定的 permission。
4. 在 **cancel_order** 卡片上选择 **Approve** 或 **Reject**。Dex Web 会替你调用 **resolve_interrupt**。

只有启动时读到了 session graph，Dex Web 才会显示这个 tab。每个 framework 页面都会在启动 Dex 之前渲染 graph。生产环境的做法见 [Show sessions in Dex Web](/reference/agents/dex-web)。

### Slack Connector tool {#slack-connector-tool}

项目配置中有 Slack connection **support-slack** 时，每个 example agent 还会得到 **slack_post_thread_reply**。这个 tool 就是 Slack Connector 的 operation **postThreadReply**，agent 用它在 Slack thread 中回复。本地开发时，Worker 从 **DEX_CONNECTOR_CONFIG_FILE** 打开这个 connection；部署后，从 **DEX_PROJECT_\*** 设置打开。两种方式见 [Connections](/reference/agents/connector-tools#connector-tools-connection)。没有 connection 时会怎样、Slack app 需要什么，见 [The Slack tool in the examples](/reference/agents/connector-tools#slack-example)。

每次调用都在自己的 tool Step 中通过 Connector SDK 运行一个 Slack operation。调用保留 Connector 的 Call ID 和幂等键。Operation 如何变成 tool、Dex 如何检查参数，见 [提供哪些 operation](#connector-tools-offered)。

Connector 的 manifest 决定调用能否再次运行。**postThreadReply** 是 Mutation，它的 manifest 没有把它标为可安全重试，所以调用只在 **CallSingleAttemptTool** 中运行一次。Worker 崩溃永远不会让同一条消息发两次。见 [崩溃](#connector-tools-crashes)。

Slack 的 manifest 没有要求 **postThreadReply** 先经审批。所以 example 传入 Python 的 **requires_approval=True** 或 TypeScript 的 **requiresApproval: true**，每次发帖都在 **AwaitToolApproval** 中等待，直到有人批准。Manifest 和应用如何决定审批，见 [审批](#connector-tools-approval)。

一次模型回复请求多个 Connector 写操作时，它们按顺序逐个运行。见 [写操作顺序](#connector-tools-write-order)。
