# 响应式更新

交互式调用方不应只能在等待整个 Flow 结束和轮询状态之间二选一。响应式更新会在调用方真正需要的边界返回，同时由 Flow 继续负责 durable 工作。

有意识地选择这个边界：

- [等待 Step 完成](/design-patterns/responsive-update/step-completion) 会在一个指定 Step 完成后返回。当该 Step 已使结果可供客户端安全读取或使用时采用它。
- [等待 Attribute 匹配](/design-patterns/responsive-update/attribute-match) 返回当前命中的 Attribute 值。当调用方需要在业务状态变化后刷新时，使用 revision watermark。
- [等待并流式接收更新](/design-patterns/responsive-update/stream) 会长轮询下一条增量更新，并从 token 继续读取。它适用于进度或持续变化的 feed。

前两种等待观察 durable 状态。它们适合定义客户端可见的边界，而不是代替应用超时或最终 Flow 结果。Stream 承载有序的增量消息；客户端保存最新的 resume token，并在下一次读取时带上它。

## 选择超时边界

**RequestTimeout** 是 SDK 调用的总预算，覆盖所有透明 transport reattachment。正值会为每次 attempt 设置本地 transport deadline。总预算到期时，SDK 返回有类型的 request-timeout 错误。已经接受的 durable Update 仍可由使用同一 logical Request ID 的后续调用重新附着。

普通 durable wait 应让 **RequestTimeout** 保持为 0。此时，它会一直等待，直到成功、Flow 关闭或调用方取消。在 HTTP 或 admission 边界，应显式设置应用响应预算。

Server 还会限制单次 transport attempt。这个 cap 完全是内部行为。SDK 会使用同一 logical Request ID 重新附着，因此它不会重置 **RequestTimeout**、结束 Temporal Update handler 或创建新的 Update generation。

**InternalHandlerTimeout** 是高级 Temporal 控制项。正值限制单个 Update handler generation 的生命周期。到期后，service 创建下一代并继续等待，不向调用方返回 handler-timeout 错误。除非 Workflow history 增长或运维需求要求换代，否则应保持为 0。较短的值会增加 Update events，也可能增加 Temporal Cloud Actions。

| 设置 | 默认值 | 行为 |
| --- | --- | --- |
| **RequestTimeout** | 0 | 调用方可见的 SDK 总预算。0 表示等待到成功、Flow 关闭或调用方取消。 |
| **InternalHandlerTimeout** | 0 | Temporal Update generation 生命周期。0 表示不按时间换代。 |
| Transport attempt cap | Server 管理 | 只触发透明 reattachment，不是应用可见的 timeout。 |
