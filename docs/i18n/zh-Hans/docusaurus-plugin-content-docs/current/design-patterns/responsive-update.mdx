# 响应式更新

交互式调用方不应只能在等待整个 Flow 结束和轮询状态之间二选一。响应式更新会在调用方真正需要的边界返回，同时由 Flow 继续负责 durable 工作。

有意识地选择这个边界：

- [等待 Step 完成](/design-patterns/responsive-update/step-completion) 会在一个指定 Step 完成后返回。当该 Step 已使结果可供客户端安全读取或使用时采用它。
- [等待 Attribute 匹配](/design-patterns/responsive-update/attribute-match) 返回当前命中的 Attribute 值。当调用方需要在业务状态变化后刷新时，使用 revision watermark。
- [等待并流式接收更新](/design-patterns/responsive-update/stream) 会长轮询下一条增量更新，并从 token 继续读取。它适用于进度或持续变化的 feed。

前两种等待观察 durable 状态。它们适合定义客户端可见的边界，而不是代替应用超时或最终 Flow 结果。Stream 承载有序的增量消息；客户端保存最新的 resume token，并在下一次读取时带上它。

## 选择等待 budget

**MaximumWaitTime** 限制调用方可见的等待时间。它不同于调用方 context、HTTP deadline 或 transport long-poll timeout。正值 budget 到期时，调用方会收到有类型的 timeout。

正值 **MaximumWaitTime** 是极少使用的安全阀，不是常规 request timeout。普通响应超时应让它保持为 0，并使用调用方 context 或 HTTP deadline。较短的正值可能让重复等待向 Workflow history 增加大量 Temporal Update accepted 和 completed events，也可能增加 Temporal Cloud Actions。确实需要正值时，应从至少 1 分钟开始；只有经过实际测量并有明确需求时才使用更短的值。

| **MaximumWaitTime** | 适用场景 | 行为 |
| --- | --- | --- |
| 0 | 推荐用于普通等待。 | 一直等待 Step 完成或 Attribute 命中。使用调用方 deadline 限制单次响应时间。 |
| 正值 | 极少使用：等待本身需要调用方可见的最长时长。建议至少 1 分钟。 | budget 到期时返回有类型的 timeout。较短的值可能向 Workflow history 增加大量 Temporal Update events。 |
