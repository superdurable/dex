# 响应式更新

交互式调用方不应只能在等待整个 Flow 结束和轮询状态之间二选一。响应式更新会在调用方真正需要的边界返回，同时由 Flow 继续负责 durable 工作。

有意识地选择这个边界：

- [等待 Step 完成](/design-patterns/responsive-update/step-completion) 会在一个指定 Step 完成后返回。当该 Step 已使结果可供客户端安全读取或使用时采用它。
- [等待 Attribute 匹配](/design-patterns/responsive-update/attribute-match) 返回当前命中的 Attribute 值。当调用方需要在业务状态变化后刷新时，使用 revision watermark。
- [等待并流式接收更新](/design-patterns/responsive-update/stream) 会长轮询下一条增量更新，并从 token 继续读取。它适用于进度或持续变化的 feed。

前两种等待观察 durable 状态。它们适合定义客户端可见的边界，而不是代替应用超时或最终 Flow 结果。Stream 承载有序的增量消息；客户端保存最新的 resume token，并在下一次读取时带上它。

## 选择 durable handler 的生命周期

对于 Step 和 Attribute 等待，Dex 会从 Step execution 或完整的 Attribute 条件派生逻辑 Temporal Update ID。同一 active Flow 上相同的逻辑等待会重新附着到已接受的 Update。该标识跨 transport long poll 和 Continue-As-New 保持不变，因此普通调用方不需要提供 Request ID。

**MaximumWaitTime** 限制调用方可见的等待时间，并在已接受的 durable Update handler 上记录 deadline。它不同于调用方 context、HTTP deadline 或 transport long-poll timeout。正值 budget 到期时，调用方会收到有类型的 wait-handler timeout；Temporal 不会取消已接受的 handler。

Dex 不会为该 deadline 创建 durable timer。只有其他事件触发新的 Workflow Task 时，已接受的 handler 才会检查 deadline。在此之前，handler 仍处于 accepted 状态并继续占用 in-flight Update slot。

| **MaximumWaitTime** | 适用场景 | 资源行为 |
| --- | --- | --- |
| 0 | 推荐用于普通等待。一个 Flow 只有少量不同的等待，并且它们应一直保持 durable，直到完成或命中。 | 每个不同的已接受等待占用一个 in-flight Update slot。重新附着到相同逻辑等待会复用该 slot。 |
| 正值 | 调用方需要有类型的 timeout，但可以接受 handler 继续 pending。 | 调用方会在 budget 到期时返回。只有后续 Workflow Task 观察到 deadline 后，handler 才释放 slot。 |

在已接受的 handler 结束前发起的调用会重新附着到同一个 Update。只有旧 handler 实际以 deadline error 完成后，Dex 才会创建下一个 -N Update generation。每个新 generation 都是另一个已接受的 Update 和 history entry，也可能是另一个 Temporal Cloud Action。只有重复的 Update 使用相同 Update ID 时，Temporal Cloud 才会去重。

Temporal 当前的 self-hosted 默认值是每个 Workflow Execution 最多 10 个 in-flight Update、总计 2,000 个 Update。这些限制可以配置，并取决于具体部署，不是 Dex 的保证。请参阅 [Temporal self-hosted 默认值](https://docs.temporal.io/production-deployment/self-hosted-guide/defaults)和 [Temporal Cloud Action 计费规则](https://docs.temporal.io/cloud/actions)。
