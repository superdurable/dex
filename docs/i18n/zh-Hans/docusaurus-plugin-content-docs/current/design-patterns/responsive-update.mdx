# 响应式更新

交互式调用方不应只能在等待整个 Flow 结束和轮询状态之间二选一。响应式更新会在调用方真正需要的边界返回，同时由 Flow 继续负责 durable 工作。如果是 Flow 自己在等待外部系统，请使用 [Polling](/design-patterns/polling)。

有意识地选择这个边界：

- [等待 Step 完成](/design-patterns/responsive-update/step-completion) 会在一个指定 Step 完成后返回。当该 Step 已使结果可供客户端安全读取或使用时采用它。
- [等待 Attribute 匹配](/design-patterns/responsive-update/attribute-match) 返回当前命中的 Attribute 值。当调用方需要在业务状态变化后刷新时，使用 revision watermark。
- [等待并流式接收更新](/design-patterns/responsive-update/stream) 会长轮询下一条增量更新，并从 token 继续读取。它适用于进度或持续变化的 feed。

前两种等待观察 durable 状态。它们适合定义客户端可见的边界，而不是代替应用超时或最终 Flow 结果。Stream 承载有序的增量消息；客户端保存最新的 resume token，并在下一次读取时带上它。

## 选择超时边界

**RequestTimeout** 是 SDK 调用的总预算，覆盖所有透明 transport reattachment。正值会为每次 attempt 设置本地 transport deadline。总预算到期时，SDK 返回有类型的 request-timeout 错误。已经接受的 wait 仍可由使用同一 logical Request ID 的后续调用重新附着。

普通 durable wait 应让 **RequestTimeout** 保持为 0。此时，它会一直等待，直到成功、Flow 关闭或调用方取消。在 HTTP 或 admission 边界，应显式设置应用响应预算。

Server 还会限制单次 transport attempt。这个 cap 完全是内部行为。SDK 会使用同一 logical Request ID 重新附着，因此它不会重置 **RequestTimeout**，也不会结束已经接受的 wait。

**InternalHandlerTimeout** 是高级容量控制项。在 Temporal 后端上，一个 Flow 同时最多只能有 10 个在 Flow 内等待的 in-flight 请求，例如已经接受的 waits，以及带锁或 transactional 的 RPC。request timeout 或 cancellation 会结束 SDK 调用，但不会结束已经接受的 wait。因此，已经被调用方放弃的 wait 仍可能占用这 10 个 slots 中的一个，直到条件命中或 Flow 关闭。

只有当被放弃的 waits 可能累积并接近这个上限时，才应把 **InternalHandlerTimeout** 设为正值。它到期后，Dex 会结束这个已经接受的 wait 并释放它的 slot。仍然活跃的 SDK 调用会透明地重新注册 wait 并继续等待。这个机制不会提高上限。每次重新注册都是 Flow 上的又一个已接受请求，也可能增加 Temporal Cloud Actions。这个值应明显长于常见的 **RequestTimeout** 和预期的重连间隔。如果 waits 通常会及时完成，或 Flow 会在被放弃的 waits 形成容量风险前关闭，应保持为 0。

| 设置 | 默认值 | 行为 |
| --- | --- | --- |
| **RequestTimeout** | 0 | 调用方可见的 SDK 总预算。0 表示等待到成功、Flow 关闭或调用方取消。 |
| **InternalHandlerTimeout** | 0 | 回收被放弃的 accepted waits，避免其无限占用 in-flight slots。每次到期后，活跃调用会重新注册 wait。 |
| Transport attempt cap | Server 管理 | 只触发透明 reattachment，不是应用可见的 timeout。 |
