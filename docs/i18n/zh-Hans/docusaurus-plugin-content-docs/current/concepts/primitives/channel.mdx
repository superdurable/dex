# Channel

**Channel** 是单个 Flow run 内部一条持久化的 first-in, first-out (FIFO) 队列。Step 和 RPC 向它发布有类型的消息。Step 在 `WaitFor` 里等待这个 Channel，从而消费消息。消息不会跨 Flow run。

<ChannelScopeDiagram markdownDescription="Flow run 拥有一个由其 Step 和 RPC 共享的 FIFO Channel。发布者添加消息，每条消息由一个等待中的消费 Step 消费。" />

<a id="什么时候用-channel"></a>

## 什么时候用 Channel {#when-to-use-a-channel}

Channel 适合 Step 要等待的事件，例如一次审批、用户回复或新的工作项。会被覆盖、多次读取的状态，用 [Attribute](/concepts/primitives/attribute)。可以丢失的实时进度，用 [Stream](/concepts/primitives/stream)。

要等待并行分支完成，用 **Join**；见[等待](/concepts/step#waiting)。

<a id="保证"></a>

## 保证 {#guarantees}

- Dex 把每条消息和 Flow 一起持久化存储。
- 消息保持到达顺序。
- 一条消息由一个 wait 消费。Dex 不会把它复制给其他等待中的 Step。
- 消息可以在 Step 开始等待之前到达。Dex 会保留它，直到之后的 wait 消费它。
- 只有发布消息的 Step 方法或 RPC 成功时，Dex 才会发布这条消息。见 [Step 的保证](/concepts/step#guarantees)。
- 重复的发布请求会把消息存储两次。在消息里放一个业务 key，已经处理过的 key 就跳过。

被取消的 Step 可能把已消费的消息放回 Channel，所以一条消息可能两次到达 `Execute`；Flow 关闭时 Dex 则会丢弃这些消息。在同一个 Channel 上，等待一条消息和等待多条消息的 Step 可能让对方永远等不到。见[被取消的 Step 放回已消费的消息](/reference/server/runtime-data#canceled-step-messages)和[等待者顺序](/reference/server/runtime-data#channel-waiter-order)（英文）。

## 定义、发布和等待 {#persistence-schema}

Channel 有稳定的名字和消息类型。先定义它，再加到 Flow 的 persistence schema。

在这个例子里，start Step 等待 `ApprovalMessages` Channel 上的一条消息，或者一个 Timer。`publishApprovalMessage` RPC 发布审批消息。

这个 Step 还会读取第二个 Channel `QueuedMessages`，但不等待它。它的 `StepOptions` 让 Dex 为 `Execute` 加载这个 Channel 的待处理消息。`Execute` 先检查这些消息，再按 ID 删除它用掉的那条，这样这条消息就不会被再次读到。[管理待处理消息](#manage-pending-messages)解释了这些调用。只做普通等待时，你只需要第一个 Channel 和这个 RPC。

```python
class ChannelWait(Step[int]):
    def __init__(
        self,
        approval_messages: Channel[str],
        queued_messages: Channel[str],
    ) -> None:
        self.approval_messages = approval_messages
        self.queued_messages = queued_messages

    def get_step_options(self) -> StepOptions:
        return StepOptions(execute_load_channels=(self.queued_messages,))

    def wait_for(self, context: Context, input: int) -> Wait:
        return Wait.any_of(
            self.approval_messages.for_one(),
            Timer.by_duration(timedelta(seconds=input)),
        )

    def execute(self, context: Context, input: int) -> StepDecision:
        pending_queued_messages = self.queued_messages.pending_messages(context)
        if pending_queued_messages:
            self.queued_messages.delete(context, pending_queued_messages[0].message_id)
            return graceful_complete(pending_queued_messages[0].value)
        if context.has_timer_fired():
            return graceful_complete("approval timed out")
        approval_message_values = self.approval_messages.results(context)
        return graceful_complete(approval_message_values[0])

class ChannelFlow(Flow[int]):
    approval_messages = Channel("ApprovalMessages", str)

    @rpc
    def publish_approval_message(self, context: Context) -> None:
        self.approval_messages.publish(context, "approved")
```

```go
	QueuedMessages      = dex.DefineChannel[string]("QueuedMessages")
	PrioritizedMessages = dex.DefineChannel[string]("PrioritizedMessages")

func (channelWait) WaitFor(_ dex.Context, input int) (*dex.Wait, error) {
	return dex.AnyOf(
		ApprovalMessages.ForOne(),
		dex.Timer(time.Duration(input)*time.Second),
	), nil
}

func (channelWait) Execute(ctx dex.Context, _ int) (*dex.StepDecision, error) {
	pendingQueuedMessages, err := QueuedMessages.PendingMessages(ctx)
	if err != nil {
		return nil, err
	}
	if len(pendingQueuedMessages) > 0 {
		if err := QueuedMessages.Delete(ctx, pendingQueuedMessages[0].MessageID); err != nil {
			return nil, err
		}
		return dex.GracefulComplete(pendingQueuedMessages[0].Value), nil
	}
	if ctx.HasTimerFired() {
		return dex.GracefulComplete("approval timed out"), nil
	}
	approvalMessageValues, err := ApprovalMessages.GetConditionResults(ctx)
	if err != nil {
		return nil, err
	}
	return dex.GracefulComplete(approvalMessageValues[0]), nil
}

func (*ChannelFlow) PublishApprovalMessage(ctx dex.Context, _ dex.None) (*dex.RPCResult[dex.None], error) {
	if err := ApprovalMessages.Publish(ctx, "approved"); err != nil {
		return nil, err
	}
	return &dex.RPCResult[dex.None]{}, nil
}
```

```rust
static APPROVAL_MESSAGES: LazyLock<Channel<String>> =
    LazyLock::new(|| Channel::new("ApprovalMessages"));

fn wait_for(&self, _context: &mut Context, input: Self::Input) -> HandlerResult<Wait> {
    Ok(Wait::any_of([
        APPROVAL_MESSAGES.for_one(),
        Timer::by_duration(Duration::from_secs(input.max(0) as u64)),
    ]))
}

fn execute(&self, context: &mut Context, _input: Self::Input) -> HandlerResult<StepDecision> {
    let pending_queued_messages = QUEUED_MESSAGES.pending_messages(context)?;
    if let Some(queued_message) = pending_queued_messages.first() {
        QUEUED_MESSAGES.delete(context, &queued_message.message_id)?;
        return Ok(StepDecision::graceful_complete(
            queued_message.value.clone(),
        ));
    }
    if context.has_any_timer_fired() {
        return Ok(StepDecision::graceful_complete(
            "approval timed out".to_owned(),
        ));
    }
    let approval_message_values = APPROVAL_MESSAGES.condition_results(context)?;
    Ok(StepDecision::graceful_complete(
        approval_message_values[0].clone(),
    ))
}

fn publish_approval_message(&self, context: &mut Context) -> HandlerResult<()> {
    APPROVAL_MESSAGES.publish(context, "approved".to_string())
}
```

Timer 分支在读取 Channel 结果之前返回。审批胜出时，Channel condition 已经消费了一条消息，所以第一个结果一定存在。完整示例还会在 persistence schema 中注册这些 Channel，并注册 RPC。

## 等待并消费 {#wait-and-consume}

`WaitFor` 中的 Channel condition 会等到队列里有足够的消息。然后 Dex 按 FIFO 顺序移除选中的消息，作为 Channel results 传给 `Execute`。

| Condition | 何时继续 | 消费什么 |
| --- | --- | --- |
| `ForOne` | 至少有一条消息在队列中。 | 正好一条消息。 |
| `ForN` | 队列中至少有请求的数量。 | 正好这个数量的消息。 |
| `AtLeast` | 队列中至少有请求的数量。 | 当前所有可用消息。 |
| `AtMost` | 立即继续，队列为空时也一样。 | 当前队列中最多请求数量的消息。 |
| `AtLeastAtMost` | 队列中至少有下限数量。 | 当前队列中从下限到上限数量的消息。 |

## 发布消息 {#publish-messages}

在 Step 或 RPC 里，用 handler 的 **Context** 发布。

Worker 之外的代码，例如 web handler，通过调用 Flow 的 RPC 来发布。这样校验、授权和相关的状态变更都留在 Flow 内。RPC 在 Worker 上运行，所以必须有这个 Flow type 的 Worker 已连接，见 [RPC 的保证](/concepts/primitives/rpc#guarantees)。

要在 Worker 离线时存储消息，见[没有 Worker 运行时投递事件](/concepts/client#inbound-commands)。重复的发布会把消息存储两次，所以让消费消息的 Step 能安全处理重复消息；见[最多发送一次命令](/concepts/client#inbound-commands)。

## 管理待处理消息 {#manage-pending-messages}

Dex 接受每条消息时会给它一个 ID。Step 或 RPC 可以加载待处理消息，按 FIFO 顺序读取，并按 ID 删除其中一条。读取不会消费消息。handler 运行时，其他 Step 和 RPC 可能改变队列，所以加载到的列表可能已经过时。

在 Step 或非 transactional RPC 中，删除一条已经不在的消息不会有任何效果。transactional RPC 则会失败，Dex 不保存它的任何修改。从 dexcli 或 Dex Web 直接删除时，会返回 not-found 错误。见 [Pending messages](/reference/server/runtime-data#manage-pending-messages)（英文）。

## ChannelMap {#channelmap}

一个 Flow 需要很多独立队列时，例如每个订单、客户或任务一条，用 **ChannelMap**。ChannelMap 有一个名字和一种消息类型。每个 instance key 有自己的 FIFO 队列。
