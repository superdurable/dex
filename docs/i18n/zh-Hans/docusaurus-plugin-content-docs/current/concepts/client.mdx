# Client

**Client** 是应用在 Worker 之外与 Dex 交互的方式。HTTP handler、后台任务或脚本都通过它调用 Dex。Client 把请求发给 Dex Server。它不运行 Flow 代码，Flow 代码由 Worker 运行。

## 什么时候用 Client

在应用和它的 Flow 之间的边界上使用 Client：

- <a id="启动-flow"></a>**启动** Flow：一个请求开始一个业务流程时。见 [Start a Flow](/reference/server/runtime-client#start-a-flow)。
- <a id="调用-rpc"></a><a id="读写-flow-状态"></a>**调用 RPC**：向 Flow 发送命令，或读取需要 Flow 逻辑的视图。见 [Invoke an RPC](/reference/server/runtime-client#invoke-an-rpc)。
- <a id="read-attributes"></a>**读取 Attribute**：只需要已存储的值时。见 [Read Attributes](/reference/server/runtime-client#read-attributes)。
- **等待**：等 Flow 结束、Step 完成，或 Attribute 达到某个值。
- **搜索**：按 Flow type、状态或已索引的 Attribute 查找 Flow。
- <a id="停止-flow"></a>**运维** Flow：查看、停止、跳过 Timer、更新配置或 Time Travel。停止 Flow 见 [Stop a Flow](/reference/server/runtime-client#stop-a-flow)。

## 从 API 服务启动 Flow {#start-from-an-api-service}

Client 按已注册的定义启动 Flow。它用这份注册来确定 Flow type，并编码启动输入和 RPC 参数。所以启动 Flow 的服务也要构建 Flow 对象。Client 从不运行 Step，这些对象也就从不调用它们的服务，用替身即可。[快速开始](/quick-start) 就是这样做的：它的启动程序用一个从不会被调用的 mock API 构建 Flow。每个 Client 进程还会打开自己的 [blob cache](/components/application#blob-cache)。

## 没有 Worker 时投递事件 {#deliver-without-a-worker}

SDK 发送命令的方式是 RPC。RPC 在 Worker 上运行。如果 10 秒内没有该 Flow type 的 Worker 接手，调用方会收到 **Unavailable** 错误，而且什么都不会保存。

FlowService 请求 `PublishToChannel` 在没有 Worker 连接时也会把 Channel 消息保存在 server 上。Worker 再次运行时，等待中的 Step 会被唤醒。SDK Client 没有提供这个请求。可以通过 gRPC 或 **dexcli api call PublishToChannel** 调用。目前重复发布不会被丢弃，见 [限制](/intro/limits)。

## 一个命令最多处理一次 {#inbound-commands}

Dex 目前会再次执行重复的命令。调用方在响应丢失后重试的 RPC 会再运行一次，重复的 `PublishToChannel` 会把消息投递两次。

按所有 Worker 都停止时必须成立的条件选择方式：

- **RPC** 立即应答并可以返回值，但需要有正在运行的 Worker。
- **`PublishToChannel`** 在没有 Worker 连接时也会保存命令，等待中的 Step 之后再处理它。

在 Dex 丢弃重复之前，请在 Flow 里丢弃它们。让调用方为每个命令生成一个请求 ID，并随 RPC 参数或 Channel 消息一起发送。把 Flow 已经处理过的 ID 保存在一个 Attribute 或 AttributeMap 里。处理命令的 RPC 或 Step 先检查这份记录，对已经处理过的 ID 什么也不做。如果有多个 Step 或 RPC 可能同时处理命令，就给这份记录[加锁](/concepts/primitives/attribute#locking)。

[限制](/intro/limits#requests-that-can-repeat) 跟踪计划中的修复。

## 和其他原语的关系 {#related-primitives}

- [Flow](/concepts/flow)：`StartFlow` 用你选择的 **Flow ID** 创建 Flow run。Flow ID 是业务身份，例如订单号。Dex 创建 Run ID。之后的调用都用 Flow ID 指定 Flow。
- [RPC](/concepts/primitives/rpc)：通过 RPC 修改运行中的 Flow。要修改 Attribute、AttributeMap、Channel 或 ChannelMap 状态，为每个命令定义一个 typed RPC，再用 `InvokeRPC` 调用。这样 validation、authorization、lock 和 transaction 都留在 Flow 内。
- [Attribute](/concepts/primitives/attribute)：`GetAttributes` 直接从 server 读取已存储的值，不需要 Worker 运行。如果读取需要 Flow 内的 validation、authorization、Channel 消息、派生视图或 Attribute lock，改用 RPC。
- [Step](/concepts/step)：`WaitForStepCompletion` 阻塞到 Step 完成。`WaitForAttributeMatch` 阻塞到 Attribute 达到某个值。需要等 Flow 有了进展再响应请求时，使用它们。见 [响应式更新](/design-patterns/responsive-update)。
- [Stream](/concepts/primitives/stream)：Stream 把进度等实时更新推给 UI。它是 best effort。重要的结果要重新读取持久化状态。
- 搜索：`SearchFlows` 用搜索查询查找 Flow，例如按 Flow type 或某个已索引的 Attribute。`DescribeFlow` 读取一个已知 Flow ID 的状态。

## 保证

- `StartFlow` 返回时，Dex 已经保存了这个 Flow。即使你的进程退出，它也会继续运行。
- `GetAttributes` 返回的值是 Dex 在同一时刻一起保存的。它不会返回 Dex 还没有保存的修改。
- 等待检查的是 Flow 已保存的状态。条件满足、Flow 关闭或请求超时到期时，它就返回。之后再调用，会从当前状态重新开始等待。
- 要判断发生了什么，读取 Flow 结果或业务状态。等待结束只是一个检查点，不是最终结果。
- 返回“Flow 正在关闭”的错误，不能证明之前的请求已经成功。再次操作前，先读取 Flow 已存储的状态。
