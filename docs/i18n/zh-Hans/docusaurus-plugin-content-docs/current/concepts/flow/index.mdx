# Flow

**Flow** 是 Dex 中最顶层的工作单元。一个 Flow type 描述一类业务流程，比如订单、订阅或审批。一个 Flow run 是它的一个实例，比如 42 号订单。

Dex 负责 Flow 的生命周期和状态。你的代码不需要数据库或任务队列，就能让流程在崩溃和重启之后继续运行。

## 什么时候用 Flow {#when-to-use}

每个需要由 Dex 管理流程的业务身份，用一个 Flow。共享这个身份和生命周期的工作，放进同一个 Flow 的 [Step](/concepts/step)。一个 Flow 里的 Step 可以并行运行。

工作有自己的 owner 和生命周期时，启动另一个 Flow。两个 Flow 之间通过调用对方的 RPC 协作。父 Step 要等待子 Flow 时，用 [SubFlow](/concepts/primitives/subflow)，例如把复杂逻辑拆成更小的 Flow，或者 fan out 工作。

## 保证 {#guarantees}

一个 Flow ID 同一时间最多只有一个 active run。每个 Step 保存什么、什么时候可能再运行，见 [Step 的保证](/concepts/step#guarantees)。

## Flow 包含什么 {#implement-a-flow}

在你的语言里实现 **Flow** interface，就定义了一个 Flow。它声明三样东西：

- <a id="steps"></a>**Steps**：start Step，以及 Flow 能到达的其他所有 Step。[Step](/concepts/step) 执行后台工作。
- <a id="persistence-schema"></a>**Persistence schema**：保存 Flow 持久化状态的 [Attribute](/concepts/primitives/attribute) 和 [Channel](/concepts/primitives/channel)。读写未声明的名称会被 Dex 拒绝。
- <a id="rpc-handlers"></a>**RPC handlers**：client 在运行中的 Flow 上调用的方法。见 [RPC](/concepts/primitives/rpc)。

start Step 的 input type 也是 Flow 的 start input type。下面这个 Flow 有两个 Step、一个 Attribute、一个 Channel 和一个 RPC。

## 生命周期 {#lifecycle}

[Client](/concepts/client) 用一个 Flow ID 和 start input 启动 Flow。Dex 随后在 Worker 上运行 start Step。每个 Step 返回一个决定：进入下一个或多个 Step，或者关闭 Flow。同一时间可以有多个 Step 处于 active。

Flow 在以下情况下关闭：

- 某个 Step 完成 Flow，或让它失败；
- 它的 timeout 让它失败或取消它；
- client 停止它；
- 用同一个 Flow ID 的新启动终止它；见[新启动关闭 Flow](/reference/server/runtime-data#flow-close-by-new-start)。

timeout 也可以不让 Flow 失败或取消，而是运行一个 handler，由它决定结果。handler 运行时，活跃的 Step 继续运行。handler 提交 force-complete 或 force-fail 决策时，Dex 开始关闭 Flow。handler 的提交可能晚于截止时间。Flow 运行期间，client 通过它的 RPC 读取和修改它。

## 有自己身份的子 Flow {#child-flows}

有些子任务需要自己的业务身份。人们按它自己的编号查找、重试或停止它，或者由别的系统启动它。把这样的任务建模为独立的顶层 Flow。父 Flow 的一个 Step 通过 Client 启动它，使用稳定的 Flow ID 和 request ID。SubFlow 不适合这里，因为 Dex 从父 Flow 推导 SubFlow 的 ID。

父 Flow 持久地接收每个子 Flow 的结果：

- 子 Flow 在一个 Step 里把结果提交到 Attribute，下一个 Step 再通过 RPC 向父 Flow 报告，这个 RPC 发布到一个 Channel。报告 Step 不能在结果提交之前运行，所以这两个 Step 保持默认的 SYNC durability；见 [Durability](/reference/python/step-options#durability)（英文）。报告带一个稳定的 request ID。也可以让父 Flow 的一个轮询 Step 等待子 Flow 的终态。
- 父 Flow 为每个子 Flow 保留一条记录，以子 Flow ID 为键，结果和终态是分开的字段。报告或读取补上缺的字段，重复的报告不改变任何东西。
- 业务编号就是子 Flow ID。同一个启动请求重发时保留它的 request ID。有意重开是一次新的启动请求，使用新的 request ID。它使用允许所需的前次关闭状态、同时拒绝正在运行的 run 的 ID 复用策略；见 [ID 复用策略](/reference/go/start-flow-options#flow-id-request-id-and-already-started)（英文）。父 Flow 是否把读取、报告和停止对应到自己认领的 run ID，是一项业务决定。当业务可能在父 Flow 仍在等待时用同一个编号重开子 Flow，而父 Flow 不能混用不同的 run 时，父 Flow 这样对应。一个子 Flow 编号只有一个 run 时，Flow ID 就够了。这样对应的父 Flow 只接受带有被认领 run ID 的报告。它按 run ID 读取、等待和停止被认领的 run。带 run ID 的 client 调用作用于那个 run，即使已经有更新的 run；已关闭的 run 保留它的终态和 Attribute 值。更新的 run 是另一次尝试，父 Flow 按业务策略处理。
- 同一个逻辑请求的每次启动都推导出相同的 Flow ID 和 request ID。另一个逻辑请求仍可能用同一个 Flow ID 启动 run，即使来自同一个入口或同一个父 run。这时启动会报告 Flow 已经启动。一定要处理这个结果：读取那个 run，只有保存的业务身份匹配时才跟踪它。不匹配时，记录一条被拒绝的接纳；父 Flow 在任何报告里都把它列为被拒绝，但从不等待、计数或停止它。被拒绝是一个独立的状态，不是已结束或已失败。只有当业务身份到子 Flow ID 的映射保证只有同一逻辑请求的重放会再次启动它时，才可以跳过身份核验。有人按子 Flow 自己的编号重试或启动它时，这个保证就不成立。
- 每个子 Flow 有自己的 Flow timeout。它是启动选项，所以每个启动者都要设置它。需要报告超时的子 Flow 用会报告的 timeout handler，而不是 Timer Step。父 Flow 关闭时不会停止它的子 Flow。
- client 以取消、失败或终止的方式停止子 Flow 后，子 Flow 不会再启动新的 handler，所以它可能永远不会报告。带被认领 run ID 的 client 停止只停止那个 run，从不影响更新的 run。被认领的 run 已经关闭时，停止会报告找不到 Flow，表示它已经停止。不带 run ID 的停止作用于这个 Flow ID 正在运行的 run。正在运行的 handler 可以忽略取消，所以已经发出的报告仍可能到达。
- 被停止的子 Flow 怎样结束与父 Flow 无关时，父 Flow 停止子 Flow 后直接往下走。只需要达到所需数量的父 Flow，也这样停止剩下的子 Flow。
- 父 Flow 的结果或后续动作取决于被停止的子 Flow 怎样结束时，例如要统计它的结果、撤销它的副作用或展示它的结局，父 Flow 根据子 Flow 存储的状态对它对账。下面的步骤适用于跟踪被认领 run 的父 Flow。按 Flow ID 跟踪的父 Flow 则对账该 Flow ID 的最新 run。停止成功、停止被拒绝，或用于检查未报告子 Flow 的定时器触发后，父 Flow 先按 run ID describe 被认领的 run。找不到被认领的 run 时，例如它的数据在保留期后已被删除，按业务策略记录，比如 "unavailable"。被认领的 run 仍在运行时，稍后再读。被认领的 run 已关闭时，记录终态和那个 run 里存储的结果。其他错误直接返回，让 Step 重试。停止之后仍然到达的报告补进同一条记录。在达到所需数量之后、或在父 Flow 停止其余子 Flow 期间结束的子 Flow，按业务规则决定是否计入父 Flow 的结果。

[有业务标识的子 Flow](/design-patterns/subflows/child-flows-with-business-identity) 模式用可运行的代码展示这些规则的一种变体。它的报告 RPC 在锁内直接写父 Flow 的记录，而不是发布到 Channel。启动时发现单号已经被启动，它记录为 `rejected`，而不是读取那个 run 再比对身份。

## 标识符 {#identifiers}

"Flow" 这个词可以指 Flow 定义，也可以指一次 Flow run。下面这些标识符把它们区分开。

| 标识符 | 谁设置 | 含义 |
|--------|--------|------|
| `FlowType` | 应用（Flow 实现） | Dex 路由 Worker 调用和搜索结果使用的稳定类型名。 |
| **Flow ID** | 应用在 start 时 | 一次 Flow run 的业务身份。ID reuse policy 控制能否用同一个 Flow ID 再启动一个 run。 |
| **Run ID** | Dex Server | 这个 Flow ID 的一次 run 的身份。Time Travel 保留它，并创建一个新的 run 尝试。请用 Flow ID 定位 Flow。只有要定位某一个确切的 run 时才加上 Run ID，比如被认领的子 Flow run。 |
| `StepType` | 应用（Step 实现） | Flow 内一个 Step 定义的稳定名称。 |
| `StepExecutionID` | Dex Server | 某个 Step 类型的一次执行，格式为 **StepType-Number**。 |

大多数 SDK 默认用语言里的类型名作为 `FlowType`，你也可以显式覆盖。还有 Flow run 在运行时，不要改这些名称。

每个 Flow 类型和 Step 类型都按业务领域命名。一个 `StepType` 对多个输入做同一种工作。不同种类的工作，比如调用不同的服务，用各自的 Step 类型，这样图上能看出它们，每种也能有自己的选项。

## Start options 和配置 {#start-options}

用稳定的业务 Flow ID 启动；要让重试安全，设置 request ID 和 already-started 选项。[StartFlow 最佳实践](/reference/python/start-flow-options#start-flow-best-practices)给出安全重试的做法，[StartFlowOptions](/reference/python/start-flow-options) 列出所有启动选项（Python 参考；每个 SDK 的参考都有同名页面）。`FlowConfig` 保存运行时设置，Flow 运行期间可以更新。
