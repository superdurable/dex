# 故障透明性证明

Dex 有一个经计算机检查的证明，讲的是遇到故障的 Flow。在下面列出的条件下，故障除了让外部副作用重复之外，不会带来任何可观察到的变化。本页说明这个证明讲了什么、依赖哪些假设，以及它对你的代码意味着什么。完整论证见论文。

- [下载论文（PDF）](/papers/dex-expressiveness.pdf)
- [GitHub 上的形式化源码](https://github.com/superdurable/dex/tree/main/formal)

## 结论 {#the-claim}

这个证明覆盖以下故障：

- server 崩溃，然后从持久日志恢复；
- 备用 server 接管；
- Step 方法的一次 attempt 失败，例如 Worker 报错、超时或 Worker 断开，然后 Dex 重试；
- Dex 已经放弃某次 attempt，Worker 却还在继续运行它；
- Worker 的结果到达两次，或在它的 attempt 被替换之后才到达；
- 客户端再次发送同一个 **StartFlow** 请求。

证明把 Flow 在这些故障下产生的事件，与同一个 Flow 在没有故障时产生的事件相比较。它分三部分。

- **有故障时的每个事件序列，都是一个无故障的序列加上重复。** 从目前为止的事件中去掉每个重复的外部副作用。剩下的，是这个 Flow 在没有故障时、对同样的请求（去掉 **StartFlow** 重试）能产生的序列。
- **每个无故障的序列仍然都可能发生。** 有故障的运行只要恰好没有出故障，就能产生它。
- **对公平的运行，结局不变。** 取一次有故障的公平运行的完整事件序列，它要满足[证明依赖的假设](#what-the-proof-assumes)末尾列出的条件。去掉重复。结果是一次以相同方式结束的无故障公平运行的完整事件序列：完成、卡住或一直运行。反方向只在客户端没有发送 **StartFlow** 重试时得到证明。

重复的副作用从来不是新的。它是同一个 Step 方法先前某个副作用的精确副本。

[表达能力证明](/concepts/correctness-and-expressiveness/expressiveness-proof)覆盖没有故障的运行。对于那门小型并发语言中格式良好（well-formed）的程序，两个证明可以组合。这样的程序在 Dex 上运行时，产生的是一次无故障运行的事件，只是外部副作用可能重复。在那一侧，证明只知道每个多出来的副作用与先前某个副作用的值相同。

## 为什么重复仍然简单 {#why-repeats-stay-simple}

一个 Step 方法可能分几次 attempt 运行。每次 attempt 读到的状态都相同：Dex 在第一次 attempt 时取状态快照，之后每次重试都复用它。hard-delete Attribute 是例外：Dex 在每次 attempt 时都重新读取它们，证明不覆盖它们。

证明假设 Step 方法的代码是 Dex 交给它的输入的函数。它不能以改变副作用的方式读取外部世界，也必须不关心自己是第几次 attempt。这样，每次 attempt 都会以相同的顺序算出相同的外部副作用。

一次 attempt 依次产生它的副作用。所以这些副作用首次出现时，按列表顺序出现。任何 attempt 都可能先产生某个副作用，包括 Dex 已经放弃的旧 attempt。这个副作用此后的每个副本都是重复。没有哪次 attempt 能产生新的副作用，或改变它们的顺序。

## 这对你的代码意味着什么 {#what-it-means-for-you}

一次重试可能再次执行 Step 方法的外部调用。较旧的 attempt 也可能迟到：在较新的 attempt 已经做过同一个调用之后，它才发出这个调用。证明只保证：每个多出来的外部调用，都重复了先前的某个调用。

所以，请让每个外部调用既能安全地重复，也能安全地迟到。一种常见做法是使用幂等键（idempotency key），由外部系统按它去重。用 Flow 的这次运行、Step 执行、方法和副作用来构造它。[Step 的保证](/concepts/step#guarantees)对键有更多说明。

证明覆盖一部分客户端重试，不覆盖另一部分：

- **StartFlow** 重试在以下条件下被覆盖：复用第一次启动的 request ID；第一次启动和重试都设置了返回已有运行的选项；Flow 使用默认的 ID 复用策略。重试还必须在 server 的日志中排在 Dex 清除已关闭的运行之前。先到达 server 并不够。见[启动选项](/concepts/flow#start-options)。
- 响应丢失后再次发送的 **PublishToChannel** 请求是第二个请求，可能把消息发布两次。通过 RPC request ID 只发布一次的做法已在计划中，见 [issue 1519](https://github.com/superdurable/dex/issues/1519)。
- 不带 run ID 的 **StopFlow** 重试，可能停掉同一 Flow ID 较新的一次运行。传入 run ID 的做法已在计划中，见 [issue 1520](https://github.com/superdurable/dex/issues/1520)。

## 证明依赖的假设 {#what-the-proof-assumes}

证明在以下条件下成立。超出这些条件，一次运行可能与任何无故障的运行都不同。

- **与表达能力证明相同的范围。** 一个 Flow 启动一次，并接收 Channel 消息。故障下的 RPC、SubFlow、**StopFlow** 和 Attribute 锁不在覆盖范围内。
- **只覆盖 SYNC 方法。** **ASYNC** 方法可能在 server 崩溃时丢失它的启动。它随后会在新的快照上再次运行，所以副作用可能不同。
- **重试不会用完。** 重试用完时，Dex 会让 Flow 失败。没有故障时，Flow 只有在它自己的代码决定失败时才会失败。server 长时间停机可能耗尽重试时间。
- **没有失败策略。** 失败后继续执行的策略会改变接下来运行什么。
- **代码不关心自己是第几次 attempt。** 副作用和结果不能依赖 attempt 编号、第一次 attempt 的时间、上一次错误或上一次心跳值。从心跳检查点恢复的代码不在证明范围内。
- **没有不可重试的错误。** 不可重试的错误会立即结束重试。
- **每个 attempt 命令都标明它的任务。** server 给已启动 attempt 的每个命令（例如它的结果、心跳或失败）标上运行它的任务。证明假设日志中每个这类命令都带有这个标记。
- **单个 server 上时钟不回退。** server 先检查某个 Timer 是否到期，然后给触发它的命令打时间戳。在这两步之间，它的时钟不能回退。
- **Timer 按顺序触发。** 证明假设每次触发都先取最早到期的 Timer。它们按到期时间排序，同时到期的 Timer 按固定的顺序排序。在一个很短的窗口内，真实的 server 可能先触发一个 Timer，而另一个更早到期的 Timer 仍在等待。两个证明都不覆盖这个窗口。
- **同一时刻只有一个 server。** 备用 server 接管在覆盖范围内。多个 server 同时拥有同一批 Flow 则不在范围内。

关于运行如何结束的部分对公平的运行成立。公平的运行满足这些条件：

- outcome word 中的每个请求都会按顺序得到最终结果。outcome word 按最终结果的顺序列出客户端请求。在得到任何结果之前就丢失的请求不在其中。
- server 的时钟会无限增长。
- 故障只发生有限多次，而且每次崩溃后 server 都会恢复。
- 一直处于已设置且已到期状态的 Timer 最终会触发。
- server 在线时，一直可以启动的 Step 方法最终会启动。
- 每个 Worker 任务，包括已被放弃的，最终都会结束或被丢弃。
- 每个已结束的结果最终都会提交或被忽略。
- 每个被崩溃中断的 attempt 最终都会得到处理，或被之后的崩溃清除。

## 证明没有说什么 {#what-it-does-not-say}

- 它不能阻止外部调用重复。上一节说明了怎样让重复变得安全。
- 它不涉及真实时间。按 server 的时间戳，Timer 绝不会提前触发。但时钟走快的 server 仍可能提前触发它。
- 它不涉及再次发送 **PublishToChannel** 的客户端。
- 它没有说任何重复模式都可能出现。重复遵循上文“为什么重复仍然简单”一节所述的顺序。
- 关于运行如何结束，反方向只在没有 **StartFlow** 重试时得到证明。一次重试会推进 server 的时钟，所以可能改变哪个 Timer 先到期。

## 如何验证 {#how-it-was-checked}

- **对故障的精确描述。** 每条故障规则都写了下来，并注明实现它的 server 代码。评审者对照代码逐条检查了这些规则。
- **经计算机检查的证明。** 证明用 Lean 证明助手写成，它检查每一步。
- **先测试，再证明。** 一个 fuzzer 遍历了随机的运行，其中有崩溃、重试和迟到的 attempt。它在每一步都检查论证是否成立。
- **示例和反例。** 证明助手检查了带有崩溃、重试和迟到的重复副作用的示例运行，证明适用于它们。它还检查了违反某条假设的运行，例如读取 attempt 编号的代码，并说明这时结论不成立。
