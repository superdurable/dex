# Workflow Patterns 评估

Workflow Patterns 是一组业务流程中反复出现的行为。它们由 Workflow Patterns Initiative 定义，由 Wil van der Aalst 和 Arthur ter Hofstede 主导。研究者用它们比较 BPMN、BPEL、YAWL 等 workflow 语言和引擎。每个模式都有 ID、名称和精确定义。定义见 [control-flow patterns](http://www.workflowpatterns.com/patterns/control/)。

本页按 43 个 control-flow 模式（WCP-1 到 WCP-43）为 Dex 评级。data、resource 和 exception-handling 模式不在本页评估范围内。

## 评级标准 {#rating-scheme}

评级沿用已发表评估的标准。

- **+** 表示直接支持。一个 Dex 构件就满足定义的每一部分，应用无需为它保存额外状态。
- **+/-** 表示部分支持。该模式需要应用自己做记账，例如为汇合发布 Channel 信号、Attribute 计数、锁、RPC 检查或 reset Step；或者定义中的某一部分只能以受限形式成立。
- **-** 表示不支持。

## 为什么许多汇合是部分支持 {#why-many-joins-are-partial}

Flow 没有原生的"等待另一个 Step 完成"。因此汇合要等待各分支发布的 Channel 信号，分支数也由应用提供。这种记账让大多数汇合成为 **+/-**。当工作在子 Flow 中运行时，用 **AllOf** 等待 **SubFlow** 就是原生的汇合。

## 评级如何验证 {#how-the-ratings-were-checked}

每个模式都有 TypeScript、Python、Go、Java 和 Rust 五种语言的可运行示例。每个示例都有针对真实 Dex Server 的集成测试，测试断言该模式的定义行为。例如，Deferred Choice 的测试同时发送两个相互竞争的响应，并检查恰好只有一个分支运行。

## 汇总 {#summary}

- 19 个模式直接支持（**+**）。
- 24 个模式部分支持（**+/-**）。
- 没有不支持（**-**）的模式。

## 部分支持 {#partial-support}

每个 **+/-** 评级都有原因。

- **WCP-3、WCP-7、WCP-13、WCP-14、WCP-33、WCP-37 和 WCP-41**（汇合）。各分支发布 Channel 信号，汇合 Step 等待一定数量的信号。Flow 没有原生的"等待 Step 完成"。
- **WCP-9、WCP-30 和 WCP-34**（structured 和 static partial join）。第 k 轮的分支向第 k 轮的 ChannelMap 实例发布信号。汇合在前 n 个信号到达时触发；reset Step 消费其余信号，然后开始下一轮。迟到的信号永远不会计入后面的轮次。
- **WCP-28 和 WCP-31**（blocking join）。定义写道："Subsequent enablements of incoming branches are blocked until the Blocking Discriminator has reset."信号同样按轮次存放。第 k 轮 reset 之前，没有 Step 等待第 k + 1 轮，所以下一轮的信号只会排队，不产生任何效果。reset Step 仍然是记账。
- **WCP-15 和 WCP-36**（事先不知道数量的多实例）。RPC 添加实例，Attribute 记录数量。汇合 Step 在每个结果之后重新等待，直到条件成立。
- **WCP-17 和 WCP-40**（interleaved routing）。一个共享的 Attribute lock 让各任务不重叠。这个锁只覆盖一个 **Execute**，不覆盖 **WaitFor**，也不覆盖跨多个 Step 的任务。
- **WCP-18**（Milestone）。Step 无法检查其他分支的状态。Attribute 标记 milestone，RPC 只在该 Attribute 成立时启动任务。
- **WCP-20**（Cancel Case）。只用 Client **StopFlow** 会让正在运行的 SubFlow 继续运行。所以启动 SubFlow 的 Step 同时等待一个取消 Channel。收到取消后，它用 **SubFlow.getFlowId** 读取子 Flow 的 ID，停止子 Flow，再返回 **ForceFail**。**ForceFail** 会取消其他所有活动 Step。
- **WCP-23**（Transient Trigger）。Channel 消息会一直排队，直到被 Step 消费。因此由 **WaitFor** 记录有 Step 正在等待；RPC 在共享 Attribute lock 下只接受一次触发，其余的丢弃。
- **WCP-29、WCP-32 和 WCP-35**（cancelling join）。Channel 信号汇合触发后，其 decision 按 Step type 取消其余分支。
- **WCP-38**（General Synchronizing Merge）。定义要求在"it is not possible that any branch that has not yet been enabled will be enabled at any future time"时触发汇合，而且应由汇合点根据流程结构自行判断。在 Dex 中，这一判断由应用在每次 **GoTo** 时做出：Attribute 记录仍能到达汇合点的线程数，把它降到 0 的那次提交发布一条哨兵消息，汇合 Step 等待这条消息。
- **WCP-39**（Critical Section）。Attribute lock 只覆盖一个 Step 方法。由多个 Step 组成的区段改用只含一条消息的 Channel 作为令牌。

## 评级依据的行为 {#what-the-ratings-rest-on}

评级依赖以下 Dex 行为。

- **GracefulComplete** 只在没有活动 Step 时关闭 Flow。
- **DeadEnd** 只结束一个分支，从不关闭 Flow。
- **ForceComplete** 立即关闭 Flow，并取消其他 Step。
- **AnyOf** 只消费被选中条件的消息。
- Channel 消息一直排队，直到被 Step 消费。
- decision 或 RPC 按 Step type 取消 Step。取消是协作式的。
- 同一时间只有一个 Step 方法或 RPC 持有某个 Attribute lock。
- 父 Flow 关闭后，SubFlow 会继续运行。

这些概念见 [Step](/concepts/step)、[Channel](/concepts/primitives/channel) 和 [SubFlow](/concepts/primitives/subflow)。
