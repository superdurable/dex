# Workflow Patterns 评估

Workflow Patterns 是一组业务流程中反复出现的行为。它们由 Workflow Patterns Initiative 定义，由 Wil van der Aalst 和 Arthur ter Hofstede 主导。研究者用它们比较 BPMN、BPEL、YAWL 等 workflow 语言和引擎。每个模式都有 ID、名称和精确定义。定义见 [control-flow patterns](http://www.workflowpatterns.com/patterns/control/)。

本页按 43 个 control-flow 模式（WCP-1 到 WCP-43）为 Dex 评级。data、resource 和 exception-handling 模式不在本页评估范围内。

## 评级标准 {#rating-scheme}

评级沿用已发表评估的标准。

- **+** 表示直接支持。一个 Dex 构件就满足定义的每一部分，应用无需为它保存额外状态。
- **+/-** 表示部分支持。该模式需要变通做法，例如 Attribute 计数、RPC 检查、reset Step 或 SubFlow；或者定义中的某一部分只能以受限形式成立。
- **-** 表示不支持。

## 评级如何验证 {#how-the-ratings-were-checked}

每个评为 **+** 或 **+/-** 的模式都有可运行的示例。每个示例都有针对真实 Dex Server 的集成测试，测试断言该模式的定义行为。例如，Deferred Choice 的测试检查只有最先到达的响应所对应的分支会运行。示例提供 TypeScript、Python、Go、Java 和 Rust 五种语言。

## 汇总 {#summary}

- 31 个模式直接支持（**+**）。
- 12 个模式部分支持（**+/-**）。
- 没有不支持（**-**）的模式。

## 部分支持 {#partial-support}

每个 **+/-** 评级都有原因。

- **WCP-9、WCP-30 和 WCP-34**（structured 和 static partial join）。汇合本身是 **ForN** 等待。Channel 消息会一直排队，迟到的分支可能再次触发汇合，所以需要额外的 reset Step 先消费它们。
- **WCP-28 和 WCP-31**（blocking join）。每个分支需要自己的 Channel。reset Step 等待其余分支。下一轮的信号会一直排队，直到 reset 结束。
- **WCP-15 和 WCP-36**（事先不知道数量的多实例）。一次等待只能等固定数量的消息。RPC 添加实例，Attribute 记录数量。汇合 Step 在每个结果之后重新等待，直到条件成立。
- **WCP-18**（Milestone）。Step 无法检查其他分支的状态。Attribute 标记 milestone，RPC 只在该 Attribute 成立时启动任务。
- **WCP-20**（Cancel Case）。Client **StopFlow** 取消所有活动 Step，Flow 以 canceled 状态关闭。但父 Flow 关闭后，正在运行的 SubFlow 会继续运行，需要用它自己的 Flow ID 单独停止。
- **WCP-23**（Transient Trigger）。Channel 消息会一直排队，直到被 Step 消费。因此由 **WaitFor** 记录有 Step 正在等待；没有 Step 等待时，RPC 丢弃触发。
- **WCP-38**（General Synchronizing Merge）。Flow 内没有构件能等到"不再有分支会到达"。改用 SubFlow 包住这段区域：SubFlow 在其中所有 Step 都无法再运行时关闭。所有进入汇合点的路径都必须位于该区域内。
- **WCP-39**（Critical Section）。Attribute lock 只覆盖一个 Step 方法。由多个 Step 组成的区段改用只含一条消息的 Channel 作为令牌。

## 评级依据的行为 {#what-the-ratings-rest-on}

评级依赖以下 Dex 行为。

- **GracefulComplete** 只在没有活动 Step 时关闭 Flow。
- **DeadEnd** 只结束一个分支，从不关闭 Flow。
- **ForceComplete** 立即关闭 Flow，并取消其他 Step。
- **AnyOf** 只消费被选中条件的消息。
- Channel 消息一直排队，直到被 Step 消费。
- decision 或 RPC 按 Step type 取消 Step。取消是协作式的。
- 同一时间只有一个 Step 方法或 RPC 持有某个 Attribute lock。

这些概念见 [Step](/concepts/step)、[Channel](/concepts/primitives/channel) 和 [SubFlow](/concepts/primitives/subflow)。
