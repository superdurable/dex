# 部署代码变更

Flow 可能保持打开几天甚至几个月，所以新代码经常会遇到在旧代码下启动的 Flow。这一页介绍怎样安全地修改代码，以及修复之后怎样重新运行 Flow。

<CodingAgentBox prompt="按照 https://docs.superdurable.io/zh-Hans/concepts/change-flow-code.md 检查我对 Dex Flow 的修改对还没结束的 run 是否安全。只读：不要部署、停止或重新运行任何东西。" />

## 部署会改变什么 {#what-a-deploy-changes}

- **Step 运行接手它的那个 Worker 的代码。** Dex 不会重放之前的 Step。已经在某个 Step 中等待的 Flow，条件满足时运行新的 `Execute`。
- **滚动部署把每个调用交给具备它的 Worker。** 缺少某个 Step 类型或 RPC 的 Worker 会拒绝它，Dex 把调用交给另一个 Worker，这次 Step 尝试不会被用掉。见 [Routing and availability](/reference/server/workers#routing-and-availability)（英文）。
- **已经在等待的 Step 保持旧的条件。** 新的 `WaitFor` 代码只适用于部署之后才开始的 Step 执行。要改变旧 Step 等待的内容，向它的 Channel 发布消息，或者跳过它的 Timer。

[故障转移和部署](/concepts/failover-and-deploys)列出部署和故障转移期间哪些会重新运行。

## Flow 代码的版本管理 {#versioning-flow-code}

Dex 根据记录下来的状态决定 Flow 下一步做什么，而不会重新运行你之前的 Step 代码。所以部署修改后的代码永远不会导致 replay 错误。但你仍然要让未结束的 Flow 在部署前后都能正常工作。它们可能遇到改变了的业务规则、缺失的 Step 实现、改名的 RPC，或者不兼容的数据。

### 在 Flow 启动时锁定业务行为 {#lock-business-behavior-at-flow-start}

在 Flow 启动时保存一个业务版本值，例如一个 Attribute，或启动状态里的一个字段。根据这个保存的值分支，而不是根据当前处理调用的 Worker 构建版本。已有的 Flow 保持旧的行为；部署之后，新的 Flow 可以使用新的行为。

当改动会改变某个决定、支付规则、重试策略、截止时间或其他客户能看到的含义时，用这种方式。只部署新代码是不够的，因为长时间运行的 Flow 之后可能会调用新部署的 Worker。

### 示例：给 Charge 加一笔费用 {#versioning-example}

[订单处理](/use-cases/order-processing) 中的订单 Flow 按订单金额扣款。一条新规则增加了一笔手续费。已经打开的订单必须保持旧的价格。

1. **在启动时记录版本。** 新的启动 handler 在启动 Flow 时把一个 Attribute（例如 **pricing-version**）设为 2。更早启动的 Flow 没有这个值，表示版本 1。
2. **根据保存的值分支。** **Charge** 读取 **pricing-version**。版本 1 只扣订单金额，版本 2 扣订单金额加手续费。已经在 **Ship** 中等待的 Flow 永远不会再运行 **Charge**，所以它不受影响。
3. **为改变的契约添加 Step 类型。** 假设退款现在需要一个旧 Flow 从未保存过的新输入字段。添加一个新的 Step 类型，例如 `RefundWithFee`，并且只从版本 2 转到它。为版本 1 的 Flow 保留 **Refund**。
4. **两者一起部署。** 一个 Worker 构建同时包含带分支的 **Charge**、**Refund** 和 `RefundWithFee`。在滚动部署期间，缺少 `RefundWithFee` 的旧 Worker 会把这个调用交给新 Worker。
5. **退役旧路径。** 当没有未结束的 Flow 处于版本 1 时，删除版本 1 的分支和 **Refund**。先搜索这样的 Flow。如果 **pricing-version** 是建了索引的 Attribute，搜索时除了 Flow type，还可以按它过滤。

保存的 Attribute 决定 Flow 走哪条路径，与哪个 Worker 构建处理它无关，所以 Step 代码不需要版本标记。

### 以增量方式演进数据和契约 {#evolve-data-and-contracts-additively}

添加可选字段。读取 payload 的代码必须能处理旧 run 没有设置的字段，并忽略更新的组件发送的未知字段。为缺失的字段提供安全的默认值，并保持已有字段值原来的含义。对于不兼容的 payload 或输出契约，引入新的 Step 类型或 RPC 名称，而不是悄悄修改旧的。

如果较新的 Worker 无法解码保存的输入或 Attribute，这次尝试会因解码错误失败，和 Step 方法抛出的任何错误一样。每次重试都会以同样的方式失败，所以重试窗口结束时（默认 4 小时）Step 失败，并应用它的失败策略。默认情况下，Flow 随后失败。Dex Web 在尝试上显示错误类型和信息。修复代码，然后用 [Time Travel](#time-travel) 重新运行这个 Step。

要在重试窗口结束前发现这种情况，每次部署后观察 Dex Server 的 `dexzd_step_attempt_failures_total` 指标，过滤 `failure_kind="worker_error"`。解码错误和其他 Step 错误一样计入这里。这个指标没有 Step 类型标签，所以要在 Dex Web 中打开失败的尝试，查看是哪个 Step、哪个错误。见 [Metrics](/reference/server/metrics)（英文）。

### 保留旧定义，直到旧 Flow 结束 {#keep-old-definitions-until-old-flows-finish}

只要还有未结束的 Flow 可能调用某个 Flow type、Step 类型或 RPC 实现，就保持它以原来的名字注册。把新定义和旧定义一起部署。新的 Flow 通过两种方式之一到达新定义：根据启动时保存的版本分支的决定转到新的 Step 类型，或者新代码启动一个新的 Flow type。在重试和任何经过批准的 Time Travel 恢复期间，都要让旧实现保持可用。

在删除旧定义之前，搜索旧的 Flow type，确认没有正在运行、等待、重试或可恢复的终止状态 Flow 还需要它。把搜索结果和变更记录放在一起。具体的查询取决于你的搜索字段。先按 Flow type 搜索：

~~~bash
dexcli flow search --query 'FlowType = "OldFlowType"'
~~~

只有在结果为空，或者剩下的每个 Flow 都有明确批准的退役计划之后，才删除旧代码。

### 部署前检查 {#check-before-you-deploy}

要用未结束的 Flow 测试新的 Worker 构建，运行下面这些检查：

1. **列出这个类型的未结束的 Flow。** 搜索正在运行的 Flow，以及它们正在等待的 Step 类型。`ActiveStepTypes` 是一个内置的搜索字段。

   ~~~bash
   dexcli flow search --query 'FlowType = "OrderFlow" AND ExecutionStatus = "Running"'
   dexcli flow search --query 'FlowType = "OrderFlow" AND ActiveStepTypes = "Ship"'
   ~~~

2. **确认新构建注册了这些 Flow 可能到达的每个 Step 类型和 RPC。** 缺少某一个的 Worker 会把调用交给另一个 Worker。如果所有 Worker 都没有，Step 会在队列中等待，RPC 会失败。
3. **用旧构建启动的 Flow 运行新构建的集成测试。** [测试你的 Flow](/components/testing) 介绍测试环境的搭建。快速开始的重启测试是可以照搬的模板：它在 Flow 中途停止一个 Worker，再用另一个 Worker 完成这个 Flow。做版本检查时：
   1. 检出旧构建。用它启动一个 Worker，启动 Flow，等每个 Flow 到达你关心的 Step，可以用 `wait_for_step_completion` 或搜索 `ActiveStepTypes`。
   2. 优雅地停止这个 Worker。
   3. 用新构建对同一个 Dex Server 启动一个 Worker。用 `skip-timer` 跳过 Timer，发送 Flow 正在等待的消息，然后等每个 Flow 结束。
   4. 检查每个 Flow 的结果和 Attribute，并确认新构建没有产生解码错误。

按上面的步骤运行这些检查。

## 用 Time Travel 恢复 Flow {#time-travel}

Time Travel 把一个 Flow run 移回它历史中更早的某个点，从那里重新运行。在你为失败的 Step 部署修复之后使用它。这次 run 保留原来的 Run ID，并开始一次新的尝试。

那个点之后的 Step 会再运行，它们的外部调用也会再执行。每个外部调用都需要一个[幂等键](/concepts/step#idempotency-keys)，这样重复调用才不会产生效果。

Time Travel 把 run 的状态恢复成那个点时的样子，并且默认会再应用一次那个点之后进入 run 的输入。[用 Time Travel 恢复 Flow](/components/operate-and-debug#time-travel)介绍怎样运行它以及它的选项。
