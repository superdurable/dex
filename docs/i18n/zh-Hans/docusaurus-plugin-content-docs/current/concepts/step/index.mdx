# Step

**Step** 是 [Flow](/concepts/flow) 里的一个后台工作单元。它可以先 durable 地等待某件事发生，再执行工作，然后决定下一步运行什么。Dex 在你的 Worker 上运行 Step，并记录每个结果。

Step 由一个原生 struct 或 class 实现，它的类型就是 `StepType`。同一个 Step type 在一个 Flow 里可以运行多次，甚至并行运行。每次运行是一个 `StepExecution`，用 `StepExecutionID` 标识，比如 **Charge-2**。

## Step input {#step-input}

每次 Step execution 都有自己带类型的输入，Dex 把它和这次 execution 一起保存。输入用来区分同一个 Step type 的不同 execution。起始 Step 的输入就是 Flow 的启动输入。

## WaitFor 和 Execute {#waitfor-and-execute}

一个 Step 有一个或两个方法。

- `WaitFor` 可选。它返回一个 durable 的 **Wait**。Dex 保存这个 wait，替你检查条件，条件满足后调用 `Execute`。
- `Execute` 必需。它执行工作，并返回一个 `StepDecision`。

Step 没有 `WaitFor` 时，`Execute` 立即运行。

## 等待 {#waiting}

等待不占用 Worker 或线程。Dex 把它保存在 Flow 的状态里，条件满足时唤醒 Step。Step 可以等待三类条件：

- [Timer](/concepts/primitives/timer) 触发；
- [Channel](/concepts/primitives/channel) 上有消息到达；
- [SubFlow](/concepts/primitives/subflow) 完成。

用 `AnyOf` 或 `AllOf` 组合条件。`AnyCombinationOf` 在几组条件中任意一组全部满足时成立。等待结束后，`Execute` 可以读取满足它的结果，比如它消费的 Channel 消息。见 [Waits](/reference/python/waits)。

要等待并行分支，用 **Join**。它不是另一类条件：它等待的是各分支上报结果的 [ChannelMap](/concepts/primitives/channel#channelmap)。见 [等待并行 Step](/design-patterns/parallel/await)。

## StepDecision {#stepdecision-movements}

`Execute` 返回一个 `StepDecision`。它可以进入下一个 Step，也可以同时进入多个 Step。分支、循环和并行工作都这样构建。`GoTo` 用 Step type 指定下一个 Step，并传入它的输入。由 Flow 注册的该 Step type 实例来运行它。

<StepDecisionMovementsDiagram markdownDescription="GoTo：ExampleStep 返回 GoTo(Complete Flow)，完成 Flow。GoToMany：ExampleStep 启动 StepA 和 StepB，两者并行运行。循环：ExampleStep 转到 ProcessStep，ProcessStep 再回到 ExampleStep。" />

决定也可以关闭 Flow 或结束一个分支：

- `GracefulComplete` 请求 Dex 在没有其他 active Step 时完成 Flow。
- `ForceComplete` 立即完成 Flow。
- `ForceFail` 立即让 Flow 失败。
- `DeadEnd` 结束这个分支，但不关闭 Flow。

完成类的决定可以返回 Flow output，client 把它作为 Flow result 读取。多个完成类的决定都返回 output 时，result 会保留每一个。只有最终完成的 Flow 才保留这些 output。如果 Flow 没有完成（失败、被取消、被终止或超时），它的 result 不含任何 output。

决定还可以取消其他 active Step。见 [Parallel Steps](/design-patterns/parallel) 和 [Parallel SubFlows](/design-patterns/parallel-subflows) 模式。

## StepOptions {#stepoptions}

Step 返回 `StepOptions`，控制它的方法如何运行。`WaitFor` 和 `Execute` 各有自己的设置。

- **Timeout** 限制方法的一次 attempt。
- **Retry policy** 在 attempt 失败后再次运行同一个方法。
- <a id="waitfor-failure-policy"></a><a id="execute-failure-policy"></a><a id="step-failed-事件与-last-failure-info"></a>**Failure policy** 决定重试用完之后怎么办。默认让 Flow 失败。`Execute` 可以改为进入一个 recovery Step，`WaitFor` 可以继续执行 `Execute`。见 [WaitFor failure policy](/reference/python/failure-and-retries#waitfor-failure-policy)、[Execute failure policy](/reference/python/failure-and-retries#execute-failure-policy) 和 [Last failure info](/reference/python/failure-and-retries#last-failure-info)。
- **Durability** 决定 Dex 什么时候存储结果。默认的 **SYNC** 在下一步工作开始前存储。**ASYNC** 更快，但 server 故障可能让方法再运行一次。见 [SYNC 和 ASYNC Step](#sync-and-async)。
- **Heartbeat** 让长时间运行的方法报告进度并保存 checkpoint。
- **State loading** 和 **Attribute locks** 决定方法加载哪些状态、锁住哪些 Attribute。

`StepDecision` 可以为某一次 Step execution 覆盖这些选项。

不设置 StepOptions 时，每个方法使用 server 的默认值。所有 SDK 的默认值都一样：

| 设置 | 默认值 |
| --- | --- |
| 方法超时（单次 attempt） | 2 小时 |
| Heartbeat 超时 | 1 分钟 |
| 重试次数 | 在总时长内不限次数 |
| 重试总时长 | 从第一次交给 Worker 起 4 小时 |
| 重试退避 | 1 秒起，每次翻倍，最多 100 秒 |
| Durability | SYNC |
| Failure policy | 让 Flow 失败 |

SDK 参考中的 [Timeouts and total duration](/reference/go/step-options#timeouts-and-total-duration)（英文）说明这些限制怎样相互作用。

## 保证 {#guarantees}

简而言之：完成的工作会被保存，没完成的工作可能重复。

最重要的有四条：

- **已经完成的 Step 不会再运行。** Dex 把它的结果和转到下一个 Step 的动作一起保存。
- **被中断的 Step 可能再运行一次。** 崩溃、超时或重试，可能让一个已经调用过外部系统的方法再运行一次。所以 Step 至少运行一次，而不是恰好一次。下一节说明怎样让这件事安全。
- **重试看到的是第一次 attempt 的状态。** `Execute` 的重试复用第一次 attempt 的状态快照，看不到之后写入的 Attribute。要等待这样的写入，让写入方发布一条 Channel 消息，并在下一个 Step 的 `WaitFor` 里等待它。hard-delete Attribute 是例外：Dex 在每次 attempt 时都会重新读取它们。见 [短期 secret](/concepts/primitives/attribute#hard-delete-attributes)。
- **并行写入可能互相覆盖。** 两个先读后写同一个 Attribute 的 Step 或 RPC 需要在它上面加 lock。细节见下文。

### 幂等键 {#idempotency-keys}

每个会改变外部状态的调用（例如付款或发邮件）都要带上幂等键。执行这个效果的服务用这个键丢弃重复请求。用每次 attempt 都不变的值来构造键：

- Flow 只调用一次时，用 Flow ID 加调用的名字，例如 **charge-order-1042**；
- 同一个 Flow 里这个 Step 会运行多次时，用 Flow ID 加 `StepExecutionID`，例如 `order-1042/Charge-2`。

不要在键里使用 attempt 编号、时间或随机值，它们在重试时会变。其他页面都链接到这里，而不是重复这条规则。

### Dex 保存什么 {#what-dex-saves}

简而言之：一个方法的写入会一起保存，但它们和其他 Step 及 RPC 之间没有隔离。

Dex 单独保存每次 `WaitFor` 或 `Execute` 调用。它把这次调用的 Attribute 写入和 Channel 发布与结果一起保存，而且只在方法成功时保存。对外部系统的调用不在这次保存里。

一个 Step 方法的修改会一次全部生效。但这挡不住其他 Step 和 RPC 同时修改同样的状态。方法读到的是 Dex 把它交给 Worker 时的 Flow 状态。在方法的修改生效之前，其他 Step 和 RPC 可能已经改了这些状态。Dex 不检查方法读到的值是否仍然是最新的。所以两个先读后写同一个 Attribute 的 Step 或 RPC，可能互相覆盖对方的更新。要避免这种情况，让它们都在这个 Attribute 上声明 lock。Dex 会让它们依次执行。见 [Attribute lock](/concepts/primitives/attribute#locking)。

### 失败和重新投递 {#failure-and-redelivery-summary}

简而言之：Dex 无法判断一个方法是否完成时，会再运行它，或者告诉你结果未知。

以下情况会让方法重复运行，或让它的结果未知。它们对每个 SDK 都成立：

- **Worker 在方法中途停止。** 这次 attempt 失败，重试策略会再运行这个方法。它的外部调用可能已经发生。server 重启或故障转移时，Worker 手上的每个 attempt 都会这样。
- **heartbeat 没有确认。** heartbeat checkpoint 可能丢失，所以重新运行可能从更早的 checkpoint 开始。
- **被取消的方法会继续运行。** Dex 不会停止它的代码，它的外部调用仍然会生效。
- **ASYNC Step 可能重复一次 attempt。** 见 [SYNC 和 ASYNC Step](#sync-and-async)。
- **重试用完时可能没有答案。** recovery Step 会知道工作肯定没有运行（`NOT_STARTED`），或者可能运行过（`NOT_COMPLETED`）。遇到 `NOT_COMPLETED` 时，先用幂等键在目标系统里检查，再决定是否重复或报告这个效果。

SDK 参考中的 Failure and redelivery 给出每种情况的确切规则（英文）：[Python](/reference/python/failure-and-retries#failure-and-redelivery) · [Go](/reference/go/failure-and-retries#failure-and-redelivery) · [Java](/reference/java/failure-and-retries#failure-and-redelivery) · [TypeScript](/reference/typescript/failure-and-retries#failure-and-redelivery) · [Rust](/reference/rust/failure-and-retries#failure-and-redelivery)。

### SYNC 和 ASYNC Step {#sync-and-async}

Step 的 **durability** 决定 Dex 什么时候保存它的进度。

- **SYNC** 是默认值。Dex 在 Worker 收到任务之前保存每次 attempt 的开始，在 Flow 继续之前保存结果。每一次都要等待写入对象存储。
- **ASYNC** 在保存开始和结果之前，就把任务交给 Worker 并开始后续工作。Dex 把这些写入合并成大约 20 毫秒一批。单个 Flow 跑得更快。如果 Dex Server 节点在写入之前失败，Dex 会在新的状态快照上再运行同一次 attempt，所以它可能读到不同的 Attribute 值。从丢失的结果开始的后续工作也会再运行。

需要最严格保证的效果选 **SYNC**。延迟重要、偶尔重新运行可以接受的短 Step 选 **ASYNC**。适合 ASYNC 的有：快速读取、内部记账，以及已经有幂等键保证可以安全重复的调用。付款、发邮件，或者任何在更新的快照上重新运行可能发出不同参数的调用，都保持 **SYNC**。`StepOptions` 设置单个 Step 的 durability，`FlowConfig` 设置整个 Flow 的。[Performance and Maturity](/intro/performance-and-maturity) 给出两者的实测延迟。

### 取消、完成和顺序 {#cancellation-completion-order}

取消一个 Step，会丢弃它当前方法还没有保存的一切：Attribute 写入、Channel 发布和它的决定。它的 `WaitFor` 已经保存的内容保留。一个决定或 RPC 永远不会取消它自己启动的 Step。被取消的 Step 已经消费的消息会怎样，见 [Channel 的保证](/concepts/primitives/channel#保证)。

Dex 不会强行停止被取消方法的代码。方法应检查取消状态并返回。在它返回之前，它的代码会继续运行。它对外部系统的调用仍然会生效，即使 Flow 已经关闭。

`GracefulComplete` 结束它自己的分支，并请求 Dex 完成 Flow。一旦没有 active Step，Dex 就开始完成 Flow。在此之前，其他 Step 和 RPC 仍然可以启动新的 Step，这些 Step 也会推迟完成。之后某个分支以 `DeadEnd` 结束，也不会撤回这个请求。最后一个 Step 结束后，Dex 还要处理完待写的 Attribute Sync 和已经开始的 transactional RPC，所以 Flow 可能会短暂保持 `RUNNING`。

没有待处理的 `GracefulComplete` 时，一个没有 active Step 的 Flow 会继续运行。RPC 仍然可以在里面启动新的 Step。用一个完成类的决定结束最后一个分支。如果 Flow 不能无限等待，就给它设置 Flow timeout。

Dex 大致按 Step 就绪的顺序启动它们，但不严格保证。不要依赖并行 Step 启动或结束的顺序。顺序重要时，用 Channel 或 Attribute lock。
