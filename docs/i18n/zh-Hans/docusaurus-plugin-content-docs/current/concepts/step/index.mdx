# Step

**Step** 是 [Flow](/concepts/flow) 里的一个后台工作单元。它可以先 durable 地等待某件事发生，再执行工作，然后决定下一步运行什么。Dex 在你的 Worker 上运行 Step，并记录每个结果。

Step 由一个原生 struct 或 class 实现，它的类型就是 **StepType**。同一个 Step type 在一个 Flow 里可以运行多次，甚至并行运行。每次运行是一个 **StepExecution**，用 **StepExecutionID** 标识，比如 **Charge-2**。

## Step input {#step-input}

每个 Step execution 有自己的 typed input，Dex 把它和 execution 一起保存。input 用来区分同一个 Step type 的不同 execution。start Step 的 input 就是 Flow 的 start input。

## WaitFor 和 Execute {#waitfor-and-execute}

一个 Step 有一个或两个方法。

- **WaitFor** 可选。它返回一个 durable 的 **Wait**。Dex 保存这个 wait，替你检查条件，条件满足后调用 **Execute**。
- **Execute** 必需。它执行工作，并返回一个 **StepDecision**。

Step 没有 **WaitFor** 时，**Execute** 立即运行。

## 等待 {#waiting}

等待不占用 Worker 或线程。Dex 把它保存在 Flow 的状态里，条件满足时唤醒 Step。Step 可以等待三类条件：

- [Timer](/concepts/primitives/timer) 触发；
- [Channel](/concepts/primitives/channel) 上有消息到达；
- [SubFlow](/concepts/primitives/subflow) 完成。

用 **AnyOf** 或 **AllOf** 组合条件。**AnyCombinationOf** 在几组条件中任意一组全部满足时成立。等待结束后，**Execute** 可以读取满足它的结果，比如它消费的 Channel 消息。见 [Waits](/reference/python/flows-and-steps/waits)。

## StepDecision {#stepdecision-movements}

**Execute** 返回一个 **StepDecision**。它可以进入下一个 Step，也可以同时进入多个 Step。分支、循环和并行工作都这样构建。

<StepDecisionMovementsDiagram markdownDescription="GoTo：ExampleStep 返回 GoTo(Complete Flow)，完成 Flow。GoToMany：ExampleStep 启动 StepA 和 StepB，两者并行运行。循环：ExampleStep 转到 ProcessStep，ProcessStep 再回到 ExampleStep。" />

决定也可以关闭 Flow 或结束一个分支：

- **GracefulComplete** 在没有其他 active Step 时完成 Flow。
- **ForceComplete** 立即完成 Flow。
- **ForceFail** 立即让 Flow 失败。
- **DeadEnd** 结束这个分支，但不关闭 Flow。

完成类的决定可以返回 Flow output，client 把它作为 Flow result 读取。多个完成类的决定都返回 output 时，result 会保留每一个。只有最终完成的 Flow 才保留这些 output。如果 Flow 没有完成（失败、被取消、被终止或超时），它的 result 不含任何 output。决定还可以取消其他 active Step。被取消的 Step 会放回它的 wait 消费的 Channel 消息，除非这个决定同时用 **ForceComplete** 或 **ForceFail** 关闭 Flow。被这个决定取消的 Step，不会拿到同一个结果发布的消息，除非这个决定也立即关闭了 Flow。见 [Parallel Steps](/design-patterns/parallel) 和 [Parallel SubFlows](/design-patterns/parallel-subflows) 模式。

## StepOptions {#stepoptions}

Step 返回 **StepOptions**，控制它的方法如何运行。**WaitFor** 和 **Execute** 各有自己的设置。

- **Timeout** 限制方法的一次 attempt。
- **Retry policy** 在 attempt 失败后再次运行同一个方法。
- <a id="waitfor-failure-policy"></a><a id="execute-failure-policy"></a><a id="step-failed-事件与-last-failure-info"></a>**Failure policy** 决定重试用完之后怎么办。默认让 Flow 失败。**Execute** 可以改为进入一个 recovery Step，**WaitFor** 可以继续执行 **Execute**。见 [WaitFor failure policy](/reference/python/flows-and-steps/step-options#waitfor-failure-policy)、[Execute failure policy](/reference/python/flows-and-steps/step-options#execute-failure-policy) 和 [Last failure info](/reference/python/flows-and-steps/step-options#last-failure-info)。
- **Durability** 决定 Dex 什么时候存储结果。默认的 **SYNC** 在下一步工作开始前存储。**ASYNC** 更快，但 server 故障可能让方法再运行一次。
- **Heartbeat** 让长时间运行的方法报告进度并保存 checkpoint。
- **State loading** 和 **Attribute locks** 决定方法加载哪些状态、锁住哪些 Attribute。

**StepDecision** 可以为某一次 Step execution 覆盖这些选项。

## 保证 {#guarantees}

每次 **WaitFor** 或 **Execute** 调用是一个独立的提交。Dex 把它的 Attribute 写入和 Channel 发布与结果一起提交，而且只在方法成功时提交。对外部系统的调用不在这个提交里。

提交是原子的，但不是隔离的。方法读到的是 Dex 把它交给 Worker 时已经 commit 的 Flow 状态。在这个方法 commit 之前，其他 Step 和 RPC 可以先 commit。Dex 不检查方法读到的值在 commit 时是否仍然是最新的。所以两个先读后写同一个 Attribute 的 Step 或 RPC，可能互相覆盖对方的更新。让它们都声明同一个 [Attribute lock](/concepts/primitives/attribute#locking)。

一个 Step 方法可能运行不止一次：失败后的重试会再运行它。Dex 不一定知道失败的 attempt 有没有执行工作。请让每个外部副作用都幂等，用 Flow ID 加 StepExecutionID，或你自己的业务 key 作为幂等 key。Dex 无法判断的情况见 [Failure and redelivery](/reference/python/flows-and-steps/failure-and-redelivery)。

重试用完时，recovery Step 能知道工作是肯定没有运行，还是可能运行过。

取消一个 Step，会丢弃它当前方法还没有 commit 的一切：Attribute 写入、Channel 发布和它的决定。它之前的方法已经 commit 的内容保留。一个决定或 RPC 永远不会取消它自己启动的 Step。被取消的 Step 已经消费的消息会怎样，见 [Channel 的保证](/concepts/primitives/channel#保证)。

取消是协作式的。被取消的方法应检查取消状态并返回。在它返回之前，它的代码会继续运行。它对外部系统的调用仍然会生效，即使 Flow 已经关闭。

**GracefulComplete** 结束它自己的分支，并请求 Dex 完成 Flow。一旦没有 active Step，Dex 就开始完成 Flow。待处理的 Attribute Sync 写入或已经接受的 transactional RPC，可能让 Flow 保持 **RUNNING**，直到 Dex 记录关闭。在没有 active Step 之前，其他 Step 和 RPC 仍然可以启动新的 Step，这些 Step 也会推迟完成。这个请求一直有效。之后某个分支以 **DeadEnd** 结束，也不会撤回它。

没有待处理的 **GracefulComplete** 时，一个没有 active Step 的 Flow 会继续运行。RPC 仍然可以在里面启动新的 Step。Dex 不会因为没有 active Step 而关闭 Flow。用一个完成类的决定结束最后一个分支。不能无限等待的 Flow，要设置 Flow timeout。

Dex 大致按 Step 就绪的顺序启动它们，但不严格保证。不要依赖并行 Step 启动或结束的顺序。顺序重要时，用 Channel 或 Attribute lock。
