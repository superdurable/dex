# Dex App Builder

Dex App Builder 是创建 Dex 应用或流程产品的**主要 Skill**。它覆盖完整的过程：梳理业务流程、用 Go、Python、TypeScript、Java 或 Rust 构建后端、在本地测试，最后交付结果。它会问你是否需要自己的 UI、Dex Web 或已发布的 Connector，只加入你选择的部分。它也负责对应用做范围明确的 SDK 工作，例如调试一个 Flow，或添加一个 Step。

## 安装与使用 {#install-and-use}

先[安装 Dex Skills](/build-with-ai/dex-developer-skill#install-and-use-dex-skills)，一次安装全部三个 Skills。然后在编程 Agent中调用这个 Skill，例如在 Codex 中，以及在装了 Plugin 的 Claude Code 中：

```text
$dex-app-builder Design and build an event-registration application.
/superdurable-dex:dex-app-builder Design and build an event-registration application.
```

[安装和使用 Dex Skills](/build-with-ai/dex-developer-skill#install-and-use-dex-skills) 列出了每个 host 的调用方式。

## 何时使用 {#when-to-use-it}

需求包含以下任意一项时，使用 App Builder：

- 梳理或完善业务流程；
- 定义角色、权限、审批、等待、重试和恢复；
- 构建后端，以及你的 UI 或其他调用方使用的应用 API；
- 构建你自己的 UI，或者用 Dex Web 做运维和管理；
- 基于受支持的模板构建新的 Dex 应用；
- 使用已发布的 Connector，或找出缺少的 Connector；
- 从后端到 UI，构建并测试一个完整功能；
- 在还没有具体流程时，先了解并搭建 Dex。

如果只是范围很小的 SDK 任务，App Builder 会跳过产品流程，见 [SDK 工作](#sdk-work)。独立贡献官方 Connector 时，请改用 [Dex Connector Contributor](./dex-connector-contributor.mdx)。

## 入门 Dex {#get-started-with-dex}

App Builder 也可以帮你了解并搭建 Dex。例如这样问它：

```text
$dex-app-builder Help me understand and set up Dex.
```

它先用几句话讲清核心模型，然后安装 `dexcli`。接着它启动 `dexcli dev`，并告诉你 Dex Web 的地址。最后，它问你是从一个示例开始，还是从你自己的流程开始。

## 开始实现前 {#before-implementation}

App Builder 会先确认 coding-agent host 能让它写入 repository 或项目目录、编辑文件、执行命令。

如果不具备这些条件，App Builder 仍然可以梳理流程、设计架构、写出实现方案，但不能创建文件、运行测试、构建产物或部署应用。

## 工作流程 {#workflow}

### 1. 确认业务流程 {#1-confirm-the-business-process}

这个 Skill 先和你讨论，而不是马上写代码。它会弄清楚：

- 谁维护、管理、操作、审批和参与这个流程；
- 每个角色能做哪些操作，每个人工操作需要哪个固定的权限；
- 触发条件、输入、输出、截止时间、等待、重试、恢复、审计，以及哪些数据是敏感的；
- 涉及哪些外部系统，以及每个系统是否要用已发布的 Connector；
- 你需要哪种 UI：你自己的 UI、Dex Web、两者都要，或者都不要；
- 是否已有宿主应用负责用户登录，并把用户角色映射为它信任的权限。

这一步的产出是：一张角色、操作与权限的对照表，一份生命周期方案，你对 UI 和 Connector 的选择，以及你的 UI 或调用方需要的应用 API 操作。所有重要的疑问都会在写代码之前和你确认清楚。

### 2. 设计并实现后端 {#2-design-and-implement-the-backend}

后端是应用的核心。它使用应用所用语言的 Dex SDK：Go、Python、TypeScript、Java 或 Rust。已有的应用沿用它的语言。新应用使用你指定的语言；你没有指定时使用 TypeScript。App Builder 遵循 [SDK 工作](#sdk-work) 中说明的通用 SDK 规则，再加上自己更严格的规则：

- 严格按照 Dex Web 和 Flow Definition Graph 2.0 的渲染要求来写，只使用 [Flow visualization reference](/reference/web/flow-visualization) 为该语言列出的指令；
- 只在 `Execute` 中调用外部 provider；
- `WaitFor` 中不调用 provider，也不修改 Dex 状态；
- 每个人工操作都建模为带明确权限的 typed Action；
- 凭据放在运行环境或 Connector 配置中，不放在应用代码里；
- 对你选择用 Connector 的系统，使用它已发布的能力，不在应用里新增 provider client。

写代码之前，Skill 会先说明 Flow 的标识、typed 输入和输出、Step、状态转换、Attribute、Channel、RPC、Timer、重试、恢复，以及 Connector 的边界。它和 Flow 一起设计应用的 HTTP API 契约，并从契约生成服务端代码。

### 3. 验证并交付 {#3-verify-and-hand-off}

开发过程中，Skill 会运行与每次改动相关的测试。最后运行模板的完整检查，覆盖应用 API、你选择的 UI、生成的代码、生产构建、在真实 Dex Server 上的行为、恢复路径和 FDG 2.0 分析。

交付内容包括：你确认过的产品决定、已实现的功能、确切的测试结果、Connector 发布或贡献的状态，以及已知的限制。工作以一个干净的 Git commit 结束。

## UI 和 Connector 都是可选的 {#ui-and-connectors-are-optional}

App Builder 在确认业务流程时，对下面每一项只问你一次，并且只加入你选择的部分。

| 选项 | 适用情况 | 构建内容 |
| --- | --- | --- |
| **你自己的 UI** | 大多数产品：给你的用户用的页面、参与者门户，或带品牌的应用。 | Skill 基于应用 API 构建 React 和 TypeScript 前端。页面方案还有待定的地方时，它先做出静态线框页面给你确认。 |
| **Dex Web** | 你想要一个现成的运维和管理界面：Run、Work Queue、Action、字段编辑、历史和诊断。 | Skill 加上 Dex Web 读取的 Summary、Display、Action 和权限契约。只有你提出时，你自己的 UI 才会重复这些功能。 |
| **已发布的 Connector** | 流程用到外部系统，例如 Slack 或 Gmail，并且你想用现成的集成。 | Skill 使用已发布 Connector 的 operation 和 Trigger。不用 Connector 时，应用在自己的 Step 代码里调用这个系统。 |

你可以选择自己的 UI、Dex Web，或者两者都要。你自己的 UI 不需要额外的理由。在本地，Skill 工作时 `dexcli dev` 始终会在 Dex Web 中展示你的 Flow。

## 如何处理 Connector 缺口 {#how-connector-gaps-are-handled}

为你选择的 Connector 写集成代码之前，App Builder 会先查看已发布的 Connector 能做什么。如果缺少某个官方 Connector，或者应用需要的 operation、Trigger、配置界面单元缺失或有问题，它会加载 [Dex Connector Contributor](./dex-connector-contributor.mdx)。

贡献还在 review 时，应用可以先用本地的 Connector package 测试。但在这个 Connector 以确切版本发布之前，应用不能进入生产。Skill 绝不会把 branch、commit SHA、pseudo-version 或本地替换作为生产依赖提交。

## SDK 工作 {#sdk-work}

对已有应用做范围明确的技术工作时，App Builder 跳过产品发现以及 UI 和 Connector 的问题，直接进入 Flow 和 SDK 规则。它支持 Python、Go、Java、TypeScript 和 Rust。例如这样问它：

```text
$dex-app-builder Add a reminder Step to this approval Flow.
```

这条路线覆盖：

- Flow、Step、等待、状态转换和失败路由；
- Attribute、AttributeMap、Channel、ChannelMap 和 Stream；
- typed RPC、Timer、SubFlow、Worker 和 Client；
- 重试、超时、heartbeat、durability、lock 和恢复；
- SDK 版本兼容、测试、排错或运维；
- Dex Web、`dexcli`、Flow 可视化和应用可观测性。

这个 Skill 处理的是你的应用，不是 Dex 本身。除非你明确要求它开发 Dex，否则它不会为了解决应用问题去修改 Dex Server。

### 版本与来源 {#version-and-source-authority}

写代码之前，Skill 会先弄清应用的语言、包管理器、已安装的 Dex SDK 版本、Worker 和 Client 如何启动，以及 repository 的测试命令。

Skill 以 repository 源码、lockfile、已安装的 SDK 和对应版本的官方示例为准。除非你要求升级，否则它保留当前安装的版本。如果找不到与该版本完全对应的源码，它只做到与版本无关的 Flow 模型设计为止，不会编造 API。

它只加载你所用语言的 handbook 和任务需要的参考资料，不会把五种语言都加载进来。

### 建模、实现与验证 {#model-implement-and-verify}

对于不简单的改动，Skill 会在修改代码前先写出模型：Flow 的标识、typed 启动输入和完成输出、Step 和状态转换、选项、持久状态、消息、RPC、Timer、失败恢复，以及应用如何调用 Flow。模型使用准确的领域名称，并优先采用官方 Dex 模式，而不是手写的协调循环。

完整的改动包括 typed 输入、输出和失败，Flow 和 Step 定义，持久化 schema 条目，注册与配置，以及针对真实 Dex Server 的集成测试。正在运行的 Flow 会限制哪些名称可以修改。除非你有明确的迁移方案，否则 Skill 会保留现有的 Flow、Step、Attribute、Channel、Stream 和 RPC 名称。

### 诊断与运维 {#diagnostics-and-operations}

诊断问题时，Skill 默认只读。它可以查看 Dex Web、`dexcli`、SDK 错误和应用日志。未经你授权，它不会 stop、Time Travel、publish、invoke、删除、编辑或以其他方式修改 Flow。

## 预期结果 {#expected-result}

App Builder 完成后，你会得到：

- 确认过的流程和权限模型；
- 用所选语言构建的 Dex 应用，以及它的应用 API；
- 你选择的 UI：你自己的 UI、Dex Web、两者都要，或者都不要；
- 本地运行和真实 Dex Server 的测试证据；
- 仍然阻碍上线的 Connector 发布清单（如果有）；
- 可以直接 review 的 repository。
