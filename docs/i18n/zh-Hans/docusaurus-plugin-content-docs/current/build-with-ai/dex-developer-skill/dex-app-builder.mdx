# Dex App Builder

Dex App Builder 是创建 Dex 应用或流程产品的**主要 Skill**。它覆盖完整的过程：梳理业务流程、选择 UI、构建 Go 后端、在本地测试，最后交付结果。

## 安装与使用 {#install-and-use}

先[安装 Dex Skills](/build-with-ai/dex-developer-skill#install-and-use-dex-skills)，一次安装全部三个 Skills。然后在编程 Agent中调用这个 Skill，例如在 Codex 中，以及在装了 Plugin 的 Claude Code 中：

```text
$dex-app-builder Design and build an event-registration application.
/superdurable-dex:dex-app-builder Design and build an event-registration application.
```

[安装和使用 Dex Skills](/build-with-ai/dex-developer-skill#install-and-use-dex-skills) 列出了每个 host 的调用方式。

## 何时使用 {#when-to-use-it}

需求包含以下任意一项时，使用 App Builder：

- 梳理或完善业务流程；
- 定义角色、权限、审批、等待、重试和恢复；
- 判断 Dex Web 是否够用，还是需要自定义 UI；
- 基于受支持的模板构建新的 Dex 应用；
- 使用已发布的 Connector，或找出缺少的 Connector；
- 从 UI 到后端，构建并测试一个完整功能。

如果只是范围很小的 SDK 调试，或者独立贡献官方 Connector，请直接调用 [Dex SDK](./dex-sdk.mdx) 或 [Dex Connector Contributor](./dex-connector-contributor.mdx)。

## 开始实现前 {#before-implementation}

App Builder 会先确认 coding-agent host 能让它写入 repository 或项目目录、编辑文件、执行命令。

如果不具备这些条件，App Builder 仍然可以梳理流程、设计架构、写出实现方案，但不能创建文件、运行测试、构建产物或部署应用。

## 工作流程 {#workflow}

### 1. 确认业务流程 {#1-confirm-the-business-process}

这个 Skill 先和你讨论，而不是马上写代码。它会弄清楚：

- 谁维护、管理、操作、审批和参与这个流程；
- 每个角色能做哪些操作，每个人工操作需要哪个固定的权限；
- 触发条件、输入、输出、截止时间、等待、重试、恢复、审计，以及哪些数据是敏感的；
- 涉及哪些外部系统，需要哪些已发布 Connector 的能力；
- 是否已有宿主应用负责用户登录，并把用户角色映射为它信任的权限。

这一步的产出是：一张角色、操作与权限的对照表，一份生命周期方案，一个 UI 决定，以及一张所需 Connector 能力的清单。所有重要的疑问都会在写代码之前和你确认清楚。

### 2. 选择应用界面 {#2-choose-the-application-surface}

App Builder 在两种管理流程的方式中选一种：

| 模式 | 适用情况 | 构建内容 |
| --- | --- | --- |
| **Dex Web** | Run、Work Queue、搜索、字段和 Action 已经能满足用户需要。 | Dex Web 就是流程界面。应用只额外提供一个不含业务页面的小外壳，以及供外部系统调用的接口。 |
| **Custom UI** | 产品需要 Dex Web 没有的业务页面或交互。 | Skill 先用模拟数据做出 React 和 TypeScript 原型。你试用并确认后，才接入真实后端。 |

默认使用 Dex Web。模板里留下的 Hello World 页面或生成的 API client，本身不能成为构建自定义 UI 的理由。

### 3. 设计并实现 Flow {#3-design-and-implement-the-flow}

后端使用受支持的应用模板和 Dex Go SDK。App Builder 会加载 [Dex SDK](./dex-sdk.mdx) 获取通用的 SDK 规则，再加上自己更严格的规则：

- 应用后端使用 Go；
- 严格按照 Dex Web 和 Flow Definition Graph 2.0 的渲染要求来写；
- 只在 `Execute` 中调用外部 provider；
- `WaitFor` 中不调用 provider，也不修改 Dex 状态；
- 每个人工操作都建模为带明确权限的 typed Action；
- 凭据放在 Connector 或运行环境中，不放在应用代码里；
- 使用已发布 Connector 的能力，不在应用里新增 provider client。

写代码之前，Skill 会先说明 Flow 的标识、typed 输入和输出、Step、状态转换、Attribute、Channel、RPC、Timer、重试、恢复，以及 Connector 的边界。

### 4. 验证并交付 {#4-verify-and-hand-off}

开发过程中，Skill 会运行与每次改动相关的测试。最后运行模板的完整检查，覆盖所选的 UI 模式、生成的代码、生产构建、在真实 Dex Server 上的行为、恢复路径和 FDG 2.0 分析。

交付内容包括：你确认过的产品决定、已实现的功能、确切的测试结果、Connector 发布或贡献的状态，以及已知的限制。工作以一个干净的 Git commit 结束。

## 如何处理 Connector 缺口 {#how-connector-gaps-are-handled}

写集成代码之前，App Builder 会先查看已发布的 Connector 能做什么。如果缺少某个官方 Connector，或者应用需要的 operation、Trigger、配置界面单元缺失或有问题，它会加载 [Dex Connector Contributor](./dex-connector-contributor.mdx)。

贡献还在 review 时，应用可以先用本地的 Connector module 测试。但在这个 Connector 以确切版本发布之前，应用不能进入生产。Skill 绝不会把 branch、commit SHA、pseudo-version 或本地替换作为生产依赖提交。

## 预期结果 {#expected-result}

App Builder 完成后，你会得到：

- 确认过的流程和权限模型；
- 在 Dex Web 和自定义 UI 之间的明确选择；
- 基于受支持模板的 Go Dex 应用；
- 本地运行和真实 Dex Server 的测试证据；
- 仍然阻碍上线的 Connector 发布清单（如果有）；
- 可以直接 review 的 repository。
