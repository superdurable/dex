# 客户退款

客户申请退款。Flow 检查订单和退款政策，金额较大时等待经理审批，然后退款并通知客户。本页包含这个流程的三个 Flow：一个适合先读的短 Flow，以及两个更大的 Go Flow。

**SDK：** Python、TypeScript、Java 和 Rust（经理审批的退款）、Go（确定性策略和 agentic 审核）

## 经理审批的退款 {#refund-with-manager-approval}

Northstar Studio 在一次服务中断后，申请退还一笔 1,249.00 USD 的订阅续费。`CustomerRefundFlow` 运行八个 Step，分为 Intake、Evidence、Control、Resolution 和 Close 几组。

<DocsFlowDefinitionGraph graph={readableFlow} />

这张图来自 Python 示例。TypeScript 示例的 Step、分组、Attribute、Channel 和跳转都相同。它的 RPC 名为 `approveRefund` 和 `rejectRefund`。它的 **Check policy** 只有一条拒绝分支，而不是两条。

**Check policy** 应用退款政策。超过 30 天的扣款，或没有记录到服务中断的扣款，会被拒绝。超过 1,000 USD 的金额进入 **Request manager approval**，较小的金额直接退款。**Request manager approval** 在一个 Channel 上等待一条消息，再按经理的决定退款或拒绝。

```java
    final class CheckPolicy implements Step<RefundCase> {
        @Override
        public Class<RefundCase> getInputType() {
            return RefundCase.class;
        }

        @Override
        public StepDecision execute(final Context context, final RefundCase input) {
            final Order order = input.order();
            final boolean outsideWindow = order.daysSinceCharge() > REFUND_WINDOW_DAYS;
            final boolean noOutage = order.outageHours() == 0;
            if (outsideWindow || noOutage) {
                CASE_STATUS.set(context, "denied");
                final String note;
                if (outsideWindow && noOutage) {
                    note = "The charge is outside the 30-day window and no outage was recorded.";
                } else if (outsideWindow) {
                    note = "The charge is outside the 30-day window.";
                } else {
                    note = "No outage was recorded for this order.";
                }
                return StepDecision.goTo(WriteCustomerMessage.class, input.withOutcome("denied", note));
            }
            if (order.amountUsd() > MANAGER_APPROVAL_LIMIT_USD) {
                CASE_STATUS.set(context, AWAITING_MANAGER);
                return StepDecision.goTo(RequestManagerApproval.class, input);
            }
            return StepDecision.goTo(IssueRefund.class, input);
        }
    }

    /** Wait for a manager to approve or reject the refund. */
    final class RequestManagerApproval implements Step<RefundCase> {
        @Override
        public Class<RefundCase> getInputType() {
            return RefundCase.class;
        }

        @Override
        public Wait waitFor(final Context context, final RefundCase input) {
            return Wait.until(MANAGER_DECISIONS.forOne());
        }

        @Override
        public StepDecision execute(final Context context, final RefundCase input) {
            final ManagerDecision decision = MANAGER_DECISIONS.getConditionResults(context).get(0);
            if (decision.approved()) {
                return StepDecision.goTo(IssueRefund.class, input);
            }
            CASE_STATUS.set(context, "denied");
            return StepDecision.goTo(
                    WriteCustomerMessage.class, input.withOutcome("denied", decision.reason()));
        }
    }
```

```typescript
class CheckPolicy implements Step<RefundCase> {
  public getStepType(): string {
    return "CheckPolicy";
  }

  public execute(context: Context, input: RefundCase): StepDecision {
    const order = input.order;
    const windowExpired = order.daysSinceCharge > REFUND_WINDOW_DAYS;
    const noOutage = order.outageHours === 0;
    if (windowExpired || noOutage) {
      caseStatus.set(context, "denied");
      const notes = [
        windowExpired ? WINDOW_EXPIRED_NOTE : "",
        noOutage ? NO_OUTAGE_NOTE : "",
      ];
      return goTo(WriteCustomerMessage, { ...input, outcome: "denied", note: notes.join(" ").trim() });
    }
    if (order.amountUsd > MANAGER_APPROVAL_LIMIT_USD) {
      caseStatus.set(context, AWAITING_MANAGER);
      return goTo(RequestManagerApproval, input);
    }
    return goTo(IssueRefund, input);
  }
}
```

```rust
impl Step for CheckPolicy {
    type Input = RefundCase;

    fn execute(&self, context: &mut Context, input: Self::Input) -> HandlerResult<StepDecision> {
        let order = &input.order;
        let mut denial_reasons = Vec::new();
        if order.days_since_charge > REFUND_WINDOW_DAYS {
            denial_reasons.push("The charge is outside the 30-day refund window.");
        }
        if order.outage_hours == 0 {
            denial_reasons.push("No service outage was recorded for this charge.");
        }
        if !denial_reasons.is_empty() {
            CASE_STATUS.set(context, CaseStatus::Denied)?;
            let note = denial_reasons.join(" ");
            let denied = ResolvedCase::new(input, RefundOutcome::Denied, note);
            return Ok(StepDecision::go_to(
                &WriteCustomerMessage::new(&self.services),
                denied,
            ));
        }
        if order.amount_cents > MANAGER_APPROVAL_LIMIT_CENTS {
            CASE_STATUS.set(context, CaseStatus::AwaitingManager)?;
            return Ok(StepDecision::go_to(
                &RequestManagerApproval::new(&self.services),
                input,
            ));
        }
        Ok(StepDecision::go_to(
            &IssueRefund::new(&self.services),
            input,
        ))
    }
}

impl Step for RequestManagerApproval {
    type Input = RefundCase;

    fn wait_for(&self, _context: &mut Context, _input: Self::Input) -> HandlerResult<Wait> {
        Ok(Wait::until(MANAGER_DECISIONS.for_one()))
    }

    fn execute(&self, context: &mut Context, input: Self::Input) -> HandlerResult<StepDecision> {
        let decision = MANAGER_DECISIONS
            .condition_results(context)?
            .into_iter()
            .next()
            .ok_or_else(|| HandlerError::new("MissingManagerDecision", "no manager decision"))?;
        if decision.approved {
            return Ok(StepDecision::go_to(
                &IssueRefund::new(&self.services),
                input,
            ));
        }
        CASE_STATUS.set(context, CaseStatus::Denied)?;
        let denied = ResolvedCase::new(input, RefundOutcome::Denied, decision.reason);
        Ok(StepDecision::go_to(
            &WriteCustomerMessage::new(&self.services),
            denied,
        ))
    }
}
```

一个批准 RPC 和一个拒绝 RPC 把经理的决定发布到这个 Channel。每个 RPC 都要求填写原因，并在发布之前检查 `case-status` 是否为 `awaiting-manager`。在 Python 和 TypeScript 示例中，每个 RPC 还声明了一个 Dex Web Action：**Approve refund** 或 **Reject refund**。只有 `case-status` 为 `awaiting-manager` 时，Dex Web 才提供这两个 Action。

这个示例还包含生产环境的退款需要的几项内容：

- **Issue refund** 和 **Send message** 向 billing 和 email 传入幂等 key。Time Travel 点之后的 Step 会再次运行，这些 key 保证退款和邮件都只有一次。前提是所有 Worker 共用本地 fake 服务的同一份持久账本。
- **Issue refund** 遇到支付超时，每 5 秒重试一次。一个运行可以先要求两次超时。这时 Dex Web 中最后一个 **Issue refund** 事件显示第 3 次尝试成功，并保留最近一次失败的详情。
- 在 Python 和 TypeScript 中，Worker 上传 `dexcli visualize` 生成的设计，所以 Dex Web 会在每个运行上绘制这张图。
- 在 Python 和 TypeScript 中，提供 payload key 文件时，Worker 和 Client 会加密 payload。`case-status` 和 `customer-email` 保持可读。

Java 和 Rust 示例用各自的 `decide` 命令批准或拒绝退款。Java 和 Rust SDK 不能声明 Dex Web Action，也不能加密 payload。`dexcli visualize` 只读取 Go、Python 和 TypeScript 源码，所以这两个示例的 Worker 不上传设计，它们的运行在 Dex Web 中没有 **Design** 视图。

[Python](https://github.com/superdurable/dex/tree/main/examples/python/dex_examples/products/customer_refund)、[TypeScript](https://github.com/superdurable/dex/tree/main/examples/typescript/src/products/customer-refund)、[Java](https://github.com/superdurable/dex/tree/main/examples/java/src/main/java/io/superdurable/dex/products/customerrefund) 和 [Rust](https://github.com/superdurable/dex/tree/main/examples/rust/src/products/customer_refund) 的示例文件夹列出了每个场景的命令：审批、先失败后成功的退款、用 Time Travel 修复缺失的 billing 调用。Python 和 TypeScript 文件夹还展示了加密。

## 确定性策略

Go 中的 `CustomerRefundFlow` 运行七个 Step。它先确认订单存在，再应用 30 天规则。调用支付 provider 之前，它会先记录幂等 key。如果 provider 拒绝退款，或者结果未知，Flow 会把这个结果记为 case 状态。

<DocsFlowDefinitionGraph graph={deterministicFlow} />

Summary 展示 charge reference、请求金额和 recommendation。Display 额外展示证据、计费结果和可编辑的 operator note。这个 Flow 有意不声明任何 Action，用来说明 Action 列表为空的 Flow 在 Dex Web 中同样有效。

## Agentic 审核

`AgenticCustomerRefundFlow` 在一个由 Step 组成的循环里收集证据。随后由 guardrail 决定：要么自动执行决定，要么等待经理审批。每次等待经理审批都有自己的 gate key。Flow 会先记录要执行的操作，再执行 billing、subscription 和 customer-message 操作。这些操作都是幂等的。

<DocsFlowDefinitionGraph graph={agenticFlow} />

批准 Action 直接显示为按钮，不需要输入。拒绝 Action 要求填写原因。Dex Web 会自动填入一个隐藏的 gate key，取自详情页打开时读到的 Attribute 值。RPC 发布 verdict 之前，会把这个 key 与当前 gate 比较。如果 gate 已经变了，RPC 会返回错误，操作员需要刷新页面。

两个 Action 也会读取当前 case status。Flow Definition Graph 2.0 中的可见性条件只控制按钮是否出现，不做权限控制。
