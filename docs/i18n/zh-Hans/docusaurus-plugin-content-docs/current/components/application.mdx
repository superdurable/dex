# 你的应用

Dex 应用就是你部署的代码。它包含两部分：

- **Worker** 承载 Flow 定义。Dex 分配工作时，它运行 `WaitFor`、`Execute` 和 RPC handler。
- **Client** 启动 Flow、调用 RPC、读取 Attribute 和搜索 Flow。见 [Client](/concepts/client)。

一个进程可以只运行 Worker，只运行 Client，也可以两者都运行。

<a id="与其他组件的关系"></a>

## 与其他组件的关系 {#how-it-fits-with-the-other-components}

Worker 和 Client 连接 Dex Server。每个 Worker 都是拉取模式 Worker：它主动向 server 建立出站任务流，从不监听调用。因此 Worker 不需要开放入站端口，可以运行在 NAT 或防火墙后面。

Dex 把所有 Flow、SubFlow、Step 和 RPC 调用都发给你的 Worker，不需要配置 Worker 地址。[Dex Web](/components/web) 或 `dexcli` 启动的 Flow 也在你的 Worker 上运行。

Worker 启动时，可以把它的 Flow 的 Flow Definition Graph 发布到 server。Dex Web 从 server 读取它们，画出每个 Flow。

<a id="启用拉取模式"></a>

## 在现有服务中加入 Dex {#add-to-a-service}

Dex 是加进你服务里的一个库，不是包在服务外面的框架。安装你所用语言的 SDK：

~~~bash
pip install dex-python-sdk==1.45.0                       # Python
go get github.com/superdurable/dex/sdk-go@v1.45.0        # Go
npm install @superdurable/dex@1.45.0                     # TypeScript
cargo add dex-sdk@=1.45.0                                # Rust
~~~

Java 项目在 Gradle 或 Maven 构建中加入 Maven Central 上的 `io.superdurable:dex-sdk:1.45.0`。

这些命令固定的是快速开始所用的版本。每个快速开始示例的构建文件里都写着同样的版本：[Python](https://github.com/superdurable/dex/blob/main/examples/python/quick-start/pyproject.toml)、[Go](https://github.com/superdurable/dex/blob/main/examples/go/quick-start/go.mod)、[Java](https://github.com/superdurable/dex/blob/main/examples/java/quick-start/build.gradle)、[TypeScript](https://github.com/superdurable/dex/blob/main/examples/typescript/quick-start/package.json) 和 [Rust](https://github.com/superdurable/dex/blob/main/examples/rust/quick-start/Cargo.toml)。SDK 和 Dex Server 只要协议范围有重叠就能一起工作，与版本号无关；[Upgrades](/reference/server/upgrades)（英文）说明了这条规则。

Worker 可以运行在两个地方：

- **在你的服务进程里。** 和 HTTP server 一起启动，[订单处理](/use-cases/order-processing) 示例就是这样。一次部署既处理请求，也运行 Step。
- **在单独的进程里。** 如果 Step 需要和 API 不同的扩容方式、资源或发布节奏，就单独部署。[快速开始](/quick-start) 的 Worker 就是这样运行的。

无论哪种方式，Worker 只发起出站连接，所以不需要负载均衡器或入站端口。你的 handler 创建 Client 来启动 Flow、调用 RPC。[Dex 和你的数据库](/components/your-database) 说明 Step 怎样写入你服务已有的数据库。[测试你的 Flow](/components/testing) 介绍怎样用真实的 Dex Server 测试它们。

## 新建项目 {#start-a-new-project}

每种语言的 [快速开始](/quick-start) 文件夹都是一个完整的小项目。把你所用语言的文件夹（例如 `examples/python/quick-start`）从仓库里复制出来，就能开始自己的项目。每份副本都包含同样的部分：

| 部分 | Python | Go | Java | TypeScript | Rust |
| --- | --- | --- | --- | --- | --- |
| 固定版本的 SDK | `pyproject.toml` 和 `uv.lock` | `go.mod` 和 `go.sum` | `build.gradle` | `package.json` 和 `package-lock.json` | `Cargo.toml` 和 `Cargo.lock` |
| Flow | `quick_start/order_flow.py` | `order_flow.go` | `OrderFlow.java` | `order-flow.ts` | `src/order_flow.rs` |
| Step 调用的服务 | `quick_start/shop_api.py` | `shop_api.go` | `ShopApi.java` | `shop-api.ts` | `src/shop_api.rs` |
| 服务器地址和设置 | `quick_start/config.py` | `config.go` | `QuickStartConfig.java` | `config.ts` | `src/config.rs` |
| Worker 程序 | `worker.py` | `cmd/worker` | `WorkerMain.java` | `worker.ts` | `src/bin/worker.rs` |
| 启动程序 | `start.py` | `cmd/start` | `StartMain.java` | `start.ts` | `src/bin/start.rs` |
| 内含 Worker 的 HTTP 服务 | `service.py` | `cmd/service` 和 `service.go` | `ServiceMain.java` 和 `OrderService.java` | `service.ts` 和 `order-service.ts` | `src/bin/service.rs` 和 `src/order_service.rs` |
| 集成测试 | `tests/test_quick_start.py` | `quickstart_test.go` | `QuickStartTest.java` | `test/quick-start.test.ts` | `tests/quick_start.rs` |

复制之后，给项目改名：`pyproject.toml` 里的 **name**、`go.mod` 里的 **module** 路径、`settings.gradle` 里的 `rootProject.name` 和 Java 包名、`package.json` 里的 **name**，或 `Cargo.toml` 里的 **name**。然后用你自己的 Flow 和 API 替换订单 Flow 和模拟 API。保留复制来的构建文件里的 SDK 版本，升级时再更新它。

## 启动 Worker {#enable-pull-mode}

给 Worker 配置 server 地址。Client 也只需要 server 地址。你还可以设置 pull 选项，调整任务容量、注册和关闭行为。

Worker 和 Client 各自还需要两个对象：一个 Registry 和一个 blob cache。

### Registry {#registry}

Registry 保存你的 Flow。Worker 运行其中 Flow 的 Step 和 RPC。Client 用同样的定义来编码 Flow 的启动输入和 RPC 参数，并解码结果。所以 Client 也要构建 Flow 对象，虽然它从不运行 Step。在只启动 Flow 的进程里，给 Flow 传入替身服务就行，因为 Client 从不调用它们；[从 API 服务启动 Flow](/concepts/client#start-from-an-api-service) 说明了这一点。其他语言写的服务有两种做法：用自己的语言写一份 Flow 代码，或者像 `dexcli flow start` 那样，通过 gRPC 调用 FlowService 的 `StartFlow` 请求，传入 Flow type 和 Flow 能解码的输入。

### 只调用 API 的进程 {#api-only-process}

只启动 Flow 的进程用替身服务构建 Flow，并把它注册给自己的 Client。快速开始的启动程序就是这样：它的模拟 API 从不会被调用。

```go
	orderID, err := orderIDFromArgs()
	if err != nil {
		return err
	}
	orderFlow := quickstart.NewOrderFlow(&quickstart.ShopAPI{})
	registry, err := dex.NewRegistry([]dex.Flow{orderFlow})
	if err != nil {
		return err
	}
	cache, err := quickstart.OpenCache(".dex-blob-cache/client")
	if err != nil {
		return err
	}
	defer func() { err = errors.Join(err, cache.Close()) }()

		return err
	}
	defer func() { err = errors.Join(err, client.Close()) }()

		return err
	}
	fmt.Printf("Started Flow %s. Ship runs in %d seconds.\n", orderID, int(quickstart.ShipDelay().Seconds()))
	return nil
}
```

### Blob cache {#blob-cache}

Dex 用引用来传递大的值，例如很大的 Attribute。blob cache 是本地一个有大小上限的目录，用来保存这些值，进程就不必再次下载。每个 Worker 和 Client 进程使用自己的目录。缓存里只有副本，删除它不会丢数据。

各 SDK 参考都有可运行的启动示例：[Go](/reference/go/workers)（英文）、[Python](/reference/python/workers)（英文）、[Java](/reference/java/workers)（英文）、[TypeScript](/reference/typescript/workers)（英文）和 [Rust](/reference/rust/workers)（英文）。

## 把服务传给 Flow {#pass-services-to-the-flow}

Flow 要调用的每个服务，比如支付 API，都通过 Flow 的构造函数传入。这样从 Worker 注册 Flow 的那一刻起，每个 Step 就有了它的服务，测试也可以用同样的方式传入假服务。用 setter 或全局变量会留下一段空档，Step 可能在没有服务的情况下运行。

## 在 handler 里启动 Flow {#start-a-flow-from-a-handler}

**start** handler 启动 Flow。如果调用方需要知道第一个 Step 已经完成，比如订单页显示“已付款”之前要先扣款，handler 就用 Client 的等待 Step 完成调用来等这个 Step：Python 和 Rust 中是 `wait_for_step_completion`，Go 中是 `WaitForStepCompletion`，Java 和 TypeScript 中是 `waitForStepCompletion`。Dex 记录下这个 Step 时等待就结束，所以 handler 不需要自己的状态表或轮询循环。

```go
// StartOrder starts the order's Flow once, however often the request is retried.
// It returns after Charge completes.
func StartOrder(ctx context.Context, client *dex.Client, flow *OrderFlow, orderID string) error {
	requestID := "start-" + orderID
	options := dex.StartFlowOptions{
		RequestID:      &requestID,
		AlreadyStarted: &dex.AlreadyStartedOptions{IgnoreError: true},
	}
	if _, err := client.StartFlow(ctx, flow, orderID, orderID, options); err != nil {
		return err
	}
	return client.WaitForStepCompletion(ctx, orderID, dex.StepExecutionID{StepType: "Charge"},
		dex.WaitForStepCompletionOptions{RequestTimeout: 30 * time.Second})
}
```

有三个启动选项让重试的请求变得安全：

- **订单 ID 就是 Flow ID。** Dex 为每个 ID 只保留一个 Flow，默认的 ID 复用策略会拒绝第二次启动。
- **request ID** 是 **start-** 加上订单 ID。这个请求每次重试时它都相同。
- **already-started 选项**在 request ID 匹配时返回已有的 run。它在 Python 和 Rust 中是 `ignore_already_started`，在 Java 和 TypeScript 中是 `ignoreAlreadyStarted`，在 Go 中是 `AlreadyStarted.IgnoreError`。同一个订单如果用了不同的 request ID，仍然会收到 already-started 错误，服务用 409 回应。

所以客户端把请求发送两次，订单也只扣款一次。这只在 run 存在期间成立；见[这些保护持续多久](/components/your-database#how-long-protections-last)。[启动选项和配置](/concepts/flow#start-options) 列出了这些选项，[Dex 和你的数据库](/components/your-database#write-your-row-and-start-the-flow) 展示了同时写入你自己的表的 handler。运行这个服务，然后发送一个订单。

## 通过 RPC 发命令、读状态 {#send-commands-through-rpcs}

要改变 Flow 的 handler 调用一个 RPC，比如 **approve**。RPC 把消息发到 Channel，正在等待的 Step 就会醒来。要读取 Flow 的 handler 调用读 RPC，比如 **describe**。RPC 在 Worker 上基于 Flow 的当前状态运行，所以 handler 读写的状态和 Step 用的是同一份。handler 从构造函数或工厂函数参数拿到 Client 和 Flow。

RPC 需要有正在运行的 Worker（[RPC 保证](/concepts/primitives/rpc#guarantees)）。要在没有 Worker 运行时保存一条消息，见[没有 Worker 运行时投递事件](/concepts/client#deliver-without-a-worker)。

[订单处理](/use-cases/order-processing) 示例用完整代码展示了这三种模式。

## 容量和关闭 {#capacity-and-shutdown}

<a id="容量和关闭"></a>

Worker 为每个任务槽位建立一个 stream。Dex 只把任务发给空闲的槽位，所以 Worker 不会因为容量不足而拒绝工作。没有 Worker 接手的 Step 会在持久任务队列中等待。RPC 如果在限定时间内没有 Worker 接手，就会失败。部署时要优雅地停止 Worker，让正在运行的任务完成。

[Workers and the task queue](/reference/server/workers)（英文）介绍就绪检查、路由、容量、关闭和网络设置。

## 在容器中运行 {#run-in-containers}

Worker 和 Client 适合运行在无状态容器中：

- **网络。** Worker 只向 Dex Server 发起出站连接，所以它的容器不需要为 Dex 开放入站端口或负载均衡器。在每个进程的配置中设置服务器地址，例如用环境变量。
- **凭据。** 服务器要求认证时，把 token 作为文件挂载，并通过 `credential` 选项传入文件凭据。见[从 Worker 和 Client 发送凭据](/reference/server/authentication#sdk-credentials)（英文）。
- **Blob cache。** [blob cache](#blob-cache) 是本地副本缓存。临时目录（例如容器的临时磁盘）就够用。每个进程使用自己的目录。新容器从空缓存开始，需要时再重新加载数据。
- **相同的 Flow 定义。** 用注册同一组 Flow 的代码构建每个 Worker 和 Client 镜像，这样 Client 编码输入的方式和 Worker 解码的方式一致。滚动部署期间，缺少某个 Step 类型的旧 Worker 会把这次调用交给新 Worker。见 [故障转移和部署](/concepts/failover-and-deploys)。
- **优雅停止。** 先发送停止信号，在容器被强制终止前给进程留出时间完成正在运行的任务。见[容量和关闭](#capacity-and-shutdown)。
