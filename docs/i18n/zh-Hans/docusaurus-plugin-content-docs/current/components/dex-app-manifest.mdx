# Dex app manifest 和仓库结构 {#dex-app-manifest-and-repository-layout}

本页列出 [Managed Dex App](/components/managed-dex-app) 仓库的文件、manifest 字段、YAML 规则、限制、规则 S1 到 S8，以及导入 finding。用它为导入准备仓库，或者修复被拒绝的导入。

最小示例 [`superdurable-apps/cloud-dex-app-example`](https://github.com/superdurable-apps/cloud-dex-app-example) 满足所有规则。它是一个 TypeScript process。

本页的数值是 Dex Cloud 当前的数值。

## 仓库结构 {#repository-layout}

每个仓库的根目录都有这些文件：

| 路径 | 内容 |
| --- | --- |
| `.superverse/template.json` | template manifest：build profile、kind、stack 和命令（[S1](#s1)） |
| `dex-app.yaml` | 部署 manifest：端口、健康检查路径、Flow 源文件和 connector（[S2](#s2)） |
| `Makefile` | template manifest 的命令所指定的 target（[S4](#s4)） |
| `AGENTS.md` | 给在这个仓库里工作的 coding agent 的说明，例如如何构建和测试 |
| `openapi/openapi.yaml` | 应用 HTTP API 的 OpenAPI 文档 |

build profile 还需要它自己的文件（[S3](#s3)）。使用 `go-react-v1` profile 的 Go process 如下：

~~~text
.superverse/template.json
dex-app.yaml
Makefile
AGENTS.md
openapi/openapi.yaml
go.mod
go.sum
cmd/server/                 the web server and the Worker
internal/process/*.go       the Flow sources that dex-app.yaml declares
tools/openapi/go.mod
tools/openapi/go.sum
web/package.json            with generate and build scripts
web/package-lock.json
~~~

使用 `node-ts-v1` profile 的 TypeScript process 或 agent 在根目录放 `package.json` 和 `package-lock.json`，代替 Go 和 `web/` 文件。它的 `package.json` 有 `build` script 和 `main` 入口。

Dex Cloud 按 build profile 构建应用。你的仓库里不需要 Dockerfile。

## Template manifest {#template-manifest}

`.superverse/template.json` 是一个最多 64 KiB 的 JSON 对象：

~~~json
{
  "schemaVersion": 1,
  "buildProfile": "go-react-v1",
  "kind": "process",
  "stack": "go",
  "openapiSpec": "openapi/openapi.yaml",
  "agentInstructions": "AGENTS.md",
  "commands": {
    "bootstrap": "make bootstrap",
    "checkStatic": "make check-static",
    "testApplication": "make test-app"
  }
}
~~~

导入时每个字段都必填。

| 字段 | 类型 | 允许的值 |
| --- | --- | --- |
| `schemaVersion` | integer | `1` |
| `buildProfile` | string | `go-react-v1` 或 `node-ts-v1` |
| `kind` | string | `process`（由 Flow 组成的应用）或 `agent`（用 Dex Agents 构建的应用） |
| `stack` | string | `process` 用 `go` 或 `typescript`；`agent` 用 `pi` |
| `openapiSpec` | string | `openapi/openapi.yaml`，且文件存在 |
| `agentInstructions` | string | `AGENTS.md`，且文件存在 |
| `commands.bootstrap` | string | `make <target>` |
| `commands.checkStatic` | string | `make <target>` |
| `commands.testApplication` | string | `make <target>` |

Dex Cloud 读取上面的字段，忽略其他字段。

stack 决定 build profile：

| `stack` | `kind` | `buildProfile` |
| --- | --- | --- |
| `go` | `process` | `go-react-v1` |
| `typescript` | `process` | `node-ts-v1` |
| `pi` | `agent` | `node-ts-v1` |

Dex Cloud 尚未构建的 agent 框架会被拒绝，并提示暂不支持，例如 `claude-agent-sdk`、`vercel-ai`、`mastra` 和 `openai-agents`。

每个命令由 `make`、一个空格和一个 target 组成。target 以小写字母开头，只包含小写字母、数字和 `-`。对应的模式是 `^make [a-z][a-z0-9-]*$`。Dex Cloud 在准备 coding workspace 时运行 `bootstrap`，Preview 使用这个 workspace。

你让 coding agent 做修改时，它会提交到 `main`。Dex Cloud 按这些规则检查这些 commit，并对它们运行 `checkStatic` 和 `testApplication`。本页把这些检查称为 commit 检查。commit 检查只读取 `schemaVersion`、`buildProfile`、`checkStatic` 和 `testApplication`，缺少 `buildProfile` 时按 `go-react-v1` 处理。

你自己推送的 commit 要到 Preview 或 Live 构建读取它们时才会被检查。coding agent 的输出把 commit 检查显示为 "Source gate"。

## 部署 manifest {#dex-app-yaml}

`dex-app.yaml` 声明应用如何对外提供服务、定义了哪些 Flow、使用了哪些 connector。下面这个 Go process 通过 Gmail connector 发送邮件：

~~~yaml
schemaVersion: superverse.dev/dex-app/v1
application:
  port: 8080
  healthPath: /api/health
flowDefinitions:
  - sourcePath: internal/process/lead_follow_up_flow.go
connectors:
  - connectionName: gmail
    connectorId: gmail
    modulePath: github.com/superdurable/dex-connectors-library/connectors/google/gmail/go
    version: v0.25.2
    authMethodId: google-oauth
    operations: [sendMessage]
~~~

应用不使用 connector 时，声明一个空列表：

~~~yaml
schemaVersion: superverse.dev/dex-app/v1
application:
  port: 8080
  healthPath: /api/health
flowDefinitions:
  - sourcePath: src/greeting-flow.ts
connectors: []
~~~

Dex Cloud 在导入、commit 检查，以及 Preview 和 Live 读取 manifest 时检查下面的字段。对每个 Flow 源文件的检查（1,000 条上限、文件是否存在、`node_modules` 和大小限制）在导入和构建时运行。本页未列出的字段会报错。

### 顶层字段 {#top-level-fields}

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `schemaVersion` | string | 是 | 必须是 `superverse.dev/dex-app/v1`。 |
| `application` | mapping | 是 | 应用如何对外提供服务。见 [`application`](#application)。 |
| `flowDefinitions` | list | 是 | 至少 1 条，最多 1,000 条。见 [`flowDefinitions`](#flow-definitions)。 |
| `connectors` | list | 是 | 可以为空（`[]`）。缺失或为 `null` 会报错。见 [`connectors`](#connectors)。 |

### `application` {#application}

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `port` | integer | 是 | 1024 到 65535。应用以非特权用户运行，所以只能绑定 1024 及以上的端口。 |
| `healthPath` | string | 是 | 以一个且仅一个 `/` 开头，例如 `/api/health`。其中不能有 `?`、`#`、回车或换行。 |
| `workerSlots` | integer | 否 | 1 到 64。Worker 同时运行的 Step 和 RPC 数量。默认值是 4。 |
| `environment` | list | 否 | 应用读取的环境变量。最多 128 条。见 [`application.environment`](#application-environment)。 |

### `application.environment` {#application-environment}

每一条声明应用读取的一个变量。变量的值在 Dex Cloud 中设置，条目本身只声明变量。

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `name` | string | 是 | 匹配 `^[A-Z][A-Z0-9_]{0,127}$`。在列表中唯一。保留名称会被拒绝（见下）。 |
| `required` | boolean | 否 | 应用需要值时设为 `true`。默认值是 `false`。 |
| `secret` | boolean | 否 | 凭证设为 `true`。默认值是 `false`。secret 字段不能有 `enum`。 |
| `minLength` | integer | 否 | 0 到 32768 个字符。默认值是 0。 |
| `enum` | list of strings | 否 | 允许的值。最多 128 个不同的值。每个值最多 32768 字节的合法 UTF-8，不含 NUL，长度至少为 `minLength` 个字符。 |

以下名称是保留的：

- 以 `SUPERVERSE_`、`DEX_`、`AWS_`、`LD_`、`GIT_` 或 `GO` 开头的名称；`GO` 也包括 `GOOGLE_API_KEY` 这样的名称。
- `PATH`、`HOME`、`PORT`、`HOST`、`NODE_OPTIONS`、`SSL_CERT_FILE`、`SSL_CERT_DIR`、`PUBLIC_BASE_URL`、`HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 和 `NO_PROXY`。

~~~yaml
application:
  port: 8080
  healthPath: /api/health
  workerSlots: 8
  environment:
    - name: SUPPORT_INBOX
      required: true
    - name: CRM_API_TOKEN
      required: true
      secret: true
    - name: REGION
      enum: [eu, us]
~~~

### `flowDefinitions` {#flow-definitions}

每一条用它唯一的字段 `sourcePath` 指定一个 Flow 源文件。

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `sourcePath` | string | 是 | 从仓库根目录算起的已提交文件路径。 |

`sourcePath` 的要求：

- 是规范的相对路径：开头没有 `/`，没有 `.` 段，没有 `//`，结尾没有 `/`。任何位置都不能有 `..`，文件名里也不行。
- 以 `.go`、`.ts` 或 `.json` 结尾。build profile 会进一步限定：`go-react-v1` 接受 `.go` 文件，`node-ts-v1` 接受 `.ts` 文件或已提交的 `.json` graph。
- 在列表中只出现一次。
- 指向 `node_modules` 目录之外的已提交普通文件。
- `.json` graph 最多 8 MiB，其他源文件最多 32 MiB。

`.json` 源文件是已提交的 Flow Definition Graph（FDG）2.0，例如 Dex Agents 的 session graph。`.go` 或 `.ts` 源文件的 graph 由 Dex Cloud 从代码渲染。

### `connectors` {#connectors}

每一条声明到 [Dex connector library](https://github.com/superdurable/dex-connectors-library) 中某个已发布 connector 的一个连接。应用的 lockfile 固定同一个版本：Go 用 `go.mod` 和 `go.sum`，TypeScript 用 `package-lock.json`。构建时从 lockfile 解析版本。

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `connectionName` | string | 是 | 非空。在列表中唯一。 |
| `connectorId` | string | 是 | connector 的 ID，例如 `gmail`。 |
| `modulePath` | string | Go | 已发布的 Go module，位于 `github.com/superdurable/dex-connectors-library/connectors/` 下。 |
| `package` | string | TypeScript | npm 包 `@superdurable/connector-<name>`。 |
| `version` | string | 是 | Go：module 版本，例如 `v0.25.2`。TypeScript：精确的 npm 版本，例如 `"0.7.0"`，要加引号，不带 `v`，也不能是范围。 |
| `authMethodId` | string | 是 | 该版本的认证方式。版本只有一种认证方式时写 `""`。 |
| `optional` | boolean | 否 | `true` 表示没有为它选择连接时，Preview 和 Live 也能启动；一旦选择了连接，连接必须有效。应用必须能处理连接缺失的情况。默认值是 `false`。 |
| `operations` | list of strings | 见下 | 应用调用的 operation。每个都是非空字符串。 |
| `triggerBindings` | list | 见下 | 应用绑定的 Trigger。 |

每一条只写 `modulePath` 或 `package` 中的一个。至少有一个 operation 或一个 Trigger binding。

`modulePath` 的每个路径段只包含小写字母、数字、`-` 和 `_`。它可以以 `/go` 结尾。

每个 `triggerBindings` 条目有两个字段：

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| `triggerName` | string | 是 | connector 的 Trigger。非空。 |
| `bindingName` | string | 是 | binding 的名称。非空。`triggerName` 和 `bindingName` 的组合在条目内唯一。 |

TypeScript connector 的写法如下：

~~~yaml
connectors:
  - connectionName: slack
    connectorId: slack
    package: "@superdurable/connector-slack"
    version: "0.7.0"
    authMethodId: ""
    operations: [postThreadReply]
~~~

当应用的某个 Flow 在 graph 的 `v2.connectorTriggerBindings` 中声明了这个 Trigger binding、启用了配置，并且使用 `dex-app.yaml` 固定的版本时，这个 Trigger binding 才可以配置。按 Flow type 顺序，第一个匹配的条目生效。所有声明的 Trigger binding 都配置好之后，Preview 才会启动（只针对非 optional 的 connector，或已经选择了连接的 connector）。只有所有 Flow 源文件都是已提交的 `.json` graph 时，导入才会检查这一点，因为 `.go` 或 `.ts` 源文件要渲染之后才有 graph。

## YAML 规则 {#yaml-rules}

`dex-app.yaml` 是严格的 YAML。YAML 1.1 和 YAML 1.2 的库对每个被接受的文件读出的结果都相同。JSON 也被接受，因为 JSON 就是 YAML。

文件可以包含：

- 恰好一个 YAML 文档，根节点是 mapping。
- 键为字符串的 mapping，每个键只出现一次。
- sequence。
- 任何风格的字符串。带引号的 scalar 和 block scalar 总是字符串。
- 最大 2147483647 的无符号十进制整数，不带前导零。
- `true` 和 `false`，也可以写成 `True`、`TRUE`、`False` 或 `FALSE`。
- `null`、`~` 或空值，按缺失处理。

解码器会拒绝以下内容，并尽可能给出行号和列号：

- anchor（`&name`）、alias（`*name`）、merge key（`<<`），以及 `!!str` 这样的 tag。
- 重复的键。
- 会被读成其他类型的键，例如 `1` 或 `true`。
- `---` 之后的第二个文档。
- 浮点数，例如 `1.5` 或 `1e3`，以及带符号的数，例如 `-1` 或 `+1`。
- 日期，例如 `2026-11-16`。
- YAML 1.1 和 YAML 1.2 读法不同的 plain 值：任意大小写的 `yes`、`no`、`on`、`off`、`y` 和 `n`，`=`，带前导零的数如 `0123`，版本号如 `0.6.0`，十六进制、八进制或二进制数如 `0x1F`，以及时间如 `12:30`。

文件超过大小限制、文件为空，以及出现第二个文档时，错误信息中没有行号和列号。

必须是字符串的值要加引号：

~~~yaml
version: "0.7.0"
authMethodId: ""
enum: ["yes", "no"]
~~~

## 限制 {#limits}

| 项目 | 上限 |
| --- | --- |
| `dex-app.yaml` | 1 MiB |
| `dex-app.yaml` 的嵌套层数 | 64 层 |
| `dex-app.yaml` 中值的数量（每个键、值和列表项） | 100,000 |
| `dex-app.yaml` 中的单个 scalar | 64 KiB |
| `dex-app.yaml` 中的单个整数 | 2147483647 |
| `flowDefinitions` 条目 | 1,000 |
| 单个已提交的 `.json` Flow graph | 8 MiB |
| 单个其他 Flow 源文件 | 32 MiB |
| `application.environment` 条目 | 128 |
| `.superverse/template.json` | 64 KiB |
| 根目录 `Makefile` | 4 MiB |
| `node-ts-v1` 的 `package.json` 和 `package-lock.json`；`go-react-v1` 的 `web/package.json` | 各 4 MiB |
| 仓库中的文件数 | 5,000 |
| 单个文件 | 10 MiB |
| 所有文件合计 | 100 MiB |
| 文件数加不同目录数再加 1 | 20,000 |
| 最坏情况下的源码归档 | 128 MiB |

## 每条规则何时检查 {#when-checked}

导入检查 S1、S2、S3、S4 和 S8。在你创建 project 之前，它会列出仓库违反的每条规则。其他规则在 commit 检查、构建 Preview 或 Live，或者运行应用时检查。

| 规则 | 导入时 | 之后 |
| --- | --- | --- |
| [S1](#s1) | 每个字段 | commit 检查读取 `schemaVersion`、`buildProfile`、`checkStatic` 和 `testApplication` |
| [S2](#s2) | manifest、每个 Flow 源文件，以及 `.json` graph 的 Trigger binding | commit 检查读取 manifest。构建时检查 Flow 源文件。Preview 和 Live 渲染每个 Flow，并拒绝无效的 Flow。 |
| [S3](#s3) | 每个文件是否存在 | Live 构建编译这些文件 |
| [S4](#s4) | 根目录 `Makefile` | commit 检查运行这些 target。Dex Cloud 在准备 coding workspace 时运行 `bootstrap`，Preview 使用这个 workspace。Go 的 Preview 还会运行 `generate`。 |
| [S5](#s5) | 不检查 | commit 检查运行 `make test-app` |
| [S6](#s6) | 不检查 | Preview 和 Live 运行应用 |
| [S7](#s7) | 不检查 | Go 代码的 commit 检查；每次 Go 的 Live 构建 |
| [S8](#s8) | 全部 | Live 构建拒绝链接、不规范路径和超出限制的归档 |

仓库的许可证由仓库所有者决定。Dex Cloud 对此不做检查。

## 阅读导入报告 {#import-report}

每条 finding 写明问题在哪里、错在哪里以及如何修复，并链接到对应的规则；finding 代码用于在本页找到它。每个代码在下面都有自己的小节，锚点是 `#<code>`，例如 [`flow_source_missing`](#flow_source_missing)。

报告中每条规则最多列出 10 条 finding，其余的只计数。

如果导入结果说无法读取仓库，就在 GitHub 上给 SuperDurable Dex Cloud GitHub App 授予该仓库的访问权限。这种情况属于 finding 列表之外的情况。

## S1：Template manifest {#s1}

根目录有 `.superverse/template.json`，最多 64 KiB，是包含 [template manifest](#template-manifest) 字段的 JSON 对象。`schemaVersion` 是 `1`。`buildProfile`、`kind` 和 `stack` 都受支持且彼此一致。`openapiSpec` 是 `openapi/openapi.yaml`，`agentInstructions` 是 `AGENTS.md`，两个文件都存在。`commands` 声明了 `bootstrap`、`checkStatic` 和 `testApplication`，每个都是 `make <target>`。

### `template_manifest_missing` {#template_manifest_missing}

仓库缺少 `.superverse/template.json`。

在仓库根目录添加 `.superverse/template.json`，从[示例](#template-manifest)开始，把 `buildProfile`、`kind` 和 `stack` 设为你的应用对应的值。

### `template_manifest_too_large` {#template_manifest_too_large}

template manifest 超过 64 KiB。

把 `.superverse/template.json` 精简到示例中的字段。Dex Cloud 最多读取它的 64 KiB。

### `template_manifest_invalid` {#template_manifest_invalid}

template manifest 无法解码为包含 template manifest 字段的 JSON 对象。

修复所示行的 JSON，常见原因是缺少逗号或引号，并让每个字段使用示例中的类型。

### `template_schema_version` {#template_schema_version}

`schemaVersion` 缺失或不是 `1`。

把 `schemaVersion` 设为数字 `1`，这是 Dex Cloud 读取的唯一 template manifest 版本：

~~~json
"schemaVersion": 1
~~~

### `build_profile_unknown` {#build_profile_unknown}

`buildProfile` 缺失，或者指定了 Dex Cloud 不构建的 build profile。

Go process 加 React web UI 时把 `buildProfile` 设为 `go-react-v1`，TypeScript process 或 agent 时设为 `node-ts-v1`。

### `kind_unknown` {#kind_unknown}

`kind` 的值在 `process` 和 `agent` 之外。

由 Flow 组成的应用把 `kind` 设为 `process`，用 Dex Agents 构建的应用设为 `agent`。

### `stack_unknown` {#stack_unknown}

`stack` 指定了未知的 stack。

把 `stack` 设为应用使用的语言或 harness：process 用 `go` 或 `typescript`，agent 用 `pi`。

### `stack_unsupported` {#stack_unsupported}

`stack` 指定了 Dex Cloud 暂不构建的 stack，例如 `claude-agent-sdk`、`vercel-ai`、`mastra` 和 `openai-agents`。

在 Dex Cloud 现在构建的 stack 上构建应用，process 用 `go` 或 `typescript`，agent 用 `pi`，并把 `stack` 设为它。

### `stack_kind_mismatch` {#stack_kind_mismatch}

stack 属于另一种 kind。

让 `kind` 和 `stack` 一致：把 `kind` 设为 stack 所属的 kind，或者选择属于你设置的 kind 的 stack。

~~~json
"kind": "process",
"stack": "go"
~~~

### `stack_profile_mismatch` {#stack_profile_mismatch}

build profile 构建的是另一种 stack。

把 `buildProfile` 设为构建该 stack 的 profile：`go` 用 `go-react-v1`，`typescript` 和 `pi` 用 `node-ts-v1`。

~~~json
"buildProfile": "node-ts-v1",
"stack": "typescript"
~~~

### `context_path_field` {#context_path_field}

`openapiSpec` 或 `agentInstructions` 指定了其他路径。

把 `openapiSpec` 设为 `openapi/openapi.yaml`，把 `agentInstructions` 设为 `AGENTS.md`，这是 Dex Cloud 读取的固定路径，并把文件移到那里。

### `openapi_document_missing` {#openapi_document_missing}

仓库缺少 `openapi/openapi.yaml`。

把应用 HTTP API 的 OpenAPI 文档提交到 `openapi/openapi.yaml`。构建时会根据它生成 server。

~~~yaml
openapi: 3.1.0
info:
  title: Orders
  version: 1.0.0
paths:
  /api/health:
    get:
      operationId: getHealth
      responses:
        "200":
          description: The application is healthy.
~~~

### `agent_instructions_missing` {#agent_instructions_missing}

仓库缺少 `AGENTS.md`。

在仓库根目录提交 `AGENTS.md`，写明 coding agent 在这个仓库中要遵循的说明，例如如何构建和测试。

### `command_missing` {#command_missing}

`commands` 缺少 `bootstrap`、`checkStatic` 或 `testApplication`。

在 `.superverse/template.json` 的 `commands` 下以 `make <target>` 的形式添加该命令，并在根目录 `Makefile` 中定义这个 target。

### `command_not_make` {#command_not_make}

某个命令使用了 `make <target>` 之外的形式。

把命令要运行的内容移到根目录 `Makefile` 的一个 target 中，并把命令写成 `make <target>`，这是 Dex Cloud 唯一会运行的形式。

~~~json
"testApplication": "make test-app"
~~~

## S2：部署 manifest {#s2}

根目录有 `dex-app.yaml`，最多 1 MiB，遵守 [YAML 规则](#yaml-rules)，并通过[部署 manifest](#dex-app-yaml) 的每条字段规则。它最多声明 1,000 个 Flow 源文件。每个都是 `node_modules` 之外的已提交普通文件，`.json` graph 最多 8 MiB，其他源文件最多 32 MiB。每个 Trigger binding 都由某个 Flow 以固定的版本声明。只有所有 Flow 源文件都是已提交的 `.json` graph 时，导入才检查最后这条。

### `app_manifest_missing` {#app_manifest_missing}

仓库缺少 `dex-app.yaml`。

在仓库根目录添加 `dex-app.yaml`，声明应用的端口和健康检查路径、Flow 源文件和 connector。从[示例](#dex-app-yaml)开始。

### `app_manifest_too_large` {#app_manifest_too_large}

`dex-app.yaml` 超过 1 MiB。

只声明应用实际使用的 Flow 源文件和 connector，让 `dex-app.yaml` 保持在 1 MiB 以内。

### `app_manifest_invalid` {#app_manifest_invalid}

Dex Cloud 拒绝了 `dex-app.yaml`。错误信息会指出字段或 YAML 规则。

对照[示例](#dex-app-yaml)、[字段规则](#top-level-fields)和 [YAML 规则](#yaml-rules)，修改错误信息指出的部分。

### `flow_definitions_too_many` {#flow_definitions_too_many}

`dex-app.yaml` 声明了超过 1,000 个 Flow 源文件。

最多声明 1,000 个 Flow 源文件：合并小的 Flow，或者删除应用已经不再运行的 Flow。

### `flow_source_node_modules` {#flow_source_node_modules}

某个 Flow 源文件位于 `node_modules` 下。

把 Flow 源文件移到应用自己的源码目录中，例如 `src/`，并让 `sourcePath` 指向那里。

~~~yaml
flowDefinitions:
  - sourcePath: src/order-flow.ts
~~~

### `flow_source_missing` {#flow_source_missing}

声明的某个 Flow 源文件缺失，或者它不是已提交的普通文件。

在这个路径提交 Flow 源文件，或者把 `dex-app.yaml` 中的 `sourcePath` 改成从仓库根目录算起的正确路径。

### `flow_source_too_large` {#flow_source_too_large}

某个 Flow 源文件超过了构建读取的大小。

把 Flow 拆成更小的 Flow，或者把辅助代码移到其他文件。已提交的 `.json` graph 最多 8 MiB，其他 Flow 源文件最多 32 MiB。

### `flow_graph_invalid_json` {#flow_graph_invalid_json}

某个已提交的 `.json` graph 不是合法的 JSON，或者有字段类型错误。

重新导出 Dex 写出的 FDG 2.0 JSON，不要手工编辑，并检查所示行的语法错误。

### `flow_graph_invalid` {#flow_graph_invalid}

某个已提交的 `.json` graph 没有通过 FDG 2.0 检查。

从 Dex 重新导出 graph，让它成为有效的 FDG 2.0 graph，并修复错误信息指出的部分。

### `flow_bundle_invalid` {#flow_bundle_invalid}

声明的 graph 之间有冲突，例如两个 graph 定义了同一个 Flow type。

解决错误信息指出的 graph 之间的冲突，让它们能一起加载。

### `trigger_binding_undeclared` {#trigger_binding_undeclared}

`dex-app.yaml` 声明的某个 Trigger binding 在所有 Flow 中都找不到声明。

在启用了配置的 Flow 中声明这个 Trigger binding（`v2.connectorTriggerBindings`），或者把它从 `dex-app.yaml` 中删除。

### `trigger_binding_release_mismatch` {#trigger_binding_release_mismatch}

声明 Trigger binding 的 Flow 固定的是另一个 connector 版本。

在 `dex-app.yaml` 和声明这个 Trigger binding 的 Flow 中固定同一个 connector 版本，即同一个 `modulePath` 和 `version`。

## S3：Build profile 文件 {#s3}

仓库包含 build profile 需要的文件。每个 Flow 源文件的后缀都是 profile 接受的后缀。S1 已经报告过的文件（例如 `openapi/openapi.yaml`）只报告一次。

`go-react-v1` 需要：

| 要求 | 原因 |
| --- | --- |
| `go.mod` 和 `go.sum` | 构建时离线下载 module，所以每个依赖都需要校验和。 |
| Go package `cmd/server` | 构建时编译 `./cmd/server`。 |
| `openapi/openapi.yaml` | 构建时根据它生成 server。 |
| `tools/openapi/go.mod` 和 `tools/openapi/go.sum` | OpenAPI 代码生成器的 module。 |
| 带 `generate` 和 `build` script 的 `web/package.json`，以及 `web/package-lock.json` | 构建时在 `web/` 中运行 `npm ci`、`generate` 和 `build`。 |
| 根目录 `Makefile` 中的 `generate` target | Preview 运行 `make generate`。 |
| `.go` Flow 源文件 | 这个 profile 只渲染 Go Flow。 |

Live 构建还会运行 `go vet ./...` 和 `go test ./...`，并要求 Dex Go SDK `github.com/superdurable/dex/sdk-go` 为 `v1.16.0` 或更高版本。这些由构建检查，导入时不检查。

`node-ts-v1` 需要：

| 要求 | 原因 |
| --- | --- |
| `package.json` 和 `package-lock.json`，各最多 4 MiB | 构建时运行 `npm ci`。 |
| `package.json` 中写出 `dist` 的 `build` script | 构建和 Preview 运行 `npm run build`。 |
| `package.json` 中的 `main` | Node.js 启动 `main` 指定的 module。 |
| `.ts` Flow 源文件或已提交的 `.json` graph | 这个 profile 渲染 TypeScript Flow 并读取已提交的 graph。 |

构建使用 Node.js 22.19 或更高版本，或 Node.js 24。只有你的 `build` script 读取 `tsconfig.build.json` 时才需要它。

### `flow_source_suffix` {#flow_source_suffix}

某个 Flow 源文件的后缀不被 build profile 接受。

用 build profile 的语言编写 Flow：`go-react-v1` 用 `.go` 文件；`node-ts-v1` 用 `.ts` 文件或已提交的 `.json` graph。

### `profile_file_missing` {#profile_file_missing}

缺少 build profile 需要的某个文件，例如 `go.sum` 或 `package-lock.json`。

提交这个文件，构建时会复制它。用对应的工具生成 lockfile，例如用 `npm install` 生成 `package-lock.json`，用 `go mod tidy` 生成 `go.sum`。

### `profile_file_too_large` {#profile_file_too_large}

某个 npm manifest 超过了构建读取的大小。

把文件缩小到错误信息给出的大小以内，例如删掉没用的依赖。

### `go_package_missing` {#go_package_missing}

仓库缺少 Go package `cmd/server`。

像 Go 模板那样添加 Go package `cmd/server`，在其中写启动应用的 `main` 函数。构建时编译 `./cmd/server`。

~~~go
// cmd/server/main.go
package main

func main() {
	// Start the web or the worker mode from os.Args[1].
}
~~~

### `npm_package_invalid` {#npm_package_invalid}

`package.json` 不是合法的 JSON，或者有字段类型错误。

修复 `package.json` 中所示行的 JSON。`npm pkg fix` 或 JSON linter 会指出错误位置。

### `npm_script_missing` {#npm_script_missing}

`package.json` 缺少构建要运行的 script。

在 `package.json` 的 `scripts` 下添加这个 script。构建时用 `npm run` 运行它。

~~~json
"scripts": {
  "build": "tsc -p tsconfig.build.json"
}
~~~

### `npm_main_missing` {#npm_main_missing}

`package.json` 缺少 `main`。

把 `package.json` 中的 `main` 设为编译后的入口 module，Node.js 会启动它。

~~~json
"main": "dist/main.js"
~~~

## S4：Make target {#s4}

根目录 `Makefile` 为 `commands` 指定的每个 target 定义规则，使用 `go-react-v1` 时还要定义 `generate`。导入只读取根目录中名为 `Makefile` 的文件。它从每一行第一列以 `target:` 开头的内容中取 target，一行可以写多个 target。只在 include 进来的文件中定义的 target 按缺失处理。根目录 `Makefile` 最多 4 MiB。

### `makefile_missing` {#makefile_missing}

仓库缺少根目录 `Makefile`。

在仓库根目录添加 `Makefile`，为 `.superverse/template.json` 中的每个 make 命令定义 target。

~~~makefile
bootstrap:
	./scripts/bootstrap.sh
check-static:
	go vet ./...
test-app:
	go test ./internal/apptest
~~~

### `makefile_too_large` {#makefile_too_large}

根目录 `Makefile` 超过 4 MiB。

把较长的 recipe 移到它调用的脚本中，让根目录 `Makefile` 保持在 4 MiB 以内。

### `make_target_missing` {#make_target_missing}

某个 make target 缺失，或者只在 include 进来的文件中定义。

在根目录 `Makefile` 本身中定义这个 target。Dex Cloud 只读取根目录 `Makefile`，不读取它 include 的文件。

~~~makefile
generate:
	./scripts/generate-openapi.sh
~~~

## S5：应用测试 {#s5}

`make test-app` 针对一个只为这次运行存在的 Dex Server 运行应用的 API 测试，并使用 connector 的 mock package。template manifest 声明了 `testApplication` 时，commit 检查会运行它。Preview 和 Live 启动时用不到它。导入时不检查它，所以它没有 finding。

## S6：运行时约定 {#s6}

同一次构建以两种模式运行，由第一个参数选择：

- `web` 在 `PORT` 环境变量指定的端口上提供应用和它的 `healthPath`。
- `worker` 运行 Worker。slot 注册完成后，它在运行时设置中的 readiness 地址上响应 `GET /readyz`。

两种模式都读取 Dex Cloud 放在 `/tmp` 下的运行时设置文件。它们只在 `/tmp` 下写入。应用以非特权用户、在只读的根文件系统上运行。

收到 SIGTERM 时，web 进程完成正在处理的请求。Worker 撤销 readiness，在 drain 超时内处理完正在运行的任务，然后退出。

Dex Cloud 根据声明的 Flow 源文件渲染并发布 Flow 定义，所以 Worker 不上传任何 Flow 定义。

Preview 和 Live 通过运行应用来检查这条规则。导入时不检查它，所以它没有 finding。

## S7：connector mock 只用于测试 {#s7}

只有测试代码导入 connector 的 mock package。

commit 检查对 Go 代码执行这条规则。每次 Go 的 Live 构建也会执行，违反时以 `connector-mock-in-production` 失败。TypeScript 代码不在检查范围内。导入时不检查它，所以它没有 finding。

## S8：仓库形态 {#s8}

仓库：

- 处于活跃状态（未归档），并且是你自己的仓库，而不是 Dex Cloud 为某个 project 创建的仓库。
- 默认分支是 `main`，并且 `main` 至少有一个 commit。
- 最多属于一个 project，也就是这个 project。
- 在 GitHub 上有完整的 tree 列表。
- 只包含普通文件：submodule 和符号链接会被拒绝，指向仓库内部的链接也一样。
- 只提交非密钥文件。下面这些文件名算作密钥文件，匹配时忽略大小写：
  - `.env` 和 `.env.*`，`.env.example`、`.env.sample` 和 `.env.template` 除外。
  - SSH 私钥 `id_rsa*` 和 `id_ed25519*`，它们的 `.pub` 文件除外。
  - `testdata` 目录之外的 `*.pem` 文件。
- 在文件和归档的[限制](#limits)之内：5,000 个文件，单个文件 10 MiB，总计 100 MiB，文件和目录合计 20,000，最坏情况下源码归档 128 MiB。

密钥文件检查只匹配这些文件名。其他文件里的密钥检测不到。

导入之后，只有 Live 构建会重新检查 S8 的一部分。它拒绝链接、不规范路径和超出限制的归档。

### `tree_truncated` {#tree_truncated}

GitHub 返回的 tree 不完整，所以导入只报告这一条 finding。

从 `main` 中删除生成的文件、vendor 的文件和构建产物，并把它们加入 `.gitignore`，让仓库保持在文件数限制之内。

~~~text
# .gitignore
node_modules/
dist/
.local/
~~~

### `submodule` {#submodule}

仓库有 Git submodule。

用 submodule 的文件替换它：先用 `git rm` 删除它，再把它的文件复制进仓库并提交。

~~~bash
git rm <path>
cp -R <its files> <path>
git add <path>
~~~

### `symbolic_link` {#symbolic_link}

仓库有符号链接。

用链接指向内容的副本替换链接，或者修改代码，直接读取目标路径。

### `unsupported_entry_mode` {#unsupported_entry_mode}

某个条目的 Git mode 不是普通文件。

在这个路径改为提交一个普通文件。

### `repository_file_too_large` {#repository_file_too_large}

某个文件超过 10 MiB。

从 `main` 中删除这个文件，把大数据放在仓库之外，例如对象存储中，在运行时加载。

### `secret_file` {#secret_file}

提交了密钥文件，例如 `.env`。

从 `main` 中删除这个文件，把它加入 `.gitignore`，并轮换它包含的每个凭证，因为 Git 历史仍然保留着它们。改为提交一个示例文件，例如 `.env.example`。

~~~text
# .gitignore
.env
.env.*
!.env.example
~~~

### `too_many_files` {#too_many_files}

仓库有超过 5,000 个文件。

从 `main` 中删除生成的文件、vendor 的文件和构建产物，并把它们加入 `.gitignore`。

### `repository_too_large` {#repository_too_large}

所有文件合计超过 100 MiB。

从 `main` 中删除大的生成文件或二进制文件，把它们加入 `.gitignore`，并把大数据放在仓库之外。

### `archive_too_many_entries` {#archive_too_many_entries}

文件和它们的目录合计超过 20,000 个归档条目。

减少 `main` 中的文件和目录：删除生成的目录树和 vendor 的目录树，并把它们加入 `.gitignore`。

### `archive_too_large` {#archive_too_large}

源码归档加上头部信息可能超过 128 MiB。

从 `main` 中删除大的文件或生成的文件，或者缩短很长的路径，让源码归档符合 release 构建的限制。

### `repository_archived` {#repository_archived}

仓库已归档。

在 GitHub 的仓库设置中取消归档，然后再检查一次。

### `repository_managed` {#repository_managed}

这个仓库是 Dex Cloud 为某个 project 创建的。

打开 Dex Cloud 为之创建这个仓库的 project，或者导入你自己的仓库。

### `repository_bound_elsewhere` {#repository_bound_elsewhere}

另一个 project 已经在使用这个仓库。

打开已经使用这个仓库的 project，或者先删除那个 project。一个仓库同一时间只属于一个 project。

### `default_branch_not_main` {#default_branch_not_main}

默认分支使用了 `main` 之外的名字。

在仓库设置中把 `main` 设为默认分支，必要时重命名当前分支，然后再检查一次。

~~~bash
git branch -m master main
git push -u origin main
~~~

### `main_branch_missing` {#main_branch_missing}

仓库是空的，或者缺少 `main` 分支。

把应用推送到 `main` 分支，然后再检查一次。

~~~bash
git push -u origin main
~~~
