# Channel

**Channel** 是单个 Flow execution 内部一条 durable 的 first-in, first-out (FIFO) 队列。Step 和 RPC 向它发布有类型的消息。Step 在 **WaitFor** 里等待这个 Channel，从而消费消息。

Channel 只属于一个 Flow execution。消息不会跨 Flow execution。

<ChannelScopeDiagram markdownDescription="Flow execution 拥有一个由其 Step 和 RPC 共享的 FIFO Channel。发布者添加消息，等待中的消费 Step 将每条消息消费一次。" />

## 什么时候用 Channel

Channel 适合 Step 要等待的事件，例如一次审批、用户回复或新的工作项。会被覆盖、多次读取的状态，用 [Attribute](/primitives/attribute)。可以丢失的实时进度，用 [Stream](/primitives/stream)。

## 保证

- Dex 把每条消息和 Flow 一起 durable 存储。
- 消息保持到达顺序。
- 一条消息只被一个 wait 消费一次。Dex 不会把它复制给其他等待中的 Step。
- 消息可以在 Step 开始等待之前到达。Dex 会保留它，直到之后的 wait 消费它。
- 发布和产生它的 Step 或 RPC 结果一起 commit。

## 定义、发布和等待 {#persistence-schema}

Channel 有稳定的名字和消息类型。先定义它，再加到 Flow 的 persistence schema。

在这个例子里，start Step 等待 **ApprovalMessages** Channel 上的一条消息，或者一个 Timer。**publishApprovalMessage** RPC 发布审批消息。

var ApprovalMessages = dex.DefineChannel[string]("ApprovalMessages")

func (channelWait) WaitFor(_ dex.Context, input int) (*dex.Wait, error) {
	return dex.AnyOf(
		ApprovalMessages.ForOne(),
		dex.Timer(time.Duration(input)*time.Second),
	), nil
}

func (channelWait) Execute(ctx dex.Context, _ int) (*dex.StepDecision, error) {
	if ctx.HasTimerFired() {
		return dex.GracefulComplete("approval timed out"), nil
	}
	approvalMessageValues, err := ApprovalMessages.GetConditionResults(ctx)
	if err != nil {
		return nil, err
	}
	return dex.GracefulComplete(approvalMessageValues[0]), nil
}

func (*ChannelFlow) PublishApprovalMessage(ctx dex.Context, _ dex.None) (*dex.RPCResult[dex.None], error) {
	if err := ApprovalMessages.Publish(ctx, "approved"); err != nil {
		return nil, err
	}
	return &dex.RPCResult[dex.None]{}, nil
}

Timer 分支在读取 Channel 结果之前返回。审批胜出时，Channel condition 已经消费了一条消息，所以第一个结果一定存在。完整示例还会在 persistence schema 中注册 Channel，并注册 RPC。

## 等待并消费 {#wait-and-consume}

**WaitFor** 中的 Channel condition 会等到队列里有足够的消息。然后 Dex 按 FIFO 顺序移除选中的消息，作为 Channel results 传给 **Execute**。

| Condition | 何时继续 | 消费什么 |
| --- | --- | --- |
| **ForOne** | 至少有一条消息在队列中。 | 正好一条消息。 |
| **ForN** | 队列中至少有请求的数量。 | 正好这个数量的消息。 |
| **AtLeast** | 队列中至少有请求的数量。 | 当前所有可用消息。 |
| **AtMost** | 立即继续，队列为空时也一样。 | 当前队列中最多请求数量的消息。 |
| **AtLeastAtMost** | 队列中至少有下限数量。 | 当前队列中从下限到上限数量的消息。 |

## 发布消息 {#publish-messages}

在 Step 或 RPC 里，用 handler 的 **Context** 发布。Worker 之外的代码调用一个负责发布的 Flow RPC。这样校验、授权和相关的状态变更都留在 Flow 内。

## 管理待处理消息 {#manage-pending-messages}

Dex 接受每条消息时会给它一个 ID。Step 或 RPC 可以加载待处理消息，按 FIFO 顺序读取，并按 ID 删除其中一条。读取不会消费消息。handler 运行时，其他 Step 和 RPC 可能改变队列，所以加载到的列表可能已经过时。

删除一条已经不在的消息不起作用，transactional RPC 除外。transactional RPC 会失败，什么也不 commit。见 [Pending messages](/reference/server/runtime-data#manage-pending-messages)。

## ChannelMap {#channelmap}

一个 Flow 需要很多独立队列时，例如每个订单、客户或任务一条，用 **ChannelMap**。ChannelMap 有一个名字和一种消息类型。每个 instance key 有自己的 FIFO 队列。
