# Step options

本页介绍用于深度定制你的 Step type 的 **StepOptions** 进阶功能。基础功能见 [Basic Step](/primitives/step/basic#stepoptions) 页面。

## Retry After

如果要深度定制 retry behavior，使用 **RetryAfter**。它覆盖 **RetryPolicy** 的 retry schedule。

Retry 用于从失败的 attempt 中恢复。不要用 **RetryAfter** 等待外部系统；请使用 [Polling](/design-patterns/polling) 模式。

同一次 **Execute** 调用的 retry 会复用 Dex 把首次 attempt 交给 Worker 时取得的 [state snapshot](#selective-state-loading)，因此看不到之后写入的 Attribute。如果要等待外部写入，写入方还需要直接或通过 RPC handler 发布一条 [Channel](/primitives/channel) 消息，下一个 Step 在 **WaitFor** 中等待这条消息。也可以让下一个 Step 等待一个 [Timer](/primitives/timer)，在运行时读取最新的 state。

## Durability {#durability}

**SYNC** durability 会将 Step completion 同步记录到 Dex Server，并持久化到 storage。它还会在 Worker 收到任务之前，把 attempt 的开始记录持久化到 storage。

**ASYNC** durability 会异步完成这些事。Dex Server 会在开始记录和 completion 持久化之前就把任务交给 Worker 并开始后续工作，并在大约 20 毫秒内批量提交这些记录。两种模式下 server 能持续承担的吞吐量差不多。**ASYNC** 延迟更低，单个 Flow 运行得更快。在写入延迟低的 object storage 上，**ASYNC** 发出的请求也少得多。

如果某个 Dex Server 节点在提交之前故障，最近的 **ASYNC** 结果会丢失。这个 method 会再次运行，基于该结果开始的后续工作也会再次运行。如果节点在 **ASYNC** 的开始记录持久化之前故障，Dex 会回滚这次开始，并再次运行同一个 attempt 编号。这不消耗 retry，而且 attempt 看到的输入可能不同。同一个 attempt 编号的两次执行可能重叠，Step Stream 的写入也可能在同一个 source 中重复。**ASYNC** method 以及它启动的工作都应具备幂等性。

不论哪种模式，同一个 Step 的各次 attempt 都不是严格顺序的。取消是协作式的，所以被中断的执行可能仍在运行，而下一次 attempt 或 failure route 已经开始。

需要最严格保证的副作用选择 **SYNC**。延迟重要、Step 较短并且可以接受偶尔重新运行时选择 **ASYNC**。完整对比见 [失败与重新投递](/primitives/step/basic#failure-and-redelivery)。

Dex 在 method 调用变为 pending 时固定它的 durability。修改 Flow config 中的 **step_durability** 只影响之后调度的 method 调用。

**SYNC** 是默认值。Dex 按这个顺序确定 durability：**StepOptions** 中的 method override、Flow 的 **FlowConfig**，最后是 **SYNC**。

Durability 只改变 Dex Server 持久化结果的时机。两种模式下，retry policy、method timeout 和 heartbeat 设置都作用于每一次 attempt。默认 method attempt timeout 是两小时，默认 heartbeat timeout 是一分钟。

Method timeout 和 heartbeat timeout 从 Dex 把任务发送给 Worker 时开始计时。等待 lock 或等待 Worker 的时间不计入，包括在任务队列中的时间。任务中的 deadline 是发送时间加上 method timeout。

两种 durability mode 的默认 retry total duration（**TotalDuration**）都是四小时。显式设置的 retry duration 可以更短或更长。**TotalDuration** 从 Dex 首次把 attempt 1 交给 Worker 时开始计时；如果 attempt 1 在没有运行的情况下被退回，计时会重置。Step 在任务队列中等待时，Dex 不检查 **TotalDuration**，所以等待超过它的 retry 仍会运行。retry 在队列末尾等待，这段等待计入 **TotalDuration**。积压很长之后，失败的 retry 可能没有剩余时间。Dex 只在 attempt 失败之后用 **TotalDuration** 判断是否 retry。它不会中断正在运行的 attempt，所以最后一次 attempt 可能在 **TotalDuration** 之后开始或结束。只有 method timeout 限制单次 attempt。要限制一次很长的 attempt，请设置 **ExecuteMethodTimeout** 或 **WaitForMethodTimeout**，而不是 **TotalDuration**。Server 不再产生 RETRY_DEADLINE 失败类型。SDK 的 **IsRetryTotalDurationExceeded** helper 及其他 SDK 中的同类 helper，只可能对升级之前的记录返回 true。

## Heartbeat {#heartbeat}

在每次 attempt 中，Worker 必须在 **HeartbeatTimeout** 到期前发送 heartbeat 或 [Stream message](/primitives/stream)。换句话说，发送 Stream message 就是 implicit heartbeat。

**HeartbeatTimeout** 默认是一分钟。默认允许的最小值是 10 秒。

例如，**Execute** method timeout 为 60 秒、**HeartbeatTimeout** 为 10 秒时，Dex 大约 10 秒后就能 retry 这个 Step，而不必等满 60 秒。

如果要在一个持续发送 heartbeat 的 Step 中等待外部系统，使用 [Polling](/design-patterns/polling) 模式。

Heartbeat 可以持久化 checkpoint value。下一次 attempt 会收到最新值，并从那里继续。显式发送不带 value 的 heartbeat 会清除之前的 checkpoint。Stream message 产生的 implicit heartbeat 会保留最新的显式状态，包括已经显式清空的状态。

```go
func (heartbeatStep) GetStepOptions() *dex.StepOptions {
	return &dex.StepOptions{
		ExecuteMethodTimeout: 60 * time.Second,
		HeartbeatTimeout:     10 * time.Second,
		ExecuteRetry:         &dex.RetryPolicy{MaximumAttempts: 3},
	}

func (step heartbeatStep) Execute(ctx dex.Context, batches int) (*dex.StepDecision, error) {
	completedBatches := 0
	if _, err := ctx.GetLastHeartbeatValue(&completedBatches); err != nil {
		return nil, err
	}
	for batch := completedBatches; batch < batches; batch++ {
		select {
		case <-ctx.Done():
			return dex.DeadEnd(), nil
		default:
		}
		time.Sleep(2 * time.Second)
		if err := ctx.RecordHeartbeat(batch + 1); err != nil {
			return nil, err
		}
	}
	return dex.GracefulComplete("processed"), nil
}
```

## 选择性加载状态 {#selective-state-loading}

每次 **WaitFor**、**Execute** 和 timeout handler 调用都会收到所有普通 Attribute，以及每个 Channel 和 ChannelMap instance 的 size metadata。除非对应方法显式选择，否则不会加载 AttributeMap value 和 pending Channel message。

**StepOptions** 为 **WaitFor** 和 **Execute** 提供独立的 selection。方法需要枚举当前 instance 时，选择整个 AttributeMap 或 ChannelMap；已经知道 key 时，只选择精确的 map instance。Attribute lock 只控制并发，不会加载 AttributeMap value。

两个方法收到独立的 snapshot。获胜的 Wait condition 消费消息之后，**Execute** 才读取自己的 snapshot，因此不会再次看到已经消费的消息。Dex 在把 attempt 1 交给 Worker 时取得它的 snapshot。同一个逻辑方法调用的 retry，以及回到 pending 的 attempt，都会复用这个 snapshot。

下面的 Step 只为 **Execute** 加载 **Queued** 的 pending message，并在同一个成功的 handler response 中删除第一条消息。

## Attribute locks

并发 Step 和 RPC invocation 可以读取和写入同一个 Attribute。这可能导致 race condition。要避免它，使用 Attribute lock。Dex Server 会确保同一时间只有一个 Step execution 或 RPC handling 能 acquire 这个 lock。

**WaitFor** 与 **Execute** 有独立的 lock set。通过返回 **StepOptions** 设置它们。

还没有被交出过的首次 attempt 不持有 lock，但之后需要同一把 lock 的 Step 会排在它后面等待。被退回的 attempt（例如 Worker 拒绝了它的 Step type）和 retry attempt 在队列中等待时继续持有 lock。没有 Worker 能运行它们时，它们会一直持有 lock，直到 Flow 超时或被停止。这期间针对这些 key 的 transactional RPC 会得到 lock conflict。

更多细节见 [Attribute locking](/primitives/attribute#locking)。

## 动态提供 StepOptions {#stepoptions-override-per-stepexecution}

Step implementation 返回的 **StepOptions** 默认适用于每一次 Step execution。有时为某一次 Step execution 动态 override 它们会很有用。
