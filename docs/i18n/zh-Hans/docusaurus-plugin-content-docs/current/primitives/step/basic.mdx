# Step 基础功能

本页介绍 Step 的默认形态：typed input、可选的 **WaitFor**、必需的 **Execute**、通过 **StepDecision** 做 movement，以及默认 **StepOptions** 行为。

Dex Step 由原生代码实现。实现该 Step 的 struct 或 class 决定 **StepType**。在大多数语言里，SDK 默认从原生类型名推导 StepType；你也可以显式覆盖。

同一个 Step type 可以在同一个 Flow 中执行多次。每次执行都是一个 **StepExecution**，对应一个 **StepExecutionID**，格式是 **StepType**-**Number**，由 Dex 分配并维护。

## Step input {#step-input}

起始 Step 接收 Flow input。之后每个 Step 接收调度它的 movement 带来的 input。Step input 随图传递，不是隐藏的全局变量。

## WaitFor and Execute {#waitfor-and-execute}

Step implementation 通常只有一个或两个小方法：**WaitFor** -> **Execute**。

**WaitFor** 是可选的。它向 Dex Server 返回 durable **Wait**。Dex 持久化该 waiting state，代表应用持续评估这些条件；条件满足后再调用 **Execute**。

如果 Step 没有实现 **WaitFor**，则会直接调用 **Execute**。

**Execute** 是必需的。它返回 **StepDecision**，用于流转到下一个 Step、分支到多个 Step，或关闭 Flow。

每次 **WaitFor** 或 **Execute** 调用都有独立的 commit 边界。Dex Server 会暂存该 method 内的 Attribute 写入和 Channel publish，并只在 method 成功返回时，将它们与相应的 **Wait** 或 **StepDecision** 一起 commit。如果 method 失败，这些 durable 变更都不会被 commit。**WaitFor** 和 **Execute** 不共享一次 commit，外部 API 调用也不在这个原子边界内。

在最终 **Wait** 或 **StepDecision** 之前，handler 可以发送 [heartbeat checkpoint](/primitives/step/step-options#heartbeat) 和任意多条 best-effort [Stream message](/primitives/stream)。Response stream 必须以且仅以一个最终 result 结束。这些 progress frame 不属于 method commit，Stream Store 写入失败也不会让 Step 失败。

## StepOptions {#stepoptions}

大多数时候，需要自定义 failure handling —— timeout、retry 与 failure policy。还有 heartbeat、durability 等更高级的 [Step options](/primitives/step/step-options)。

* **Timeout** 自定义一次方法（WaitFor/Execute）调用 attempt 的 timeout。
* **Retry policy** — 在**同一** Step execution 上重复调用**同一**方法，直到 attempt 耗尽。
- **Failure policy** — 决定 retry 结束**之后**发生什么。默认失败 Flow，但 WaitFor 仍可运行 Execute，Execute 也可以前往 recovery Step。

通过在 Step 方法中实现返回 StepOptions 来配置。

### WaitFor failure policy

WaitFor method retry 耗尽时：

- **FailFlow** — 失败 Flow。这是默认行为。
- **PROCEED** — 继续调用 Execute。

### Step Failed 事件与 last failure info

- 终态事件 **StepExecuteFailed** / **StepWaitForFailed** 在 Step 最终失败时携带 failure output。
- **Retry 期间**（failure policy 运行前），Step 事件与 live Flow 状态暴露 **lastFailureInfo**——最近一次 attempt 的错误（type、detail、worker 元数据）。
- 在 Dex Web 中打开事件详情，可在 retry 进行中查看 **Last failure**。Flow 概览中的活跃 Step 也显示 lastFailureInfo。

Last failure info 描述 **retry attempt**。Failure policy 决定 retry 结束后的行为。

## 失败与重新投递 {#failure-and-redelivery}

Retry 和 failure route 处理失败的 attempt。但有些失败会让 Dex 无法知道工作是否已经运行。如果 Step 的外部副作用不能重复，例如付款或发送邮件，就必须为这些情况做好设计。本节说明应用目前可以依赖什么。

### Heartbeat 没有确认 {#heartbeats-not-acknowledged}

Heartbeat 调用在 Worker 将它放入队列或发出后就返回，不会等待 Dex 存储任何内容。Python 的 **heartbeat**、Go 的 **RecordHeartbeat**、Java 和 TypeScript 的 **recordHeartbeat**，以及 Rust 的 **record_heartbeat** 都是这样。Heartbeat 调用返回，并不能证明 Dex 已经存储了 checkpoint。SYNC Step 也是如此，尽管 SYNC Step 只在 Dex 把 attempt 的开始持久化之后才运行用户代码。

Heartbeat checkpoint 可能丢失。Dex 会批量处理 checkpoint，每批只保留最新的值。attempt 结束时，例如超时或被取消，或者 Dex Server 节点故障时，checkpoint 也可能丢失。发生中断之后，下一次 attempt 收到的是 Dex 最后存储的 checkpoint。它可能比 Step 最后发送的那个更旧。不要把 checkpoint 当作外部副作用已经发生的唯一记录。

### Attempt 在 Dex 交给 Worker 时开始 {#same-attempt-redelivery}

Step attempt 在 Dex 把它交给 Worker 的那一刻开始。Dex 先预留一个空闲的 Worker slot，然后记录开始。这条记录会固定 attempt 的输入 snapshot，并获取它的 Attribute lock。最后 Dex 才发送任务。对于 SYNC Step，开始记录在 Worker 收到任务之前就已经持久化到 object storage。ASYNC Step 不等待这次写入。

Dex 把 attempt 交给 Worker 之后，就不会再把同一个 attempt 编号交给另一个 Worker。如果 Worker 崩溃或连接断开，不论它是否已经发出输出，这个 attempt 都会失败，然后 retry policy 运行：消耗一次 retry，并等待 backoff。如果 Worker 不再响应但没有断开，attempt 会在 heartbeat timeout 到期时失败。Server 重启或 failover 对每个已经交出的 attempt 都是同样的处理，失败类型为 STARTED_ATTEMPT_INTERRUPTED。这些情况下 SYNC 和 ASYNC 的行为相同。

少数情况会让 attempt 回到 pending。它保留 attempt 编号、输入 snapshot 和 lock，并且不消耗 retry。只有在可以确定 Worker 从未运行过这个 attempt 时才会这样：

- Worker 以 Step type 未知为由拒绝了任务。之后 Dex 会让这个 Step type 避开该 Worker。
- 任务从未到达 Worker，因为发送前 stream 已经关闭，或者发送失败。
- 使用 reserved-slot dispatch 的 Worker 在任务还没有任何输出时干净地关闭了 stream。这是正常的 Worker 关闭。正在关闭的 Worker 会先完成正在运行的任务，发送它们的结果，然后才关闭。关闭期间到达的任务不会运行，会返回给 Dex。
- 较旧 SDK 的 Worker 因容量不足而拒绝了任务。

ASYNC Step 还有一种情况。如果 Dex Server 节点在 ASYNC 的开始记录写入 object storage 之前崩溃，Dex 会回滚这次开始。同一个 attempt 编号随后再次运行，不消耗 retry，输入也可能不同。因此对 ASYNC 来说，同一个 attempt 编号可能运行两次，两次执行也可能重叠。这时 Step Stream 的写入可能在同一个 source 中重复。

不论哪种 durability，同一个 Step 的各次 attempt 都不是严格顺序的。取消是协作式的，所以被中断的执行可能仍在运行，而下一次 attempt 或 failure route 已经开始。

| | SYNC（默认） | ASYNC |
| --- | --- | --- |
| 一个 attempt 编号会到达几个 Worker | 最多一个，上面描述的 attempt 回到 pending 的情况除外。 | 最多一个，但节点崩溃后的回滚会让同一个编号再次运行。 |
| 开始与执行的顺序 | 开始记录在 Worker 收到任务之前已经持久化。 | Worker 可能在开始记录持久化之前就运行。 |
| Worker 断开或节点 failover | attempt 失败，retry policy 运行。 | 相同。开始记录写入之前节点崩溃属于回滚的情况。 |
| **attempt_progress** | **NOT_STARTED** 或 **NOT_COMPLETED**。 | 始终是 **NOT_COMPLETED**。 |
| attempt 重叠 | 取消之后可能出现，因为取消是协作式的。 | 取消之后可能出现，同一个 attempt 编号的两次执行之间也可能出现。 |
| Step Stream 写入 | 可能在各次 attempt 之间重复。 | 在同一个 attempt 编号内也可能在同一个 source 中重复。 |
| 何时使用 | 需要最严格保证的副作用。 | 延迟重要、Step 较短，并且可以接受偶尔重新运行。 |

### Failure route 无法判断工作是否运行过 {#unknown-outcome}

没有 Worker 接收的 Step attempt 不会失败。它在持久任务队列中等待，不消耗 retry，有 Worker 接收后才运行。只有 RPC 会在 dispatch wait 内没有 Worker 接收时失败。确实失败的 Step attempt 可能在 Worker 收到它之前失败，也可能在之后失败，仅凭它的 error type 和 error detail 并不总能分辨是哪一种。

Recovery error（**RecoveryErrorInfo**）还带有 **attempt_progress**。它是失败的方法调用的所有 attempt 中走得最远的进度：

- **NOT_STARTED**：没有任何 attempt 到达过可能运行它的 Worker。Handler 一定没有运行。
- **NOT_COMPLETED**：至少有一个 attempt 被交给了 Worker 并且可能运行过，但没有一个完成。
- **UNSPECIFIED**：较旧的 server 没有报告进度，或者调用在升级之前就已开始。按 **NOT_COMPLETED** 处理。

ASYNC 的失败始终报告 **NOT_COMPLETED**，因为被回滚的执行可能已经运行过。

**NOT_COMPLETED** 是保守的。即使 Worker 从未运行 handler，Dex 也可能报告它：

- Server 在开始记录持久化之后、任务到达 Worker 之前崩溃。
- 连接在 Dex 刚写出任务之后、Worker 读取之前断开。
- Worker 拒绝了任务或干净地关闭了，但 server 在记录这件事之前崩溃。
- SDK 在调用 handler 之前失败，例如读取输入 blob 或解码。Dex 把它报告为普通的 Worker 错误。**FlowServiceAddress** 配置错误会让每个带有 blob 输入的 attempt 都这样失败。**values.hydrateBeforeDispatch** 可以避免。

Failure route 可以依赖 **NOT_STARTED** 表示工作没有运行，但不能依赖 **NOT_COMPLETED** 表示工作运行过。Flow 的 history 会记录 Dex 所知道的情况，Dex Web 也会显示。

### 按这些限制设计 {#design-for-redelivery}

- 让每个外部副作用保持幂等。用一个在各次 attempt 之间保持不变的 ID 作为 key，例如 Flow ID 加 Step execution ID，或者你自己的业务 key。把这个 key 发送给执行副作用的服务，让它只执行一次。
- 只有在这些限制之内，单次 attempt 的 Step 才算 at most once。被中断的 attempt 可能已经发出调用，被取消的执行也可能仍在运行。它的 failure route 可能在工作已经发生时运行，也可能在工作从未运行时运行。对 ASYNC 来说，同一个 attempt 编号还可能运行两次。
- 对结果未知的情况做对账。当 failure route 看到 **NOT_COMPLETED** 时，先用幂等 key 或业务 key 到目标系统中检查，再决定是否重复或报告这个副作用。把查到的结果记录到 Flow 中。

关于 agent 包中单次 attempt 的 tool Step，见 [Tool call limits](/production/agents#tool-call-limits)。
