# Metrics and alerts

Set **metrics.listen** to serve plain HTTP **GET /metrics** on its own listener,
separate from **api.listen**. It is empty by default, which turns the endpoint
off. The endpoint has no authentication, so never expose it publicly. In Kubernetes, bind it to
**0.0.0.0:9090** and restrict access with a NetworkPolicy.

The response uses the OpenMetrics text format. The endpoint also serves metrics
while the node recovers or waits for its lease. Every label value comes from a
fixed set.
No series has a Flow, Flow type, partition, tenant, or key label.

## Metrics levels {#metrics-levels}

Since 0.1.29, **metrics.level** selects the metric families that the endpoint
exports. It defaults to **advanced**. Each level exports every family of the
levels below it.

~~~yaml
metrics:
  listen: 0.0.0.0:9090
  level: advanced
~~~

| Level | Exports | Use it for |
| --- | --- | --- |
| **basic** | Golden signals: serving, errors, latency, saturation, and the health of commits and object storage | SLOs and page-worthy alerts with the fewest series |
| **advanced** (default) | Adds capacity, cost, and the lag and failure signals of hot standby, external search, Attribute Store sync, and history offload | Operating a deployment |
| **verbose** | Adds internal mechanisms, invariant detectors that also log, throughput detail, and the Linux process metrics | Investigating a problem |

A family has the same labels and histogram buckets at every level that exports
it, so one dashboard or alert works at each of those levels. The level changes
only what a scrape returns. The node records every metric at every level.
**basic** also skips the local disk walk behind **dexzd_local_storage_bytes**,
and only **verbose** reads the Linux process metrics from **/proc**.

For scale, one node that ran a few Flows exported 68 series at **basic**, 155
at **advanced**, and 207 at **verbose**, plus 4 process series on Linux. The
partition count does not change these numbers.

Changed in 0.1.29: before this release, the endpoint exported every family.
The default **advanced** level now leaves out the **verbose** families listed
in the [catalog](#catalog), including the Linux **process_** metrics. Set
**metrics.level** to **verbose** to export them again.

Changed in 0.1.29: **dexzd_commit_batches_total** was removed. It always
equaled **dexzd_commit_latency_seconds_count**. Use that series instead.

## Catalog {#catalog}

Counters end in **_total**. A histogram exports **_bucket**, **_sum**, and
**_count** series; its buckets are listed in
[Histogram buckets](#histogram-buckets). The Level column names the lowest
level that exports the family. The [Labels](#labels) section lists each
label's values.

Since 0.1.29, **dexzd_object_store_versioned_listing_stale_total** counts
listings of versioned objects that missed a version the node had just written.
Only the **aliyunOSS** provider writes such versions, so other providers stay
at 0. Its **site** label is one of:

- **confirm_created_version**: the listing right after a write did not show
  the new version as the newest. The write fails with an unknown outcome, and
  the caller reads the key again.
- **reclamation**: the listing that deletes old versions did not show the
  version the node had confirmed, and no version two or more generations newer
  exists that could have deleted it. The node deletes nothing in that pass;
  the key's next write tries again.

Alert on any increase. In every test so far, an OSS listing showed each write
at once, so an increase means a listing lagged behind a write. Once every node
runs 0.1.29 or later, replacements stay correct while that lag is shorter than
10 minutes. See
[Aliyun OSS provider](/reference/server/0.1.30/object-storage#aliyun-oss).

## Labels {#labels}

Most labeled families export every label combination from startup.
**dexzd_api_requests_total**, **dexzd_object_store_requests_total**, and
**dexzd_step_attempt_failures_total** export a combination once it first
counts.

| Label | Values |
| --- | --- |
| **outcome** | **ok**, **error**; for **dexzd_history_uploads_total**, see below |
| **rpc_class** | **flow_write**, **flow_read**, **search**, **worker_poll**, **worker_respond** |
| **code** | The gRPC status code in snake case, such as **ok** or **unavailable** |
| **role** | **starting**, **standby**, **recovering**, **serving**, **draining** |
| **operation** | **put**, **get**, **list**, **delete** |
| **object_kind** | **log**, **snapshot**, **manifest**, **lease**, **history**, **other** |
| **durability** | **sync**, **async** |
| **failure_kind** | For Step failures: **worker_error**, **method_timeout**, **heartbeat_timeout**, **dispatch_error**, **invalid_response**, **unsupported_feature**, **value_too_large**, **request_too_large**, **retry_deadline**, **started_attempt_interrupted**. For Attribute Store sync: **retryable**, **non_retryable** |
| **close_status** | **completed**, **failed**, **terminated**, **canceled** |
| **event** | **delivered**, **closed** |
| **reason** | For unserved queues: **no_worker**, **no_supporting_worker**. For returned attempts: see below. For dropped Step Stream writes: see [Streams](/reference/server/0.1.30/configuration#streams) |
| **error** | See below |
| **state** | **inactive**, **bootstrapping**, **following**, **behind**, **restarting**, **failed** |
| **standby_mode** | **hot**, **cold** |
| **store_source** | **hot_standby**, **restored** |
| **kind**, **source** | **page** or **blob**; **local**, **cache**, or **object_store** |
| **site** | **confirm_created_version**, **reclamation** |

**rpc_class** labels the latency histogram only for the unary classes, so
**worker_poll** has no latency series. Only a standby in **following** is hot.
The active process and a cold standby report **inactive**. **store_source** is
**hot_standby** when the node serves the store that its hot standby kept
current. It is **restored** when the node opened its own store or restored a
snapshot, for example because the standby store was missing or stale.
**dexzd_takeover_duration_seconds** covers only hot takeovers, labeled by
**store_source**.

**dexzd_step_attempts_returned_total** counts attempts that went back to
pending without consuming a retry. Its **reason** is one of:

- **unsupported**: a Worker declined the Step type.
- **legacy_no_capacity**: a Worker on an older SDK declined for capacity. This
  count should drop to zero once every SDK is upgraded.
- **not_delivered**: the task never reached the Worker.

The **error** label of **dexzd_worker_stream_protocol_errors_total** is one of:

- **no_capacity_on_reserved_slot**: a reserved-slot Worker declined a task for
  capacity. The attempt fails as not run, and the stream ends.
- **half_close_after_output**: a Worker closed its stream after it sent output
  but before the final result. The attempt fails with NOT_COMPLETED.
- **reject_after_output**: a Worker declined a task after it had already sent
  output for it. The attempt fails as possibly run, with NOT_COMPLETED. The
  server ends that stream with INVALID_ARGUMENT, so the stream gets no more
  tasks.

**dexzd_matching_unsupported_type_evictions_total** is a counter. It counts
evictions from the cache of pairs that Dex remembers as unsupported. Dex does
not send an evicted pair to its Worker again until that Worker completes a
Step. So while the cache overflows, a type that a Worker declined can be
offered to it again after each Step it completes. Raise
**matching.unsupportedTypeCacheEntries** when this counter rises steadily or
the server logs the full-cache WARN.

Workers poll over one persistent stream, so there is no count of empty polls.
**dexzd_worker_stream_events_total** counts each stream close. With
**event="delivered"**, it counts every task frame sent, including RPC task
frames. When Dex hands out a returned attempt again, it counts again. Long-poll
waits count toward **flow_read** latency.

## History offload metrics {#history-offload-metrics}

Changed in 0.1.23: **dexzd_history_offload_mode_skipped_partitions_total** was
removed with the **history.offloadEnabled** switch. Each Flow run now chooses
history offload when it starts, so partitions no longer record an offload mode.

**dexzd_history_upload_backlog_segments** counts sealed history segments that
are not uploaded yet. It changes as each seal and each recorded upload commits.
**dexzd_history_upload_backlog_bytes** is the uncompressed size of those
segments. That gauge and **dexzd_history_upload_oldest_sealed_age_seconds** come
from a rescan of every partition each minute. Both drop to 0 once the segment
count does. The rescan also corrects the segment count, for example after a
Flow run with waiting segments is deleted. Changed in 0.1.23: before this
release, the segment count also came only from that rescan. A backlog that grew
after a rescan did not show until the next one, and a node that ran for less
than a minute showed 0.

Since 0.1.23, **dexzd_history_upload_concurrency_limit** is the number of
uploads the node currently allows at once, and
**dexzd_history_upload_in_flight_bytes** is the bytes those uploads reserve for
encoding and encoded objects. See
[Upload concurrency](/reference/server/0.1.30/configuration#history-upload-concurrency).

The **outcome** of **dexzd_history_uploads_total** is one of:

- **created**.
- **already_present**: a repeated upload found the same content.
- **replaced**: an existing object had other content.
- **failed**.

The first three are counted once the upload is recorded. The server retries a
transient object storage failure with backoff, and any other failure at the
next rescan. Alert when
**dexzd_history_upload_oldest_sealed_age_seconds** stays above 900, or when
**dexzd_history_upload_checksum_mismatches_total** or
**dexzd_history_upload_rescan_errors_total** rises.

Since 0.1.22, **dexzd_history_expired_objects_deleted_total** counts the objects
of expired history segments that the node deleted.
**dexzd_history_orphan_objects_deleted_total** counts the history objects of
deleted Flow runs that its periodic sweep removed.

**dexzd_history_reads_total** counts history reads. **kind** is **page** for
GetHistoryEvents and **blob** for LoadBlobs. For a page, **source** is **local**
when only local disk served it. Otherwise the read counts once for each part of
an uploaded segment that it read, the header or the records: **cache** when the
part came from the disk read cache, and **object_store** when it came from
object storage. For LoadBlobs, **source** is
**local** for each value that local disk served, **cache** for each value from
the disk read cache, and **object_store** for each value and each segment header
read from object storage.

Since 0.1.22, **dexzd_history_value_revivals_total** counts values that the
lease holder restored on local disk from their uploaded segments. The lease
holder does this when a Worker result, client write, or RPC result references a
value after offload deleted it locally. The reads behind these restores count
as LoadBlobs reads in **dexzd_history_reads_total**.

## Alerts {#alerts}

Each of these alerts works at the **basic** level and above.

~~~text
# Failed API calls by class and code
sum by (rpc_class, code) (rate(dexzd_api_requests_total{code!="ok"}[5m]))

# A node that is not serving
dexzd_node_role{role="serving"} == 0

# Failed lease renewals
increase(dexzd_lease_renewals_total{outcome="error"}[10m]) > 0
~~~

The alerts on the [High availability](/reference/server/0.1.30/high-availability#hot-standby-lease-and-alerts),
[Search](/reference/server/0.1.30/search#search-projection-monitoring), and
[Attribute Store sync](/reference/server/0.1.30/attribute-store-sync#attribute-store-monitoring)
pages need the default **advanced** level unless their comment names another
level.
