# Flows and Steps

This page covers Flow and Step behavior in the Rust SDK: start options,
Flow configuration, waits, Step decisions, Step options, and what happens when
an attempt fails or is interrupted. For the concepts, read
[Flow](/primitives/flow) and [Step](/primitives/step) first. For the exact
signature of one API, read the [Rust SDK API reference](./index.mdx#api-reference).

## Flow definition {#flow-definition}

A Flow registers its Steps, its persistence schema, and its RPC handlers.

- **steps** registers one start Step and every
  other Step type the Flow may reach through Step decision movements. The
  start Step input type is also the Flow start input type. An empty Step list,
  or a list with no start Step, is valid when the Flow is driven entirely by
  RPCs that later move into Steps.
- The persistence schema lists every Attribute and Channel used from Steps or
  RPCs. Dex rejects reads and writes to names that are not declared.
- Return an **RpcList** from **rpcs** to bind RPC definitions to handlers.
  **Rpc::new** declares the durable RPC name explicitly.

Most SDKs derive the **FlowType** and the **StepType** from the native type
name unless you override it.

## StartFlowOptions {#start-flow-options}

**StartFlowOptions** apply when a client starts a Flow or a SubFlow. They are
immutable after start.

| Field | Purpose |
|-------|---------|
| **Timeout** | Flow timeout. Omit it or set zero to disable it. |
| **TimeoutPolicy** | What happens when the Flow timeout fires. |
| **TimeoutHandlerOptions** | Execution, retry, recovery, durability, locking, and state loading for a timeout handler. |
| **IDReusePolicy** | How to reuse an existing Flow ID to start. |
| **RequestID** | Idempotency key for retrying one start request. |
| **AlreadyStartedOptions** | How to handle an already-started Flow. |
| **RetryPolicy** | Not supported. server-zd rejects it with **INVALID_ARGUMENT**. See [RetryPolicy](#retry-policy). |
| **StartDelay** | Not supported. server-zd rejects a positive value with **INVALID_ARGUMENT**. See [StartDelay](#start-delay). |
| **Attributes** | Initial Attribute values. |
| **FlowConfig** | Per-execution Flow configuration, sent as **ConfigOverride**. |

For an application-defined outcome at the Flow deadline, see
[Graceful Timeout](/design-patterns/failure-handling/graceful-timeout).

```rust
fn start_flow_options() -> StartFlowOptions {
    StartFlowOptions::new()
        .timeout(Duration::from_secs(3_600))
        .config_override(FlowConfig::new().step_durability(StepDurability::Sync))
}
```

### Timeout and TimeoutPolicy {#timeout-and-timeout-policy}

**Timeout** is one durable timer for the whole Flow. Set **TimeoutPolicy** only
when **Timeout** is positive.

- **FAIL**: fail the Flow with a timeout error.
- **CANCEL**: cancel the Flow. It does not retry.
- **HANDLER**: run one logical Flow timeout-handler execution.

With a positive **Timeout**, a Dex SDK uses **FAIL** by default. If the Flow has
a timeout handler, it uses **HANDLER** instead. **HANDLER** is invalid when the
Flow has no handler.

**TimeoutHandlerOptions** is valid only with a positive **Timeout** and a final
**HANDLER** policy. It uses Execute semantics: a method timeout limits each
attempt, **Retry** can run multiple attempts, **HeartbeatTimeout** detects
stalled attempts, and **Failure** can route exhausted retries to a registered
no-input Step. The recovery Step receives null or unit input and reads the
final error from the handler **Context**.

The handler's attempt and retry clocks begin when the soft Flow timeout fires.
They may extend past the original Flow deadline. If no failure target is
configured, an exhausted handler fails the Flow.

Ordinary Attributes and all Channel size metadata load automatically.
AttributeMap values and pending Channel messages require explicit selections in
**TimeoutHandlerOptions**. The handler may stage Attribute writes, Channel
deletions, and Channel publications before returning its decision. Flow-level
retry does not exist, so the timeout handler runs once per Flow run.

Set **TimeoutPolicy** to **HANDLER** to run this code when the timeout fires.
This handler records why the Flow ended, then fails it with an application
reason.

```rust
impl ExampleFlow {
    fn describe(&self, context: &mut Context, _input: ()) -> HandlerResult<RpcResult<String>> {
        let value = STATUS.get(context)?.unwrap_or_default();
        Ok(RpcResult::new(value))
    }

    fn handle_timeout(&self, context: &mut Context) -> HandlerResult<StepDecision> {
        STATUS.set(context, "timed out".to_string())?;
        Ok(StepDecision::force_fail("processing deadline reached"))
    }
}

impl Flow for ExampleFlow {
    type StartInput = i32;

    fn steps(&self) -> StepList<'_, Self::StartInput> {
        StepList::start(&self.example).and(&self.finish)
    }

    fn persistence(&self) -> PersistenceSchema {
        PersistenceSchema::new().attribute(&STATUS).channel(&NOTIFY)
    }

    fn timeout_handler(&self) -> Option<FlowTimeoutHandler<Self>> {
        Some(Self::handle_timeout)
    }

    fn rpcs(&self) -> RpcList<Self> {
        RpcList::new().function(DESCRIBE, Self::describe)
    }
}
```

### Flow ID, RequestID, and AlreadyStartedOptions {#flow-id-request-id-and-already-started}

**IDReusePolicy** says what to do when this Flow ID already exists.
**RequestID** says whether this call retries the same start request.

<a id="how-these-options-work-together"></a>
<a id="这些选项如何一起工作"></a>

These options answer different questions, in this order:

1. **RequestID** identifies one start request. When omitted, the SDK generates
   a new UUID, so another StartFlow call is a new request. Reuse it only for a
   retry of the exact same start. Dex compares the RequestID, not the start
   input or options.
2. **IDReusePolicy** decides whether that request may start another run with
   this Flow ID.
3. **AlreadyStartedOptions.IgnoreError** matters only when the ID reuse policy
   rejects the start as already started. It returns the existing Run ID only
   when the RequestID matches.

| Retry request | **AlreadyStartedOptions.IgnoreError** | When the ID reuse policy rejects the start |
|---------------|---------------------------------------|---------------------------------------------|
| No **RequestID** | Off or on | The SDK sends a new UUID. Dex returns an already-started error. |
| A different **RequestID** | Off or on | Dex returns an already-started error. |
| Same **RequestID** | Off | Dex returns an already-started error. |
| Same **RequestID** | On | Dex returns the existing Run ID. |

The ID reuse policy determines whether Dex rejects the start in the first place:

| **IDReusePolicy** | Existing active Flow | Existing closed Flow |
|-------------------|----------------------|----------------------|
| **IDReuseDefault** | Rejects the start. A matching RequestID with **IgnoreError** returns the active Run ID. | Rejects the start. A matching RequestID with **IgnoreError** returns the existing Run ID. |
| **IDReuseAllowIfPreviousFailed** | Rejects the start. A matching RequestID with **IgnoreError** returns the active Run ID. | Starts a new run only after a failed run; otherwise rejects it. |
| **IDReuseAllowIfNotRunning** | Rejects the start. A matching RequestID with **IgnoreError** returns the active Run ID. | Starts a new run. |
| **IDReuseDisallow** | Rejects the start. A matching RequestID with **IgnoreError** returns the existing Run ID. | Rejects the start. A matching RequestID with **IgnoreError** returns the existing Run ID. |
| **IDReuseTerminateIfRunning** | Terminates the active run and starts a replacement. It does not produce an already-started error. | Starts a new run. |

<a id="what-dex-server-does"></a>
<a id="dex-server-的逻辑"></a>

#### What Dex Server does {#start-request-server-behavior}

Dex Server requires a non-empty **RequestID**. An SDK generates one before
sending the request when you omit it. The server records it with the Flow
execution, then starts the Flow using the requested ID reuse policy.
**IDReuseDefault** uses the server default: reject every previously used Flow
ID. Choose **IDReuseAllowIfNotRunning** explicitly when a closed Flow ID should
start a new execution.

If the Flow is already started, Dex checks
**AlreadyStartedOptions.IgnoreError**. When it is on, Dex reads the existing
run's recorded RequestID. It returns that Run ID only when the two RequestIDs
match. Otherwise it returns the already-started error.

### StartFlow best practices {#start-flow-best-practices}

Call **StartFlow** directly with a stable business **Flow ID**. Do not read a
snapshot, search for the Flow, or check its status first just to avoid a
possible retry conflict. A successful start also needs no read to recheck the
identity, owner, or initial Attributes you supplied.

For retries of one logical start, combine a stable **RequestID**,
**IDReuseDisallow**, and the ignore-already-started option. Keep the same input
and options on every retry. **IDReuseDisallow** prevents another execution
after closure; a policy that permits another run can bypass the
matching-RequestID path.

The following helper accepts a validated integer input and a stable Flow ID.
Those are the complete business inputs in this example, so together they
determine the RequestID. All other start values are fixed. In a real
application, include every logical input that changes the operation, such as
tenant, owner, mode, revision, or initial business Attributes. Dex compares
RequestIDs; it does not compare payload equality. Do not reuse a RequestID for
a changed logical request.

The helper returns the known business Flow ID after acceptance and propagates
errors. It performs no read before or after the start. The returned ID is an
acknowledgement, not a current business snapshot or proof that the Flow has
completed.

```rust
pub fn start_example_flow_request(
    client: &Client,
    example_flow: &ExampleFlow,
    flow_id: &str,
    input_num: i32,
) -> SdkResult<String> {
    let options = StartFlowOptions::new()
        .id_reuse_policy(IdReusePolicy::Disallow)
        .request_id(format!("start-example-flow:{input_num}:{flow_id}"))
        .ignore_already_started(true)
        .initial_attribute(&STATUS, "queued".to_owned());
    client.start_flow_with_options(example_flow, flow_id, input_num, options)?;
    Ok(flow_id.to_owned())
}
```

Example: [examples/rust/src/primitives/flow/controller.rs](https://github.com/superdurable/dex/tree/main/examples/rust/src/primitives/flow/controller.rs)

For example, starting **invoice-42** with input **7** sends RequestID
**start-example-flow:7:invoice-42**. Retrying that call returns the same
execution, even after it closes, while Dex retains it. Starting the same Flow
ID with input **8** sends a different RequestID and returns an already-started
error. No snapshot comparison is needed on the successful path.

#### Wait when the response promises a business milestone {#wait-for-required-milestone}

If the API must confirm an important operation, call **WaitForAttributeMatch**
or **WaitForStepCompletion** immediately after **StartFlow** succeeds,
including matching-request deduplication. Deduplication confirms the same start
was accepted; it does not prove the operation has finished. No identity-check
read is needed between the start and the wait.

For example, an API may promise that a row has been committed to a database
table used as the business source of truth. The owning Flow writes that row in
**Execute**, then records a committed Attribute or completes the persistence
Step. The API waits for that committed Attribute value or the specific
**StepExecutionID** before returning confirmed persistence. Publish the marker
only after the database commit succeeds. **WaitForStepCompletion** confirms
that Step completed; it does not return its output or wait for the whole Flow
to finish.

```text
API → StartFlow succeeds or deduplicates → wait for the required commit milestone
Flow Execute → commit business row to database → record committed Attribute / complete Step
API → milestone wait succeeds → return confirmed persistence
```

Wait only for the condition that establishes the response's promised outcome.
If the response only acknowledges accepted background work, return immediately
after the start without a wait. Bound required waits with a caller deadline or
request timeout. A wait timeout does not undo the start or prove the database
write failed; report completion as pending or unknown according to the API
contract and preserve the same start identity for retries.

See [Wait for a Step](/reference/server/runtime-client#wait-for-a-step) and
[Wait for an Attribute match](/reference/server/runtime-client#wait-for-an-attribute-match)
for these waits. Attribute waits target an active run. If a Flow
closes before the wait attaches, reconcile the actual wait error through the
authoritative business record or a supported terminal read; do not assume the
Attribute wait can query a closed run.

#### Read only when the error outcome needs it {#start-error-reconciliation}

Error handling follows the business contract. If an already-started error can
simply become **ALREADY_EXISTS**, return that conflict directly. Do not add a
read-only RPC just because the error occurred. The helpers above preserve the
typed error for that boundary translation.

Read existing state only when it changes the response or next business
decision. For example, an API that explicitly permits continuing an existing
operation may call its typed read-only RPC after the conflict to decide whether
that operation satisfies the request. An API that promises a current snapshot
must read current state; it cannot label the submitted initial Attributes as
that snapshot. An accepted start does not prove business completion.

| Situation | Action |
| --- | --- |
| Start accepted; response only acknowledges acceptance | Return the Flow ID and the agreed acceptance fields. No snapshot read. |
| Start accepted or deduplicated; response promises a critical operation | Wait for the committed Attribute condition or selected Step completion, then return that milestone outcome. |
| Already started; business accepts **ALREADY_EXISTS** | Return the conflict. No snapshot read. |
| Already started; business permits resuming an existing operation | Read its typed snapshot only to decide whether that contract permits resuming it. |
| Response lost; start acceptance is unknown | Retry within a bounded policy with the same identity and options, or read authoritative state if it can establish the outcome. |

Do not retry a proven conflict indefinitely. If no stable RequestID was
supplied, separate SDK calls use fresh IDs; enabling the ignore option alone
does not deduplicate them.

#### Put dependent starts inside the owning Flow {#durable-dependent-starts}

For one business operation, the API starts one owning Flow. Its durable Steps
perform the follow-on work. Do not start the first Flow, read its status, and
start a dependent Flow in the HTTP handler. If that process exits between the
starts, no durable Step owns the missing launch.

Use Steps when the work shares one identity and lifecycle. When it needs a
separate top-level Flow with its own owner and lifecycle, launch it from an
**Execute** Step with stable downstream Flow ID, RequestID, and start options.
Persist the launch input in the owning Flow. If the Worker dies after the
downstream start is accepted but before the Step commits, the Step can retry
the same start without creating another execution. Keep **WaitFor** for
durable conditions. A separately owned top-level Flow does not need to become a
SubFlow merely because another Flow starts it.

```text
API → StartFlow for the owning operation → accepted response
Owning Flow Execute → StartFlow for separately owned work → durable progress
Worker replacement → retry the same downstream start identity → no duplicate launch
```

### RetryPolicy {#retry-policy}

server-zd does not support a Flow-level **RetryPolicy**. A start request that
sets one fails with **INVALID_ARGUMENT**. Tracked in
[issue 996](https://github.com/superdurable/dex/issues/996). To retry work, use
[Step retry](#retry-and-failure-policies), which is supported.

### StartDelay {#start-delay}

server-zd does not support **StartDelay**. A start request with a positive
delay fails with **INVALID_ARGUMENT**. Tracked in
[issue 995](https://github.com/superdurable/dex/issues/995). To delay the first
work, start the Flow without a delay and begin the start Step with a durable
**Timer** wait.

### Attributes {#attributes}

**Attributes** write initial values. Each value must match an Attribute or
AttributeMap in the Flow persistence schema.

## FlowConfig {#flow-config}

**FlowConfig** holds runtime behavior. Unlike **StartFlowOptions**, it is
mutable after start.

Use **ConfigOverride** in **StartFlowOptions** to change the initial
configuration for one Flow. It changes only the fields you provide. It does not
replace the whole **FlowConfig**. At start, Dex applies the supplied fields
over the Dex Server defaults. Omitted fields keep their default values.

| Field | Behavior |
|-------|----------|
| **ActiveStepSearchMode** | Index every active Step, only Steps that ran **WaitFor**, or no active Steps. The built-in server default does not index active Steps. Set an explicit mode to opt in. |
| **StepDurability** | Default durability for methods without a Step override. Dex resolves a method override first, then this value, then **SYNC**. |
| **AttributeStoreNames** | Dex Server Attribute Stores for Attributes that opt in to Attribute sync. |

### Update FlowConfig with a Client {#update-flow-config-with-a-client}

Call **UpdateFlowConfig** while the Flow is active. Send only the fields you
want to change. Dex merges them with the existing configuration. The SDK
**UpdateFlowConfig** call does not change the Flow's Worker routing.

## Step methods and commits {#commit-boundary}

Each **WaitFor** or **Execute** invocation is a separate commit boundary. Dex
Server stages the Attribute writes and Channel publications from that method,
then commits them with its **Wait** or **StepDecision** only after the method
returns successfully. If the method fails, none of those durable changes are
committed. **WaitFor** and **Execute** do not share a commit. External API
calls are outside this atomic boundary.

Before its final **Wait** or **StepDecision**, a handler can send
[heartbeat checkpoints](#heartbeat) and any number of best-effort
[Stream messages](/primitives/stream). The response stream must end with
exactly one final result. These progress frames are not part of the method's
commit, and a Stream Store failure does not fail the Step.

## Waits {#waits}

**WaitFor** returns a **Wait** with a wait type and the conditions to wait for.
Dex persists the waiting state and evaluates the conditions when related state
changes. [Timer](/primitives/timer), [Channel](/primitives/channel), and
[SubFlow](/primitives/subflow) are the condition kinds.

- **Until** waits for one condition.
- **AnyOf** is met when any condition is met.
- **AllOf** is met when all conditions are met.
- **AnyCombinationOf** is met when any one group of conditions is all met.

**Until**, **AnyOf**, and **AllOf** accept Conditions without condition IDs. Do
not add IDs merely because a Condition is nested in one of these waits. Read
Channel results from the Channel definition and inspect Timer outcomes through
the **Context**. Add IDs only when another API requires them, such as
**AnyCombinationOf** or a Timer selected by ID.

```rust
impl Step for WaitTypesStep {
    type Input = WaitTypesInput;

    fn wait_for(&self, _context: &mut Context, input: Self::Input) -> HandlerResult<Wait> {
        let timeout = Duration::from_secs(input.timeout_seconds.max(0) as u64);
        match input.mode.as_str() {
            "any" => Ok(Wait::any_of([
                SIGNAL_A_CHANNEL.for_one().with_id("signal"),
                Timer::by_duration(timeout).with_id("timeout"),
            ])),
            "all" => Ok(Wait::all_of([
                SIGNAL_A_CHANNEL.for_one().with_id("signal-a"),
                SIGNAL_B_CHANNEL.for_one().with_id("signal-b"),
            ])),
            "combo" => Ok(Wait::any_combination_of([
                ConditionCombination::all_of([
                    SIGNAL_A_CHANNEL.for_one().with_id("signal-a"),
                    Timer::by_duration(timeout).with_id("timeout"),
                ]),
                ConditionCombination::all_of([SIGNAL_B_CHANNEL.for_one().with_id("signal-b")]),
            ])),
            _ => Err(HandlerError::new(
                "WaitTypes",
                format!("unknown wait mode {}", input.mode),
            )),
        }
    }

    fn execute(&self, _context: &mut Context, input: Self::Input) -> HandlerResult<StepDecision> {
        Ok(StepDecision::graceful_complete(input.mode))
    }
}
```

### Condition results {#condition-results}

After **WaitFor** completes, **Execute** can read what satisfied the Wait. For a
[Channel](/primitives/channel), use **GetConditionResults** / **results** /
**condition_results** to read published messages. For a
[SubFlow](/primitives/subflow), use **SubFlowResult** / **getConditionResults**
/ **condition_result** to decode the child Flow output.

Channel consumption is not greedy across **AnyOf** alternatives. Dex consumes
messages only from the Channel condition selected to satisfy the Wait. Other
Channel conditions consume nothing even if they are also ready, so their
messages remain queued.

When several **AnyOf** alternatives are ready in one evaluation, Dex selects
the first feasible candidate in canonical order: Timer conditions in
declaration order, then Channel conditions in declaration order, then SubFlow
conditions in declaration order. An earlier condition that is not ready does
not block a later ready condition. Mixed condition kinds therefore do not share
one global call argument order.

Use **AnyOf** for a race among the current alternatives. For strict priority
that must keep waiting for a higher-priority input, return only that condition
until it is resolved.

```rust
impl Step for ChannelWait {
    type Input = i32;

    fn options(&self) -> StepOptions<Self::Input> {
        StepOptions::new().execute_load_channel(&QUEUED_MESSAGES)
    }

    fn wait_for(&self, _context: &mut Context, input: Self::Input) -> HandlerResult<Wait> {
        Ok(Wait::any_of([
            APPROVAL_MESSAGES.for_one(),
            Timer::by_duration(Duration::from_secs(input.max(0) as u64)),
        ]))
    }

    fn execute(&self, context: &mut Context, _input: Self::Input) -> HandlerResult<StepDecision> {
        let pending_queued_messages = QUEUED_MESSAGES.pending_messages(context)?;
        if let Some(queued_message) = pending_queued_messages.first() {
            QUEUED_MESSAGES.delete(context, &queued_message.message_id)?;
            return Ok(StepDecision::graceful_complete(
                queued_message.value.clone(),
            ));
        }
        if context.has_any_timer_fired() {
            return Ok(StepDecision::graceful_complete(
                "approval timed out".to_owned(),
            ));
        }
        let approval_message_values = APPROVAL_MESSAGES.condition_results(context)?;
        Ok(StepDecision::graceful_complete(
            approval_message_values[0].clone(),
        ))
    }
}
```

### AnyCombinationOf {#anycombinationof}

**AnyCombinationOf** expresses an OR of AND groups. Build each inner group as
an all-of combination.

Channel consumption is not greedy across combinations. Dex consumes messages
only from Channel conditions in the selected combination. Conditions belonging
only to other ready combinations consume nothing, so their messages remain
queued.

Every Condition in its combinations requires a unique **condition ID**.

### Step execution local {#step-execution-local}

**SetStepExecutionLocal** stores a value on this **StepExecution** so
**Execute** can read it with **GetStepExecutionLocal**. Use it when **WaitFor**
computes something **Execute** needs but a Flow-level **Attribute** is
overkill. Step input is already passed to both methods. Do not copy input into
a local.

```rust
fn wait_for(&self, context: &mut Context, input: Self::Input) -> HandlerResult<Wait> {
    context.set_step_execution_local("note", format!("approval:{input}"))?;
    Ok(Wait::until(APPROVAL.for_one()))
}

fn execute(&self, context: &mut Context, _input: Self::Input) -> HandlerResult<StepDecision> {
    let note: String = context.step_execution_local("note")?;
    Ok(StepDecision::graceful_complete(note))
}
```

### Skip immediately {#skip-immediately}

**SkipWaitImmediately** waits for no condition. Use it in a dynamic **WaitFor**
method when one branch must not wait for anything.

```rust
Ok(Wait::skip_immediately())
```

## Step decisions {#step-decisions}

**Execute** returns a **StepDecision**. It moves to next Steps, closes the
Flow, or both stops this branch and cancels other Steps.

### Multiple next Steps {#gotomulti}

**GoTo** starts one next Step. **GoToMany** starts multiple next Steps. Each
Step movement has its own input and can also have its own
[Step options](#stepoptions-override-per-stepexecution).

```rust
impl Step for Route {
    type Input = String;

    fn execute(&self, _context: &mut Context, mode: Self::Input) -> HandlerResult<StepDecision> {
        match mode.as_str() {
            "graceful" => Ok(StepDecision::graceful_complete(String::from("done"))),
            "dead-end" => Ok(StepDecision::go_to_many([
                StepMovement::to(&BranchWorker, "left".to_string()),
                StepMovement::to(&BranchWorker, "right".to_string()),
            ])),
            _ => {
                let quote = Quote {
                    carrier: "winner".to_string(),
                    price: 9,
                };
                Ok(StepDecision::go_to_many([
                    StepMovement::to(
                        &CarrierA,
                        Quote {
                            carrier: "A".to_string(),
                            price: 10,
                        },
                    ),
                    StepMovement::to(
                        &CarrierB,
                        Quote {
                            carrier: "B".to_string(),
                            price: 12,
                        },
                    ),
                    StepMovement::to(&Winner, quote),
                ]))
            }
        }
    }
}
```

### Close decisions {#close-decisions}

| Decision | What it does |
| --- | --- |
| **GracefulComplete** | Stops this branch and triggers the Flow to prepare for completion. When all branches and Steps are stopped, the Flow completes. |
| **DeadEnd** | Stops this branch only. |
| **ForceComplete** | Completes the Flow immediately. |
| **ForceFail** | Fails the Flow immediately. |

**GracefulComplete** and **ForceComplete** can return an output. **ForceFail**
returns a failure reason. The Flow result returns each output with the Step
type and Step execution ID. When multiple Steps complete gracefully, all their
outputs return together.

A Flow can have no active Steps and still keep running. **DeadEnd** stops this
branch without making a decision that triggers the Flow to complete.

### ForceCompleteIfChannelsEmpty {#forcecompleteifchannelsempty}

**ForceCompleteIfChannelsEmpty** atomically checks whether all named Channels
are empty. A Channel with queued messages is non-empty. After a message is
consumed and committed to a Step, that Channel remains non-empty until the Step
finishes processing **Execute**. If every named Channel is empty, it completes
the Flow. Otherwise, it goes to other Steps.

Use it to drain Channels and complete the Flow, so the Flow can stay short. See
[Drain External Channel](/design-patterns/draining-channel-for-external-publishing)
for the full example.

```rust
impl Step for DrainChannel {
    type Input = String;

    fn wait_for(&self, _context: &mut Context, input: String) -> HandlerResult<Wait> {
        if input.is_empty() {
            return Ok(Wait::until(EXTERNAL_QUEUE.for_one()));
        }
        Ok(Wait::skip_immediately())
    }

    fn execute(&self, context: &mut Context, input: String) -> HandlerResult<StepDecision> {
        let item = if input.is_empty() {
            EXTERNAL_QUEUE
                .condition_results(context)?
                .into_iter()
                .next()
                .unwrap_or_default()
        } else {
            input
        };
        context.record_event("drained-channel", item)?;
        Ok(StepDecision::force_complete_if_channels_empty(
            String::new(),
            StepMovement::to(&DrainChannel, String::new()),
            [EXTERNAL_QUEUE.when_empty()],
        ))
    }
}
```

## StepOptions {#step-options}

A Step type returns **StepOptions** to customize its methods. **WaitFor** and
**Execute** have separate retry policies, timeouts, failure policies, state
selections, and lock sets.

### Override StepOptions per Step execution {#stepoptions-override-per-stepexecution}

The **StepOptions** returned by a Step implementation apply to every Step

**StepOptions** override when a **StepDecision** goes to the next Steps.

```rust
impl Step for OverrideFirst {

            .wait_for_failure(WaitForFailurePolicy::Proceed);

            &OverrideSecond,
            payload,

}
```

### Retry and failure policies {#retry-and-failure-policies}

- **Timeout** limits a single attempt of the method invocation. See
  [Timeouts and total duration](#timeouts-and-total-duration).
- **Retry policy** re-invokes the **same** method on the **same** Step
  execution until attempts are exhausted.
- **Failure policy** decides what happens **after** retries end. The default
  fails the Flow. **WaitFor** can run **Execute** anyway, and **Execute** can
  go to a recovery Step.

```rust
fn options(&self) -> StepOptions<Self::Input> {
    StepOptions::new().execute_retry(
        RetryPolicy::new()
            .initial_interval(Duration::from_secs(1))
            .backoff_coefficient(2.0)
            .maximum_attempts(5),
    )
}
```

Example: [examples/rust/src/primitives/step/retry_flow.rs](https://github.com/superdurable/dex/tree/main/examples/rust/src/primitives/step/retry_flow.rs)

#### WaitFor failure policy {#waitfor-failure-policy}

When **WaitFor** retries are exhausted:

- **FailFlow** fails the Flow. This is the default.
- **PROCEED** continues to invoke **Execute**.

With **PROCEED**, the same Step's **Execute** receives the durable input
unchanged. **waitForMethodFailed()** returns true. **getRecoveryError()** has
the error type and detail from the final failed **WaitFor** attempt.

```rust
impl Step for FailingWait {
    type Input = String;

    fn options(&self) -> StepOptions<Self::Input> {
        StepOptions::new()
            .wait_for_failure(WaitForFailurePolicy::Proceed)
            .wait_for_retry(RetryPolicy::new().maximum_attempts(2))
    }

    fn wait_for(&self, _context: &mut Context, _input: Self::Input) -> HandlerResult<Wait> {
        Err(HandlerError::new(
            "ProceedOnWaitFailure",
            "planned WaitFor failure",
        ))
    }

    fn execute(&self, context: &mut Context, input: Self::Input) -> HandlerResult<StepDecision> {
        if !context.wait_for_method_failed() {
            return Err(HandlerError::new(
                "ProceedOnWaitFailure",
                "waitFor failure was not reported",
            ));
        }
        Ok(StepDecision::go_to(&Finish, format!("{input}_recovered")))
    }
}
```

### RetryAfter {#retry-after}

Use **RetryAfter** to choose the delay before the next attempt. It overrides
the retry schedule of the **RetryPolicy**.

Retries recover from failed attempts. Do not use **RetryAfter** to wait for an
external system; use the [Polling](/design-patterns/polling) pattern.

A retry of one **Execute** call reuses the
[state snapshot](#selective-state-loading) loaded for that attempt.
To wait for an external write, have the writer also publish a
[Channel](/primitives/channel) message, directly or from an RPC handler, and
wait on that message in the **WaitFor** of the next Step. Alternatively, the
next Step can wait on a [Timer](/primitives/timer) and read fresh state when it
runs.

```rust
if i32::try_from(context.attempt()).unwrap_or(i32::MAX) < ready_after_attempt {
    return Err(HandlerError::retry_after(
        7,
        "CustomRetry",
        format!("not ready on attempt {}", context.attempt()),

}
Ok(StepDecision::graceful_complete(String::from("ready")))
```

### Durability {#durability}

**SYNC** durability records the Step completion in Dex Server and persists it
to storage synchronously.

**ASYNC** durability does this asynchronously. Dex Server starts the next work
before the Step completion is persisted, and it batches these commits within
about 20 milliseconds.

If a Dex Server node fails before the commit, a recent **ASYNC** result is
lost. The method runs again, and so does any later work that started from that
result. Make **ASYNC** methods and the work they start idempotent.

**SYNC** is the default. Dex resolves durability in this order: a method
override in **StepOptions**, the Flow's **FlowConfig**, then **SYNC**.

Durability changes only when Dex Server persists a result. Retry policy, method
timeout, and heartbeat settings apply to every attempt in both modes.

```rust
impl Step for SyncWork {
    type Input = String;

    fn options(&self) -> StepOptions<Self::Input> {
        StepOptions::new().execute_durability(StepDurability::Sync)
    }

    fn execute(&self, _context: &mut Context, mode: Self::Input) -> HandlerResult<StepDecision> {
        Ok(StepDecision::go_to(
            &FinishDurability,
            format!("sync:{mode}"),
        ))
    }
}

impl Step for AsyncWork {
    type Input = String;

    fn options(&self) -> StepOptions<Self::Input> {
        StepOptions::new().execute_durability(StepDurability::Async)
    }
```

### Timeouts and total duration {#timeouts-and-total-duration}

Three options bound the time a Step method can take.

| Limit | Option | Default | Enforcement |
| --- | --- | --- | --- |
| Longest single attempt | **WaitForMethodTimeout** or **ExecuteMethodTimeout** | Two hours. The server has no hard cap. | Dex times out the attempt. Another attempt starts only while **TotalDuration** has time left. |
| Longest total time, including every retry | **TotalDuration** in the retry policy | Four hours, for both durability modes. | The budget starts when the first attempt is scheduled and covers every retry. It also stops the attempt in progress. |
| Stalled Worker | **HeartbeatTimeout** | One minute. The default allowed minimum is 10 seconds. | Dex times out an attempt that sends no heartbeat or Stream message within this window. The retry policy then starts another attempt. See [Heartbeat](#heartbeat). |

An attempt's deadline is the method timeout, shortened to the time left in
**TotalDuration**. An attempt that **TotalDuration** stops fails with the
RETRY_DEADLINE failure kind.

To bound a long wait, set the method timeout and **TotalDuration** to the same
maximum. Dex enforces both, so the Step does not need its own deadline. Give
the retry policy a few attempts with backoff for transient errors and Worker
crashes.

When a timeout expires, Dex fails the attempt with a timeout error. After
retries end, the failure policy decides what happens next. If no failure route
is configured, the Flow fails. See
[Execute Failure Recovery](/design-patterns/failure-handling/execute-failure-recovery).
For a long wait on an external system, see
[Polling](/design-patterns/polling).

### Heartbeat {#heartbeat}

During an attempt, the Worker must send a heartbeat or a
[Stream message](/primitives/stream) before the **HeartbeatTimeout** expires.
Sending a Stream message is an implicit heartbeat.

For example, an **Execute** method timeout of 60 seconds and a
**HeartbeatTimeout** of 10 seconds lets Dex retry the Step in about 10 seconds
instead of waiting for the full 60 seconds. To wait for an external system in
one heartbeating Step, use the [Polling](/design-patterns/polling) pattern.

A heartbeat can persist a checkpoint value. The next attempt receives the
latest stored value and can resume from it. An explicit heartbeat without a
value clears the previous checkpoint. An implicit heartbeat from a Stream
message preserves the latest explicit state, including an explicitly cleared
state. Checkpoints are lossy; see
[Heartbeats are not acknowledged](#heartbeats-not-acknowledged).

```rust
fn options(&self) -> StepOptions<Self::Input> {
    StepOptions::new()
        .execute_method_timeout(Duration::from_secs(60))
        .heartbeat_timeout(Duration::from_secs(10))
        .execute_retry(RetryPolicy::new().maximum_attempts(3))
}

fn execute(&self, context: &mut Context, batches: Self::Input) -> HandlerResult<StepDecision> {
    let completed_batches = context.last_heartbeat_value::<i32>()?.unwrap_or_default();
    for batch in completed_batches..batches {
        if context.is_cancelled() {
            return Ok(StepDecision::dead_end());
        }
        thread::sleep(Duration::from_secs(2));
        context.record_heartbeat_value(batch + 1)?;
    }
    Ok(StepDecision::graceful_complete(String::from("processed")))
}
```

### Cancellation {#cancellation}

Dex cancels a running attempt directly. It sends a cancel request to the
Worker when the Step is canceled, for example by a **StepDecision** or an RPC,
and when the attempt times out. The SDK also cancels the handler when the
attempt deadline in the task passes. The handler does not need to complete,
fail, or record a heartbeat to receive cancellation.

Cancellation is cooperative. The SDK cannot stop running code. A long handler
must check for cancellation and return, as the heartbeat example above does.
See [Make the Step stop](/reference/server/runtime-data#cancel-honour) for the
check in each language, and
[Cancel running Steps](/reference/server/runtime-data#cancel-running-steps) for
how Dex ends a canceled attempt.

Because cancellation is cooperative, an interrupted execution may still run
while the next attempt or the failure route starts.

### Selective state loading {#selective-state-loading}

Every **WaitFor**, **Execute**, and timeout-handler call receives all ordinary
Attributes and size metadata for every Channel and ChannelMap instance.
AttributeMap values and pending Channel messages are not loaded unless that
method selects them.

**StepOptions** has separate selections for **WaitFor** and **Execute**. Select
an entire AttributeMap or ChannelMap when the method must enumerate current
instances. Select an exact map instance when its key is already known. An
Attribute lock controls concurrency but does not load the AttributeMap value.

The two methods receive independent snapshots. **Execute** reads its snapshot
after the winning Wait conditions consume their messages, so it does not see
those consumed messages again. A retry reloads state and reacquires its
Attribute locks for the new attempt.

This Step loads pending queued messages only for **Execute**. It deletes the
first pending message in the same successful handler response.

```rust
impl Step for ChannelWait {
    type Input = i32;

    fn options(&self) -> StepOptions<Self::Input> {
        StepOptions::new().execute_load_channel(&QUEUED_MESSAGES)
    }

    fn wait_for(&self, _context: &mut Context, input: Self::Input) -> HandlerResult<Wait> {
        Ok(Wait::any_of([
            APPROVAL_MESSAGES.for_one(),
            Timer::by_duration(Duration::from_secs(input.max(0) as u64)),
        ]))
    }

    fn execute(&self, context: &mut Context, _input: Self::Input) -> HandlerResult<StepDecision> {
        let pending_queued_messages = QUEUED_MESSAGES.pending_messages(context)?;
        if let Some(queued_message) = pending_queued_messages.first() {
            QUEUED_MESSAGES.delete(context, &queued_message.message_id)?;
            return Ok(StepDecision::graceful_complete(
                queued_message.value.clone(),
            ));
        }
        if context.has_any_timer_fired() {
            return Ok(StepDecision::graceful_complete(
                "approval timed out".to_owned(),
            ));
        }
        let approval_message_values = APPROVAL_MESSAGES.condition_results(context)?;
        Ok(StepDecision::graceful_complete(
            approval_message_values[0].clone(),
        ))
    }
}
```

Example: [examples/rust/src/primitives/channel/flow.rs](https://github.com/superdurable/dex/tree/main/examples/rust/src/primitives/channel/flow.rs)

### Attribute locks {#attribute-locks}

Concurrent Steps and RPC invocations can read and write the same Attribute. To
avoid races, use Attribute locks. Dex Server ensures only one Step execution or
RPC handling can acquire the lock at a time. **WaitFor** and **Execute** have
separate lock sets. Set them by returning **StepOptions**.

See [Attribute locks](/reference/server/runtime-data#attribute-locks) for when
a Step attempt takes and holds its locks, with **WaitFor** and **Execute**
examples. See [Locks](/primitives/attribute#locking) for the lock model.

## Failure and redelivery {#failure-and-redelivery}

Retries and failure routes handle attempts that fail. Some failures leave Dex
without knowing whether the work ran. A Step with an external effect that must
not repeat, such as a payment or an email, has to plan for these cases. This
section states what an application can rely on.

### Heartbeats are not acknowledged {#heartbeats-not-acknowledged}

A heartbeat call returns once the Worker has queued or sent it. It does not
wait for Dex to store anything. Python's **heartbeat**, Go's
**RecordHeartbeat**, Java's and TypeScript's **recordHeartbeat**, and Rust's
**record_heartbeat** all behave this way. A returned heartbeat call does not
prove that Dex knows the attempt started its work.

Heartbeat checkpoints are lossy. Dex batches them and keeps only the latest
value of each batch. A checkpoint can also be lost when the attempt ends, such
as on a timeout or a cancellation, or when a Dex Server node fails. After an
interruption, the next attempt receives the last checkpoint that Dex stored.
That checkpoint can be older than the last one the Step sent. Do not use a
checkpoint as the only record that an external effect happened.

### An attempt can run again at the same attempt number {#same-attempt-redelivery}

Dex delivers an attempt again, with the same attempt number and without using a
retry, in two cases:

- The Worker dies or disconnects before the attempt sends any output, such as a
  heartbeat or a Stream message, and before the dispatch wait ends. The
  dispatch wait is 10 seconds by default, counted from when Dex starts to look
  for a Worker.
- A Dex Server node restarts, or another node takes over its Flows. Dex
  dispatches every running attempt again, whether or not it has sent output.

In both cases the earlier run may already have made its external call. The new
run sees the same attempt number, so the attempt number cannot tell the two
runs apart.

When a Worker disconnects after the attempt has sent output, or after the
dispatch wait, the attempt fails and uses a retry. When a Worker stops
responding without disconnecting, the attempt fails when its heartbeat timeout
expires.

### A failure route cannot tell whether the work ran {#unknown-outcome}

When no Worker accepts an attempt within the dispatch wait, the attempt fails
without running and uses a retry. This happens when every Worker of the Flow
type is at its task limit, or when none is running. The failure has the same
recovery error type as a Worker that disconnected in the middle of an attempt:
**FLOW_ERROR_TYPE_WORKER_API_FAIL**. Only the error detail differs. A failure
route that reads the recovery error therefore cannot tell whether the work ran.
The Flow's history records which of the two happened, and Dex Web shows it.

### Design for these limits {#design-for-redelivery}

- Make each external effect idempotent. Key it by an ID that stays the same
  across attempts and redeliveries, such as the Flow ID and the Step execution
  ID, or your own business key. Send the key to the service that applies the
  effect, so that it applies the effect once.
- Treat a Step with a single attempt as at most once only within these limits.
  A redelivery at the same attempt number can still run it twice. Its failure
  route can run although the work happened, or although it never ran.
- Reconcile an unknown outcome. When a failure route cannot know whether the
  effect happened, check the target system by the idempotency key or your
  business key before you repeat or report the effect. Record the outcome you
  find in the Flow.

For the agent packages' single-attempt tool Steps, see
[Tool call limits](/agent-frameworks/deploy-agents#tool-call-limits).
