# RSS after history offload and ResetFlow

This investigation addresses [issue #1398](https://github.com/superdurable/dex/issues/1398).
It measures revision `b219e3ea0` on macOS 26.6.2, Apple M5 Pro, 18 CPUs, 48 GiB RAM,
with Rust 1.97.1 and Go 1.26.5. These are observations of this revision and host,
not a process memory guarantee.

## Result

The system allocator retains substantial freed memory. Live allocations alone do
not explain the observed RSS. A global allocator replacement did not improve both
workloads in these trials, so this change keeps the production allocator and all
persisted formats unchanged.

The checked-in [measurement driver](../integ/cmd/rss-measurement/main.go) validates
every Step index, successful Flow completion, and run attempt 2 after ResetFlow.
It provides two workloads on an otherwise empty local server:

- `small`: one Flow with 20,000 serial Steps. Each Step rewrites one Attribute
  with a distinct 1 KiB string.
- `large`: one Flow with 200 serial Steps. Each Step rewrites one Attribute
  with a distinct 2 MiB string. Thirty seconds after completion, ResetFlow
  returns to the beginning with the default write-reapplication behavior.
  The Worker disconnects before the reset, so the new attempt remains pending.

RSS samples use `ps -o rss= -p <pid>` once per second. Profiles use macOS `heap -s
-z`, `vmmap -summary`, and, in separate diagnostic runs, `MallocStackLogging=lite`
with `malloc_history -callTree -invert -ignoreThreads -consolidateAllBySymbol`.
Samples pause while profiles are collected. Sampling can miss brief peaks;
profiling, concurrent runs, and memory compression can affect RSS. Physical
footprint, live heap size, reserved address space, and RSS are different measures.

## Measurements

All values below are MiB. The [RSS samples and profile extracts](rss-1398/)
are included so the reported maxima and idle samples can be checked. The idle
RSS is the last sample before the final profile, after 60 seconds of sampling
following the completion profile.

| Workload | Rust allocator | Largest sampled RSS | Idle RSS |
| --- | --- | ---: | ---: |
| 20,000 Steps, 1 KiB | System | 1893.5 | 453.7 |
| 20,000 Steps, 1 KiB | mimalloc | 798.1 | 797.0 |
| 200 Steps, 2 MiB, ResetFlow | System | 602.7 | 494.2 |
| 200 Steps, 2 MiB, ResetFlow | jemalloc | 860.4 | 606.8 |
| 200 Steps, 2 MiB, ResetFlow | mimalloc | 976.3 | 974.7 |

Both 20,000-Step runs completed successfully. All large-value runs completed
and ResetFlow returned run attempt 2. The system allocator reproduces the
reported GiB-scale RSS growth with small Steps. mimalloc reduces that sampled
peak, but raises idle RSS and uses more RSS in the large-value workload.
The large-value reproduction did not reach the originally reported 1.3–1.6 GiB
high-water mark. It demonstrates retention at a smaller high-water mark.

The native profiles distinguish retained memory from live heap allocations:

- Around Step 10,000, the system allocator held 132.5 MiB of live allocations.
  Another 230 MiB was resident in regions marked **MALLOC_LARGE (empty)**.
  The physical footprint was 365.9 MiB. At completion, live allocations were
  134.5 MiB, and after idle they were 134.4 MiB. The final physical footprint
  fell to 239.1 MiB. The 1893.5 MiB RSS sample occurred later during execution;
  it was not a simultaneous heap profile, so these snapshots do not attribute
  every byte at that brief maximum.
- Immediately after the large-value reset, the system allocator's live heap
  was 18.3 MiB. Its zone table reported 425.5 MiB of dirty-plus-swapped
  fragmentation, with another 108.1 MiB resident in separate empty large
  regions. After idle, live heap remained 18.2 MiB; zone fragmentation was
  370.9 MiB and separate empty large regions held 0.9 MiB. Physical footprint
  was still 395.7 MiB. This is freed memory retained by the allocator, not a
  395.7 MiB collection of live Dex values.
- A separate stack-logged large-value diagnostic attributed about 36.3 MiB
  of live heap to RocksDB arenas and 34.3 MiB to RocksDB block allocations
  around Step 100. Those are expected memtable and block-cache allocations.
  Stack logging changes allocator behavior, so this diagnostic is not used
  for the allocator comparison table.
- After the jemalloc large-value run's idle period, its own counters reported
  about 17.0 MiB allocated and 396.9 MiB resident. The native allocator still
  held C/C++ allocations separately. mimalloc reported a 912.5 MiB committed
  arena and a 976.3 MiB process RSS peak at shutdown. Replacing Rust allocation
  alone did not eliminate retention in these trials.

These measurements establish allocator retention. They do not prove the absence
of every possible leak or identify every allocation responsible for the brief
small-Step RSS maximum.

The checked-in driver's additional large-value verification used
process-crash-safe durability: its largest sampled RSS was 574.0 MiB and its
last idle sample was 308.6 MiB. It also completed and reset successfully.
Different durability settings, profile timing, and other host activity affect
the high-water mark; the results do not establish one universal RSS plateau.

## Reproduce

Build the executable from the repository root:

```bash
cargo build --locked --release --manifest-path server-zd/Cargo.toml -p dexzd-server
cat > /tmp/dex-rss.yaml <<'YAML'
history:
  offloadEnabled: true
commit:
  batchWindow: 1ms
dev:
  durabilityMode: processCrashSafe
YAML
data_directory=$(mktemp -d /tmp/dex-rss.XXXXXX)
server-zd/target/release/dex-server-zd local \
  --data-dir "$data_directory" --listen 127.0.0.1:17233 \
  --config /tmp/dex-rss.yaml
```

The 1 ms commit batch window and process-crash-safe durability shorten the run.
They do not change history, replay, cache, or memtable budgets. The object store
is embedded s3local; no container or external S3 service is needed.

In another terminal, run one workload:

```bash
cd server-zd/integ
GOWORK=off go run ./cmd/rss-measurement -address 127.0.0.1:17233 -scenario small
```

For the large workload, stop the server with Ctrl-C, start it with a fresh data
directory, and use `-scenario large`. The driver waits for gRPC readiness and
prints its Flow ID, progress, and completion. Leave the server running for at
least 60 seconds afterward to distinguish idle memory from transient work.
Stop the server after collecting the last profile.

For allocation stack attribution, prefix the server command with
`MallocStackLogging=lite`. Repeat without that setting when comparing RSS;
stack logging changes allocation behavior and adds its own memory.

## What the budgets bound

The configured budgets bound particular working sets. They do not add up to a
hard limit on process RSS:

- `history.timeTravelReplayMemoryBytes` defaults to 1 GiB per computation, not
  per node. Successful ResetFlow releases its computation's temporary values.
  Freeing a value does not require the allocator to return its pages to the OS.
- RocksDB has a shared 128 MiB block-cache capacity. Pinned blocks, iterators,
  compaction buffers, and table metadata are additional memory.
- Each of six column families uses a 64 MiB write-buffer target. RocksDB's
  default two write buffers per column family give a nominal aggregate of
  768 MiB before accounting for allocation overhead and concurrent work.
  This capacity is not allocated in full at startup.
- History upload concurrency defaults to 16 and the segment target to 4 MiB.
  Uploads retain buffers while in flight. The segment target is a sealing
  threshold; a segment can exceed it by the records and checkpoint that seal it.
- The history read cache's default 1 GiB capacity is on disk. The header cache
  separately charges up to 64 MiB of encoded headers and key lengths; decoded
  objects and container overhead cost additional memory.
- Embedded s3local, outstanding commands, active Flows, thread stacks, mapped
  code, and allocator caches also contribute. Concurrent Flow computations
  multiply per-Flow working sets.

Consequently, a 1 GiB replay budget does not imply a 1 GiB RSS bound. Lowering
that budget can reject resets that previously fit. Lowering a cache or buffer
target can trade memory for additional I/O. Neither change repairs allocator
retention, so no default is reduced on the basis of these measurements.

## Allocator experiments

Temporary executables called the same **dexzd_server::run_from_command_line**
entry point with a Rust global allocator. They did not replace C/C++ malloc,
change the engine, or change persisted formats. Neither experiment is included
as a production dependency:

- `tikv-jemallocator` 0.7.0, default settings. A temporary stats thread used
  `tikv-jemalloc-ctl` 0.7.0 to advance the epoch and read allocated, active,
  resident, mapped, and retained bytes once per second. Background purging is
  unavailable on this macOS target; this is not a measurement of Linux with
  background purging enabled.
- `mimalloc` 0.1.52, default settings, with `MIMALLOC_SHOW_STATS=1` for shutdown
  statistics. Its bundled allocator is v3.

The large-value comparison used the default strict durability and a 1 ms commit
batch window. The full small-value comparison used the reproduction
configuration above. Use comparisons within each workload; these trials are
not throughput benchmarks or evidence about other operating systems.

## Validation

No production fix was selected, so there is no fail-before/pass-after product
regression test. The workload is an executable reproduction rather than a
platform-dependent RSS assertion in the ordinary test suite. It fails on a
missing, repeated, or reordered Step, an unsuccessful Flow, or an unsuccessful
reset. The checked-in driver was also exercised through the large workload.

Local checks:

- `make -C server-zd/integ compile` and `make -C server-zd/integ check-scripts`.
- `make -C server-zd/integ zdIntegTests` with an allowlist containing
  `TestResetByStateIdWorkflowTemporal`, `TestHardDeleteAttributeResetTemporal`,
  `TestGetHistoryEventsNotFoundTemporal`, and `TestS3GetSetDataAttributesTemporal`.
- `cargo test --manifest-path server-zd/Cargo.toml -p dexzd-server --lib`:
  98 passed; the three existing child-process scenarios are exercised by their
  parent tests and remain ignored for direct execution.
- The `local_command::` and `history_uploads::` process tests: three passed.
- `cargo fmt --manifest-path server-zd/Cargo.toml --all --check`.
- `cargo clippy --manifest-path server-zd/Cargo.toml -p dexzd-server --all-targets -- -D warnings`.
- `make rust-rules-check` and `make copyright-check`.

No PostgreSQL, MongoDB, Cadence, Docker, or MinIO was started. CI retains its
ordinary external-store coverage. No file under `docs/` changes.
