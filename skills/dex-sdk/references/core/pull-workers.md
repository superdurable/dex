# Pull Workers

For a remote Go pull Worker behind a TLS gateway, set **WorkerOptions.FlowServiceTLS** and **ClientOptions.FlowServiceTLS** independently. The pull task streams use the Worker's FlowService connection. From TypeScript SDK v1.35.0, a TypeScript pull Worker sets **WorkerOptions.flowServiceTls** and its Client sets **ClientOptions.flowServiceTls** the same way. Python, Java, and Rust pull Workers and Clients set their FlowService TLS option the same way. See [FlowService TLS](operations.md#flowservice-tls).

From SDK v1.25.0 in all five languages, every Worker is a pull Worker. It opens outbound task streams to Dex Server and never listens for incoming calls, so it needs no inbound port. Set the Worker's Dex Server address; the pull options are optional and tune capacity, registration, and shutdown. A Client needs only the Dex Server address. StartFlow and SubFlow always route to pull Workers, so there is no Worker address or target to configure, and UpdateFlowConfig does not change a Flow's Worker routing. The listening Worker mode, its bind address, and every public WorkerTarget option were removed in v1.25.0; when upgrading, delete those settings. server-zd always rejected a Worker address, so no stored Flow holds one. From SDK v1.26.0 the protocol has no Worker address or headless field, and `dexcli flow start --config` rejects a non-null `workerTarget`. See the published [Pull Workers guide](https://docs.superdurable.io/primitives/components/application).

Copy application setup from the runnable [Go](https://github.com/superdurable/dex/blob/sdk-go/v1.35.0/examples/go/production/pull-workers/worker.go), [Java](https://github.com/superdurable/dex/blob/sdk-java/v1.37.0/examples/java/src/main/java/io/superdurable/dex/production/pullworkers/PullGreetingExample.java), [Python](https://github.com/superdurable/dex/blob/sdk-python/v1.37.0/examples/python/dex_examples/production/pull_workers.py), [TypeScript](https://github.com/superdurable/dex/blob/sdk-typescript/v1.35.0/examples/typescript/src/production/pull-workers.ts), or [Rust](https://github.com/superdurable/dex/blob/sdk-rust/v1.37.0/examples/rust/src/production/pull_workers.rs) example at each language's published SDK tag. These examples include bounded registration waits, cleanup on startup failure, and snapshot-based readiness helpers. The examples select the SDK version pinned in each language's example project at that tag. Combine those helpers with application lifecycle health for production probes.

Each pull Worker opens outbound streams to its app Worker ID queue and every Flow type it registers. Flow types must be unique within a Dex Server. The app Worker ID identifies one process, changes after every restart, and cannot equal a registered Flow type. Let the SDK generate it unless a deployment needs an explicit process-unique value. Dex first tries the previously used app Worker ID. When that ID has no connected streams after a restart, crash, or deployment, Dex immediately tries the Flow type queue; the sticky wait applies only while that ID still has connected streams. Keep durable state in Dex; sticky routing does not promise the same process.

From server-zd newer than v0.1.16, a Step that no Worker takes does not fail. Dex first tries a connected sticky Worker for up to five seconds, then any Worker of the Flow type for **matching.syncMatchWait** (200 milliseconds by default). When its Step type already has a backlog that a connected Worker can run, a new Step goes straight to the queue. The attempt then waits in a durable task queue until a Worker takes it, the Flow times out, or the Flow stops. The wait consumes no retry. Steps are dispatched roughly in the order they became ready; strict ordering is not guaranteed. Queue time does not count toward the method timeout or the heartbeat timeout; both start when Dex hands the attempt to a Worker. With no Flow timeout, a Step with no Worker waits forever. An RPC never queues: if no Worker takes it within the dispatch wait, the caller gets an Unavailable error. The dispatch wait is 10 seconds, including up to five seconds of sticky wait, and never extends past the caller's deadline.

On server-zd v0.1.16 and earlier, if no Worker accepted a task within the dispatch wait, a Step got a retryable unavailable failure that **consumed one Step retry**.

A Step attempt starts when Dex hands it to a Worker. From server-zd newer than v0.1.16, Dex never hands the same attempt number to a second Worker. When the Worker disconnects or crashes after the hand-out, the attempt fails as possibly run and the retry policy runs, for SYNC and ASYNC Steps alike. One exception remains: when a Dex Server node crashes before an ASYNC attempt start is persisted, Dex rolls the start back and runs the same attempt number again, possibly on another Worker. That rerun consumes no retry, and the two runs can overlap. Make external effects idempotent, for example keyed by the Flow ID and Step execution ID, and reconcile uncertain outcomes. A recovery path can read whether the handler may have run; see [attempt progress](error-handling.md#attempt-progress).

With a v1.12.0 or later pull Worker SDK, a Worker that does not register the requested Step type or RPC name declines it before application code runs. Dex excludes that Worker and tries another Worker without consuming a Step attempt. The dispatch wait is 10 seconds, including RPCs and up to five seconds of sticky wait. If no capable Worker accepts within that wait, the Step receives a named failure and follows its failure and retry policy. The RPC caller receives **FailedPrecondition** naming the RPC, matching the legacy not-registered status code. SDKs before v1.12.0 retain the prior not-registered Worker error. During a rolling deployment, start Workers that add names before stopping old Workers; keep changed Step logic compatible because old Workers still serve the names they register.

From server-zd newer than v0.1.16, a Step type that no connected Worker supports no longer fails after the dispatch wait. The declined attempt returns to the queue with its attempt number, input snapshot, and Attribute locks, and it does not block other Step types. It keeps those locks while it waits, until a supporting Worker connects, the Flow times out, or the Flow stops; transactional RPCs on those keys get a lock conflict meanwhile. Dex remembers the unsupported type per app Worker ID until every stream with that ID disconnects. If you override the app Worker ID, set a new value after each restart; an upgraded process that reuses the old ID during a rolling deployment is otherwise excluded by the old process's entry. RPCs keep the behavior above.

SDK releases newer than Go, Java, Python, and TypeScript v1.32.0 and Rust v1.31.0 require Server protocol 4, which server-zd newer than v0.1.16 provides. Against an older Server, a new SDK Worker fails to start and a new SDK Client fails its first call, each with a clear error. Older SDK Workers and Clients keep working on the new Server. Upgrade the Server first, then upgrade the SDKs one at a time; Workers need not stop for the SDK upgrade.

## Startup registration and readiness

Go SDK v1.13.0 and Java, Python, TypeScript, and Rust SDK v1.14.0 expose startup registration waits and readiness snapshots:

| SDK | Startup wait | Readiness probe | Opt-in rejection shutdown |
| --- | --- | --- | --- |
| Go | **Worker.WaitPullRegistered(ctx)** | **Worker.PullRegistrationState().IsReady** | **PullWorkerOptions.StopOnPermanentStreamRejection** |
| Java | **Worker.waitPullRegistered(Duration)** | **Worker.getPullRegistrationState().isReady()** | **PullWorkerOptions.Builder.stopOnPermanentStreamRejection(true)** |
| Python | **Worker.wait_pull_registered(timeout=30)**; await on **AsyncWorker** | **worker.pull_registration_state().is_ready** | **PullWorkerOptions(stop_on_permanent_stream_rejection=True)** |
| TypeScript | **worker.waitPullRegistered({ timeoutMs: 10_000 })** | **worker.pullRegistrationState().isReady** | **pull.stopOnPermanentStreamRejection: true** |
| Rust | await **worker.wait_pull_registered()** | **worker.pull_registration_state().is_ready** | **PullWorkerOptions::stop_on_permanent_stream_rejection(true)** |

Start the blocking Go, Java, Python, or Rust Worker on another goroutine or thread; start Python's AsyncWorker in another task. TypeScript **start()** returns after local startup, so await it before the registration wait, or supervise **run()** separately. Use a bounded startup wait until the app Worker ID queue and every registered Flow type queue have each registered at least once. Concurrent waits before or after startup are safe. Startup failures wake waiters. Cancellation or timeout ends only that wait; it does not stop the Worker. Stop before initial registration returns an error. Once registration succeeds, later waits succeed, even after Stop; the wait proves registration, not free handler capacity.

Use the readiness snapshot for later probes. After initial registration, transient disconnects and ownership moves do not flap readiness. A permanent rejection makes it false only when that queue has no other registered stream. Queue entries expose the queue name, whether a registered stream exists, and the last permanent error using each language's native names. Successful re-registration clears that queue's error. Stop alone does not clear latched readiness: combine the snapshot with application lifecycle health and remove a stopping Worker from service separately.

Before initial readiness, a permanent rejection on a queue with no other registered stream fails the wait with **PullRegistrationError**. Rust returns an **SdkError** whose **pull_registration_error()** accessor exposes that typed rejection. The rejection identifies the queue and preserves the original transport error. Permanent statuses are **Unauthenticated**, **PermissionDenied**, **InvalidArgument**, **Unimplemented**, and **ResourceExhausted**. With SDK v1.16.0 and an [API key Credential](operations.md#api-key-credential), the first **Unauthenticated** rejection discards the token and reconnects immediately without recording a permanent error. A repeated rejection follows this path. By default the Worker keeps retrying rejected streams with a one-minute delay. A rejected surplus stream records the last permanent error and retries while another registered stream keeps the queue ready; matching limits during rolling overlap must not cause a serving Worker to exit.

The opt-in rejection shutdown defaults to false in every SDK. When true, the first permanent rejection leaving its queue with no registered stream makes the Worker drain all queues within its configured stop drain timeout, request cancellation after that deadline, wait for handlers, and report the rejection. Handlers must respond to cancellation; the deadline does not force an unresponsive handler to return. Go, Java, Python, and Rust report it from **Start** or **start()**. TypeScript reports it from **run()**; **start()** retains its non-blocking startup contract. Rust preserves the typed rejection through **pull_registration_error()**. Always call **Stop**, **stop()**, or TypeScript **close()** before process exit; cleanup remains safe after the blocking run returns.

With SDK releases newer than Go, Java, Python, and TypeScript v1.32.0 and Rust v1.31.0, readiness counts slot kinds instead of queues. The wait succeeds once at least one STEP_AND_RPC stream and, when the RPC reserve is positive, one RPC_ONLY stream have registered. Readiness queue entries and the **PullRegistrationError** queue hold the slot kind, not a Flow type or app Worker ID; Go and Java use the full POLL_WORKER_SLOT_KIND_STEP_AND_RPC and POLL_WORKER_SLOT_KIND_RPC_ONLY names. A permanent rejection matters only when no other stream of that slot kind remains registered. Readiness does not depend on free slots: a Worker whose slots are all busy stays ready. Worker start fails without background retry when its maximum concurrent task count exceeds the per-Worker limit that the Server reports at registration (**matching.maxConcurrentTasksCap**, 256 by default).

For rolling deployments, start replacement Workers and wait for their registration before stopping old Workers. Keep handling blocking Worker run failures after startup. See each language's startup and error-handling details: [Go](../go/go.md), [Java](../java/java.md#pull-workers-and-dex-credentials), [Python](../python/python.md#pull-workers-and-dex-credentials), [TypeScript](../typescript/typescript.md#pull-workers-and-dex-credentials), and [Rust](../rust/rust.md#pull-workers-and-dex-credentials).

## Reserved RPC capacity

SDK v1.15.0 in all five languages intentionally reserves one RPC slot by default when the resolved maximum concurrent task count **M** is at least two. With **M = 1**, an unset reserve becomes zero and Worker startup logs one warning. Explicit zero opts out, restoring shared capacity. Require **0 ≤ R < M**, where **R** is the reserve; invalid values fail construction. See the language handbook for the option and counter accessors.

Only RPC tasks, both API-direct and transactional, may use the reserved slots. WaitFor and Execute tasks receive **NO_CAPACITY** once the total busy-handler count reaches **M − R**. RPCs can use the full **M** slots. A decline permits reassignment within the dispatch wait without consuming an attempt. On server-zd v0.1.16 and earlier, if every Worker stays at its Step limit through that wait, the Step receives **NO_WORKER_AVAILABLE**, consumes an attempt, and follows its retry policy. Reserve declines preserve streams and registration readiness.

Size **M** for both Step concurrency and RPC demand: to retain eight simultaneous Step handlers with **R = 1**, use at least **M = 9**. Raise **R** for Workers whose Steps hold slots for minutes, based on concurrent RPC demand and handler duration. The reserve is admission capacity, not a latency guarantee; busy RPCs also count toward **M − R**, and saturation can still delay RPCs. Keep the stream caps below in the same budget.

With SDKs through Go, Java, Python, and TypeScript v1.32.0 and Rust v1.31.0, export the language's cumulative reserve-decline counter and collect debug logs with the Flow type. The counter excludes full-capacity rejections and unknown Step types or RPC names. It never resets and remains readable after shutdown. Distinguish reserve pressure from full saturation before changing concurrency. [Released reserve contract](https://github.com/superdurable/dex/blob/sdk-go/v1.35.0/sdk-go/README.md#reserved-rpc-capacity)

From SDK v1.23.0 in all five languages, a queue that declines a Step for reserved RPC capacity keeps one additional idle stream until 30 seconds after its last decline, so RPCs still find a stream during a Step backlog. The extra stream is not opened while every task slot is busy. Set the idle streams per queue to at least two for heavy Step backlogs. A decline still never closes a stream or changes registration readiness.

From SDK releases newer than Go, Java, Python, and TypeScript v1.32.0 and Rust v1.31.0, reserved RPC slots are RPC-only streams and Steps are never declined for capacity. The Worker keeps exactly **M** long-lived streams, one per execution slot. An idle stream is a free slot that serves the app Worker ID queue and every registered Flow type. **R** streams register as RPC_ONLY and never receive Steps; the other **M − R** accept Steps and RPCs. The Worker runs every task it receives. The reserve-decline counter is deprecated and always returns zero, and the idle-streams-per-queue option is deprecated and has no effect, so the decline, extra idle stream, and **NO_WORKER_AVAILABLE** rules above describe only older SDKs. When a slot frees up, Dex gives it to waiting RPCs before waiting Steps. A Step that finds every Step slot busy waits in the task queue. Older SDK Workers on server-zd newer than v0.1.16 still decline Steps for capacity; Dex returns those attempts without consuming a retry and counts them in **dexzd_step_attempts_returned_total** with **reason="legacy_no_capacity"**, which reaches zero once every Worker is upgraded. Measure Step capacity pressure with the task queue metrics in [Pull Worker server setup](operations.md#pull-worker-server-setup) instead of the counter.

From SDK v1.23.0, each SDK also sends an unsolicited upstream Pong every 20 seconds while a task runs, so a long Step or RPC with no data does not look idle to a proxy. The interval is internal and has no option. Set load balancer and proxy idle timeouts above both 20 seconds and server-zd **matching.pingInterval** (20 seconds by default), with margin; older SDKs need an idle timeout above the longest task.

## Heartbeats, capacity, and shutdown

server-zd enforces the configured **HeartbeatTimeout** for pull Steps and sends cancellation directly to the pull Worker. A long-running handler should still record heartbeats within its **HeartbeatTimeout** and handle the resulting cancellation promptly. See [server-zd cancellation](operations.md#server-zd). Set the timeout to tolerate healthy quiet periods while bounding a lost Worker, and keep each attempt within its method timeout.

The maximum concurrent task count caps active handlers. Idle streams per queue keep work ready, and each stream handles one task at a time. With SDK v1.14.1 in all five languages, a Worker gracefully closes surplus idle streams after tasks finish, preserving readiness and the configured registered idle streams per queue. After load drops, the steady-state bound per Worker is **M + (F + 1) × I**, where **M** is maximum concurrent tasks, **F** is registered Flow types, and **I** is idle streams per queue. The extra queue is the app Worker ID queue. Transient peaks during a burst remain bounded by **matching.maxConcurrentTasksCap** per app Worker ID and **matching.maxStreams** on the node. Size for both caps, not only the steady-state bound. Busy streams receive no idle Ping, so record task heartbeats often enough to keep load-balancer connections active. See [Pull Worker server setup](operations.md#pull-worker-server-setup).

With SDK releases newer than Go, Java, Python, and TypeScript v1.32.0 and Rust v1.31.0, each Worker always holds **M** streams, idle or busy, so the steady-state bound per Worker is **M** and the node holds the total slots of all Workers. Keep **matching.maxConcurrentTasksCap** at or above the largest **M**, and estimate **matching.maxStreams** from the total slots, including rolling overlap. Raise both before upgrading Workers. Every idle stream receives a Ping every **matching.pingInterval**.

On Stop, the Worker stops accepting assignments and waits for handlers up to its drain timeout (30 seconds by default). It then requests cancellation and waits for handlers to return. A half-closed task stream, including one awaiting a server-directed reconnect, is bounded by the remaining drain deadline. Keep handlers responsive to cancellation and allow shutdown to complete before terminating the process.

With those SDK releases, Stop starts no new task. Idle streams close at once. A busy stream finishes its handler and sends the final output before it closes. A task that arrives after shutdown begins is dropped without calling a handler, and Dex returns it to the queue without consuming a retry. A handler still running at the drain deadline is canceled, and Dex fails that attempt as possibly run, which consumes a retry. A final output that Dex has not yet confirmed gets a five-second flush grace, so shutdown can return up to five seconds after the drain deadline. A routine deployment whose handlers finish within the drain timeout therefore costs no Step retry.

server-zd has no wake hook. From server-zd newer than v0.1.16, a Step with no Worker waits in the durable task queue, so Worker startup time needs no Step retry budget. Scale Workers on the queue depth and oldest age metrics, **dexzd_step_task_queue_entries** and **dexzd_step_task_queue_oldest_age_seconds**. After a restart or failover, the entries gauge can read low until each partition finishes its background count, so do not scale to zero on it alone; the oldest age stays accurate. An RPC still fails after the dispatch wait while no Worker runs. With server-zd v0.1.16 or earlier, keep at least one pull Worker registered, or size dispatch waits, Worker startup time, and Step retry policy together when an external scaler starts Workers on demand.
